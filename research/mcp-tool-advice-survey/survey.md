# What published advice says about designing an MCP server's tools — survey

Compiled 2026-10-07. 91 distinct sources from 2025–2026, with two 2024 papers flagged. Every source was opened and read; none was classified from its title. Per-source data is in `survey.json`.

**Corpus.** 21 official docs, 28 vendor engineering blogs or docs, 20 independent blogs and newsletters, 2 forum threads (Cursor staff) and 20 papers. The target was ~50 and the survey has 91, because the four segments were searched separately and then deduplicated. No URL appeared twice. Companion posts were folded into one entry: the Stainless changelog, Workato's two pages, Drew Breunig's two posts, a DeployStack dev.to cross-post and the Jentic follow-up. The 41 skipped entries and the reasons are in `survey.json → skipped`.

**Gaps (being honest about them).**
- **Reddit:** blocked from this environment, so no r/mcp or r/ClaudeAI self-posts are included.
- **Geoffrey Huntley:** his detailed advice is paywalled. Only the public part is used.
- **Missing vendors:** Stripe, Linear, Notion, Zapier, Postman, Composio, Writer, Merge, Port and Honeycomb have no first-party post on tool design that I could find.
- **Announcements only:** the Sentry, Atlassian, Supabase and Datadog pages are announcements or parameter docs, so they were skipped.
- **Quote checking:** most quotes were checked against the raw page text. Some paper quotes came through a summarising fetch. Quotes that are not verbatim are marked `[paraphrase]`.

## 1. Summary counts (N = 91; 71 non-paper + 20 papers)

### (a) How many tools

| Stance | All 91 | Non-paper 71 | What it means |
|---|---|---|---|
| **FEW**: curate fewer tools on the server | 38 | 35 | "minimal viable set", "ruthlessly curated", "fewer, more capable tools" |
| **DEFER**: keep the *visible* set small with tool search, deferred loading, retrieval or filtering; the catalog can be large | 22 | 15 | Anthropic Tool Search, OpenAI tool_search, Cursor dynamic context, Speakeasy, Neon, StackOne, Klavis, RAG-MCP |
| **CODE**: one or two tools that run code or bash, so tool count stops mattering | 8 | 8 | Cloudflare Code Mode, Anthropic code execution, Vercel, AWS run_script, Stainless, Ronacher, Zechner, Fujita |
| **LIMIT**: reports a hard client cap only | 4 | 4 | VS Code 128, Vertex 128, Windsurf 100, Cursor 40 (outdated) |
| **NONE**: no advice on count | 19 | 9 | mostly benchmarks and description or naming papers, plus the spec |

- **Most say count matters:** 68 of 91 (75%) take *some* position that fewer tools should be in front of the model (FEW + DEFER + CODE).
- **They disagree on how.** 38 say "design fewer tools". 30 say "the server can be big, but the client or architecture should hide it" (DEFER + CODE).
- **The newer sources lean to the second answer.** The 2026 sources include Neon, which reversed its 2025 position; Cursor, which dropped its 40-tool cap; and Stainless, Speakeasy and Claude Code.
- **No source says "no limit, expose everything up front".** The closest are Neon (104 tools, relying on client-side progressive discovery) and PostHog ("every product should be accessible", with atomic tools).

**Specific numbers recommended: 20 sources.** Hard caps are counted separately below.

- **Where the numbers cluster:** 10–20 tools visible at once (OpenAI, Gemini, Speakeasy, bump.sh, Schmid, Workato), with "degrades at 30–50" as the outer bound.
- **Only 3 of the 20 come from the source's own measurement:** RAG-MCP D1, Rodrigues & Vas E2, and Speakeasy B8 (informal, 1.7B model). Two more cite those measurements (C12, E3). The other 15 are asserted.
- **Unit mismatch:** the often-quoted "30 tools" (Breunig E3) comes from RAG-MCP, which varied the number of **MCP server descriptions** in the prompt (N servers, Qwen-max, 20 web-search tasks), not individual tools.
- **Misattribution:** at least one 2026 SEO page credits RAG-MCP's 13.62% figure to Anthropic.

### (b) Grouping (50 sources address it)

| Stance | Count | Typical advice |
|---|---|---|
| Workflow/task-level tools (one tool per user goal, orchestrate in code) | 15 | Anthropic `schedule_event` instead of `list_users`+`list_events`+`create_event`; Block; Schmid `track_latest_order`; Lowin "atomicity is an agent anti-pattern"; Workato; Docker; bump.sh |
| Grouped (one tool + `action`/`method` parameter, CRUD-per-resource, toolsets, virtual tool groups, merging duplicates) | 15 | Claude docs A6 (`create_pr`/`review_pr`/`merge_pr` → one tool with action); GitHub MCP `issue_read`/`issue_write`, `projects_list/get/write`; VS Code/Copilot virtual tools; ToolScope merging |
| Code mode (single code/bash-executing tool) | 8 | Cloudflare, Anthropic code-execution, Vercel (80% of tools removed), AWS (8 tools for 15,000+ APIs), Stainless (2 tools) |
| Mixed / "it depends" | 9 | OpenAI (combine always-sequential calls + namespaces); Arcade (start atomic, bundle when traces show repeated sequences); Neon (1:1 generated + workflow tools); Rodrigues & Vas ("God Tool" anti-pattern) |
| **One tool per operation (atomic)** | **3** | OpenAI Apps SDK A12 (`list_/get_/create_/update_/archive_project`; split read vs write by permissions); VS Code MCP guide A16 ("focused and atomic"); PostHog handbook B16 (atomic CRUD, workflows go in skills) |

- **The camps:** 38 of 50 favour fewer, bigger tools (workflow + grouped + code mode). 3 explicitly favour atomic tools.
- **The atomic camp's reason is safety, not accuracy.** Per-tool permission prompts, `readOnlyHint` / `destructiveHint` annotations and confirmation all work only when reads and writes are separate tools. Block (B1) also concedes that merging read and write breaks per-tool approval in Goose, Claude Code and Codex.

### (c) Naming (33 sources give naming advice)

| Theme | Sources | Notes |
|---|---|---|
| Prefix/namespace by service or resource | 10 | Anthropic (`asana_search`, `asana_projects_search`), Claude docs (`github_list_prs`), OpenAI namespaces, Azure `azmcp_`, AWS `aws___`, Schmid `{service}_{action}_{resource}`, Archestra (prefix not suffix) |
| Against prefixes | 1 | Workato: needing `sales_`/`support_` prefixes means the server spans too many domains |
| Avoid near-duplicate / generic names | 10 | `create_invoice` vs `generate_invoice` (Lowin), `notification-send-user` vs `-channel` (Anthropic), `get_user`/`find_user`/`lookup_user` (Archestra); no `run`/`process`/`handle` |
| verb_noun / action-first snake_case | 7 | VS Code `{verb}_{noun}`; Archestra one verb per operation (get/list/search/create/update/delete); Neptune; Neon |
| Noun-first kebab-case (`feature-flags-list`) | 1 | PostHog, with a CI lint at **≤52 chars** |
| Length / charset limits | 7 | see §4; spec 1–128 with `.` allowed; SEP-986 1–64 with `/`; Claude API no dots; Vertex ≤64 |
| Consistent vocabulary across tools | 2 | Trent AI, Workato |
| Use names the model already "knows" | 2 | papers D8 (+up to 17% from renaming), D19 (masking names hurts small models) |

**Measured naming effects:**
- **Anthropic A1** says prefix vs suffix namespacing had "non-trivial effects" in its evals but publishes no numbers. It advises choosing by your own evals.
- **The only controlled naming measurements are two small-model papers (D8, D19).** They show that names alone move accuracy.
- **D7 is an audit, not an experiment.** It found repeated or generic tool names in about 73% of 10,831 servers.

### (d) Is it backed by a measurement?

| | All 91 | Non-paper 71 |
|---|---|---|
| Opinion / reasoning / experience | 46 | 45 |
| Cites someone else's measurement | 8 | 8 |
| Ran its own measurement | 37 | 18 |

But **what** was measured matters. Of the 37:

| What was actually measured | n | Sources |
|---|---|---|
| **Number of tools (or servers/domains) shown vs accuracy** | **10** | Papers: RAG-MCP D1, "How Many Tools…" D2, Less is More D3 (2024), LongFuncEval D4, MCP-Zero D5, MCP-Universe ablation D10, Rodrigues & Vas E2. Non-paper: **GitHub Copilot A17** (40→13 built-in tools, +2–5 pp on SWE-bench Verified/SWE-Lancer), **LangChain E1** (1→14 domains), **Speakeasy B8** (informal, qwen3-1.7B) |
| Tool search / retrieval / merging vs all tools loaded | 3 | Anthropic A4 (Opus 4: 49%→74%, Opus 4.5: 79.5%→88.1% with tool search), ToolScope D9, Klavis B20 (vs official servers) |
| Token cost only (no accuracy) | 8 | Anthropic code-exec A3 (150k→2k tokens), Cursor A21 (−46.9% tokens), GitHub B4 (−23k tokens), Speakeasy B7 (40–400 tools: 43k–405k tokens static vs ~1.3–2.5k dynamic), Zechner C10, Fujita C16, Yilmaz C18 (estimate), Köseoğlu C19 |
| Architecture (code/CLI vs tools) | 3 | Vercel A25 (80%→100% success, small internal eval), Zechner C9 (MCP vs CLI, 120 runs), Stainless B24 (vendor claim, method not shown) |
| Descriptions or names | 5 | Anthropic A1 (Claude-optimised vs human tools), D6 (+5.85 pp from better descriptions, regressions in 16.67% of cases), D7, D8, D19 |
| Retrieval quality only (no LLM tool-count variable) | 5 | StackOne B19, ScaleMCP D15, ToolRet D16, Tool-to-Agent D17, Dynamic ReAct D18 |
| Benchmark of MCP servers, tool count **not** varied | 3 | MCP-Bench D11 (single vs multi-server is confounded with task difficulty), LiveMCPBench D12, MCP-Atlas D13 |

- **Bottom line on (d).** Among the 71 non-paper sources (docs, vendor blogs, personal blogs), only 3 report their own experiment that varies tool count against accuracy: GitHub A17, LangChain E1 and Speakeasy B8. The numbers these sources recommend (10, 15, 20, 30–50) are almost all asserted, or trace back to a handful of papers.
- **"Server vs no tools" and "MCP vs CLI" are not tool-count measurements.** Neither are token counts of tool definitions, the most common "measurement" in blogs.
- **What the tool-count measurements found:**
  - **Degradation depends heavily on the model.** LongFuncEval: GPT-4o loses about 13% from 49 to 741 tools, while others lose 40–85%. LangChain: GPT-4o falls to 2% at 7 domains, while Claude 3.5 Sonnet goes from about 50% to about 40% at 14. MCP-Bench: frontier models are stable with more than 100 distractor tools, while weak models drop.
  - **Even small lists cost something.** On Claude Sonnet 4.6, an adaptive shortlist of about 2 tools gave 93.1% correct choices, against 87.1% at a fixed 5 tools (D2). Haiku 4.5 goes from 91% at 10 tools to 87% at 15 (E2).
  - **Overlap matters more than raw count.** Anthropic A2 and ToolScope D9 name ambiguity and overlap as the failure mechanism.

### Sources reporting the opposite or adding nuance

- **Accuracy holds with many tools on strong models.**
  - **MCP-Bench D11:** gpt-5, o3 and qwen3-235b are roughly stable with 10 distractor servers (100+ extra tools).
  - **LongFuncEval D4:** GPT-4o loses only about 13% across 49 to 741 tools.
  - **LangChain E1:** Claude 3.5 Sonnet and o1 hold up far better than GPT-4o.
  - **Claude docs A5:** accuracy "stays high even across thousands of tools" with tool search.
- **Cost is the real issue, not accuracy.**
  - **Token measurements:** Cursor A21, Speakeasy B7, Anthropic A3, Zechner C10, Kaxil C14, Kan Yilmaz C18 and Köseoğlu C19 all measure tokens.
  - **Response size:** Köseoğlu C19 adds that tool *responses*, not just definitions, eat the context.
  - **Design, not protocol:** bump.sh B13 calls "MCP wrecks the context window" claims "plain nonsense"; bloat is a design problem.
- **Deferred loading changes the picture.**
  - **Claude Code A7:** has no fixed cap and defers MCP tools by default. "The practical limit is your context window budget."
  - **Cursor:** dropped the 40 cap after dynamic context discovery (A21, January 2026), and the CLI got lazy loading (A22, September 2026).
  - **OpenAI A11:** tool_search defers whole namespaces.
  - **Neon B17:** went from "OpenAPI→MCP is a shaky default" (2025) to shipping 104 tools (September 2026), because "progressive discovery … lets an agent work through a large catalog."
  - **GitHub B5:** built embedding-based dynamic toolsets and shelved them as "the wrong level in the stack", so it is now the client's job. The current GitHub MCP README A18 has no dynamic-toolsets mode.
- **Code mode removes the question.** Cloudflare A20 ("LLMs have seen a lot of code. They have not seen a lot of 'tool calls'"), Anthropic A3, Vercel A25, AWS A26, Stainless B24, Ronacher C5 and Fujita C16 (63→2 tools).
- **Retrieval is itself lossy.** On ToolRet D16, retrievers stay under 52% recall@10. With retrieved tools instead of the gold set, GPT-3.5 loses 11.4 pp. Shrinking the visible set by search can hide the right tool.
- **You can over-consolidate.** Rodrigues & Vas E2 and AlphaSignal C12 name a "God Tool" anti-pattern. PostHog B16 and the OpenAI Apps SDK A12 keep atomic tools on purpose.

## 3. Strongest quotes (for an article)

1. "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality or API endpoints." Anthropic, [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11)
2. "Aim for fewer than 20 functions available at the start of a turn at any one time, though this is just a soft suggestion." OpenAI, [Function calling guide](https://developers.openai.com/api/docs/guides/function-calling)
3. "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." Anthropic, [Tool search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
4. "Use 5-8 tools per MCP server. 8-12 tools is reasonable. Consider splitting the MCP server into separate domains if you have more than 15 tools." Workato, [MCP server design](https://docs.workato.com/mcp/mcp-server-design)
5. "every extra endpoint is a tax paid in tokens and latency on every interaction. Second, atomicity is an agent anti-pattern." Jeremiah Lowin (FastMCP), [Stop Converting Your REST APIs to MCP](https://www.jlowin.dev/blog/stop-converting-rest-apis-to-mcp) (2025-07-10)
6. "MCP tools should be basic capabilities – atomic CRUD operations and simple actions. Agents compose these primitives into higher-level workflows." PostHog, [Implementing MCP tools](https://posthog.com/handbook/engineering/ai/implementing-mcp-tools). This is the dissenting view.
7. "Both more context and more tools degrade agent performance." LangChain, [Benchmarking Single Agent Performance](https://www.langchain.com/blog/react-agent-benchmarking) (2025-02-10). Measured.
8. "Claude Code doesn't impose a fixed per-server tool cap; the practical limit is your context window budget." Anthropic, [Claude Code MCP docs](https://code.claude.com/docs/en/mcp). The deferred-loading view.

Backups: Cloudflare, "LLMs have seen a lot of code. They have not seen a lot of 'tool calls'." ([Code Mode](https://blog.cloudflare.com/code-mode/), 2025-09-26).
