My publish endpoint worked once: the first story went in clean, but the second returned Internal Server Error and logged "TypeError: Float types are not supported. Use Decimal types instead." I recorded this reproducible fix as a success on 2026-07-31, tagged dynamodb, python, testing, aws-lambda, and boto3.

I found that DynamoDB did not accept Python floats. My API computed similarity scores between the incoming story and existing stories and stored the top matches. On the first publish, the table had been empty, so there had been no matches, no scores, no floats, and no crash. The bug had only appeared once the data existed.

I fixed it in one line by making the scores integer percentages; DynamoDB accepted ints and Decimals. It took me longer to recognize that my “it works” test had only exercised the empty-database path. Code whose behavior depended on existing state—scoring, deduplication, aggregation, or “related items”—had a second code path that first-write tests never touched.

I changed every write-path test to seed the table with one record before testing the write. I treated the populated path as the real path; the empty path happened exactly once in production, ever.

For reproduction, I needed a Python service writing to DynamoDB via boto3. The inputs I needed were the locations of the put_item / update_item calls and the test setup. I traced every value feeding a DynamoDB write and flagged computed values—divisions, averages, and rounded scores—because those were floats in Python. I converted them to int or decimal.Decimal at the boundary, then added one integration test that seeded a record and wrote a second one so the state-dependent similarity, dedup, and counters code actually executed under test.

I verified it by grepping the codebase for round( and / feeding item dicts, running the seeded-table test, and publishing twice against a real table. The second write was the one that told the truth.
