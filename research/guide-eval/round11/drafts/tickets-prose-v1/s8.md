I fixed a reproducible case on 2026-04-24 where agent memory writes evicted the whole Claude system prompt from the cache. I recorded it as a success, with status `n/a`, under `claude`, `prompt-caching`, `llm-agents`, `token-costs`, `mcp`, and `telegram-bot`.

My Telegram coach bot was stateless: every message made a fresh Claude call with instructions, the athlete’s profile, zones, goal, long-term facts, and MCP tools. The tool-use loop re-sent all of that 3–5 times per answer. I was paying for the whole system prompt on every message and every tool-loop iteration. Anthropic’s prompt cache reduced cached reads to ~10% of the input price, but it used a prefix hash: changing one byte made everything from that byte to the end of the cached block a miss. That conflicted with agent memory because learning something new about the user rewrote the agent’s own prompt.

My first improvement was unrelated to caching. I had been sending all ~55 tool schemas even with every “thanks!” message, so I filtered tools into groups by message keywords, always including a core set. That cut tokens on simple messages by about 75%.

Then I added long-term memory and broke caching. With a single cache marker at the end of the system prompt, every `save_fact` call rewrote the facts block, changed the prefix hash, and evicted everything, including the instruction text that never changed.

I fixed that by using two `cache_control: ephemeral` markers instead of one. The first segment contained the static instructions, ~780 tokens that were byte-identical across users and days. The second contained the per-user tail, ~240 tokens covering date, profile, zones, goal, facts, and language. A memory write then invalidated only the tail, while the static prefix stayed hot. Anthropic allowed 4 markers per request; I used 2.

I rejected top-N fact selection per message, which would have injected only facts relevant to the current question. Any per-message selection would have changed the tail on every message, preventing tail cache hits. Loading all facts every time was cheaper than loading fewer facts differently each time.

I found the same tension with aggressive tool filtering. Tools sat above the system prompt in the cached prefix, so a message that pulled in an extra tool group caused everything to be re-read once. That was tolerable because the default group set covered most messages, and the tool list stayed constant within a single message’s tool loop. Those loop iterations were where caching paid off most.

Within the 5-minute TTL, loop iterations and follow-up messages read the prompt at ~10% price, and frequent memory writes re-cached ~240 tokens instead of the ~1000+ tokens of the whole prompt.

I worked with an app that called the Claude API directly through the [Anthropic SDK](https://docs.claude.com/en/api/client-sdks) and used [prompt caching](https://docs.claude.com/en/docs/build-with-claude/prompt-caching). Its system prompt had a distinguishable invariant part for instructions and a volatile part for per-user data, per-day data, and agent memory. The approach applied to any provider with prefix-based caching, though the marker syntax I used was Anthropic-specific. For the agent doing the change, I needed the current system-prompt assembly code and a list of which parts changed per user, per day, or per memory write.

I split `system` into an array of two text blocks, each with `cache_control: {"type": "ephemeral"}`. The first held the instructions and was guaranteed byte-stable, with no interpolated dates, names, or counters. The second held everything volatile, including date, profile, and memory. I ordered that content rarest-changing first for readability; after the marker, it was one hash anyway.

I kept everything above the system prompt in the request, especially the tools array, byte-stable across calls. Where tools varied per message, I made the default selection cover the common case and avoided casually reordering or rewording tool schemas. I also kept per-message personalization such as top-N memory selection and “relevant context only” out of cached blocks, because selection defeated the cache and including everything usually cost less.

I read `usage` in every response, using `cache_creation_input_tokens` and `cache_read_input_tokens` to see exactly what happened. I verified with two messages within 5 minutes: the second showed `cache_read_input_tokens` covering roughly the whole prompt. I then triggered a memory write and sent a third message: `cache_read` still covered the static block, and `cache_creation` was roughly the size of the volatile tail only. A memory write producing `cache_creation` the size of the full prompt would have indicated that the static block was not byte-stable and that I needed to find the interpolated value.
