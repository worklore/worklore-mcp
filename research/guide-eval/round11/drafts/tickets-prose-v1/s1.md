I fixed a similar case with structured triathlon workouts that my AI agent generated and pushed to Intervals.icu via `POST /events`, which Intervals FIT-exported to my Garmin watch. Every HR corridor on the watch was silently wrong: it was clamped to the watch’s own stale, auto-detected LTHR zones instead of the range we planned. I misdiagnosed it as a watch-side LTHR mismatch for weeks.

I tried each variation through push → API readback → Garmin sync → watch face. First, `{units: "bpm", value, end}` was accepted by the API, but the watch showed an impossible 214–249 bpm because FIT export misread `bpm` as percent-of-something. Next, `{start_bpm, end_bpm}` produced a constant 101 on the watch, Garmin’s "no valid HR target" fallback; the schema was silently dropped. I then surveyed the Intervals UI target dropdown and concluded that "absolute bpm is impossible". That was wrong: the dropdown picked the units label, not the value shape.

I found the cause by building a workout in the Intervals UI with its "Instant HR" toggle and reading it back via the API. The corridor’s lower bound was `start`, not `value`. That one key name switched the FIT export mode: `{value, end}` routed as a Lap-HR / zone-mapped target, which the watch clamped to its local zones, while `{start, end}` became an Instant-HR corridor, and the watch displayed the raw bpm Intervals computed. I verified it end-to-end with Intervals LTHR 172 and watch LTHR 168: a 75–82% target rendered 129–141 bpm on the watch, matching Intervals and remaining immune to watch LTHR drift. The fix was a one-word rename after days of probing.

In the same session, I found that steps were invisible in the Intervals web UI because the UI read a separate top-level `description` in Intervals’ text grammar. In that grammar, `m` meant minutes, so `200m` was a 200-minute step; distance had to use `mtr`/`km`; a bare `Z2` resolved to power zones even for swims; and a digit at the start of a label was eaten as a duration. When the parser choked, Intervals wiped both representations.

For the reproduction, I used an Intervals.icu account with API access through an OAuth token or API key, athlete thresholds configured in Intervals with LTHR at minimum, and a Garmin watch that synced workouts from Intervals via Garmin Connect. The inputs and authorization my agent needed from me were my Intervals athlete id and API credential, my LTHR as stored in Intervals, and permission to create and later delete a test calendar event.

I created an event via `POST /api/v1/athlete/{id}/events` with `workout_doc.steps`, using `{"units": "%lthr", "start": <low>, "end": <high>}` for every HR step target, never `value`. I used percentages rather than absolute bpm because Intervals converted them at FIT-export time from its own stored threshold. I set the event’s top-level `description` in Intervals’ native text grammar so the steps rendered in the web UI, using `- Warm-up easy 10m 75-82% LTHR` as the example. I used `m`/`s` for durations and `mtr`/`km` for distance, put blank lines around `Nx` repeat blocks, kept digits off the start of labels, and avoided bare `Z<number>` outside cycling.

I read the event back with `GET /events/{id}`. Non-empty `workout_doc.steps` meant the parser had accepted the description; `steps: []` meant it had choked. I then synced the watch through Garmin Connect and opened the scheduled workout.

I verified that the watch showed a bpm corridor equal to the percentages multiplied by the LTHR stored in Intervals, rather than the watch’s own LTHR; the differing thresholds made that easiest to prove. I also verified that the Intervals web UI showed the full step chart instead of just a name and total duration.
