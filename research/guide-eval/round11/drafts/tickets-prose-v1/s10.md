I fixed a reproducible case on 2026-10-07 where our Flutter / Dart app using `posthog_flutter 5.x` used up PostHog’s free monthly event quota within a few days. I recorded it as a public success, with status `n/a`, under the tags `posthog`, `flutter`, `analytics`, `event-quota`, and `pricing`. I used Claude Code with `claude-opus-5-5`.

PostHog and similar analytics tools charged by event count. The free tier was generous enough that a small app should never have run out, but ours did. I traced the cause to our own code. Our product spec listed events like “user started typing their email” and “user moved the loan amount slider,” and we had hooked them up in the obvious place: `onChanged`. Flutter called a text field’s `onChanged` on every keystroke and a slider’s `onChanged` on every step it crossed during a drag. One email address became twenty events, and one slider drag became dozens. Multiplied across every field on every registration screen and every user, that exhausted the quota.

I couldn’t see the problem in the PostHog dashboard: the event names matched the spec exactly, and the funnels looked right. There were simply far too many events.

I kept every event name and property unchanged and changed only when the events fired. For text fields, I made the event fire once per screen visit, on the first edit, using a `bool _emailInputFired` flag on the screen state. Where I needed a final value, I used a focus-lost event instead, with the value only represented as a non-sensitive property such as “is valid.” For sliders, I moved the event from `onChanged` to `onChangeEnd`, so it fired once per drag when the user let go. For scrolls, I listened for `ScrollEndNotification` instead of every scroll update.

I checked the scope as a Flutter app sending events to PostHog, or any analytics service billed per event. My read-only search was:

```sh
grep -rn "onChanged\|addListener\|NotificationListener<ScrollNotification>\|ScrollUpdateNotification" lib/
```

For each hit, I read the callback and any methods it called, looking for `Posthog().capture`, our own capture wrapper, or an analytics `log` call. I identified the problem where a capture ran inside `onChanged`, a `TextEditingController` / `ScrollController` listener, or a scroll-update handler without a once-only flag or debounce in front of it. I considered callbacks covered where every capture sat behind a once-per-visit flag, or ran in `onChangeEnd`, a focus-lost handler, or `ScrollEndNotification` instead.

For reproduction, I used the prerequisite of a Flutter app using [posthog_flutter](https://pub.dev/packages/posthog_flutter), or another per-event-billed analytics SDK, with capture calls in widget callbacks. The information I needed for the agent was which events were allowed to stay per-change, usually none, and whether any event had to carry the field’s final value.

I first ran the check above and listed every capture inside `onChanged`, a controller listener, or a scroll-update handler. For text fields, I added `bool _<field>InputFired = false;` to the screen state, captured in `onChanged` only `if (!_<field>InputFired)`, and set the flag. Where the state object survived navigation between steps, I put the flag there and decided whether “once” meant per visit or per flow.

For tap/focus events, I captured in a `FocusNode` listener only when `hasFocus && !_tapFired`. For events that needed the final value, I captured in that listener when focus was lost (`!hasFocus`) instead of in `onChanged`. For sliders, I moved the capture from `onChanged` to `onChangeEnd` and kept `onChanged` for UI updates only. For scrolls, I captured from `NotificationListener<ScrollEndNotification>`, never from `ScrollUpdateNotification` or a `ScrollController` listener. I kept event names and properties unchanged so existing dashboards and funnels kept working.

I verified with a debug build using `PostHogConfig.debug = true`. Typing a 20-letter value into a fixed field produced one `*_input` capture in the log instead of twenty. Dragging a slider end to end produced one event when I let go. In PostHog → Activity, the event count per session for these events dropped to 1.
