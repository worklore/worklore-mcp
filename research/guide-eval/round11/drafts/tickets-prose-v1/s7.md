I fixed a similar case on 2026-04-15 while migrating my multi-tenant triathlon agent from per-user API keys to Intervals.icu OAuth so athletes could connect their account with two clicks instead of pasting a key. I recorded the outcome as a success, with status `n/a`, and the case was reproducible. It involved intervals-icu, oauth, api-integration, web-auth, and triathlon. Intervals’ OAuth mostly followed the standard authorization-code flow, but I ran into four deviations that took real debugging time and weren’t documented together in one place.

First, I found that the token response had no `refresh_token` and no `expires_in`. The access token lived until the athlete revoked it in the Intervals UI, so I needed no refresh machinery, but I couldn’t know it was dead until an API call failed. I handled revocation lazily: on the first 401 from the API, I cleared the stored token and surfaced a "reconnect" prompt. I treated the token as a perpetual credential and encrypted it at rest.

Next, I hit `Duplicate scope`. `:WRITE` implied `:READ`, so naming the same area twice, such as `ACTIVITY:READ,ACTIVITY:WRITE`, errored out with `Duplicate scope`, even though that was a natural habit from other providers. I listed each area at most once and used `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE,SETTINGS:WRITE`. I used `:WRITE` for areas I wrote to and `:READ` only for areas I never wrote to.

Then I found that the token exchange was standard-lite. `POST /api/oauth/token` wanted only `client_id`, `client_secret`, and `code`, with no `grant_type` or `redirect_uri` echo. The response also bundled `athlete: {id, name}`, which saved the "who am I" round-trip; I needed that athlete id in every API path anyway.

The fourth issue was self-inflicted, and I fixed it the same day. I had shipped the init endpoint as GET, using a plain `<a href="/api/intervals/auth/init">` link to build the authorize URL and redirect. It 401’d for every single user because a full-page navigation didn’t send the `Authorization` header the SPA kept in localStorage; those headers only traveled on XHR/fetch. I rewrote init as an authenticated POST returning `{authorize_url}` as JSON, and the frontend called `window.location.assign(authorize_url)`.

That led to the callback issue: it also arrived without an auth header because it was a redirect from Intervals. I carried the identity in `state`, using a signed JWT with the user id, a `purpose` claim, and a 15-minute TTL, and validated it before the code exchange. On reconnect, I used an account-mismatch guard that rejected the callback if the incoming athlete id differed from the one already stored.

For reproduction, I used a web app with its own user auth, where the API token traveled in an `Authorization` header through localStorage and a fetch wrapper or similar, plus an Intervals.icu OAuth client. Registration was arranged through the [Intervals.icu API access thread](https://forum.intervals.icu/t/api-access-to-intervals-icu/609), which provided a `client_id` and `client_secret` and registered the `redirect_uri`. No special agent skills were required; this was ordinary backend and SPA work. The inputs I needed for the agent were the OAuth `client_id` and `client_secret`, the registered `redirect_uri`, and the locations of the app’s JWT signing secret and per-user encrypted storage.

I implemented the init endpoint as authenticated `POST /auth/init`, called through XHR. It built `https://intervals.icu/oauth/authorize?client_id=...&redirect_uri=...&scope=...&state=...` and returned JSON `{authorize_url}`, after which the frontend called `window.location.assign(authorize_url)`. Making it a GET had caused the full-page navigation to drop the auth header. I kept each area in the scope string to one occurrence, with `:WRITE` where I wrote and `:READ` only where I never wrote.

I used a signed JWT `{sub: user_id, purpose: "intervals_oauth", exp: now+15min}` for `state`, since the callback had no other way to identify which app user it belonged to. The callback endpoint was unauthenticated GET. I validated the `state` signature, TTL, and purpose, then called `POST https://intervals.icu/api/oauth/token` with only the form fields `client_id`, `client_secret`, and `code`. I took `access_token`, `scope`, and `athlete.id` from the JSON response and stored the token encrypted. I didn’t wait for a `refresh_token`, since there wasn’t one.

The API client sent `Authorization: Bearer <token>` to `https://intervals.icu/api/v1/athlete/{athlete_id}/...`. On a 401, I cleared the stored token and marked the user as disconnected.

I verified the flow with a real Intervals.icu account, then called `GET /api/v1/athlete/{id}/wellness` with the Bearer token and got data. I revoked the app in Intervals.icu settings and repeated the call; it returned 401, and the app showed "reconnect" instead of crashing. Finally, I requested a scope with a duplicated area in the authorize URL, and Intervals rejected it with `Duplicate scope`, confirming that each area could appear only once.
