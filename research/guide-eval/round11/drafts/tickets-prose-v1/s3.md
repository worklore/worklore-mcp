Yesterday I filed an open failure for my launchd job, a daily 16:50 headless-agent review, because it produced no notification and no output. I also claimed there was no evidence it had run, but I was wrong about that part.

I checked `launchctl print gui/$UID/<job-label>`, which showed `runs = 2` and `last exit code = 1`. The job had fired on schedule both days. The log file I thought did not exist had existed the whole time. I had been debugging “launchd is not firing” when the actual problem was “my script fails and cannot tell me.”

The log revealed two stacked bugs. First, my headless agent call was not receiving its prompt in the launchd context, so the review died immediately with “Input must be provided either through stdin or as a prompt argument”. I fixed that by piping the prompt through stdin with `print -r -- "$PROMPT" | claude -p ...` instead of relying on multi-line argument parsing inside a scheduled shell.

Second, my script assigned `status=$?`. In zsh, `status` was a read-only built-in variable, so that assignment killed the script on the spot. It sat between the agent call and the failure-notification call: the job failed, and then the code meant to report the failure died before sending anything. Those two bugs accounted for the complete silence. I used `rc=$?` instead.

My takeaway was to establish whether silent automation had run first, using the runs count and last exit code from `launchctl print`, and then check whether the failure reporter was downstream of the failure. Mine was. I had initially treated that as something everyone’s reporter did until they checked.

In my correction dated 2026-09-30, I withdrew my original claim that the runs count and last exit code “do not lie”. The exit code happened to be honest in my case (`1`), but it was not proof in general: a script could exit `0` without doing anything, such as a watchdog that exited `0` on timeout. I distinguished evidence that it ran from evidence that it worked. That meant checking the real outcome—the file, message or row it was supposed to produce—and how long the run took. A headless agent run ending in a few seconds almost always meant it had failed before doing any work.

I also noted two more traps for `claude -p` under launchd from [Mihai Perdum’s seven silent launchd failures](https://dev.to/mihai_leanzero/your-unattended-ai-agent-looks-healthy-and-does-nothing-7-silent-failures-on-macos-launchd-2026-4gnm): when the prompt was an argument, stdin needed to be closed with `< /dev/null`, or the command waited on stdin; and `USER` needed to be set in the plist’s `EnvironmentVariables`, or the CLI could not find its login in the keychain and died with “Not logged in”.

The reproduction setup I recorded was a macOS launchd user agent wrapping any long-running or headless command, with the job label and wrapper script path supplied to the agent. The sequence I recorded started with `launchctl print gui/$UID/<label>` to check runs, last exit code and state, followed by reading the `StandardErrorPath` log before theorizing. It then covered replacing `status` assignments in zsh with `rc=$?`, passing prompts/config to headless tools through stdin instead of multi-line arguments—or adding `< /dev/null` when the prompt was an argument—and setting `USER` under `EnvironmentVariables` in the plist so the headless CLI could reach its keychain login. I also included logging each run’s duration, placing the failure notification as close to the top of the failure path as possible, and testing it by forcing a failure once.

For verification, I recorded running `launchctl kickstart -k gui/$UID/<label>`, then confirming `last exit code = 0`, that the real output file, message or row existed and was fresh, that the run took a plausible amount of time rather than a few seconds, and that the success notification arrived. The final check was to break the script deliberately and confirm the failure notification arrived too. The verification criteria ruled out silence in either direction and a green exit code with nothing done.
