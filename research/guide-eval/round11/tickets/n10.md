I asked Claude Code, Codex and Antigravity to add Prisma to a small TypeScript backend “using the current version from npm”. Half of them built on Prisma 7 and reported it as current. Those projects worked, so there was no failure to reveal that they were a major version behind.

I traced this to the npm tags. `prisma@latest` was Prisma 8: `8.0.0-rc.29` on 2026-11-01 and `8.0.0-rc.33` by the time I wrote this. Prisma itself had put the release candidate on `latest`, while `@prisma/client@latest` and `@prisma/adapter-pg@latest` were still `7.10.1`. The agents checked both, applied the old rule that the CLI and client had to match, and installed `7.10.1` everywhere. Nothing on npm explained the change: Prisma 8 had no `@prisma/client`; its client was `@prisma/orm-postgres`, its models lived in `src/prisma/contract.prisma`, and its setup command was `prisma orm init`, not `prisma init`. I found that choosing the stable 7 line was valid, but it did not satisfy the request for the current npm version.

The fix was to use `npx prisma@latest orm init --yes --target postgres --authoring psl`. That setup added `prisma`, `@prisma/orm-postgres`, `prisma.config.ts`, `src/prisma/contract.prisma`, `src/prisma/db.ts` and the `prisma-8.md` quick reference. The scaffold already included example `User` and `Post` models in `src/prisma/contract.prisma`; the model changes belonged there, followed by `npx prisma contract emit`. Table creation used `npx prisma db init`. Queries used `import { db } from "./src/prisma/db"`, with calls such as `db.orm.public.User.create({...})` and `db.orm.public.User.include("posts").all()`, and scripts ended with `db.close()`.

I also lost a run because `prisma orm init` prompted for answers without `--yes`, leaving the agent waiting in the terminal for an answer nobody supplied. On 2026-11-01, the Prisma 8 release candidate also crashed on `contract emit` because two of its packages pulled different toolchain versions. That crash was fixed in `rc.33`.
