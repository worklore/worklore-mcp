I investigated a daily 16:50 launchd headless-agent review that produced no notification or output. I initially reported that there was no evidence it had run, but `launchctl print gui/$UID/<job-label>` showed `runs = 2` and `last exit code = 1`. The job had fired on schedule both days, and the log file I thought was missing had existed the whole time. I had been investigating “launchd is not firing” when the script was failing and could not report it.

The log revealed two stacked bugs. The headless agent call had not received its prompt in the launchd context and had failed immediately with “Input must be provided either through stdin or as a prompt argument”. I fixed that by piping the prompt through stdin with `print -r -- "$PROMPT" | claude -p ...` instead of relying on multi-line argument parsing inside the scheduled shell.

The second bug had hidden the first: I had assigned `status=$?` between the agent call and the failure-notification call. In zsh, `status` was a read-only built-in variable, so the assignment killed the script before it could send the failure notification. I replaced it with `rc=$?`. The agent had failed, then the code meant to report that failure had died too.

In my correction on 2026-09-30, I withdrew my claim that the runs count and last exit code “do not lie”. The exit code had accurately reflected the failure in this case, but I found that a script could exit 0 without accomplishing anything, including a watchdog that exited 0 on timeout. The exit code showed that it had run, not that it had worked. The actual output file, message or row, its freshness, and the run duration mattered too; a headless agent run that ended in a few seconds almost always meant it had failed before doing any work.

I also found two more `claude -p` traps under launchd in [Mihai Perdum’s seven silent launchd failures](https://dev.to/mihai_leanzero/your-unattended-ai-agent-looks-healthy-and-does-nothing-7-silent-failures-on-macos-launchd-2026-4gnm). When the prompt was passed as an argument, stdin needed to be closed with `< /dev/null`, or the CLI waited on stdin. The plist also needed `USER` set under `EnvironmentVariables`, or the CLI could not find its login in the keychain and died with “Not logged in”.
