My AI agent generated structured triathlon workouts and pushed them to Intervals.icu via `POST /events`, which Intervals FIT-exported to my Garmin watch. Every HR corridor on the watch was silently wrong: it was clamped to the watch’s own stale, auto-detected LTHR zones instead of the planned range. I misdiagnosed this as a watch-side LTHR mismatch for weeks.

I tried `{units: "bpm", value, end}`. The API accepted it, but the watch showed an impossible 214–249 bpm because FIT export misread `bpm` as percent-of-something. I then tried `{start_bpm, end_bpm}`; the schema was silently dropped, and the watch showed a constant 101, Garmin’s “no valid HR target” fallback. I round-tripped each attempt through push → API readback → Garmin sync → watch face. I also surveyed the Intervals UI target dropdown and wrongly concluded that absolute bpm was impossible. That dropdown picked the units label, not the value shape.

I found the cause by building a workout in the Intervals UI with its “Instant HR” toggle and reading it back via the API. The corridor’s lower bound was `start`, not `value`. That one key switched the FIT export mode: `{value, end}` routed as a Lap-HR / zone-mapped target, which the watch clamped to its local zones, while `{start, end}` became an Instant-HR corridor displaying the raw bpm Intervals computed. After days of probing, the fix was a one-word rename from `value` to `start`.

The corrected event target under `workout_doc.steps`, sent via `POST /api/v1/athlete/{id}/events`, was `{"units": "%lthr", "start": <low>, "end": <high>}`. Those values were percentages, not absolute bpm; Intervals converted them at FIT-export time using its own stored threshold. I verified this end to end with Intervals LTHR 172 and watch LTHR 168: a 75–82% target rendered as 129–141 bpm on the watch, matching Intervals despite the watch’s threshold drift.

I also found why the steps had been invisible in the Intervals web UI. The UI read a separate top-level `description` in Intervals’ native text grammar, such as `- Warm-up easy 10m 75-82% LTHR`. In that grammar, durations used `m`/`s`, and `m` meant minutes, so `200m` became a 200-minute step. Distance used `mtr`/`km`, `Nx` repeat blocks needed blank lines around them, and a digit at the start of a label was eaten as a duration. A bare `Z2` resolved to power zones even for swims; bare `Z<number>` outside cycling was another trap.

When the description parser choked, Intervals wiped both representations. In the `GET /events/{id}` readback, non-empty `workout_doc.steps` meant the description had been accepted, while `steps: []` meant parsing had failed. With the description accepted, the web UI showed the full step chart instead of just a name and total duration.
