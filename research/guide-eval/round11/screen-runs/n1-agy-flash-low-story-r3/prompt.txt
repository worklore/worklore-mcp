# Mistral Vibe on OpenRouter stopped at once in my sandbox: it was reading the Keychain for a Mistral key

I run Mistral Vibe CLI 3.1.0 headless on Devstral 2 through OpenRouter, inside a macOS sandbox (`sandbox-exec`)
that keeps the agent away from my home folder and the Keychain. The launcher starts Vibe with `env -i` and an
allowlist, so the only key it passes is `OPENROUTER_API_KEY`. Every run ended within a second with exit 2, wrote
no export, and left two lines in stderr:

    Reading API keys from the macOS Keychain (set them as environment variables to skip this)
    Error: [Errno 1] Operation not permitted: '/usr/bin/security'

The OpenRouter key was set and worked. Mistral's docs give the order Vibe looks for keys in: the environment,
then `~/.vibe/.env`, then the OS keyring. They don't say that Vibe also does this for its own Mistral key when the
provider is OpenRouter. It does: with no `MISTRAL_API_KEY` in the environment, Vibe runs
`/usr/bin/security find-generic-password -s ai.mistral.vibe ...` before anything else, and my sandbox denies
`/usr/bin/security` on purpose. That one line was the whole failure.

The tempting fix is to let the sandbox run `/usr/bin/security`. That opens the Keychain to an agent whose output
goes to another company, which is what the sandbox is there to prevent. The fix that keeps the sandbox: give Vibe
any value for `MISTRAL_API_KEY`. I pass `MISTRAL_API_KEY=unused` next to `OPENROUTER_API_KEY` on the `env -i`
line; Vibe never sends it anywhere, because the active provider is OpenRouter. A `.env` in `VIBE_HOME` with the
same line works too, and so does `VIBE_TEST_DISABLE_KEYRING=1`, which I found in the binary's strings and would
not rely on, since it looks like a test switch.

## Reproduce this

Prerequisites: Mistral Vibe CLI (checked with 3.1.0) set up with a non-Mistral provider (here OpenRouter, via
`api_key_env_var = "OPENROUTER_API_KEY"`), started inside a macOS sandbox profile or any environment where
`/usr/bin/security` can't run.

Your agent will need from you: the launcher script and the sandbox profile.

Steps: read the run's stderr; if it says "Reading API keys from the macOS Keychain", Vibe is looking for
`MISTRAL_API_KEY`. Add `MISTRAL_API_KEY=unused` (any non-empty value) to the environment Vibe gets: if the
launcher uses `env -i`, it has to be on that line, not exported before it. Keep the provider's own key as it is.
Do not loosen the sandbox: `/usr/bin/security` stays denied.

Verify: the same launcher, unchanged sandbox, now gets past start-up: the Keychain line is gone, Vibe writes its
export folder, and it reaches the provider (with a wrong provider key it fails at the provider instead, with
"Invalid API key (from env var OPENROUTER_API_KEY)"). Run `/usr/bin/security list-keychains` inside the same
sandbox: it must still fail with "Operation not permitted".

Ground rules: work only inside the current directory. Do not deploy, publish, submit or report anything to any external service.
