# Почему не подключался Intervals.icu и что исправлено

Тут три независимые проблемы. Каждая сама по себе ломает подключение.

## 1. Кнопка Connect всегда даёт 401 (тикет #214, лог §1)

Вход в tricoach работает через Bearer-токен из `localStorage`. Этот заголовок
добавляет только fetch-обёртка `api()` в SPA. А кнопка Connect была обычной
ссылкой `<a href="/api/intervals/auth/init">`. По такой ссылке браузер просто
переходит на страницу и `Authorization` не отправляет: в devtools видно
document navigation без этого заголовка. `require_user()` отвечает
`401 {"error": "unauthorized"}`, и так у всех без исключения.

**Исправление:** `auth/init` теперь `POST` и возвращает `{"url": ...}`. SPA
вызывает его через `api()`, токен уходит в заголовке, и только потом браузер
переходит на полученный authorize URL. Старый `GET` убран. Токен в query
string не переносится, cookie для этого не вводятся.

## 2. Intervals отвечает на authorize `400 invalid_request` (лог §2)

С 2026-10-02 (calendar sync) в `SCOPES` указано
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
В Intervals.icu уровень `WRITE` уже включает `READ`, поэтому scope задаётся
одной записью на область. Это видно в логе §3: на запрос с
`ACTIVITY:READ,ACTIVITY:WRITE` Intervals вернул granted scope
`ACTIVITY:WRITE,WELLNESS:READ`. Если убрать `state` или поменять
`redirect_uri`, ошибка та же, а ссылка начала ломаться ровно тогда, когда
поменяли scope и добавили `CALENDAR:READ` вместе с `CALENDAR:WRITE`.
Значит, Intervals отвергает именно запрошенный набор прав.

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`.
Ещё добавлен обязательный по OAuth 2.0 параметр `response_type=code`.
Раньше его не было.

> Оговорка: на живом intervals.icu я это не проверял, потому что по условиям
> задачи нельзя обращаться к внешним сервисам. Вывод о scope сделан по логам.
> Перед релизом стоит один раз открыть новую authorize-ссылку и убедиться, что
> появляется consent-экран. Если `400` останется, следующее, что стоит проверить:
> есть ли `redirect_uri` в списке разрешённых в настройках OAuth-приложения
> на Intervals.

## 3. Через час после подключения статус «expired, reconnect» (тикет #219, лог §3)

Intervals.icu выдаёт долгоживущий access token. В ответе нет ни `expires_in`,
ни `refresh_token`, и токен действует, пока атлет не отзовёт приложение (у
Rivera оно до сих пор в списке). Но `store_connection()` при отсутствии
`expires_in` подставлял `DEFAULT_TOKEN_TTL = 3600`. Через час фоновый
`refresh_tokens()` видел, что срок «истёк» и refresh-токена нет, удалял
рабочий токен и ставил `expired, reconnect`. Получалось, что мы сами
разрывали валидное подключение.

**Исправление:**
- если `expires_in` нет, `expires_at = None` (токен бессрочный), и refresher
  такие подключения пропускает. Отсутствие refresh_token само по себе больше
  не считается ошибкой;
- если провайдер всё же передал срок, а refresh_token нет, подключение
  помечается истёкшим только после реального истечения, а не за 5 минут до
  него. Повторный ответ refresh без `expires_in` больше не падает с `KeyError`;
- настоящий отзыв доступа теперь определяется по факту: если Intervals ответил
  `401` на запрос wellness, подключение помечается `expired, reconnect`.

## Дополнительно

У Rivera granted scope был без `CALENDAR`, потому что подключение сделано до
calendar sync. `/api/intervals/status` теперь отдаёт `missing_scopes`, и при
нехватке прав SPA показывает кнопку «Reconnect Intervals.icu». Без этого
синхронизация календаря у таких атлетов молча не работала бы.

Существующие подключения в проде, которые уже помечены `expired, reconnect`,
это исправление не вернёт: старый код стёр у них `access_token`. Этим
атлетам (Rivera) нужно один раз подключиться заново.

## Проверка

Проверял локально на фейковом Intervals на `127.0.0.1` (`INTERVALS_BASE`) и
отдельном порту, потому что 8766 занят другим процессом. Результаты:
`POST auth/init` без токена даёт 401, с токеном возвращает URL с новыми scope
и `response_type=code`. Callback выдаёт 302, токен обменивается, в статусе
`connected`, `missing_scopes: []`. После нескольких проходов refresher'а
подключение остаётся `connected`, wellness отдаётся.
