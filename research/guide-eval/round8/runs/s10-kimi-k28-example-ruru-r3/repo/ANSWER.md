# Реализация событий аналитики (docs/EVENTS.md)

Все 6 событий из спецификации реализованы через существующую обёртку
`Analytics.capture` (lib/analytics.dart). Имена событий и свойства совпадают
со спецификацией один в один, PII (email, телефон) нигде не отправляется.
Просмотры экранов не трекаются вручную — за это уже отвечает `PosthogObserver`
в lib/main.dart.

## Что сделано

### Экран регистрации — lib/screens/registration_screen.dart

| Событие | Где срабатывает | Свойства |
|---|---|---|
| `registration_email_started` | При первом редактировании поля Email (один раз за посещение, флаг `_emailStartedFired`, lib/screens/registration_screen.dart:30) | — |
| `registration_phone_started` | При первом редактировании поля Phone (один раз за посещение, флаг `_phoneStartedFired`, lib/screens/registration_screen.dart:38) | — |
| `loan_amount_changed` | В `onChangeEnd` слайдера (один раз за протягивание, lib/screens/registration_screen.dart:77) | `amount` (int, `v.round()`) |
| `terms_accepted` | Когда чекбокс становится отмеченным (lib/screens/registration_screen.dart:86) | — |
| `registration_continue_tapped` | В `onPressed` кнопки Continue, до навигации (lib/screens/registration_screen.dart:95) | `amount` (int), `terms` (bool) |

### Экран предложений — lib/screens/offer_screen.dart

| Событие | Где срабатывает | Свойства |
|---|---|---|
| `offers_scrolled` | В `NotificationListener<ScrollEndNotification>` над списком (один раз в конце жеста скролла, lib/screens/offer_screen.dart:32) | `offset` (double, `metrics.pixels`) |

Флаги «один раз» живут в `State` экрана регистрации: маршрут `/` создаёт
состояние заново при каждом посещении, поэтому события `*_started`
срабатывают один раз за посещение, как требовалось.

## Проверка

Запустить `flutter analyze` / debug-сборку не удалось: песочница окружения
блокирует исполнение бинарников SDK (`Operation not permitted`). Синтаксис и
структура проверены чтением обоих файлов; изменения используют только API,
которые уже применялись в проекте. Перед мерджем стоит прогнать
`flutter analyze` и проверить в debug-режиме, что ввод email из 20 символов
даёт ровно один capture `registration_email_started`, а протягивание слайдера
насквозь — один `loan_amount_changed`.

## Заметка коллеги: что пригодилось

Использовано:
- **Текстовые поля — флаг «один раз за посещение» в `onChanged`.** Прямо
  применил описанный паттерн `bool _<field>InputFired` для email и phone:
  без него каждое нажатие клавиши стало бы отдельным событием (главный риск
  из заметки — исчерпание квоты PostHog).
- **Слайдер — `onChangeEnd` вместо `onChanged`.** Событие шлётся один раз за
  протягивание, в `onChanged` осталось только обновление UI.
- **Скролл — `ScrollEndNotification`.** Событие `offers_scrolled` шлётся по
  окончании жеста, а не на каждое обновление скролла.
- **Не менять имена событий и свойства** — соблюдено, чтобы не ломать
  существующие дашборды и воронки.

Пропущено (не применимо к этой задаче):
- Capture по потере фокуса для итогового значения поля — ни одно событие не
  требует итогового значения, а по правилам спецификации значения полей
  (PII) отправлять нельзя.
- Вопрос «что означает один раз, если состояние переживает навигацию» —
  здесь `State` экрана регистрации создаётся заново при каждом посещении,
  так что «один раз» однозначно означает «за посещение».
- Пошаговое воспроизведение из заметки и проверка через
  `PostHogConfig.debug = true` — не выполнялась по той же причине, по которой
  не запустился анализатор (см. «Проверка»).
