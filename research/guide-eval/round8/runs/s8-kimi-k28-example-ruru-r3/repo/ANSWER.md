# ANSWER — кеширование системного промпта против save_fact

## Проблема

`build_system()` собирал системный промпт одним блоком: статические инструкции
(~780 токенов) + контекст атлета (дата, профиль, зоны, цель, факты, язык,
~240–300 токенов), с одним маркером `cache_control` в конце. Кеш Anthropic —
хеш префикса, поэтому каждый `save_fact` менял хвост и вытеснял весь блок:
в `logs/usage.jsonl` после каждой записи в память следующий раунд показывал
`cache_read_input_tokens: 0` и `cache_creation_input_tokens` ≈ 1046–1334 (весь
промпт), вместо дешёвого чтения.

## Изменение (bot.py, build_system)

Системный промпт разбит на два текстовых блока, у каждого свой маркер
`cache_control: {"type": "ephemeral"}`:

1. **Статический блок** — `INSTRUCTIONS + "\n\n"`. Байт в байт одинаков для
   всех пользователей и дней; никаких подстановок (дата и имя живут во втором
   блоке). Завершающие `\n\n` оставлены внутри него, чтобы итоговый текст
   промпта совпадал с прежним форматом байт-в-байт — поведение модели не
   меняется.
2. **Изменчивый хвост** — `athlete_context(a, today)`: дата, профиль, зоны,
   цель, факты, язык.

Эффект: `save_fact` инвалидирует только второй сегмент; статические инструкции
остаются в кеше и читаются по ~10% цены. По логам хвост — это те самые
~+15 токенов на факт, которые раньше оборачивались пересозданием ~1000+
токенов. Бонус: статический префикс теперь одинаков между пользователями, так
что кеш «горячим» остаётся и при переключении между атлетами (при совпадающем
наборе инструментов).

Маркеров 2 из разрешённых 4 — запас на будущее.

## Проверка

`anthropic` SDK в окружении не установлен, поэтому прогнал `reply()` со
стабом LLM (без сети): сообщение → `save_fact` в round 1 → round 2 → второе
сообщение. Подтверждено:

- все 3 вызова API получают 2 блока, у каждого есть `cache_control`;
- статический блок байт-в-байт идентичен во всех вызовах, включая вызов
  сразу после `save_fact`;
- хвост раунда 2 содержит новый факт и отличается от хвоста раунда 1
  только на него (+29 символов вместо пересоздания всего промпта);
- склейка двух блоков совпадает с прежним одноблочным форматом посимвольно;
- набор инструментов постоянен внутри цикла одного сообщения.

`data/athletes.json` после прогона восстановлен, посторонних файлов нет.

Ожидаемая картина в `logs/usage.jsonl` после деплоя: после `save_fact`
`cache_creation_input_tokens` ≈ размер хвоста, а `cache_read_input_tokens` —
по-прежнему на весь статический блок.

## Что взял из заметки коллеги

- **Главная идея — два сегмента с `cache_control` вместо одного.** Ядро
  исправления, применено как есть: блок 1 = инструкции, блок 2 = всё
  изменчивое, маркер на каждом.
- **Требование байт-в-байт стабильного статического блока.** Проверил, что
  `INSTRUCTIONS` не содержит подстановок (дата, имя, счётчики); дата уехала
  во второй блок. Это же критерий из раздела «Проверка» заметки: если бы
  статический блок содержал хоть одно меняющееся значение, кеш не попал бы.
- **Маркер на втором блоке тоже.** Закрывает сегмент хвоста; без него хвост
  не кешировался бы отдельным префиксом.
- **Пункт 2 (стабильность массива инструментов «выше» системного промпта).**
  Уже выполняется в коде: `select_tools` вызывается один раз на сообщение
  (`bot.py:198`), внутри tool-loop список инструментов не меняется — тестом
  подтверждено. Менять не пришлось, просто сверил.
- **Пункт 3 (не делать top-N отбор фактов под сообщение).** Отбор фактов в
  коде не делался — `athlete_context` всегда отдаёт все факты. Вывод заметки
  («грузить всё дешевле, чем грузить меньше, но разное») совпадает с текущим
  поведением; оставлено без изменений.
- **Пункт 4 (читать usage из каждого ответа).** Уже реализовано в
  `log_usage` (`bot.py:179-187`); это же источник цифр для проверки эффекта.

## Что пропустил

- **Фильтрация инструментов по ключевым словам** — в нашей коде уже есть с
  марта (~75% экономии токенов инструментов, см. NOTES.md), из заметки
  ничего не брал.
- **Соображение про «инструменты выше системного промпта» и набор групп по
  умолчанию** — описывает то же напряжение, что и у нас (сообщение с
  ключевым словом подтягивает новую группу и один раз перечитывает префикс),
  но текущее поведение уже соответствует рекомендации, менять нечего.
- Telegram-часть контекста заметки не релевантна этому репо (транспорт
  живёт в другом репозитории).

## Что сознательно не стал строить

- Персонализацию промпта под сообщение (отбор «только релевантных» фактов
  или секций профиля) — по выводу заметки это ломает кеш хвоста и обходится
  дороже, чем класть всё.
