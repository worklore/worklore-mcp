# Почему вторая публикация возвращает 500

## Причина

`logs/error.log`: `TypeError: Float types are not supported. Use Decimal types instead.`
из `table.put_item(Item=item)` (`src/app.py`, `publish`).

`publish()` кладёт в элемент поле `similar`: список `{slug, score}` для трёх самых
похожих историй, которые уже есть в таблице. `similarity()` возвращала
`round(0.7 * tag_score + 0.3 * word_score, 4)`, а это Python `float`. boto3/DynamoDB
float не принимает.

- **Первая публикация** (`similar=0` в логе): таблица пуста, `related()` возвращает `[]`,
  оценки не считаются, float в элемент не попадает, ответ 201.
- **Каждая следующая публикация**: в таблице есть хотя бы одна история, у элемента
  появляется `similar[0].score` типа float, `put_item` падает, ответ 500. Поэтому
  третий запрос в логе тоже упал.

Тест проверял только путь с пустой таблицей, и код, который считает оценки, под
тестом не выполнялся ни разу.

## Исправление

1. `similarity()` теперь возвращает `Decimal(str(round(..., 4)))`. Точность в
   4 знака сохраняется, а через `str` в значение не попадают двоичные хвосты float.
2. Добавлена защита на границе: `to_dynamo()` рекурсивно переводит любой float в
   `Decimal`, и `publish()` вызывает её перед каждым `put_item`. Если позже
   появится новое вычисляемое поле (среднее, процент и т.п.), этот класс ошибок
   не вернётся.
3. Тесты (`tests/test_publish.py`):
   - вторая публикация в таблицу, где уже есть запись: `similar` сохранён, `score` имеет тип `Decimal`;
   - две публикации подряд через `handler()` дают 201 и 201;
   - публикаций больше, чем `TOP_N`: сохраняется ровно `TOP_N` совпадений;
   - юнит-тест для `to_dynamo()`.

   На старом `app.py` новые тесты падают с той же `TypeError`, после исправления
   проходят все 5 (`python3 -m unittest discover tests`).

## Что пригодилось из заметки коллеги

- **Диагноз**: float из вычисленной оценки похожести, а первая запись выживает
  только потому, что таблица пуста. Совпало с нашим случаем полностью.
- **Конвертация на границе записи** в `int`/`Decimal`. Я выбрал `Decimal`, а не
  целые проценты из заметки, чтобы не менять формат и точность `score`.
- **Совет искать `round(` и `/`, которые попадают в элемент**: так нашлась `similarity()`.
- **Правило «засеять одну запись, потом писать вторую»**: на нём построен главный
  новый тест.

Что не использовал: шаг «опубликовать дважды в реальную таблицу». По условиям
задачи ничего не деплоится и внешние сервисы не трогаются. Вместо этого служит
`FakeTable`, она проверяет типы так же, как сериализатор boto3.

## Замечание (не исправлял)

`publish()` делает один `scan` и не обрабатывает `LastEvaluatedKey`. Когда таблица
вырастет больше 1 МБ, похожие истории будут искаться только по первой странице.
Это тоже поведение, которое зависит от накопленного состояния, и его стоит
поправить отдельно (или заменить полный scan на что-то масштабируемое).
