# Аналитика регистрации и списка предложений

Все шесть событий из `docs/EVENTS.md` подключены. Они идут через `Analytics.capture`
(`lib/analytics.dart`), сама обёртка не менялась. Имена и свойства точно
совпадают со спецификацией.

| Событие | Где | Когда срабатывает | Свойства |
|---|---|---|---|
| `registration_email_started` | `registration_screen.dart`, `_onEmailChanged` | один раз, на первом изменении поля email (флаг `_emailStartedFired`) | — |
| `registration_phone_started` | `registration_screen.dart`, `_onPhoneChanged` | один раз, на первом изменении поля телефона (флаг `_phoneStartedFired`) | — |
| `loan_amount_changed` | `Slider.onChangeEnd` | один раз за перетаскивание, когда пользователь отпускает слайдер | `amount`: `int` (`v.round()`) |
| `terms_accepted` | `_onTermsChanged` | только когда галочку ставят (false → true), но не когда снимают | — |
| `registration_continue_tapped` | `_onContinue` | при нажатии Continue, перед переходом на `/offers` | `amount`: `int`, `terms`: `bool` |
| `offers_scrolled` | `offer_screen.dart`, `NotificationListener<ScrollEndNotification>` | один раз за жест прокрутки, когда прокрутка остановилась; только для самого списка (`depth == 0`) | `offset`: `double` (`metrics.pixels`) |

PII: email и телефон в свойства не попадают. Значения полей вообще не читаются
для аналитики.

## Принятые решения (стоит подтвердить с продуктом)
- «Начал вводить» срабатывает один раз за время жизни экрана регистрации. Экран
  остаётся в стеке, пока открыты предложения. Поэтому если пользователь вернулся
  кнопкой «Назад» и снова правит поле, повторного события не будет. Получается
  «один раз за flow», и для воронки этого достаточно.
- `offers_scrolled` отправляется на каждый законченный жест, а не один раз за
  визит. Так в `offset` видно, как далеко пользователь долистал. Если для воронки
  нужно только одно событие за визит, достаточно добавить флаг.
- `terms_accepted` отправляется при каждой постановке галочки. Если пользователь
  её снимет и снова поставит, событий будет два. Объём при этом ничтожный.

## Что пригодилось из заметки коллеги
Заметка оказалась очень к месту. В спецификации те же формулировки («started
typing», «moved the slider», «scrolled»), а в README сказано, что проект на
бесплатном тарифе PostHog. Если повесить события напрямую на `onChanged` или на
обновления скролла, квота сгорела бы так же, как у коллег.

Пригодилось:
- Флаг «один раз за визит» для текстовых полей (`_emailStartedFired`,
  `_phoneStartedFired`).
- Перенос события слайдера из `onChanged` в `onChangeEnd`. `onChanged` теперь
  только обновляет UI.
- Прокрутка через `ScrollEndNotification` вместо `ScrollUpdateNotification` и
  слушателя `ScrollController`.
- Неизменные имена и свойства событий, потому что дашборды уже построены на них.
- Совет про проверку через `PostHogConfig.debug` (в виде инструкции выше).
- Замечание из раздела про текстовые поля: если state переживает навигацию, нужно
  решить, что значит «один раз». Отсюда пункт про «один раз за flow».

Не пригодилось:
- Шаг про события тапа/фокуса через `FocusNode`: в спецификации таких событий нет.
- Отправка финального значения при потере фокуса: ни одному событию значение
  поля не нужно, а email и телефон к тому же PII.
- `grep` из раздела «Check if this applies»: в этом проекте до моей правки
  событий не было вообще, проверять было нечего.
