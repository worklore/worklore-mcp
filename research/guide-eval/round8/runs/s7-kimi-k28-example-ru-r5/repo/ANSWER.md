# Почему не работало подключение Intervals.icu

Интеграция была сломана в трёх независимых местах сразу — каждое давало свой
симптом из тикетов #214/#219 и `logs/connect-attempt.log`.

## Причина 1 — кнопка Connect не несла авторизацию (тикет #214, все атлеты)

Кнопка «Connect Intervals.icu» была обычной ссылкой
`<a href="/api/intervals/auth/init">` (`static/app.js`). Это полноценная
навигация браузера, а запросы навигации **не получают** заголовок
`Authorization` — токен сессии SPA живёт в localStorage и добавляется только
fetch-обёрткой на XHR. Сервер в `auth_init` требовал авторизацию → отвечал
401 → браузер показывал белую страницу с `{"error": "unauthorized"}`.
Поэтому кнопка не работала ни у кого, а единственная удавшаяся связка
(Ривера) получилась, только потому что коллега вручную вставил authorize-URL
в браузер, минуя кнопку.

**Исправление:** `POST /api/intervals/auth/init` теперь возвращает JSON
`{authorize_url}`, а фронтенд запрашивает его через fetch (заголовок
доезжает) и сам перенаправляет браузер через
`window.location.assign(authorize_url)` (`server.py`, `static/app.js`).

## Причина 2 — scope с дублирующимися областями (invalid_request у authorize)

`config.py` запрашивал `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,
CALENDAR:READ,CALENDAR:WRITE`. У Intervals `:WRITE` уже включает `:READ`, и
упоминание одной области дважды отклоняется с ошибкой «Duplicate scope»
(в логе — `HTTP/2 400 {"error":"invalid_request"}` ещё до экрана согласия).
Это появилось 2026-10-02 вместе с календарной синхронизацией, поэтому
«вручную вставить ссылку», как в сентябре, больше не получалось.

**Исправление:** каждая область — один раз:
`SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`.

## Причина 3 — самодельное «истечение» вечного токена (тикет #219, Ривера)

Intervals.icu не выдаёт ни `refresh_token`, ни `expires_in` — токен живёт,
пока атлет не отзовёт приложение в настройках. Но `store_connection`
по умолчанию ставил TTL 3600 с, а фоновый «refresher» через час без
refresh-токена помечал связку `expired, reconnect` и обнулял токен. Лог
подтверждает: `17:41 connected (expires in 3600s) → 18:37 expired, reconnect`.
Токен при этом на стороне Intervals был жив (Ривера ничего не отзывала) —
сломало только наше учётное хранилище.

**Исправление:** подключение больше не получает фейковый срок жизни;
фоновый refresher удалён целиком (рефрешить нечего). Отзыв токена теперь
обнаруживается лениво: первый 401 от API сбрасывает токен и переводит
статус в `expired, reconnect`, карточка показывает кнопку переподключения
(`server.py: Handler.wellness`).

## Причина 4 (по заметке коллеги) — лишние поля в обмене кода

`exchange_code` отправлял `grant_type` и `redirect_uri` сверх
`client_id/client_secret/code`. По логу от 2026-09-19 обмен с этими полями
проходил, так что это не причина жалоб, но приведено к документированному
виду — Intervals хочет ровно три поля.

## Что изменено

- `server.py` — init перенесён в POST и возвращает `{authorize_url}`; из
  обмена кода убраны `grant_type`/`redirect_uri`; убраны дефолтный TTL и
  фоновый refresher; в `wellness` добавлена ленивая обработка 401 (сброс
  токена + `expired, reconnect`).
- `config.py` — scope без дублей; удалён неиспользуемый `REFRESH_INTERVAL`.
- `static/app.js` — Connect теперь кнопка: POST через fetch-обёртку →
  `window.location.assign(authorize_url)`.

## Как проверял

End-to-end против локального мока провайдера (`INTERVALS_BASE` на
127.0.0.1): ни один запрос не уходил на настоящий intervals.icu. Прогон
(14 проверок, все зелёные): init без токена → 401; init с токеном →
authorize_url без дублей в scope; callback с подделанным state → 400;
корректный callback → 302 и обмен ровно тремя полями; status/wellness →
данные; подключение не «истекает» со временем; после переключения мока на
401 wellness → 409 с просьбой переподключиться, статус →
`expired, reconnect`; повторный connect → данные снова читаются.

## Какие части заметки коллеги пригодились

- **П. 4 (init должен быть POST, не GET)** — точное описание Причины 1;
  механика «POST возвращает URL, фронт делает location.assign» взята отсюда.
- **П. 2 («Duplicate scope», `:WRITE` подразумевает `:READ`)** — точное
  описание Причины 2, включая правило «каждая область не более одного раза».
- **П. 1 (нет refresh_token и expires_in; ленивая обработка отзыва по 401;
  убрать всю refresh-машинерию)** — точное описание Причины 3.
- **П. 3 (обмен кода: только client_id, client_secret, code)** — Причина 4.

Не пригодилось (осознанно пропущено):

- **JWT-state с `purpose`-claimом** — текущий state уже подписан HMAC с TTL
  15 минут и проверкой целостности; жалоб на подделку state не было, менять
  формат не стал.
- **Guard на несовпадение athlete_id при переподключении** — не был причиной
  ни одного симптома; для коучингового приложения смена привязанного аккаунта
  может быть легитимной, решение за продуктом.
- **Шифрование токена at rest** — здесь dev-стор в памяти; для prod-таблиц
  это отдельная задача, к данной поломке отношения не имеет.
