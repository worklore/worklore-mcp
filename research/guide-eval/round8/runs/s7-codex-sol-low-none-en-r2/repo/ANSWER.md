# Intervals.icu connection failures

1. The Connect link navigated directly to `/api/intervals/auth/init`. Browser navigation does not include the SPA's `Authorization: Bearer` header, so the server returned 401. The button now calls that endpoint through the authenticated fetch wrapper and navigates to the returned authorization URL.
2. The OAuth client ID, secret, and callback URI were hardcoded to development placeholders. Production environment credentials were ignored, so a manually opened authorize URL used `tricoach-dev` and Intervals.icu rejected it before consent. These values now come from `INTERVALS_CLIENT_ID`, `INTERVALS_CLIENT_SECRET`, and `INTERVALS_REDIRECT_URI` when set. The configured redirect URI must match the URI registered for the Intervals.icu app. The requested scopes also contained redundant READ permissions alongside WRITE; WRITE includes READ. The request now asks only for `WELLNESS:READ,CALENDAR:WRITE`, matching the app's stated use.
3. Intervals.icu's token response has no refresh token or expiry. The backend invented a one-hour lifetime, then marked the connection expired because it could not refresh it. A token without `expires_in` now has no scheduled expiry. Tokens with an explicit expiry still follow the refresh path.

The captured 400 response does not identify its rejected parameter, so the hardcoded development client and redirect are the actionable configuration defects rather than a conclusively identified parameter from that response alone. Local placeholder credentials cannot complete a live OAuth flow; the registered production values must be supplied in the environment.
