# Почему интеграция Intervals.icu не работала

Были три независимых дефекта, которые складывались в общую картину: кнопка
Connect не работала ни у кого, а единственная удавшаяся связь «умирала» через
час, после чего переподключиться было невозможно (из-за тех же дефектов).

## 1. Кнопка Connect открывала `/api/intervals/auth/init` без заголовка авторизации

**Симптом:** белая страница `{"error": "unauthorized"}` у всех (тикет #214,
первый блок `logs/connect-attempt.log`).

**Причина:** кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`,
то есть полноценным переходом браузера. Токен сессии живёт в `localStorage` и
подставляется только fetch-обёрткой SPA в заголовок `Authorization: Bearer`,
которую навигация по ссылке не использует. Сервер (`require_user` в
`server.py`) такой запрос отклонял с 401. Лог это подтверждает: документная
навигация, «no Authorization header».

**Исправление:** `auth/init` теперь возвращает JSON `{"url": "<authorize URL>"}`
(`server.py:200`), а фронт сначала делает fetch с заголовком через `api()`, и
только потом уходит на полученный URL (`static/app.js:31`,
`static/app.js:41`). Ручной обход поддержки тоже сохранился:
`curl -H 'Authorization: Bearer …' …/auth/init | jq -r .url`.

## 2. Authorize-запрос отклонялся: `400 {"error":"invalid_request"}`

**Симптом:** после релиза календарного синка 2026-10-02 Intervals.icu стал
отвечать ошибкой до экрана согласия (тикет #219, второй блок
`logs/connect-attempt.log`).

**Причина:** вместе с календарным синком в `SCOPES` добавили
`CALENDAR:READ,CALENDAR:WRITE`. Запрос на `/oauth/authorize` стал запрашивать
scope, на который приложение tricoach не зарегистрировано/не одобрено —
Intervals отклоняет весь запрос с `invalid_request`, не доходя до согласия.
Параметры `state` и `redirect_uri` ни при чём (поддержка меняла их — тело
ошибки то же); до 2026-10-02 с той же конфигурацией, но без календарных scope,
флоу работал (подключение Rivera 2026-09-19).

**Исправление:** `SCOPES` возвращены к одобренному набору
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ` (`config.py:17`) и вынесены в
переменную окружения `INTERVALS_SCOPES`. Как только владелец приложения
добавит CALENDAR-доступ в регистрацию приложения на странице управления
Intervals.icu, календарные scope можно вернуть одной настройкой env, без правки
кода. До этого календарный синк запрашивать нечего — провайдер блокирует весь
флоу, не одну фичу.

## 3. Связь принудительно «протухала» через час

**Симптом:** у Rivera подключение от 2026-09-19 через ~час перешло в статус
«expired, reconnect» (третий блок `logs/connect-attempt.log`, тикет #219).

**Причина:** Intervals.icu не истекает access token: его ответ на обмен кода —
`{token_type, access_token, scope, athlete}`, без `expires_in` и без
`refresh_token` (так и в наших логах). Код же в этом случае выдумывал срок жизни
`DEFAULT_TOKEN_TTL = 3600`, а фоновый «обновлятель» через час помечал связь
просроченной. Обновить токен было нечем (refresh token у провайдера не
выдаётся), поэтому честное поведение — считать такой токен бессрочным.

**Исправление:** нет `expires_in` в ответе → `expires_at = None`, токен
бессрочный (`server.py:66-71`); обновлятель пропускает такие связи и по-прежнему
обслуживает токены с реальным сроком жизни и refresh token, если провайдер их
когда-либо выдаст (`server.py:83`).

## Проверка

Прогнал весь флоу end-to-end против локальной заглушки провайдера (никаких
внешних вызовов): status → auth/init (без заголовка — 401, с Bearer — 200 и URL
без CALENDAR) → callback → 302 → подключение сохранено с `expires_at=None` →
wellness проксируется → после проходов обновлятеля связь остаётся connected;
дополнительно проверены пути refresh и «expired, reconnect» для гипотетических
истекающих токенов и disconnect. 14/14 проверок пройдено; `node --check
static/app.js` и `py_compile` чистые.
