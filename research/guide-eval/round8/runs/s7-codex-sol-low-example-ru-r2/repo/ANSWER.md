# Причины сбоя Intervals.icu

1. Кнопка Connect была обычной ссылкой на `GET /api/intervals/auth/init`. При переходе браузер не добавляет `Authorization` из SPA, поэтому сервер возвращал 401 каждому атлету. Теперь кнопка вызывает авторизованный `POST` через `fetch`, получает `authorize_url` и открывает его.
2. В OAuth scope одновременно стояли `ACTIVITY:READ` и `ACTIVITY:WRITE`, а также `CALENDAR:READ` и `CALENDAR:WRITE`. Запись уже включает чтение; повтор области приводил к ошибке на этапе авторизации. Теперь запрашиваются `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`.
3. Ответ Intervals на обмен кода не содержит `expires_in` и `refresh_token`. Код придумывал срок в 3600 секунд и после него удалял действующий токен. Удалены искусственный срок и фоновое обновление. При реальном 401 от Intervals токен очищается, а интерфейс показывает необходимость повторного подключения.

Из заметки коллеги пригодились сведения о POST init, уникальных областях scope, бессрочном токене, полях обмена кода и обработке отзыва по 401. Обмен кода теперь передаёт только `client_id`, `client_secret` и `code`. Добавлена проверка, что повторное подключение не заменит сохранённого атлета другим. Подписанный `state` уже существовал; проверка дополнена запретом будущей отметки времени и неизвестного пользователя. JWT из заметки не понадобился: существующая подпись HMAC и ограничение в 15 минут решают задачу для этого приложения. Шифрование в покое здесь неприменимо: демонстрационный сервер хранит подключения только в памяти; для постоянного хранилища оно остаётся отдельным требованием.

Локально проверены HTTP методы init, авторизация, scope и state, поля обмена кода, сохранение подключения, защита от подмены атлета и переход в `reconnect required` после 401. Реальный OAuth с Intervals не выполнялся: в `config.py` находятся заглушки client credentials и redirect URI локального сервера.
