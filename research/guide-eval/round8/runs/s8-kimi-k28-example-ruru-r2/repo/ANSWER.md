# Что изменил

## Причина

`build_system()` в bot.py собирал системный промпт одним текстовым блоком с
одним маркером `cache_control: ephemeral`. Кеш Anthropic — это хеш префикса:
`save_fact` дописывает факт в конец блока, хеш всего блока меняется, и следующий
вызов (вторая итерация цикла инструментов и все сообщения до конца TTL)
пересчитывает весь промпт по полной цене. В logs/usage.jsonl это видно как
`cache_creation_input_tokens` ~1000+ и `cache_read_input_tokens: 0` сразу после
каждого `save_fact`.

## Изменение

bot.py, функция `build_system()`: системный промпт разбит на два блока, у каждого
свой маркер `cache_control: {"type": "ephemeral"}`:

1. **Статический блок** — только `INSTRUCTIONS`. Байт-в-байт одинаков для всех
   атлетов и всех дней (дата, имя, факты — всё вынесено во второй блок).
2. **Изменчивый хвост** — `athlete_context()`: дата, профиль, зоны, цель,
   долговременные факты, язык.

Теперь запись в память инвалидирует только хвост (~300 символов), а статический
префикс (~2500 символов инструкций) остаётся кеш-попаданием. Это именно паттерн
«два сегмента cache_control» из заметки коллеги. Заодно поправлено описание в
README.md («a cache_control marker» → два блока).

`select_tools()` (фильтрация инструментов по ключевым словам) не тронут — в
NOTES.md помечено как явный выигрыш, и коллега в заметке тоже советует его
оставить. Известный недостаток сохраняется: сообщение с ключевым словом
(`plan_week`, `predict_race`) подтягивает новую группу инструментов и один раз
перекеширует всё — терпимо, как в заметке.

## Проверка

SDK Anthropic в окружении нет, поэтому проверял без сети, с фейковым LLM:

- `build_system()` возвращает два блока, оба с маркером.
- Блок 1 байт-в-байт идентичен для разных атлетов, после `save_fact` и при
  смене даты; блок 2 меняется при `save_fact` и при смене даты.
- Прогон `reply()` через цикл с `save_fact`: во второй итерации статический блок
  в запросе неизменен, хвост вырос ровно на один факт.
- Побочные записи теста в `data/athletes.json` и `logs/usage.jsonl` откачены,
  `__pycache__` удалён.

Живую проверку по `usage` (как описано в заметке: после `save_fact` третье
сообщение должно показать `cache_read` на статический блок и `cache_creation`
размером с хвост) стоит сделать при следующем деплое с реальным ключом.

## Что пригодилось из заметки коллеги

- **Главный приём** — разбить `system` на два блока с отдельными маркерами
  `cache_control: ephemeral`: статические инструкции / изменчивый хвост. Это и
  есть суть фикса.
- **Объяснение механики** — кеш это хеш префикса, изменение одного байта
  валидирует всё от него до конца блока. Подтвердило диагноз по usage.jsonl.
- **Требование байт-в-байт стабильности статики** — дата, имя и факты нельзя
  подставлять в блок инструкций; проверяю это в тесте явно.
- **Пункт про `usage`** — читать `cache_creation_input_tokens` /
  `cache_read_input_tokens` в каждом ответе как точную диагностику.

Не пригодилось (пропустил):

- **Фильтрация инструментов по ключевым словам** — в этом боте уже реализована
  (March, `select_tools`), менять не нужно.
- **Отказ от top-N отбора фактов под сообщение** — такого кода здесь нет и не
  планировался; просто не применимо, но принцип «включать все факты дешевле,
  чем персонализировать» учтён: персонализацию внутри блоков не добавлял.
