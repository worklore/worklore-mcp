# Почему ночная задача молчала

Согласно `launchctl-print.txt`, launchd **запустил задачу шесть раз**; её последний код выхода — 1. Значит, проблема не в расписании. В `Library/Logs/nightly-review.err` после каждого запуска стоят две ошибки: `Not logged in · Please run /login` от `claude` и `read-only variable: status` от zsh.

1. В окружении задачи из `launchctl print` есть `PATH`, но нет `USER`. При таком запуске `claude` не находил свой вход в учётную запись. В plist добавлен `USER=vk`, как в пользовательском сеансе, для которого создан агент. Это устраняет видимое различие окружений; подтвердить действующую авторизацию `claude` можно только на исходном Mac при настоящем запуске.
2. После неудачи `claude` скрипт присваивал код выхода переменной `status`. В zsh она доступна только для чтения, поэтому выполнение обрывалось **до** ветки с сообщением об ошибке. Переменная заменена на `rc`.
3. Уведомитель подавлял тело ответа Telegram, а обычный `curl -sS` возвращает код 0 и при HTTP-ошибке. Теперь `curl -fsS` сообщает о такой ошибке ненулевым кодом; ошибка чтения токена из keychain также явно выводится в stderr. По снимку нельзя утверждать, что эта третья проблема уже случалась: до уведомителя прежний скрипт не доходил.

Скрипт также закрывает stdin для `claude -p` с prompt в аргументе, отвергает пустой результат, пишет начало и длительность запуска, а ошибку отправки уведомления отражает в коде выхода и stderr. Поэтому код 0 теперь требует непустого отчёта и успешного завершения уведомителя. Это не доказывает доставку сообщения адресату: её подтверждает только реальная проверка в Telegram.

## Что пригодилось из заметки коллеги

- Проверка `launchctl print` и stderr: они сразу отделили срабатывание расписания от сбоя скрипта.
- Запрет присваивания `status` в zsh: это точная причина, по которой не отправлялось сообщение об ошибке.
- `USER` в plist: это соответствует ошибке авторизации и отсутствующей переменной в сохранённом окружении.
- Закрытый stdin при prompt-аргументе, проверка реального результата и длительности: добавлены как защита от ложного успешного запуска.

Передача prompt через pipe **не понадобилась**: в логе нет ошибки о неполученном prompt, а сам prompt уже передавался аргументом. Совет выполнить `kickstart` и послать тестовые сообщения здесь не применялся: по условию работа ограничена снимком, без загрузки агента и обращения к внешним сервисам.

## Проверка в снимке

`zsh -n`, `bash -n`, `plutil -lint` и `git diff --check` прошли. Локальные заглушки без сети подтвердили четыре ветки: успешный отчёт и уведомление (код 0), ошибка агента (код 7 и сообщение о сбое), пустой отчёт (код 1 и сообщение о сбое), ошибка уведомителя (код 1). Заглушка `curl` подтвердила ненулевой выход при HTTP-ошибке. Настоящие авторизация `claude`, keychain, загрузка изменённого plist и доставка Telegram из этого снимка не проверялись.
