# Кеширование после save_fact

## Причина
`build_system` клал инструкции и контекст атлета (дата, зоны, список фактов) в **один** text-блок с одним `cache_control`. Кеш префиксный, поэтому после `save_fact` (список фактов изменился) весь блок получал другой хеш, и ~1000 токенов инструкций заново писались в кеш (`cache_read=0`, `cache_creation≈1000` в `logs/usage.jsonl`). То же самое происходило при смене даты.

## Что изменено (`bot.py`, `build_system`)
System теперь состоит из двух блоков:
1. `INSTRUCTIONS` (статика) с `cache_control` — не зависит от фактов и даты.
2. `athlete_context(...)` (динамика) со своим `cache_control` — чтобы раунды tool-цикла и следующие сообщения читали и его.

Порядок: tools → инструкции → контекст, поэтому изменение фактов затрагивает только хвост. Фильтрацию инструментов по ключевым словам не трогал (по NOTES.md она полезна).

## Ограничение — проверьте на реальных логах
Минимум для кеширования у Sonnet 4.5 — 1024 токена в префиксе до точки кеша. По логам весь запрос ≈1046 токенов, контекст ≈100, значит статический префикс (инструкции + core-инструменты) ≈ 950 токенов — **вблизи или чуть ниже порога**. Если после правки `cache_creation_input_tokens` на статике останется 0, префикс не кешируется из-за размера, и тогда нужно, чтобы статическая часть превысила 1024 токена (например, добавить в инструкции реально полезные примеры ответов) — текст я не раздувал. Точных токенов без вызова API я не считал, проверка не запускалась (ключа/сети нет, ничего не отправлялось).

Дополнительно: набор tools тоже входит в префикс, поэтому сообщения с разными группами инструментов (plan/race) кешируются раздельно.
