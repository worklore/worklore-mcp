# Почему вторая публикация возвращает 500

## Причина
`similarity()` в `src/app.py` возвращала `round(..., 4)`, то есть Python `float`. Эти оценки
попадают в `item["similar"]`, а `put_item` в boto3 не принимает float
(`TypeError: Float types are not supported. Use Decimal types instead.`, см. `logs/error.log`).
При первой публикации таблица пуста, `related()` возвращает `[]`, ни одного float нет, и запись проходит.
Со второй публикации в `similar` появляются оценки, и запись падает. Ошибка зависит от состояния таблицы.

## Исправление
- `similarity()` теперь возвращает целые проценты (`int`, 0–100).
- `assert_no_floats()` перед `put_item` проверяет весь item. Если float появится снова,
  ошибка сразу покажет имя поля.
- Добавлен тест `test_second_publish_with_existing_story`: он сначала кладёт запись в таблицу,
  потом публикует вторую, так что код, зависящий от состояния, выполняется. Старый тест проверял
  только путь с пустой таблицей. Фейковая таблица отклоняет float так же, как boto3.

## Что пригодилось из заметки коллеги
- Диагноз (float в оценках похожести, падение только при непустой таблице) и исправление
  (целые проценты) совпали с нашим случаем.
- Урок про тест с предварительно засеянной таблицей: применён.
- Поиск `round(` и `/` рядом со словарями элементов: так найден единственный источник float.
  `published_at` уже `int`.
- Остальное (реальная таблица, деплой) пропущено: по условиям задачи ничего не публикуется во внешние сервисы.

## Замечание, не исправлено
`scan` не обходит страницы (`LastEvaluatedKey`). Когда таблица вырастет больше 1 МБ, похожие истории
будут считаться только по первой странице. Это отдельная проблема.
