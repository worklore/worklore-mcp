# Почему атлеты не могут подключить Intervals.icu

Ниже причины по порядку их влияния на пользователя. Для каждой указано, что исправлено в коде и что остаётся проверить вручную.

## 1. Кнопка Connect всегда отдаёт 401 (тикет #214)

`<a href="/api/intervals/auth/init">` делает обычную навигацию браузера. Браузер не добавляет заголовок `Authorization`, а сервер авторизует пользователя только по Bearer-токену из `localStorage`, который шлёт `api()` в `static/app.js`. Поэтому `auth/init` всегда получал 401 и показывал `{"error": "unauthorized"}`. Это совпадает с логом `connect-attempt.log`, раздел 1.

**Исправлено:** `auth/init` теперь возвращает JSON `{"url": ...}`. SPA получает его через `api()` (с заголовком) и переходит по нему через `location.href`.

## 2. Подключение «истекает» через час (тикет #219, Rivera)

Intervals.icu не выдаёт refresh-токен, и в ответе token endpoint нет `expires_in`. Код при этом подставлял `DEFAULT_TOKEN_TTL = 3600` и через час сам помечал подключение как `expired, reconnect`, хотя токен был ещё действителен. В логе это видно: подключение в 17:41:04, «expired» в 18:37:12, то есть примерно через час, когда выдуманный срок почти вышел.

**Исправлено:** если `expires_in` не пришёл, срок не выдумывается. Токен сбрасывается только тогда, когда Intervals сам отвечает 401 на запрос данных (`/wellness`). Фоновая проверка по таймеру для таких токенов не работает. Refresh-ветка сохранена для случая, когда провайдер когда-нибудь вернёт refresh-токен.

## 3. Authorize-шаг возвращает `400 invalid_request` (тикет #219, с 2 октября)

Причина в запросе, а не в состоянии подключения. Ошибка не меняется, если убрать `state` или поменять `redirect_uri`, значит, проблема в другом параметре. По документации Intervals формат scope у нас верный: через запятую, имена `ACTIVITY`, `WELLNESS`, `CALENDAR`. Рабочий токен Rivera вернул уже нормализованный набор `ACTIVITY:WRITE,WELLNESS:READ`, где READ-дублей нет. Текущий запрос содержал избыточные пары `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`, а `CALENDAR:*` появился вместе с календарной синхронизацией 2 октября.

**Исправлено:** scope сокращён до `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`, его можно переопределить через `INTERVALS_SCOPES`.

**Не подтверждено:** ни один запрос к живому intervals.icu я не делал, поэтому не знаю, что именно вызывает 400. Если после деплоя ошибка осталась, проверьте на странице приложения в Intervals:
- какие scope одобрены для клиента (если `CALENDAR:WRITE` не одобрен, запрос будет отклонён);
- что приложение одобрено: пока оно в статусе «Pending», OAuth-поток не работает;
- что `redirect_uri` зарегистрирован в точности (`http://localhost:8766/api/intervals/callback` или его production-аналог);
- не включён ли PKCE: по документации, если он включён, запрос без `code_challenge` отклоняется.

## 4. Клиентские данные захардкожены в placeholder-ах

В `config.py` стояли `CLIENT_ID = "tricoach-dev"` и `CLIENT_SECRET = "s3cr3t-placeholder-0000"`. Комментарий говорит, что настоящая пара лежит в deploy env, но код её никогда не читал. Прод отправлял бы placeholder-ы.

**Исправлено:** `CLIENT_ID`, `CLIENT_SECRET`, `APP_SECRET`, `SCOPES` читаются из окружения: `INTERVALS_CLIENT_ID`, `INTERVALS_CLIENT_SECRET`, `APP_SECRET`, `INTERVALS_SCOPES`. Значения по умолчанию остаются dev-заглушками.
**Нужно сделать вручную:** задать эти переменные в deploy env. Я ничего не деплоил.

## Что проверено

- Поток проверен локально на фейковом Intervals (127.0.0.1:9999, `INTERVALS_BASE`): `auth/init` с Bearer возвращает URL, без Bearer даёт 401; callback сохраняет подключение без срока; `/wellness` возвращает 200; после 401 от провайдера статус становится `expired, reconnect`.
- Синтаксис `server.py`, `config.py` и `static/app.js` проверен.
- Вживую с intervals.icu не проверялось.

## Что осталось и нужно решить отдельно

- **Дефолтный токен в SPA.** `static/app.js` берёт `tok-okafor`, если в `localStorage` нет `tc_token`. Любой пользователь без токена работает как C. Okafor и может подключить аккаунт тренера. Это похоже на ошибку, и я её не трогал: сначала нужно решить, как должен выглядеть экран входа.
- **Пользователи, которые уже «подключались» через вставленную ссылку (Rivera).** В Intervals у них остаётся приложение tricoach. Пусть нажмут Connect заново. Старое подключение лучше отозвать (`DELETE /api/v1/disconnect-app`).
- **Блокировка на время HTTP-запросов.** `refresh_tokens()` держит `LOCK` во время сетевого вызова, и все запросы ждут до 15 с. Для Intervals это не важно, пока refresh-токенов нет.
- **Хранилище в памяти.** Подключения теряются при перезапуске сервера. В прод-схеме это, по README, Postgres.
