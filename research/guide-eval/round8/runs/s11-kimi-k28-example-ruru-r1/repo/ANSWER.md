# Почему вторая публикация падала с 500

## Причина

`similarity()` в `src/app.py` возвращала Python `float` (результат `round()` над
float-арифметикой: деления и коэффициенты `0.7`/`0.3`). Этот `score` попадает в
поле `similar` элемента, который пишется в DynamoDB через `put_item`. boto3 не
сериализует float и бросает `TypeError: Float types are not supported. Use
Decimal types instead.` — именно эта ошибка в `logs/error.log` (стектрейс
заканчивается на `types.py:164`).

Первая публикация выживала не из-за особенности запроса, а потому что при пустой
таблице `related()` возвращает `[]` — непохожих историй нет, оценок нет, float в
элементе нет, и запись проходит. Бага проявлялась только когда в таблице уже
была хотя бы одна запись, то есть начиная со второй публикации и далее всегда.

## Исправление

`src/app.py`, функция `similarity()`: оценки теперь считаются в
`decimal.Decimal` (числители оборачиваются в `Decimal`, коэффициенты —
строковые литералы `Decimal("0.7")`/`Decimal("0.3")`). Возвращаемое значение —
`Decimal`, который DynamoDB принимает нативно. Изменение сортировки и формата
элемента не потребовалось.

Так, чтобы не могло повториться (по уроку из заметки коллеги):

- В `tests/test_publish.py` добавлен тест `test_publish_with_existing_row`:
  сначала в таблицу сажается одна история, затем публикуется вторая. Только
  этот путь выполняет зависящий от состояния код (расчёт похожести), и теперь
  любой regression на float-значениях в элементе поймается — `FakeTable`
  валидирует типы так же, как boto3.
- Проверен слепок кода на другие источники float в элементе: искались `round(` и
  `/`, питающие словари элементов. Единственным таким местом была `similarity()`;
  `published_at` уже `int`, остальные поля — строки/списки строк.

Проверка: `python3 -m unittest discover tests` — оба теста зелёные; ручной
прогон двух публикаций подряд показывает `similar: [{'slug': ..., 'score':
Decimal('0.4500')}]` вместо падения.

## Что из заметки коллеги пригодилось

- Диагноз «float в запись DynamoDB, видимый только со второй записи, когда
  появляются данные» — совпал один в один, включая механизм (пустая таблица →
  нет совпадений → нет оценок → нет падения).
- Идея «настоящий путь — с заполненной таблицей»: тест теперь сначала сеет
  запись и только потом проверяет публикацию.
- Чек-лист воспроизведения: проследить вычисляемые значения (деления, средние,
  округления), идущие в элемент; поиск `round(` и `/`; проверка двумя
  реальными публикациями подряд.

Не пригодилось / пропущено:

- Конкретный фикс «сделать оценки целыми процентами» (int) — вместо потери
  точности выбран `Decimal`, который хранит дробное значение как есть и тоже
  принимается DynamoDB.
- Деплой и публикация в реальную таблицу AWS — по правилам задачи ничего не
  деплоилось; валидация выполнена через `FakeTable`, который воспроизводит
  отказ boto3 на float.
