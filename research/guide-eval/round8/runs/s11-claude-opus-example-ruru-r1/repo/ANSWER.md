# Почему вторая публикация возвращает 500

## Причина

`publish()` сохраняет вместе с историей список `similar: [{slug, score}]`.
`score` считает `similarity()` — `round(0.7 * tag_score + 0.3 * word_score, 4)`,
а это Python `float`. boto3 не сериализует float в DynamoDB и бросает
`TypeError: Float types are not supported. Use Decimal types instead.`
(`logs/error.log`, `src/app.py` строка 63 → `table.put_item`). `handler()` ловит это
как обычное `Exception` и возвращает 500.

Первая публикация прошла, потому что таблица была пуста: `scan` ничего не вернул,
`related()` вернул `[]`, ни одного float в записи не было (в логе `similar=0`).
С любой второй публикации в таблице уже есть история, считается оценка, и каждая
запись падает (в логе — обе попытки после первой).

Единственный тест проверял только запись в пустую таблицу, поэтому до ветки
с вычислением похожести не доходил. Фейковая таблица при этом уже умела
отвергать float так же, как boto3, — тест просто не давал ей float.

## Исправление

- `src/app.py`, `similarity()`: оценка возвращается как `Decimal(str(round(..., 4)))`
  — точность (4 знака) сохраняется, сортировка работает так же.
- `src/app.py`, новая `to_dynamo()`: перед `put_item` вся запись рекурсивно
  проходит через конвертацию float → `Decimal`. Это граница с DynamoDB: если
  кто-то позже добавит в запись ещё одно вычисляемое поле (среднее, долю, вес),
  оно не уронит запись тем же способом.
- `tests/test_publish.py`: два новых теста — запись в таблицу, где уже есть
  история (проверяется, что `similar` сохранён и score > 0), и три публикации
  подряд через `handler()` с ожиданием 201. На старом коде оба падают
  с тем самым `TypeError`, на новом проходят (`python3 -m unittest discover tests`: 3 OK).

## Что пригодилось из заметки коллеги

- **Диагноз** совпал полностью: float в записи DynamoDB плюс то, что пустая таблица
  не даёт кода, создающего float. Это сразу объяснило «работает один раз».
- **«Конвертировать на границе в int или Decimal»** — взял, но выбрал `Decimal`
  вместо целых процентов, чтобы не терять точность и не менять смысл поля `score`.
  Дополнительно поставил общий конвертер прямо перед `put_item`.
- **«Каждый тест записи сначала сажает одну запись»** — взял: это и есть новый тест
  с непустой таблицей.
- **«Поищите `round(` и `/`, питающие словари записи»** — сделал: единственное место —
  `similarity()`; `published_at` уже `int(time.time())`.

Не пригодилось / пропустил:
- «Опубликуйте дважды в реальную таблицу» — по условиям задачи ничего не
  деплою и не обращаюсь к внешним сервисам; эту роль выполняет `FakeTable`,
  которая валидирует типы как boto3.
- Общие рассуждения про Lambda/boto3 setup и «что нужно от вас» — здесь всё
  было видно в репозитории.
