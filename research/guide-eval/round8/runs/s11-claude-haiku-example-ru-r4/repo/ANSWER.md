# Почему вторая публикация возвращает 500

## Причина

`publish()` сохраняет в элемент DynamoDB поле `similar`: список `{slug, score}`.
`score` считает `similarity()` и возвращает `round(..., 4)`. Это значение типа
Python `float`, а boto3 `put_item` float не принимает. Отсюда
`TypeError: Float types are not supported. Use Decimal types instead.`

Почему первая публикация проходит: таблица пуста, `related()` возвращает `[]`,
score не вычисляется, float в элементе нет. Во второй публикации в таблице уже
есть история, `similar` содержит score, и запись падает. Лог подтверждает это:
в `logs/error.log` первая публикация в 09:14 прошла с `similar=0`, а
публикации в 09:21 и 09:22 с ненулевым `similar` упали с 500.

Ошибка была не в том, что где-то вычисляется float, а в том, что граница записи
в DynamoDB ничего не проверяла. Существующий тест покрывал только пустую таблицу,
поэтому путь с данными никогда не выполнялся.

## Исправление

1. `src/app.py`: добавлена функция `to_dynamo(value)`. Она рекурсивно проходит
   по dict, list и tuple и заменяет каждый `float` на `Decimal(str(value))`.
   `publish()` вызывает `table.put_item(Item=to_dynamo(item))`. Формат score
   не меняется (четыре знака после запятой), меняется только тип в записи.
2. `tests/test_publish.py`:
   - `test_second_publish_with_similar_stories_is_stored`: публикует историю в
     пустую таблицу, затем вторую, которая получает `similar`, и проверяет, что
     score сохранён как `Decimal`. Это тот путь, который падал.
   - `test_handler_second_publish_returns_201`: тот же сценарий через `handler`,
     с ответом 201 вместо 500.
   - `test_converts_nested_floats_to_decimal`: проверка `to_dynamo` на
     вложенных структурах.

## Почему не повторится

- Любой float, появившийся в будущем в любом поле элемента, преобразуется на
  границе записи, а не в месте вычисления. Новый score или среднее не сломают
  запись, даже если разработчик об этом не подумал.
- Тесты записи теперь всегда используют заполненную таблицу. Путь, который
  выполняется один раз (пустая таблица), больше не единственный покрытый.
- `tests/fake_dynamo.py` по-прежнему отклоняет float в `put_item`. Если кто-то
  уберёт `to_dynamo`, тесты упадут. Проверено: без исправления в `app.py` три
  теста из четырёх падают (1 failure, 2 errors).

## Проверка

- `python3 -m unittest discover tests`: 4 теста, все проходят.
- Без исправления в `src/app.py` (через `git stash` только этого файла): тесты
  падают (1 failure, 2 errors).
- Публикация против реальной таблицы DynamoDB не выполнялась: по правилам задачи
  ничего не публикуется и не деплоится. Поэтому проверка выполнена на
  `FakeTable`, который повторяет проверку типов boto3. Перед деплоем стоит
  опубликовать две истории подряд на тестовой таблице.

## Что взято из заметки коллеги

- **Пригодилось:** идея, что путь с существующими данными — отдельный путь,
  который тесты на пустой таблице не выполняют. Это и есть причина бага, поэтому
  тест на вторую публикацию добавлен.
- **Пригодилось:** шаг «найти все float, попадающие в запись». В проекте
  единственное место — `round()` в `similarity()`, его перехватывает `to_dynamo`.
- **Не использовано:** перевод score в целые проценты. Это изменило бы формат
  поля `similar.score`, который читает страница. `Decimal` решает проблему без
  смены контракта.
- **Не использовано:** публикация дважды на реальной таблице. Пункт требует
  публикации и деплоя, а это запрещено правилами задачи.
