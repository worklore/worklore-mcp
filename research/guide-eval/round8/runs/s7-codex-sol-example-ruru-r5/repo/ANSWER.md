# Почему подключение Intervals.icu ломалось

1. **Кнопка всегда приводила к 401.** Она была ссылкой на `GET /api/intervals/auth/init`. Переход по ссылке не отправляет Bearer-токен из `localStorage`, хотя защищённый эндпоинт его требует. Это прямо видно в `logs/connect-attempt.log`. Теперь SPA вызывает `POST /api/intervals/auth/init` через свой `fetch` с заголовком авторизации, получает `authorize_url` в JSON и затем переходит по нему.
2. **Ручной authorize URL отклонялся до consent screen.** В настройке одновременно запрашивались `ACTIVITY:READ` и `ACTIVITY:WRITE`, а также `CALENDAR:READ` и `CALENDAR:WRITE`. У Intervals `WRITE` уже включает `READ`, поэтому повтор области недопустим. Строка scope теперь `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`. По имеющемуся журналу ошибка Intervals была лишь `invalid_request`, поэтому конкретную причину этого 400 мы выводим из строки scope и заметки коллеги, а не из текста ответа провайдера.
3. **Рабочее подключение искусственно истекало через час.** Ответ Intervals для Rivera содержал `access_token` и `athlete`, но не `expires_in` и не `refresh_token`. Сервер назначал срок 3600 секунд и фоновым потоком сбрасывал токен. Этот механизм удалён: токен остаётся подключённым, пока Intervals не вернёт 401 на API-запрос. При 401 сервер удаляет токен и показывает статус `reconnect required`.

## Что пригодилось из заметки

- Правило о включении `READ` в `WRITE` помогло исправить scope.
- Описание бессрочного токена без refresh помогло убрать ложное истечение и перейти к обработке 401.
- Схема авторизованного POST для init и перехода браузера по возвращённому URL объяснила постоянный 401.
- Формат обмена кода (`client_id`, `client_secret`, `code`) применён; `athlete.id` берётся из ответа. Подписанный `state` с назначением и сроком 15 минут связывает callback с пользователем; при повторном подключении другой `athlete.id` отклоняется.

Пункт о шифровании токена при хранении к этому демонстрационному серверу неприменим: его хранилище только в памяти. Для постоянного хранилища в production токен следует шифровать. Реальный OAuth-проход не выполнялся: в `config.py` стоят заглушки учётных данных, а внешние сервисы по условию задачи не вызывались.

Локальная проверка: `python3 -m unittest -v test_intervals` — 3 теста прошли; `python3 -m py_compile server.py config.py` и `node --check static/app.js` — без ошибок. HTTP-тесты проверяют авторизацию init, URL и scope, callback, сохранение токена, wellness, обработку 401 и защиту от подмены аккаунта.
