# Почему nightly-review молчал

## Коротко

Задача запускалась по расписанию и каждый раз падала, а механизм,
который должен был сообщать о падениях, умирал раньше, чем успевал
что-то отправить. Молчание было двуслойным, плюс один латентный баг.

Доказательство, что job работал: `launchctl-print.txt` показывает
`runs = 6` и `last exit code = 1` — задача стартовала все 6 ночей и
все 6 раз завершилась с ошибкой. Заметка коллеги права: exit code
доказывает, что задача *запускалась*, но не то, что она *работала*.

## Слой 1: claude не мог залогиниться («Not logged in»)

`Library/Logs/nightly-review.err` начинается каждый прогон со строки
`Not logged in · Please run /login`. В снапшоте `launchctl print`
видно, что окружение job'а содержит только `PATH` — переменной `USER`
нет. Без неё CLI под launchd не находит свою запись в keychain и
падает сразу, не получив промпт.

Исправление: в `Library/LaunchAgents/com.vk.nightly-review.plist`
в `EnvironmentVariables` добавлен `<key>USER</key><string>vk</string>`.

## Слой 2: zsh убивал «почтальона» (`status=$?`)

Строка 19 старого скрипта: `status=$?`. В zsh `status` — встроенная
переменная только для чтения (синоним `$?`). Присваивание ей убивает
скрипт на месте. Это стояло *между* вызовом агента и вызовом
`notify.sh` с сообщением об ошибке: job падал, а нотификатор
умирал, не сказав ни слова. Именно это видно во второй строке каждой
пары в логе: `nightly-review.zsh:19: read-only variable: status`.
Воспроизвёл локально: `zsh -c 'true; status=$?'` → та же ошибка.

Исправления в `bin/nightly-review.zsh`:

- `rc=$?` вместо `status=$?`.
- Промпт передаётся через stdin: `print -r -- "$PROMPT" | claude -p ...`
  вместо многострочного аргумента — надёжнее в запланированном шелле.
- Добавлен `trap ... EXIT`: любой ненулевой exit шлёт failure-нотификацию
  и пишет в runlog строку с датой, exit-кодом и длительностью. Молчание
  теперь невозможно ни при успехе, ни при падении, на любом участке
  скрипта (включая `cd` в несуществующий репозиторий).

## Что пригодилось из заметки коллеги

- **`launchctl print` (runs, last exit code)** — ключевой поворот:
  «launchd не запускает» оказалось «запускает и падает». Переосмыслил
  задачу до теорий.
- **Читать stderr-лог до теорий** — оба симптома были уже в логе.
- **`status` read-only в zsh, использовать `rc=$?`** — точное попадание
  в слой 2.
- **Передавать промпт через stdin** — применено как профилактика
  (слой 3, латентный).
- **`USER` в `EnvironmentVariables` против «Not logged in»** — точное
  попадание в слой 1.
- **Логировать длительность прогона** — добавлено в trap; прогон,
  закончившийся за секунды, теперь виден как подозрительный.
- **Нотификация об ошибке как можно ближе к началу failure path** —
  применено в виде trap на EXIT, покрывающего все точки выхода.
- **Поправка коллеги об exit code** — верна: exit code говорит, что
  задача запустилась, а не что она сработала; проверять реальный
  результат (файл, сообщение) и длительность.

Не пригодилось:

- **`< /dev/null` при промпте-аргументе** — промпт переведён на stdin,
  где закрытый поток получается сам; под launchd stdin и не терминал.
- **Шаг «Verify: launchctl kickstart -k ...»** — в полном объёме
  выполнить нельзя: это снапшот домашней директории, работать можно
  только внутри текущей папки и ничего не отправлять во внешние
  сервисы. Вместо этого — прогон со стабами (ниже).

## Как проверял

- `zsh -n bin/nightly-review.zsh`, `bash -n bin/notify.sh`,
  `plutil -lint` plist — синтаксис чист.
- End-to-end в текущей папке со стабами `claude` (читает промпт из
  stdin, падает по флагу) и `notify.sh` (пишет «сообщение» в файл,
  HOME подменён на тестовый каталог):
  - успех → exit 0, файл отчёта создан, success-нотификация дошла;
  - «Not logged in» → exit 1, failure-нотификация дошла (раньше —
    ни того ни другого);
  - репозиторий недоступен → exit 1, failure-нотификация дошла;
  - ошибки `read-only variable: status` больше нет.

## Как применить на реальной машине

Снапшот не деплоил (по правилам ничего не отправляю). На машине владельца:

```sh
launchctl bootout gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl kickstart -k gui/$UID/com.vk.nightly-review
launchctl print gui/$UID/com.vk.nightly-review   # runs, last exit code
```

Затем проверить: exit code = 0, файл отчёта за сегодня существует и
не пуст, длительность прогона правдоподобна, в Telegram пришёл
success. Потом один раз сломать намеренно (например, убрать USER) и
убедиться, что приходит failure-нотификация.

(Мелочь: при прогоне теста в песочнице `date -v-1d` ругался — там
GNU date; на macOS это валидный BSD-синтаксис, в скрипте он был и
остался.)
