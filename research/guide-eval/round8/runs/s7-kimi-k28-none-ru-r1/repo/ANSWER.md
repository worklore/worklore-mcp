# Почему не работала интеграция Intervals.icu

Три независимые поломки (по одной на каждый симптом). Исправлены `config.py`,
`server.py`, `static/app.js`; проверено end-to-end локально против стаба,
повторяющего ответы Intervals.icu из официальной документации
(https://intervals.icu/api/v1 → разделы OAuth support / Scopes).

## 1. Кнопка Connect у всех отдавала 401 (тикет #214)

**Причина:** кнопка Connect в SPA была обычной ссылкой
(`<a href="/api/intervals/auth/init">`, app.js). Клик по ней — навигация
браузера, и браузер **не подставляет** заголовок `Authorization: Bearer` (его
добавляет только fetch-обёртка `api()`). Сервер требует этот заголовок
(`require_user`) → 401 «unauthorized». Это видно в логе:
`GET /api/intervals/auth/init 401 (no Authorization header)` при document
navigation. Поэтому кнопка не работала ни у кого, а «обход» поддержки —
вставка authorize-ссылки вручную из curl — срабатывал.

**Исправление:** `/api/intervals/auth/init` теперь возвращает 200 JSON
`{"authorize_url": "..."}` (а не 302), a SPA делает fetch с токеном и сама
направляет браузер на полученный URL. Токен остаётся в заголовке, в URL он не
светится.

## 2. Authorize-шаг стал отвечать 400 invalid_request (с 2026-10-02)

**Причина:** в `SCOPES` на каждую категорию было запрошено по два модификатора:
`ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`. По документации
Intervals.icu («for each scope specify READ or WRITE (to update, implies READ
access)») на каждую категорию указывается **один** модификатор, WRITE
подразумевает READ. Пары READ+WRITE для одной категории — malformed scope list,
поэтому эндпоинт отвечал `{"error":"invalid_request"}` ещё до экрана согласия.
Подтверждения в логах: 400 начался с релиза календарного синка 2026-10-02,
который переписал SCOPES; 400 не исчезал при удалении `state` и замене
`redirect_uri` (т.е. ругался именно на scope); а грантовый ответ успешного
коннекта 2026-09-19 — ровно «по одному на категорию»
(`"scope":"ACTIVITY:WRITE,WELLNESS:READ"`).

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"` —
функциональность прежняя (чтение активностей/велнеса, запись плановых
тренировок в календарь), но один модификатор на категорию. Заодно в authorize
URL добавлен `response_type=code` (обязателен по RFC 6749; эндпоинт его
принимает).

## 3. Связь «протухала» через час и просила reconnect (тикет #219, T. Rivera)

**Причина:** Intervals.icu в ответе токена **не возвращает ни `expires_in`, ни
`refresh_token`** (так в официальной документации, так и в нашем логе от
2026-09-19) — механизма обновления токенов у провайдера нет, токен живёт до
отзыва. Код же при отсутствии `expires_in` самовольно ставил TTL 3600 с
(`DEFAULT_TOKEN_TTL`), а фоновый «обновлятель» токенов, не найдя refresh-токен,
переводил связь в статус `expired, reconnect`. Отсюда: Rivera подключилась
17:41, в 18:37 связь уже «просрочена», хотя на стороне Intervals.icu приложение
осталось подключённым.

**Исправление:** выдуманный TTL и весь refresh-механизм удалены
(`refresh_tokens`, `DEFAULT_TOKEN_TTL`, `REFRESH_INTERVAL`); в хранилище
`expires_at = None`, связь держится до disconnect или отзыва доступа атлетом.
Лог при подключении теперь прямо говорит, что токены Intervals.icu не
истекают.

## Проверка

Поднят локальный стаб Intervals.icu (token-ответ точь-в-точь как в доках, без
`expires_in`/`refresh_token`) и прогнан полный флоу: sign-in → init с токеном
(200 JSON, корректные scope/`response_type`/подписанный state) → callback
(302 → `/?connected=1`) → status «connected» → wellness-прокси дошёл до стаба;
второй пользователь подключился независимо; init без токена по-прежнему 401;
плохой state по-прежнему 400. Все 17 проверок прошли, тестовые артефакты
удалены.

Замечание (не баг): после отзыва доступа на стороне Intervals.icu API начнёт
отдавать 401 — wellness-эндпоинт проксирует этот код как прежде, автоматической
пометки связи «expired» не добавлял (вне рамок жалоб).
