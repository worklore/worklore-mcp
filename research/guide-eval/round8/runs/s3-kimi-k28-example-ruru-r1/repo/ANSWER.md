# Почему nightly-review молчал, и что исправлено

## Короткий ответ

Задача запускалась по расписанию и падала каждую ночь. Молчание было
двухслойным:

1. **Claude не мог залогиниться под launchd** — в окружении задачи нет
   переменной `USER`, CLI не находил свой логин в keychain и умирал с
   `Not logged in · Please run /login`. Обзор никогда не начинался.
2. **Гонец умирал раньше, чем успевал заговорить** — скрипт делал
   `status=$?`, а в zsh `status` — встроенная переменная только для чтения
   (синоним `$?`). Присваивание убивало скрипт на строке 19, **до** ветки,
   которая вызывает `notify.sh` об ошибке. Уведомление о падении стояло ниже
   по течению от самой ошибки.

Доказательства в снапшоте:

- `launchctl-print.txt`: `runs = 6`, `last exit code = 1` — задача работала
  и падала (загружена 2026-10-12, снимок 2026-10-18 — 6 ночей).
- `Library/Logs/nightly-review.err`: ровно 6 одинаковых пар строк —
  `Not logged in · Please run /login` и
  `nightly-review.zsh:19: read-only variable: status`.
- `launchctl-print.txt`, секция `environment`: только `PATH` и
  `XPC_SERVICE_NAME` — `USER` отсутствует.
- `Library/Logs/nightly-review.out` пуст, что согласуется с картиной
  (claude ничего не успевал вывести).

Я воспроизвёл обе ошибки локально в песочнице (поддельный `claude`, стаб
`notify.sh`, изолированный `HOME`): старый скрипт при падающем claude
завершается с 1 и **не отправляет ничего** — точь-в-точь боевое поведение.

## Что исправлено (в файлах снапшота)

**`bin/nightly-review.zsh`**
- `status=$?` → `rc=$?` — главный фикс «гонца»: ветка уведомления об ошибке
  теперь достижима.
- Промпт передаётся через stdin: `print -r -- "$PROMPT" | claude -p
  --output-format text` — многострочный аргумент, пропущенный через
  разбор запланированного шелла, ненадёжен.
- Если claude вышел с 0, но файл пустой — это тоже падение, с уведомлением
  (защита от «зелёного кода выхода при несделанной работе»).
- Уведомления идут через функцию `notify`; если `notify.sh` сам падает,
  об этом пишется в stderr (попадает в `nightly-review.err` — тишина
  становится невозможной даже при дохлом гонце).
- В stderr пишется длительность запуска — запуск, длившийся пару секунд,
  видно сразу, не дожидаясь Telegram.

**`Library/LaunchAgents/com.vk.nightly-review.plist`**
- В `EnvironmentVariables` добавлены `USER=vk` и `HOME=/Users/vk`. Без
  `USER` claude CLI не находит логин в keychain — это была причина
  «Not logged in» (`plutil -lint` — OK).

**`bin/notify.sh`**
- Если токен не читается из keychain, скрипт пишет
  `notify.sh: could not read tg-bot token from keychain` в stderr вместо
  молчаливого `exit 1` под `set -e`.

## Как проверял (локально, без внешних сервисов)

- `zsh -n` / `bash -n` — синтаксис; `plutil -lint` — plist.
- Песочница с поддельным `claude` (ок/fail/пустой вывод), стабом
  `notify.sh` (пишет в файл вместо отправки) и изолированным `HOME`:
  - падающий claude → приходит «FAILED (exit 1)» (раньше — тишина);
  - успешный claude → приходит «done: …», длительность в stderr;
  - пустой вывод при exit 0 → приходит «wrote nothing»;
  - падающий `notify.sh` → след в stderr;
  - отсутствующий репозиторий → приходит «repo missing»;
  - многострочный промпт доходит до claude через stdin целиком.
- Проверил по ходу и собственную ошибку: изначально использовал
  `$EPOCHSECONDS`, который в неинтерактивном zsh недоступен без модуля
  `zsh/datetime` и убивает скрипт под `set -u`. Заменил на встроенный
  `$SECONDS`.

## Что осталось сделать на реальной машине (я это не делал — работал только
## в снапшоте)

1. Положить исправленные файлы на место в `~/`.
2. Перезагрузить агент:
   `launchctl bootout gui/$UID/com.vk.nightly-review` затем
   `launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist`
   (plist изменился — перезагрузка обязательна).
3. `launchctl kickstart -k gui/$UID/com.vk.nightly-review` и проверить:
   `last exit code = 0` в `launchctl print`, свежий непустой
   `~/Library/Logs/nightly-review-<дата>.md`, пришло уведомление об успехе.
4. Намеренно сломать (например, временно переименовать `~/projects/shop`)
   и убедиться, что приходит уведомление об ошибке. Вернуть как было.

## Что пригодилось из заметки коллеги

- **Проверить реальность через `launchctl print` в первую очередь** —
  пригодилось: `runs = 6`, `last exit code = 1` сразу перевели диагноз с
  «launchd не запускает» на «скрипт падает и не может сообщить».
- **Читать StandardErrorPath до построения теорий** — пригодилось: обе
  ошибки лежали там парой строк, диагноз занял одну команду `cat`.
- **`status=$?` в zsh убивает скрипт** — пригодилось напрямую: это был
  слой №2, точное совпадение с моим случаем. Фикс `rc=$?`.
- **Промпт headless-агенту через stdin, не многострочным аргументом** —
  пригодилось, применил.
- **`USER` в `EnvironmentVariables` plist** — пригодилось: именно
  отсутствие `USER` давало «Not logged in», слой №1.
- **«Код выхода говорит, что задача запускалась, а не что сработала»** —
  пригодилось: добавил проверку непустого результата и лог длительности.

## Что не пригодилось (и почему)

- **`< /dev/null` для `claude -p`** — не понадобилось: это защита для
  формы «промпт аргументом», а я перешёл на форму «промпт через stdin»,
  где stdin и есть канал промпта.
- **Тест с `launchctl kickstart` и намеренной поломкой на боевой машине** —
  в снапшоте выполнить нельзя, оставил как шаги выше; локально заменил
  прогоном песочницы со стабами.
