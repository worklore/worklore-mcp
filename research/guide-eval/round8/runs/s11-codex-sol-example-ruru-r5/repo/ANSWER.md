# Причина

При первой публикации `scan()` возвращает пустой список, поэтому `similar` пуст и запись в DynamoDB проходит. При второй публикации `related()` вычисляет оценку через деление и `round()` в `similarity()`. Результат — Python `float` в `similar[0].score`. Сериализатор boto3 отклоняет `float` при `put_item`, что видно в `logs/error.log`; обработчик превращает исключение в HTTP 500.

# Исправление

`similarity()` теперь считает доли и взвешенную оценку в `Decimal`, округляя результат до четырёх знаков. Таким образом, в `similar.score` не возникает `float`, а прежний масштаб оценки от 0 до 1 и точность сохраняются. Добавлен регрессионный тест: два вызова `handler()` с одной таблицей, проверка обоих ответов 201 и сохранённой оценки второй истории. До исправления этот тест получал 500 на втором вызове. После исправления `python3 -m unittest discover tests -v` проходит: 2 теста.

# Что пригодилось из заметки коллеги

- Объяснение различия пустой и заполненной таблицы: `similar` возникает только после первой записи.
- Поиск вычисляемых значений на пути к `put_item`: деление и `round()` давали `float`.
- Регрессионная проверка записи при уже существующей истории и использование `Decimal`, который принимает DynamoDB.

Вместо целых процентов выбран `Decimal`, чтобы не менять формат и точность оценки. Проверка выполнена локально с `FakeTable`; совет публиковать дважды в настоящую таблицу не применялся, поскольку внешние сервисы по условиям задачи запрещены.
