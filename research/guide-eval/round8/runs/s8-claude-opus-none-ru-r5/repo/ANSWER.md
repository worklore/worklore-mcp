# Почему save_fact сбрасывал кеш и что изменено

## Причина

`build_system()` собирал весь системный промпт в **один** блок с одним `cache_control`:
инструкции + профиль + дата + список фактов + `Language`. Кеш Anthropic ищет совпадение
по префиксу, а записи ключуются по точкам `cache_control`. `save_fact` дописывал строку
в середину этого блока (до `Language: ...`). Из-за этого менялся весь блок, и
единственная запись в кеше больше не совпадала. Следующий вызов (раунд 2 того же сообщения,
потому что `run_tool` сразу меняет `a.facts`) заново записывал в кеш всё, ~1000+ токенов.
В `logs/usage.jsonl` это видно: каждая строка после `save_fact` выглядит так:
`cache_read_input_tokens: 0, cache_creation_input_tokens: ~1050–1100`.

Просто вынести инструкции в отдельный блок с отдельной точкой кеширования мало. Минимальный
кешируемый префикс у Sonnet 4.5 — 1024 токена. По логам tools + инструкции + профиль
занимают около 950–1000 токенов: у атлета 77 весь промпт вместе с двумя фактами весит
ровно 1024. Такой блок молча не закешировался бы.

## Что изменено (только `bot.py`)

- `athlete_context()` теперь содержит только то, что не меняется при записи факта:
  дату, имя, вид спорта, зоны, цель, язык и заголовок списка фактов. Строка `Language`
  переехала выше фактов, а заглушка `(none yet)` убрана, чтобы список фактов только
  дописывался в конец.
- `build_system()` возвращает блоки `[инструкции + профиль] [- факт 1] … [- факт N]`.
  `cache_control` стоит на первом и на последнем блоке, всего 2 точки из 4 допустимых.
- Когда добавляется факт N+1, старые блоки не меняются. API проверяет границы предыдущих
  блоков (до 20 назад) и находит запись, которую сделал прошлый вызов (она заканчивается
  на факте N). Из кеша читается весь прежний префикс, а заново оплачивается только новый
  факт (~15 токенов). Затем создаётся новая запись. Префикс при этом остаётся больше
  1024 токенов, так что минимум не мешает.
- Точка на первом блоке — запасной вариант на случай, если факты когда-нибудь будут
  редактироваться или удаляться. Если она меньше минимума, API её просто проигнорирует.

Фильтрация tools по ключевым словам не тронута, как просит NOTES.md.

## Проверка

API не вызывался: ключа нет, наружу ничего не отправлялось. Я прогнал `reply()` с
поддельным LLM, который моделирует префиксный кеш по блокам с lookback на 20 блоков,
на копии `athletes.json`. Сценарий: сообщение → сообщение с `save_fact` (2 раунда) →
следующее сообщение. Раньше раунд после `save_fact` давал полный промах. Теперь все
вызовы после первого попадают в кеш: в раунде сразу после `save_fact` закеширован весь
префикс, кроме нового факта. На реальном трафике это должно выглядеть так: после
`save_fact` `cache_read_input_tokens` ≈ прежнему значению, а `cache_creation_input_tokens`
≈ 15–20.

## Что осталось за рамками

- Tools идут в префиксе раньше system. Поэтому сообщение, в котором сработала группа
  `plan`/`race`, по-прежнему полностью пересоздаёт кеш (в логах это строки на 1305/1334).
  Это цена фильтрации tools, её я не менял.
- В первом блоке есть дата `Today`, поэтому раз в сутки кеш пишется заново. При TTL
  5 минут это ничего не стоит.
