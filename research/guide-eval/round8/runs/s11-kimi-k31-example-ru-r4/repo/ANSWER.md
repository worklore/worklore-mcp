# Причина

Вторая публикация падала в `table.put_item()` с ошибкой `TypeError: Float types are not supported. Use Decimal types instead.` (`logs/error.log:25`). Функция `similarity()` возвращала результат `round(..., 4)` — Python `float`. При непустой таблице этот результат попадал в `Item.similar[].score`, а DynamoDB через boto3 не сериализует `float`.

Первая публикация проходила, потому что таблица была пуста: `related()` возвращал пустой список, вычисленных оценок и значений `float` в записываемом объекте не было. Ошибка проявлялась только на пути с уже существующими данными.

# Исправление

- В `src/app.py:24-30` оценка схожести преобразуется в целое число процентов от 0 до 100: `round(100 * (...))`. Промежуточные вычисления по-прежнему могут использовать `float`, но в объект для DynamoDB попадает только `int`.
- В `tests/test_publish.py:27` добавлен регрессионный тест двух последовательных публикаций через `handler()`. Он проверяет ответы `[201, 201]`, сохранение связанной записи и целочисленный тип `score`. Тест использует `FakeTable`, который отклоняет `float` так же, как сериализатор boto3. До исправления тест получал `[201, 500]`.

# Что пригодилось из заметки коллеги

- Объяснение, почему первая запись в пустую таблицу скрывает ошибку, а вторая выполняет код расчёта схожести.
- Рекомендация проследить вычисляемые значения до записи и преобразовать оценку в `int` или `Decimal`; выбран вариант с целыми процентами.
- Рекомендация добавить тест записи при уже заполненной таблице. Поиск `round(` и деления подтвердил, что единственный такой путь в `src` заканчивается теперь целым `score`.
- Проверку на реальной таблице не выполнял, поскольку обращение к внешним сервисам запрещено; вместо неё использованы существующий локальный адаптер DynamoDB и полный путь HTTP-обработчика.

# Проверка

`python3 -m unittest discover tests` — 2 теста, `OK`.

Отдельный прогон двух публикаций через `handler()` вернул `201` для обеих; у второй записи сохранено `similar: [{'slug': 'first-story', 'score': 85}]`.
