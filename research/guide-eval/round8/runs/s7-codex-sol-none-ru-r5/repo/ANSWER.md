# Почему не работало подключение Intervals.icu

1. Кнопка Connect была обычной ссылкой на `/api/intervals/auth/init`. Переход браузера по ссылке не добавляет `Authorization: Bearer ...` из `fetch`-обёртки приложения, поэтому сервер возвращал 401. Теперь кнопка сначала вызывает этот endpoint через авторизованный `fetch`, получает URL авторизации в JSON и затем переводит браузер на Intervals.icu.

2. В запрос авторизации добавили `CALENDAR:READ,CALENDAR:WRITE`. После этого authorize URL стал возвращать `400 invalid_request` ещё до экрана согласия (см. `logs/connect-attempt.log`). Эти права убраны из запроса; остались права на активности и wellness. В этом репозитории нет кода синхронизации календаря, поэтому отдельное право на её запись здесь не запрашивается. Какое право поддерживает Intervals.icu для такой записи, по локальным данным установить нельзя.

3. В успешном ответе токена для Rivera не было ни `expires_in`, ни `refresh_token`. Сервер сам назначал срок 3600 секунд и затем требовал повторное подключение. Теперь срок действия устанавливается только при наличии `expires_in` в ответе провайдера. Если срок не указан, фоновое обновление токен не трогает. Если срок указан, прежняя логика обновления и истечения сохраняется. Ответ Intervals 401 при запросе wellness также переводит подключение в состояние повторного подключения.

Проверено локально: `python3 -m unittest -v test_server.py`, `node --check static/app.js`, `git diff --check`. Живой OAuth-поток с Intervals.icu не проверялся: по условию задачи запросы к внешним сервисам не выполнялись.
