# Почему вторая публикация возвращает 500

**Причина.** `similarity()` в `src/app.py` возвращает `float` (`round(0.7*... , 4)`), и он попадает в `item["similar"][i]["score"]`. boto3 не умеет сериализовать float в DynamoDB: `TypeError: Float types are not supported. Use Decimal types instead.` (logs/error.log). При первой публикации таблица пуста, `related()` возвращает `[]`, floats нет — поэтому всё работало. Со второй публикации есть с чем сравнивать, появляются score-float, и `put_item` падает.

**Исправление.** `similarity()` теперь возвращает `Decimal(str(round(..., 4)))` — точное значение, формат поля `score` для читателей не изменился (число с 4 знаками). Других float в записываемом item нет (`published_at` — int, `tags` — список строк).

**Защита от повторения.** Добавлен тест `test_second_publish_with_populated_table`: сначала кладёт запись, затем публикует вторую, так что выполняется путь с непустой таблицей. `FakeTable` отвергает float так же, как boto3. Раньше единственный тест проходил только пустой путь.

## Что пригодилось из заметки коллеги
- Диагноз (float → DynamoDB, ломается только при непустой таблице) — совпал полностью.
- Идея тестировать запись на заполненной таблице — применена.
- Конвертация на границе записи — применена, но через `Decimal`, а не целые проценты: так не меняется формат `score` для читателя страницы.
- Не использовано: grep по `round(`/`/` по всему коду (код — один файл, проверен вручную); публикация дважды в реальную таблицу — нельзя по условиям задачи (ничего не деплоить и не обращаться к внешним сервисам).
