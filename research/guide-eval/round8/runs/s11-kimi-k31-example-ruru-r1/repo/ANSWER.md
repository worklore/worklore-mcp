# Причина

В `logs/error.log` вторая публикация падает в `table.put_item(Item=item)` с ошибкой `TypeError: Float types are not supported. Use Decimal types instead.`

`src/app.py` вычисляет похожесть через деление и `round()`, поэтому `similarity()` возвращала `float`. Эти значения попадали в `item["similar"][*]["score"]`, а DynamoDB через boto3 не принимает Python `float`.

Первая публикация проходила только потому, что таблица была пуста: `related()` возвращал пустой список, и ни одного `float` в записи не было. На второй публикации появлялась существующая история, вычислялась оценка похожести, и сериализация завершалась ошибкой 500.

# Исправление

- В `src/app.py` `similarity()` теперь возвращает целый процент похожести от 0 до 100 (`round(100 * ...)`). В сохраняемом поле `score` оказывается `int`, поддерживаемый DynamoDB; вычисления с `float` больше не попадают в `put_item`.
- В `tests/test_publish.py` добавлен регрессионный тест `test_second_publish_stores_integer_similarity_scores`: он сначала записывает одну историю, затем публикует вторую, проверяет связь с первой, целочисленный тип `score` и наличие двух записей. Так путь с непустой таблицей закреплён в тестах и регрессия будет обнаружена до выкладки.

Проверка: `python3 -m unittest discover tests` — 2 теста, успешно. Дополнительно два последовательных вызова `handler()` с тестовой таблицей вернули 201, в таблице остались обе записи.

# Что пригодилось из заметки коллеги

Пригодились объяснение ограничения DynamoDB на `float`, причина скрытия ошибки на пустой таблице, рекомендация преобразовать вычисляемое значение в `int` или `Decimal` и идея обязательного теста с предварительно заполненной таблицей.

Вариант с `Decimal` не понадобился: целочисленные проценты дают простое поддерживаемое представление оценки. Повторная публикация в реальную таблицу не выполнялась, поскольку задача запрещает обращения к внешним сервисам; вместо этого использован `FakeTable`, который проверяет типы так же, как сериализатор boto3.
