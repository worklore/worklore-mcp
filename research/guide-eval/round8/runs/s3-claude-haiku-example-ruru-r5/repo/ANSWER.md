# nightly-review: почему задача молчала

## Что показал лог

`Library/Logs/nightly-review.err` содержит 6 пар строк, по одной на каждый ночной запуск. Это совпадает с `runs = 6` и `last exit code = 1` в `launchctl-print.txt`. Значит, launchd запускал задачу каждую ночь, и проблема в самом скрипте.

Каждый запуск давал две строки:

```
Not logged in · Please run /login
/Users/vk/bin/nightly-review.zsh:19: read-only variable: status
```

`.out` пустой. Задача падала в два слоя.

### Баг 1: `status=$?` убивает скрипт (строка 19)

В zsh `status` — встроенная read-only переменная (синоним `$?`). Присваивание ей — ошибка, которая завершает неинтерактивный скрипт. Воспроизведено на zsh 5.9: `status=$?` даёт `read-only variable: status` и выход с кодом 1.

Строка стояла между вызовом `claude` и уведомлением об ошибке. Поэтому уведомление никогда не выполнялось. Это и есть «гонец, который умер до того, как заговорил».

### Баг 2: `claude -p` не залогинен под launchd

Вторая строка лога, `Not logged in · Please run /login`, означает, что headless CLI не нашёл свои учётные данные в контексте launchd. Plist задаёт только `PATH`. Заметка коллеги называет вероятной причиной отсутствие `USER` в `EnvironmentVariables`.

Лог подтверждает сам отказ, но не подтверждает, что причина именно `USER`. На этой машине launchd запустить нельзя, поэтому проверить это здесь нельзя. Поэтому `USER` добавлен как правдоподобное исправление, а не как доказанное.

## Что изменено

- `bin/nightly-review.zsh`:
  - `status` заменён на `rc`.
  - Уведомление об ошибке перенесено в EXIT-ловушку (`trap finish EXIT`). Оно срабатывает при любом ненулевом выходе, в том числе при падении вроде исходного. Проверено: скрипт с намеренно вставленным `status=$?` всё равно присылает уведомление `FAILED`.
  - Stdin `claude` закрыт (`< /dev/null`), промпт передаётся аргументом.
  - `claude` пишет stderr в `nightly-review-DATE.stderr`. Первые 200 байт попадают в текст уведомления, так что причина видна в Telegram.
  - Пустой вывод при коде 0 считается провалом.
  - В уведомлениях и stdout-логе есть длительность запуска.
- `Library/LaunchAgents/com.vk.nightly-review.plist`: добавлен `USER` = `vk`.

## Что проверено, а что нет

Проверено на заглушках в изолированном `HOME` (настоящий `claude` и Telegram не вызывались):

- успех: уведомление `done`;
- `claude` с кодом 1 и `Not logged in`: уведомление `FAILED` с текстом причины;
- код 0 при пустом выходе: `FAILED`;
- отсутствующий репозиторий: `FAILED`;
- ранний отказ вроде `read-only variable`: `FAILED`.

Не проверено:

- запуск через launchd (`launchctl kickstart`) — здесь нет такого окружения;
- логин `claude` под launchd — выяснится только при реальном запуске;
- доставка в Telegram — и это тоже только на вашей машине.

## Что сделать на вашей машине

1. Скопировать `bin/nightly-review.zsh` в `~/bin/` (сохранить `+x`) и plist в `~/Library/LaunchAgents/`.
2. Перезагрузить задачу:
   ```
   launchctl bootout gui/$UID/com.vk.nightly-review
   launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
   ```
3. Запустить вручную: `launchctl kickstart -k gui/$UID/com.vk.nightly-review`.
4. Проверить все три условия:
   - `launchctl print gui/$UID/com.vk.nightly-review` показывает `last exit code = 0`;
   - в `~/Library/Logs/` свежий непустой `nightly-review-DATE.md`, а длительность в stdout-логе правдоподобна (не пара секунд);
   - пришло уведомление `done`.
5. Проверить уведомление об ошибке: например, переименовать `~/projects/shop` на время, запустить `kickstart` и убедиться, что пришло `FAILED`.
6. Если в шаге 3 снова `Not logged in`, `USER` не помог. Тогда причина в учётных данных. Попробуйте в той же пользовательской сессии `claude /login` и повторите запуск. Это следующая гипотеза, не проверенная.

Отдельно: в снимке нет файла `nightly-review-*.md`. Хотя `> "$OUT"` создаёт файл даже при провале, возможно, снимок их просто не включил. Проверьте, есть ли они у вас.

Оставшийся риск: `notify.sh` берёт токен из keychain. Если он не сработает под launchd, уведомление не дойдёт. Тогда ошибка окажется только в `.err`. Поэтому шаг 5 нужен и после исправления.

## Что из заметки коллеги пригодилось

- **Пригодилось:** `status` → `rc` (тот же баг, что у нас); `< /dev/null`; `USER` в `EnvironmentVariables`; уведомление ближе к точке отказа с проверкой намеренной поломкой; логирование длительности; критерий успеха «код 0 И результат существует И время правдоподобно»; оговорка, что код 0 не доказывает работу (мы добавили проверку пустого вывода).
- **Не пригодилось:** исправление с передачей промпта через stdin. Наш лог не содержит ошибки `Input must be provided…`, а промпт и так передаётся аргументом. Этот способ оставлен без изменений.
- **Не проверено:** ссылка на статью Михая Пердума не открывалась, использован только пересказ из заметки. `launchctl kickstart` не запускался: здесь нет launchd с вашими задачами.
