# Intervals.icu: почему атлеты не могут подключиться

Три отдельные причины. Две исправлены в коде, третья требует действия в настройках Intervals.icu.

## 1. Кнопка Connect даёт 401 — исправлено

`static/app.js` рисовал кнопку как `<a href="/api/intervals/auth/init">`. Браузер при переходе по ссылке
не передаёт заголовок `Authorization`, а сервер (`server.py`, `require_user`) принимает только Bearer-токен.
Поэтому каждый клик отвечал `{"error": "unauthorized"}`, у всех athletes, независимо от аккаунта.
Токен SPA добавляет только в `fetch`-обёртке, а не при навигации.

Исправлено:
- `server.py` `auth_init` теперь отвечает JSON `{"authorize_url": ...}` вместо 302.
- `static/app.js`: кнопка — `<button>`; по клику SPA делает `fetch` на `auth/init` с токеном и только потом
  переводит браузер на `authorize_url`.

Проверено локально: без токена 401, с токеном 200 с корректной ссылкой (state теперь корректно закодирован, `%3D%3D`).

## 2. «Expired, reconnect» через час — исправлено

В ответе Intervals для T. Rivera (лог 2026-09-19) нет поля `expires_in` и нет `refresh_token`.
Код подставлял `DEFAULT_TOKEN_TTL = 3600` и через час сам помечал подключение как `expired, reconnect`.
Срок жизни токена провайдер не сообщал — это было наше предположение, а не факт.

Исправлено:
- Если `expires_in` не пришёл, `expires_at = None`; фоновый обновлятель такие подключения не трогает.
- Если токен реально отклонён Intervals (HTTP 401 при запросе wellness), подключение помечается
  `expired, reconnect` и токен очищается. Это единственный сигнал, по которому мы теперь считаем токен истёкшим.
- Если `expires_in` пришёл, а `refresh_token` нет, поведение прежнее: по истечении срока статус `expired`.
- Фоновое обновление тоже не падает с `KeyError`, если в ответе refresh нет `expires_in`.

Проверено локально подменённым HTTP-вызовом: токен без срока не истекает на проходе обновления; при 401 от Intervals
статус меняется на `expired, reconnect`; при известном сроке `expires_at` считается правильно.

Повторное подключение Rivera сейчас сработает: кнопка Connect работает (пункт 1), а сам токен больше не
объявляется истёкшим по таймеру.

## 3. Intervals отвечает 400 `invalid_request` на шаге authorize — НЕ исправлено в репозитории

Логи `connect-attempt.log`, раздел 2: ссылка, которую строит `auth/init`, открытая напрямую на intervals.icu,
даёт `HTTP 400 {"error":"invalid_request"}` без экрана согласия. Тело не уточняет, какой параметр не понравился.
С 2 октября в запрос добавлены скоупы `CALENDAR:READ,CALENDAR:WRITE` (`config.py` `SCOPES`).
До этого срока подключения работали (лог 2026-09-19).

Наиболее вероятная причина: OAuth-клиент `tricoach-dev` в Intervals.icu не зарегистрирован с этими скоупами
или не имеет нужного redirect URI. Из кода это не проверить. Для этого нужен доступ к настройкам OAuth-приложения
в Intervals.icu, и я туда не ходил (по правилам работы только внутри директории).

Что сделать:
1. В кабинете разработчика Intervals.icu проверить, что клиент имеет `CALENDAR:READ` и `CALENDAR:WRITE`
   и зарегистрирован redirect URI, совпадающий с `REDIRECT_URI` (для прода — с реальным доменом).
2. Если календарь пока не нужен, убрать `CALENDAR:*` из `config.SCOPES` — подключение сразу начнёт работать,
   но синхронизация календаря не заработает.

Пока пункт 1 не сделан, даже исправленная кнопка приведёт athlete на страницу Intervals с ошибкой 400.

## Другие находки (не исправлялись, решение за вами)

- `static/app.js`: `localStorage.getItem("tc_token") || "tok-okafor"` — если токена нет, пользователь молча входит
  как C. Okafor. Athlete без сохранённого токена подключил бы чужой аккаунт tricoach. Для dev это удобно,
  но для athletes опасно. Нужен нормальный экран входа.
- `config.py`: `REDIRECT_URI` захардкожен на `localhost:8766`, `APP_SECRET` и `CLIENT_SECRET` — заглушки.
  Прод должен брать их из окружения (как уже сделано для `INTERVALS_BASE`).
- `refresh_tokens` держит `LOCK` на время HTTP-запросов к Intervals. Пока один запрос висит (до 15 с), весь API
  блокируется. Стоит вынести сетевой вызов из-под блокировки.
- Хранилище в памяти: после перезапуска сервера все подключения теряются, и athletes придётся подключаться заново.
  Это, вероятно, тоже объясняет часть повторных «reconnect», которые видели в поддержке.
- В системе уже запущен процесс `server.py` (PID 9025) на порту 8766, со старым кодом. Я его не трогал.
  Чтобы увидеть изменения, его нужно перезапустить вручную.
