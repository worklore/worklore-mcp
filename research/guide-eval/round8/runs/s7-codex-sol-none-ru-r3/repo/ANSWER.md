# Причины сбоя Intervals.icu

1. Кнопка Connect была обычной ссылкой на `/api/intervals/auth/init`. При переходе браузер не прикладывает `Authorization: Bearer` из `localStorage`; этот заголовок добавляет только SPA-обёртка `fetch`. Поэтому сервер отвечал `401` всем, кто нажимал кнопку. Это видно в `logs/connect-attempt.log` и обращении #214.
2. После добавления `CALENDAR:READ` и `CALENDAR:WRITE` ссылка авторизации стала получать `400 invalid_request` ещё до экрана согласия (`logs/connect-attempt.log`, обращение #219). Эти scope — причина отказа, на которую указывают локальные данные; ответ провайдера не называет конкретный параметр. Запрос возвращён к `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ`, с которыми ранее удалось пройти авторизацию.
3. При ответе без `expires_in` сервер выдумывал срок действия 3600 секунд. У единственного подключившегося атлета ответ также не содержал `refresh_token`, поэтому фоновый процесс спустя час пометил рабочий токен как истёкший. Теперь срок хранится только когда его вернул провайдер; токены без срока не попадают в обновление и не отключаются по локальному таймеру.

Кнопка теперь получает URL авторизации через аутентифицированный `fetch` и затем переводит браузер на этот URL. Локальные проверки `python3 -m unittest -v test_intervals` и `node test_app.js` покрывают запуск авторизации, нужные scope, callback и токен без срока. Реальный запрос к Intervals.icu и деплой не выполнялись.
