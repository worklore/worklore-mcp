# Ответ: исправление генератора пульсовых диапазонов

## Что изменили
В файле [`gen.py`](file:///tmp/h-GipLxJ/gen.py) в функции `hr_target(step)` ключ `"value"` заменён на `"start"`:

```python
def hr_target(step):
    """HR corridor for a step, as a percentage of the athlete's LTHR."""
    lo, hi = step["hr_pct"]
    return {"units": "%lthr", "start": lo, "end": hi}
```

## Почему
В Intervals.icu формат объекта целевого пульса в `workout_doc.steps` определяет логику экспорта в FIT-файл для Garmin:
- При использовании ключа `"value"` (`{"units": "%lthr", "value": lo, "end": hi}`) тренировка экспортируется как цель по зонам / Lap-HR. В этом режиме часы Garmin мапят диапазон на свои локальные (часто автоопределённые или неактуальные) зоны пульса и обрезают коридор под их границы (что и наблюдалось в `readback/watch-notes.md`).
- При использовании ключа `"start"` (`{"units": "%lthr", "start": lo, "end": hi}`) Intervals.icu трактует цель как коридор Instant-HR. При экспорте в FIT Intervals сам рассчитывает абсолютные границы в bpm на основе сохранённого у него LTHR атлета (172 bpm) и передаёт их как сырые bpm. В результате Garmin отображает точный запланированный коридор без привязки к локальным зонам часов.

## Какие части заметки коллеги пригодились

### Пригодилось:
- **Различие между `start` и `value` при формировании пульсовой цели:**
  Описание механизма экспорта в FIT (`{value, end}` -> цель по зонам с обрезкой часами; `{start, end}` -> Instant-HR с точными bpm из Intervals).
- **Схема целевого объекта:**
  Подтверждение корректного формата `{"units": "%lthr", "start": <низ>, "end": <верх>}` (использование процентов `%lthr`, а не абсолютных bpm или других ключей).

  Замечания про текстовый парсер Intervals (`m` vs `mtr`/`km`, `Nx`, голые `Z2` и т.д.) не относились к данной проблеме, поскольку проект генерирует структурированный `workout_doc` через JSON, а не текстовое поле `description`.
