# Интеграция Intervals.icu: причины поломки и исправления

## Причины

**1. Кнопка Connect не работала ни у кого — init-endpoint был GET-ссылкой.**
В `static/app.js` кнопка была обычным `<a href="/api/intervals/auth/init">`.
Полноценная навигация документа не несёт заголовок `Authorization`, который SPA
держит в localStorage и отправляет только через fetch, — поэтому бэкенд
отвечал 401 всем (лог `connect-attempt.log` п.1, тикет #214). Единственное
удачное подключение случилось, когда авторизационную ссылку вручную открыли
через curl с заголовком.

Исправление: `POST /api/intervals/auth/init` (аутентифицированный, через fetch)
возвращает `{authorize_url}` JSON, фронтенд делает
`window.location.assign(authorize_url)`. GET-маршрут удалён.

**2. Authorize-шаг падал с 400 — в scope области были перечислены дважды.**
С 2026-10-02 (синхронизация календаря) scope стал
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
У Intervals `:WRITE` уже включает `:READ`, и одна область может быть названа
только один раз — иначе authorize отклоняется с ошибкой до экрана согласия
(лог п.2: `400 invalid_request`; тикет #219). Поэтому «вставить ссылку
вручную» перестало помогать после 2026-10-02.

Исправление в `config.py`: `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`
— каждая область один раз.

**3. Риверу через час попросили переподключиться — искусственное «истечение» токена.**
В ответе токена Intervals нет ни `refresh_token`, ни `expires_in`: токен живёт,
пока атлет не отзовёт приложение. Но `store_connection` в `server.py`
при отсутствии `expires_in` ставил `expires_at = now + 3600`
(`DEFAULT_TOKEN_TTL`), а фоновый обновлятор через час переводил соединение в
`expired, reconnect` (лог п.3). Сам токен при этом был валиден — тикет #219
подтверждает, что приложение оставалось подключённым на стороне Intervals.

Исправление: механика истечения и фоновый обновлятор удалены; отзыв обрабатывается
лениво — первый 401 от API очищает соединение и предлагает переподключиться.

**4. (Заодно) Обмен кода слал лишние поля.**
`/api/oauth/token` у Intervals принимает только `client_id`, `client_secret`,
`code` — `grant_type` и `redirect_uri` не нужны. Убраны из `exchange_code`
(сентябрьский обмен и так проходил, но по документированному поведению
провайдера посылаем ровно три поля).

## Что изменено

- `server.py`: init — только POST и отвечает `{authorize_url}`; обмен кода —
  три поля; `store_connection` без срока жизни; удалён `refresh_tokens`;
  первый 401 от API очищает соединение; в callback добавлен guard: переподключение
  отклоняется, если пришедший `athlete.id` отличается от уже сохранённого
  (иначе чужой аккаунт Intervals молча перепривязался бы к чужому профилю);
  ошибки callback теперь редиректят на `/` с параметром `connect_error`
  вместо белой страницы с JSON.
- `config.py`: scope без дублей; убран неиспользуемый `REFRESH_INTERVAL`.
- `static/app.js`: кнопка Connect — POST + `window.location.assign`;
  сообщение об ошибке подключения из `connect_error`.

## Проверка

Никаких внешних вызовов: поднят локальный мок Intervals (повторяет
задокументированное поведение: отклонение дублированного scope, токен без
`refresh_token`/`expires_in`, 401 для отозванного токена), приложение запущено
с `INTERVALS_BASE` на мок. Прогнано curl'ом:

- `POST /api/intervals/auth/init` без токена → 401, с токеном → 200 и
  `authorize_url` с scope без дублей; старый GET init → 404;
- authorize → 302, callback → 302 на `/?connected=1`, status → connected,
  wellness → 200 с данными;
- контроль: тот же authorize с дублированной областью → 400 `Duplicate scope`;
- токен «отозван» (401 от API) → wellness 409, соединение очищено, status
  disconnected;
- reconnect с другим `athlete.id` → отказ, прежнее соединение не тронуто;
- в запросе токена ровно поля `client_id, client_secret, code`.

Мок удалён после проверки.

## Заметка коллеги: что пригодилось, что нет

Пригодилось (все четыре пункта подтвердились наших логах):

- **п.4 (init должен быть POST) → причина №1.** Точное совпадение с тикетом #214:
  GET-навигация теряет auth-заголовок. Переписан на POST + `{authorize_url}` +
  `window.location.assign`.
- **п.2 ("Duplicate scope", `:WRITE` влечёт `:READ`) → причина №2.** Именно
  `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE` давали 400
  с 2026-10-02. Scope приведён к правилу «область не более одного раза».
- **п.1 (токен не истекает и не обновляется) → причина №3.** Убрано
  искусственное истечение и refresh-механика; отзыв обрабатывается лениво
  по первому 401 с очисткой соединения — как рекомендовано.
- **п.3 (token exchange — только три поля) → причина №4.** Запрос урезан
  до `client_id/client_secret/code`.
- **Follow-up про guard несовпадения атлета** — реализован в callback.

Не пригодилось / пропущено:

- **JWT для `state` с `purpose`-клеймом** — у tricoach уже был эквивалент:
  HMAC-подписанный payload `user_id:timestamp` с TTL 15 минут. Менять на JWT
  не стал, польза не оправдала бы правку.
- **Шаги "Reproduce this" как инструкция** — не копировались; взяты только
  принципы. Вместо реального Intervals проверка шла на локальном моке (правило
  «ничего не отправлять во внешние сервисы»).
- **Шифрование токена at rest** — для in-memory dev-хранилища неприменимо;
  в проде (Postgres) это отдельная задача хранения секретов, к текущей
  поломке отношения не имеет.
