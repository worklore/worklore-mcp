# ANSWER: HR-коридоры на часах обрезались под зоны часов

## Симптом

Часы (Forerunner 965, LTHR 168) показывали для каждого шага свои зональные
границы (118–137, 151–162, 137–151), а не запланированные коридоры
(117–129, 151–160, 129–141 при LTHR 172 в Intervals). См.
`readback/watch-notes.md`: каждый коридор попадал ровно на границу зон часов,
и смена LTHR на часах только сдвигала эти границы.

## Причина

Генератор отправлял HR-цель как `{"units": "%lthr", "value": lo, "end": hi}`
(`gen.py`, функция `hr_target`). Ключ `value` переключает FIT-экспорт
Intervals в режим Lap-HR / zone-mapped target: часы получают «зону» и
клэмпят её к собственным локальным зонам, а не к процентам, которые мы
запланировали. API при этом событие принимает без ошибок — проблема
проявляется только на циферблате, поэтому round-trip через API её не видно.

## Что изменил

`gen.py:13` — одно слово: `"value": lo` → `"start": lo`.

Ключ `start` переключает экспорт в режим Instant-HR corridor: часы показывают
сырые bpm, посчитанные Intervals из его собственного LTHR (172), и результат
больше не зависит от LTHR и зон часов. Проверено на локальном выводе
`python3 gen.py plans/tempo-run.json`: все `hr`-цели теперь
`{"units": "%lthr", "start": <low>, "end": <high>}`. Ничего наружу не
отправлял (по правилам задачи).

## Что взял из заметки коллеги

- **Ключевой инсайт — переименование `value` → `start`.** Это точное
  попадание в наш симптом: коридоры клэмпились к зонам часов именно из-за
  формы `{value, end}`. Одно слово вместо недель диагностики.
- **Проценты LTHR вместо абсолютных bpm.** Коллега подтвердил, что правильная
  форма — `units: "%lthr"` с процентами, которые Intervals конвертирует в bpm
  при экспорте из своего порога. Наш генератор уже делал так; сохранил.
  Его неудачные попытки (`units: "bpm"` → часы показывали 214–249;
  `start_bpm`/`end_bpm` → константа 101) совпадают с «earlier tries» в
  `readback/watch-notes.md`, так что эти варианты осознанно не рассматривал.

## Что пропустил из заметки коллеги

- **Бонусный блок про top-level `description` в текстовой грамматике
  Intervals** (`m` = минуты, `mtr`/`km` для дистанции, `Z2` = мощность и т.п.)
  не пригодился: он про отображение шагов в веб-UI Intervals, а наша проблема
  — только клэмпинг коридоров на часах, и заметки о пропавших шагах в UI нет.
  Генератор description не генерирует — не стал добавлять, чтобы не расширять
  скоуп правки сверх задачи.
- **Раздел «Reproduce this»** не использовал: требует живых пушей в Intervals
  и синка через Garmin Connect, а по правилам задачи ничего во внешние
  сервисы отправлять нельзя. Проверка ограничена локальным выводом gen.py.
