# Кеширование: save_fact больше не вытесняет системный промпт

## Проблема

Кеш промпта Anthropic работает как хеш префикса: изменение одного байта
инвалидирует всё от него до конца кешируемого блока. В `bot.py` маркер
`cache_control` стоял в конце единого системного промпта (инструкции +
контекст атлета с фактами), поэтому каждый `save_fact` менял блок фактов и
вытеснял из кеша весь промпт целиком. Это видно в `logs/usage.jsonl`:
после каждого вызова `save_fact` следующий вызов имеет
`cache_read_input_tokens: 0` и `cache_creation_input_tokens` ≈ 1046–1104
(строки 4→5, 9→10, 13→14, 22→23, 28→29) — вся цена промпта заново.

## Что изменил

**`bot.py`, `build_system()`** — системный промпт разбит на два блока, у
каждого свой маркер `cache_control: {"type": "ephemeral"}`:

1. Статический блок — константа `INSTRUCTIONS`, байт-в-байт одинаковая для
   всех пользователей и дней (ни дат, ни имён внутри нет).
2. Изменчивый «хвост» — дата, профиль, зоны, цель, факты, язык.

Разделитель `\n\n` переехал в начало второго блока, так что итоговый
текст промпта остался байт-в-байт прежним — дрейфа промпта нет, меняется
только кеш-поведение.

Эффект: запись факта инвалидирует только второй сегмент. Следующий вызов
читает из кеша инструкции (и массив инструментов, идущий выше системного
промпта — внутри tool-цикла и для сообщений с тем же набором инструментов
он неизменен) и пересоздаёт кеш только для хвоста (~десятки токенов вместо
~1000+). Бонус: статический сегмент теперь шарится между атлетами в одном
5-минутном окне.

**`README.md`** — предложение про кеширование приведено в соответствие:
упомянуты два сегмента и то, что `save_fact` пересоздаёт только хвост.

Другое не трогал: фильтрация инструментов по ключевым словам оставлена как
была (см. ниже), `NOTES.md` — это исторический лог расследования.

## Как проверял

Живые вызовы API не делал (по правилам задачи ничего не отправлял во внешние
сервисы, ключа тут в любом случае нет). Проверка локальная, 18 проверок, все
зелёные:

- `python3 -m py_compile bot.py`.
- Прогнал `reply()` со стаб-LLM (реальный сценарий: сообщение → `save_fact` →
  второй раунд → следующее сообщение → сообщение второго атлета) и проверил
  структуру каждого запроса: два блока, маркеры на обоих, первый блок на всех
  вызовах — ровно `INSTRUCTIONS`, хвост меняется только после записи факта,
  отрендеренный текст совпадает со старой одноблочной версией байт-в-байт.
- Симулятор префиксного кеша (по модели из заметки коллеги): на том же
  сценарии старая сборка воспроизводит баг из логов — после `save_fact`
  read=0 и создание ~полного промпта; новая сборка — read покрывает
  статический префикс, создание ≈ хвосту (~85 из ~800 токенов по грубой
  оценке), следующее сообщение читает всё из кеша, второй атлет попадает в
  закешированный статический префикс.

Ожидаемая картина в `logs/usage.jsonl` после деплоя: после вызова `save_fact`
`cache_read_input_tokens` должно покрывать инструкции (~900), а
`cache_creation_input_tokens` — лишь хвост. Если после записи факта
`cache_creation` снова размером со весь промпт — искать нестабильный байт
в статическом блоке.

## Что пригодилось из заметки коллеги

- **Главное — сам фикс: два `cache_control`-сегмента** (статические
  инструкции / изменчивый хвост) вместо одного. Перенёс как есть.
- **Отказ от top-N выборки фактов под каждое сообщение** — принял: в коде и
  так грузятся все факты каждый раз, этого не менял (заметка права: любая
  per-message персонализация хвоста убивает его кеш).
- **Правило «статический блок должен быть байт-стабилен»** — проверил:
  `INSTRUCTIONS` — константа без интерполяций, `\n\n` унесён в изменчивый
  блок, чтобы текст промпта не дрейфовал.
- **Метод верификации по `cache_creation_input_tokens` /
  `cache_read_input_tokens`** — использовал для локальной симуляции и
  зафиксировал ожидаемую картину для прод-логов (выше).

Что пропустил как неподходящее:

- **Фильтрация инструментов по ключевым словам** — у коллеги это был отдельный
  выигрыш, у нас эта механика уже есть с марта (`select_tools`), `NOTES.md`
  велит её не трогать — не трогал.
- **Напряжение «инструменты выше системного промпта»** — у нас остаётся:
  сообщение, подтягивающее другую группу инструментов, один раз перечитает
  всё. По заметке это приемлемо (набор внутри одного сообщения и его
  tool-цикла постоянен, а там кеш окупается сильнее всего), поэтому оставил
  как есть — это прежнее поведение, к задаче про память отношения не имеет.
- Telegram-специфика и лимит «4 маркера» (у нас 2, с запасом) — не пригодились.
