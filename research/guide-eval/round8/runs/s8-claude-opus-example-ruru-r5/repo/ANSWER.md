# Кеширование промпта после save_fact

## Что было не так

`build_system()` собирал инструкции + профиль + факты в **один** текстовый блок с одним
маркером `cache_control`. Кеш — хеш префикса, проверяемый на границах блоков, поэтому
добавленный факт менял хеш единственного блока, и следующий вызов (уже второй раунд
того же цикла инструментов, ведь `run_tool` сразу дописывает факт в `a.facts`) платил
`cache_creation` за весь промпт, ~1050–1100 токенов. В `logs/usage.jsonl` это видно
после каждого `save_fact`: `cache_read_input_tokens: 0`, `cache_creation` ≈ весь промпт.

## Что изменил (`bot.py`)

- `athlete_context()` заменил на `athlete_header()`: дата, имя, вид спорта, зоны, цель,
  язык и заголовок `Long-term facts:`. Строку `Language` перенёс выше фактов, чтобы после
  фактов ничего не было.
- `build_system()` теперь отдаёт первый блок `INSTRUCTIONS + header`, а дальше **каждый
  факт идёт отдельным блоком** (`- (none yet)`, пока фактов нет). Один маркер
  `cache_control: ephemeral` стоит на последнем блоке.
- Почему это работает: `save_fact` только дописывает факт. В новом запросе граница
  «после прежнего последнего факта» остаётся границей блока, и API находит на ней
  запись прошлого запроса (автоматически проверяются до ~20 предыдущих границ блоков от
  маркера). Получается `cache_read` ≈ весь старый промпт и `cache_creation` всего на
  ~5–15 токенов нового факта.
- Фильтрацию инструментов по ключевым словам не трогал, как просили в NOTES.md.

Добавил `tests/sim_cache.py`. Это офлайн-симулятор префиксного кеша без запросов к API:
токены он оценивает по символам, минимальный префикс 1024, lookback 20 блоков. Прогон
`python3 -I tests/sim_cache.py`, сценарий для атлета 42 с двумя `save_fact`:

| вызов              | было (read / create) | стало (read / create) |
|--------------------|----------------------|-----------------------|
| раунд 2 после save_fact #1 | 0 / 1099     | 1089 / 9              |
| раунд 2 после save_fact #2 | 0 / 1105     | 1098 / 5              |
| следующее сообщение        | 1099 / 0     | 1098 / 0              |

Старый код в симуляторе даёт ровно ту картину, что в логе. Цифры приблизительные,
настоящую проверку нужно сделать на живом API (я его не вызывал): после `save_fact`
в `usage.jsonl` должно быть `cache_read` ≈ прежний размер промпта и `cache_creation` в
десятки токенов, а не ~1000.

## Что взял из заметки коллеги

Пригодилось:
- Диагноз: кеш — хеш префикса, и запись в память переписывает собственный промпт.
- Изменчивое держать **в конце** и порядок «от редко меняющегося к часто меняющемуся».
  Отсюда шапка атлета до фактов и язык перед фактами.
- Не делать отбор top-N фактов под сообщение: это ломает префикс. Факты по-прежнему
  грузятся все и в одном и том же порядке.
- Массив инструментов стоит выше `system`, его нужно держать стабильным. Фильтрацию
  оставил: смена группы (plan/race) и раньше давала один полный промах (1305/1334 в
  логе), это ожидаемо.
- Проверка по `cache_creation_input_tokens` / `cache_read_input_tokens`. Симулятор
  проверяет то же самое.

Не подошло, и это главное отличие:
- **Сам рецепт «второй маркер после статических инструкций»** здесь не сработал бы.
  У Sonnet 4.5 минимальный кешируемый префикс 1024 токена, а инструменты + инструкции
  в этом боте около 930–990 токенов. Оценка: у атлета 77 с двумя фактами весь префикс
  в логе ровно 1024. Маркер на статическом блоке API молча проигнорировал бы, и после
  `save_fact` снова был бы полный `cache_creation`. Поэтому вместо отдельного
  статического сегмента я сделал «блок на факт» и опираюсь на lookback по границам
  блоков: так кешируется весь старый префикс, а не только инструкции.
- Цифры ~780/~240 токенов и «4 маркера, используем 2» относятся к другому боту. Здесь
  нужен один маркер.

## Ограничения

- Если факт когда-нибудь будут редактировать или удалять (сейчас только append),
  промах начнётся с этого факта. Это всё равно не хуже, чем было.
- Дата стоит в первом блоке, поэтому смена дня даёт один полный промах в день. При
  TTL 5 минут это почти бесплатно.
- Новый атлет без фактов (весь промпт < 1024 токенов) не кешируется вообще, как и раньше.
