# Почему nightly-review молчал

## Что показали файлы

- `launchctl-print.txt`: `runs = 6`, `last exit code = 1`. Задачу загрузили 12.10,
  снимок сделан 18.10 в 09:10. Значит, она срабатывала каждую ночь в 02:30
  (13–18.10, шесть запусков). launchd работает, падает сам скрипт.
- `Library/Logs/nightly-review.err` повторяет одну и ту же пару строк шесть раз:
  ```
  Not logged in · Please run /login
  /Users/vk/bin/nightly-review.zsh:19: read-only variable: status
  ```

## Причины (две, одна за другой)

1. **`claude` не залогинен в окружении launchd.** В plist в
   `EnvironmentVariables` задан только `PATH`, переменной `USER` нет
   (см. блок `environment` в `launchctl print`). Без `USER` CLI не находит свой
   логин в связке ключей и сразу завершается с ошибкой «Not logged in». Обзор
   падает за секунды, `$OUT` остаётся пустым.
2. **Из-за `status=$?` (строка 19) скрипт умирал раньше, чем успевал
   сообщить об ошибке.** В zsh `status` — read-only специальная переменная
   (аналог `$?`). Присваивание в неинтерактивном скрипте — фатальная ошибка:
   zsh тут же выходит с кодом 1 (отсюда `last exit code = 1`). Эта строка
   стояла между вызовом `claude` и обоими вызовами `notify.sh`, поэтому
   не уходило ни сообщение «FAILED», ни сводка. Проверил локально:
   `zsh -c 'true; status=$?; echo after'` печатает
   `read-only variable: status` и выходит с кодом 1, а до `echo` дело не доходит.
   Кстати, этот баг ломал бы скрипт и при *успешном* `claude`, поэтому
   сообщений не было никаких, даже «done».

## Что исправлено

`bin/nightly-review.zsh`:
- `status=$?` заменено на `rc=$?`.
- Промпт передаётся через stdin (`print -r -- "$PROMPT" | claude -p ...`), а не
  многострочным аргументом. Так `claude` не может зависнуть, ожидая stdin.
- Если `claude` вышел с кодом 0, но ничего не написал, это тоже считается
  ошибкой (`exit 2` плюс уведомление): код 0 ещё не значит, что работа сделана.
- В `nightly-review.err` пишутся строки с временем: старт (с `USER`/`HOME`),
  код выхода `claude`, длительность, размер вывода. Запуск длиной в несколько
  секунд почти наверняка означает раннее падение.
- Обёртка `notify()`: если `notify.sh` сам упал (например, `security` не отдал
  токен — у него `set -e`), это записывается в лог, а не теряется молча.

`Library/LaunchAgents/com.vk.nightly-review.plist`: в `EnvironmentVariables`
добавлены `USER=vk` и `HOME=/Users/vk`. `plutil -lint` — OK.

Проверено на заглушках (поддельные `claude` и `notify.sh` во временной
папке, потом она удалена): при падении `claude` → уведомление «FAILED», exit 1;
при пустом выводе → «FAILED: … no output», exit 2; при успехе → «done», exit 0.
Настоящие `claude`, Telegram и launchd я не запускал (правила задачи).

## Что сделать у себя (я этого не делал)

```sh
launchctl bootout gui/$UID/com.vk.nightly-review
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl kickstart -k gui/$UID/com.vk.nightly-review
launchctl print gui/$UID/com.vk.nightly-review | grep -E 'runs|last exit'
tail ~/Library/Logs/nightly-review.err
```
Plist нужно перезагрузить: launchd не перечитывает его сам. Затем проверьте:
`last exit code = 0`, свежий непустой `nightly-review-YYYY-MM-DD.md`, разумная
длительность в логе и сообщение «done» в Telegram. После этого один раз сломайте
запуск нарочно (например, временно уберите `USER` или укажите неверный `REPO`)
и убедитесь, что приходит «FAILED». Если «Not logged in» останется и с `USER`,
один раз выполните `claude` → `/login` под этим пользователем.

## Что пригодилось из заметки коллеги

Пригодилось:
- «Сначала докажи, что задача запускалась»: `launchctl print` (`runs`,
  `last exit code`), затем чтение `StandardErrorPath`. Именно так нашлись
  обе причины.
- Ловушка с `status` в zsh и замена на `rc=$?`. Ровно наш второй баг.
- Поправка 2026-09-30: `USER` в `EnvironmentVariables` против «Not logged in».
  Ровно наш первый баг.
- Мысль «репортер ошибок стоит ниже места падения»: у нас notify стоял после
  фатальной строки.
- Код выхода 0 ≠ работа сделана; логировать длительность. Добавил проверку
  на пустой вывод и время в лог.
- Промпт через stdin (или `< /dev/null` при промпте в аргументе). Применил
  stdin. Здесь это профилактика, а не причина: в логе нет ошибки «Input must be
  provided», и launchd по умолчанию и так даёт stdin `/dev/null`.
- Раздел Verify (kickstart, проверка реального результата, нарочная поломка).
  Перенёс в шаги выше.

Не пригодилось / пропустил:
- Гипотеза «launchd не срабатывает». Здесь он срабатывал все 6 раз.
- Первая ошибка коллеги («Input must be provided…»). У нас её не было,
  причина другая (логин).
- Конкретика их задачи (16:50, их label) и ссылка на внешнюю статью: я её
  не открывал, хватило самого текста заметки.
