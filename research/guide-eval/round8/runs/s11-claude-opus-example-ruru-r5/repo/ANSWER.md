# Почему вторая публикация возвращает 500

## Причина

`publish()` (`src/app.py`) перед записью сканирует таблицу и для каждой уже
существующей истории считает `similarity()`. Результат — `round(0.7 * tag_score + 0.3 * word_score, 4)`,
то есть питоновский **float**. Он кладётся в `item["similar"][i]["score"]`,
и `table.put_item` падает в сериализаторе boto3:

```
TypeError: Float types are not supported. Use Decimal types instead.
```

(`logs/error.log`, app.py:63 → `boto3/dynamodb/types.py`). `handler` ловит это как
обычное `Exception` и отдаёт 500.

Первая публикация прошла, потому что таблица была пуста: `existing == []`,
`similar == []`, ни одного float в записи (в логе `similar=0 stored`). Начиная со
второй публикации есть с чем сравнивать — появляется оценка, появляется float,
и падает каждая следующая публикация (в логе две 500 подряд).

Существующий тест этого не ловил, потому что публиковал одну историю в пустую
`FakeTable`, т.е. проверял только путь, который в продакшене выполняется один раз.

## Исправление

1. **`to_dynamo()` на границе с DynamoDB** (`src/app.py`). Рекурсивно обходит
   запись и превращает каждый `float` в `Decimal(str(x))` (так `0.4667` хранится
   как `0.4667`, без двоичного хвоста); NaN/∞ отклоняются как `ValueError`, потому
   что DynamoDB их тоже не принимает. `publish()` вызывает её прямо перед
   `put_item`. Поэтому ошибка не вернётся, даже если кто-то потом добавит в
   запись ещё одно вычисляемое поле: конвертация стоит на выходе, а не в
   конкретной формуле.
   Формат `score` я не менял: это всё ещё доля 0..1 с 4 знаками, только тип
   теперь Decimal. Тем, кто читает `similar`, ничего менять не надо.
2. **Фейковая таблица стала ближе к настоящей** (`tests/fake_dynamo.py`):
   `get_item`/`scan` возвращают числа как `Decimal`, как это делает настоящий
   boto3. Тогда при повторной публикации тест работает с тем же видом данных,
   что и в продакшене.
3. **Тесты пути с заполненной таблицей** (`tests/test_publish.py`): хелпер
   `seeded_table()`; публикация второй и третьей истории (score хранится как
   Decimal в диапазоне (0, 1], ранжирование по убыванию); повторная публикация
   того же slug (история не попадает в похожие сама на себя); `handler` дважды
   подряд → 201 оба раза (точное повторение инцидента); юнит-тесты `to_dynamo`.
   Старый `app.py` на этих тестах падает, исправленный проходит:
   `python3 -m unittest discover tests` → 7 OK.

Ничего не деплоил и в реальную таблицу не писал.

## Что пригодилось из заметки коллеги

- **Пригодилось:** сам диагноз (float от вычисляемой оценки похожести; первая
  запись выживает, потому что пустая таблица = нет оценок) совпал с нашим случаем
  один в один. Ещё пригодились совет «конвертировать на границе» и правило «каждый
  тест записи сначала сажает запись» — это `seeded_table()` и тест на две
  публикации через `handler`. Совет поискать `round(` и `/`, которые попадают в
  запись, тоже сработал: нашлись ровно `similarity()` (`round` и два деления);
  `published_at` уже `int(...)`.
- **Не стал брать:** перевод оценок в целые проценты. Это меняет смысл
  поля (0.42 → 42) для читателей `similar`, а Decimal решает проблему без
  этого. Конвертация отдельно одного поля тоже не защищает от следующего float,
  поэтому я поставил общую `to_dynamo()`.
- **Не применимо здесь:** «опубликуйте дважды в реальную таблицу». По правилам
  задачи ничего наружу не отправлял; вместо этого двойная публикация
  проверяется через `handler` на фейковой таблице, которая валидирует типы так
  же, как boto3. На реальном стенде это стоит проверить отдельно, перед деплоем.
