# Что изменено

**Причина** (logs/usage.jsonl, NOTES.md): `build_system` склеивал инструкции и контекст атлета (дата, профиль, зоны, цель, факты) в один блок с одним `cache_control`. `save_fact` меняет факты → меняется хеш префикса → весь блок (~1000 токенов) пересоздаётся (`cache_read=0`, `cache_creation≈1100`).

**Исправление** (`bot.py`, `build_system`): `system` теперь два текстовых блока, у каждого `cache_control: ephemeral`:
1. `INSTRUCTIONS` — статический, байт в байт одинаковый (ни дат, ни имён);
2. `athlete_context(...)` — изменчивый хвост (дата, профиль, зоны, цель, факты, язык).

Запись в память инвалидирует только хвост. В README обновлено описание кеширования.

Не проверено на реальном API (нет ключа): ожидаемо после `save_fact` `cache_read` ≈ статический блок, `cache_creation` ≈ хвост. Один риск: у Sonnet минимум для кеширования 1024 токенов на префикс; префикс первого маркера = tools + инструкции (~780 + схемы), должен проходить, но смотрите `usage`.

# Что пригодилось из заметки коллеги
- Пригодилось: два сегмента cache_control (статика / хвост на пользователя); идея держать статический блок без подставленных значений; проверка через `cache_read_input_tokens`/`cache_creation_input_tokens`.
- Учтено, но без изменений: инструменты стоят выше system в префиксе, поэтому фильтрацию по ключевым словам не трогал (NOTES.md тоже говорит оставить); отбор top-N фактов не делал — он ломал бы кеш хвоста.
- Пропущено: MCP, Telegram-специфика, число инструментов (~55) — в этом репо не применимо.
