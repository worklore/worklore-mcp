# Причины сбоя интеграции Intervals.icu

## 1. Кнопка Connect теряла аутентификацию

Кнопка была обычной ссылкой на `GET /api/intervals/auth/init`. При переходе браузер не добавляет заголовок `Authorization: Bearer ...`, который SPA передаёт только через `fetch`, поэтому endpoint возвращал 401 всем пользователям. Это подтверждается `logs/connect-attempt.log` и локальным воспроизведением.

Теперь SPA отправляет аутентифицированный `POST /api/intervals/auth/init`. Endpoint возвращает `{"authorize_url": "..."}`, а фронтенд выполняет переход через `window.location.assign(authorize_url)`.

## 2. В authorize URL дублировались scope

В конфигурации были `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`. У Intervals `:WRITE` уже включает `:READ`, а повторное указание одной области приводит к ошибке `Duplicate scope`; в захваченном ответе она проявилась как HTTP 400 `invalid_request` до экрана согласия. Ошибка появилась после добавления calendar scope, поэтому обходной путь с ручной ссылкой тоже перестал работать.

Scope заменены на `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`: каждая область указана один раз, а необходимые права записи сохранены.

## 3. Приложение само «истекало» действующий токен через час

Intervals не возвращает `refresh_token` или `expires_in`: access token действует, пока пользователь не отзовёт доступ. Код ошибочно подставлял TTL 3600 секунд, а фоновая задача через час удаляла токен и ставила статус `expired, reconnect`. Поэтому подключение T. Rivera работало вечером, а на следующее утро требовало повторного подключения, хотя доступ не был отозван.

Искусственный TTL, поля refresh/expiry и фоновая задача обновления удалены. Токен сохраняется как бессрочный. Если Intervals всё же возвращает 401 при запросе wellness, приложение очищает сохранённый access token, ставит статус `revoked, reconnect` и больше не вызывает API до повторного подключения.

## 4. Обмен кода содержал лишние form-поля

В `POST /api/oauth/token` отправлялись `grant_type` и `redirect_uri`, хотя Intervals принимает только `client_id`, `client_secret` и `code`. Это несоответствие могло сломать callback даже после успешного authorize. Теперь отправляются только три требуемых поля; `access_token`, `scope` и `athlete.id` по-прежнему берутся из ответа.

# Что пригодилось из заметки коллеги

Пригодились все четыре наблюдения:

1. Отсутствие refresh-механики и бессрочность токена объяснили отключение через час; рекомендация обрабатывать отзыв по первому 401 добавлена в wellness-клиент.
2. Правило «одна область один раз, `:WRITE` вместо `:READ` + `:WRITE`» исправило authorize URL.
3. Точный формат token exchange исправлен; отсутствие `refresh_token` больше не считается ошибкой.
4. Схема POST init + JSON + `window.location.assign` устранила исходный 401 у кнопки.

Подписанный `state` с идентификатором пользователя и TTL 15 минут уже существовал и был сохранён: менять его на JWT только ради другого формата не потребовалось. Проверка несовпадения athlete id и шифрование постоянного хранилища не относились к зафиксированным сбоям и в этом in-memory проекте не менялись.

# Проверка

Выполнен локальный end-to-end прогон через HTTP с имитатором Intervals: POST init, проверка уникальности scope и подписи state, callback без пользовательского Authorization, точный состав token exchange, подключение без expiry/refresh metadata, запрос wellness с Bearer-токеном и athlete id, затем имитация отзыва с 401 и переход в `revoked, reconnect`. Все проверки прошли. Синтаксис Python и JavaScript также проверен. Внешние запросы к Intervals не выполнялись.
