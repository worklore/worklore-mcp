# Почему вторая публикация возвращает 500

## Причина

`similarity()` в `src/app.py` возвращает `round(0.7 * tag_score + 0.3 * word_score, 4)`.
В Python это `float`. `related()` кладёт эту оценку в `similar[].score`, и `publish()`
передаёт элемент в `table.put_item`. DynamoDB через boto3 не принимает `float`,
поэтому запись падает с `TypeError: Float types are not supported. Use Decimal types instead.`

Почему первая публикация проходила: при первой публикации таблица пуста,
`related()` ничего не сравнивает и не считает ни одной оценки, поэтому float в элементе
не появляется. Первая запись в `logs/error.log` (`similar=0 stored`) это подтверждает.
Вторая запись находит первую историю, считает оценку, и падает (`09:21:47`, `09:22:10`).

Существующие тесты не ловили это, потому что проверяли только путь с пустой таблицей.

## Исправление

1. `src/app.py`: добавлена функция `to_dynamo(value)`. Она рекурсивно переводит каждый
   `float` в `Decimal(str(x))`. Через `str` значение сохраняется как есть
   (`0.4286` остаётся `0.4286`), без двоичного хвоста. `publish()` вызывает её прямо перед
   `put_item`. Преобразование общее, поэтому будущий float в любом месте элемента тоже не упадёт.
2. `tests/test_publish.py`:
   - `test_second_publish_with_similar_story_stores`: сажает одну историю и публикует
     вторую, то есть проходит путь, где есть оценка.
   - `test_handler_returns_201_on_second_publish`: проверяет именно то, что видит клиент.
     Обработчик превращает исключения в 500, поэтому проверка `publish()` напрямую
     этот баг не показала бы.
   - `test_stored_score_is_decimal_with_same_value`: в таблице лежит `Decimal`, и значение то же.
   - `ToDynamoTest`: вложенные float конвертируются, остальные типы не меняются,
     и итоговый элемент проходит `put_item` фейковой таблицы.

## Почему это не повторится

- Любой float в элементе преобразуется на границе записи, а не в месте вычисления.
- `tests/fake_dynamo.py` уже отклоняет float так же, как boto3. Тесты с засеянной таблицей
  теперь реально выполняют путь с оценками, поэтому регрессия упадёт в тестах.

Проверка: тесты проходят (`python3 -m unittest discover tests`, 5 OK). Если убрать
вызов `to_dynamo` из `publish()`, падают 3 теста (1 failure, 2 errors). Значит, тесты
действительно ловят этот баг.

## Что осталось

- Чтение: `get_item` теперь возвращает `score` как `Decimal`. `json.dumps` на таком
  значении падает с `TypeError`. В этом репозитории читающего кода нет, поэтому я его не
  менял. Если страница чтения сериализует `similar` через `json.dumps`, её надо поправить
  (например, `default=float`). Сейчас `handler` возвращает только `slug`, поэтому
  эндпоинт публикации это не затрагивает.
- Реальную таблицу я не трогал и ничего не публиковал и не деплоил, по правилам задачи.

## Что из заметки коллеги пригодилось

- **Пригодилось:** идея тестировать путь записи с уже засеянной таблицей. Тесты
  `test_second_publish_with_similar_story_stores` и `test_handler_returns_201_on_second_publish`
  сделаны по этой схеме.
- **Пригодилось:** проверка через поиск `round(` и деления в словарях элементов. Она
  сразу показала `round(...)` в `similarity()`.
- **Пригодилось частично:** идея «конвертировать на границе записи». Использован `Decimal`,
  а не целые проценты: целые проценты меняют смысл поля (`score` в диапазоне 0..1 стал бы
  0..100), и это сломало бы читателей, которые ждут прежнего значения.
- **Не пригодилось:** «опубликовать дважды в реальную таблицу». Задача запрещает публиковать
  и деплоить, поэтому проверка сделана только на фейковой таблице.
