# Почему часы показывали свои зоны и что исправлено

## Симптом

Для события 184233 все коридоры пульса на часах (Forerunner 965) отображались
границами собственных зон часов (Z1–Z5 от его авто-LTHR 168), а не
запланированными диапазонами: 68–75 % LTHR → 118–137 вместо 117–129 и т.д.
При этом API событие принимал, `workout_doc.steps` был заполнен.

## Причина

`gen.py` формировал HR-таргет так:

```json
{"units": "%lthr", "value": <low>, "end": <high>}
```

Пара `value`/`end` — это Lap-HR (zone-mapped) таргет: при FIT-экспорте
Intervals маршрутизирует его как зональный, и часы клампят коридор к
своим локальным зонам. Отсюда и прежние неудачи из `readback/watch-notes.md`:

- `units: "bpm"` с `value`/`end` — FIT-экспорт прочитал bpm как
  «процент от чего-то», часы показали 214–249 bpm;
- `start_bpm`/`end_bpm` — неизвестная схема, молча отброшена, часы
  показали константные 101 bpm (fallback Garmin «нет валидного HR-таргета»).

## Исправление

Одноключевое переименование в `hr_target()` (`gen.py:13`): нижняя граница
коридора теперь `start`, а не `value`:

```json
{"units": "%lthr", "start": <low>, "end": <high>}
```

Пара `start`/`end` переключает FIT-экспорт в режим Instant-HR коридора: часы
показывают сырое значение bpm, которое Intervals вычисляет из своего
сохранённого порога (LTHR 172), а не из авто-порога часов. Проверено
end-to-end на аналогичном случае: таргет 75–82 % LTHR при Intervals LTHR 172
и часовом 168 показал на часах 129–141 bpm — ровно наш «Float».

Проценты LTHR оставлены как есть — конвертация в bpm происходит на
FIT-экспорте со стороны Intervals, хардкодить bpm в генераторе не нужно.

Источник: [Exact HR corridors on Garmin from Intervals.icu API workouts — start/end, not value/end](https://worklore.dev/s/2026-05-12-exact-hr-corridors-on-garmin-from-intervals-icu-api-workouts)

## Проверка

```
python3 gen.py plans/tempo-run.json
```

Все четыре таргета (Warm-up 68–75, Tempo 88–93, Float 75–82, Cool-down 65–72)
теперь сериализуются с `start`/`end`.
