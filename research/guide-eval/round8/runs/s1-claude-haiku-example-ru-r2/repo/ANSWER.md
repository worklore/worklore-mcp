# Диапазоны пульса на часах: что было и что изменено

## Причина

В `gen.py`, функция `hr_target`, нижняя граница HR-коридора писалась в ключ
`value`:

```python
return {"units": "%lthr", "value": lo, "end": hi}
```

Intervals при экспорте в FIT трактует `{value, end}` как зонную (lap-HR)
цель: часы подгоняют её под свои локальные зоны. Поэтому на часах коридоры
выглядели как границы собственных зон (118–137, 151–162 и т.д.), а не как
планируемый коридор, например 68–75% × 172 = 117–129 bpm для разминки. Ровно это описано в `readback/watch-notes.md`.

## Что изменил

`gen.py`, `hr_target`: ключ `value` заменён на `start`:

```python
return {"units": "%lthr", "start": lo, "end": hi}
```

В docstring добавлено пояснение, почему нужен `start`, чтобы следующий
человек не вернул `value` «для единообразия».

Проверка локально (пушить не пробовал):

- `python3 -I gen.py plans/tempo-run.json` выдаёт цели
  `{units: %lthr, start, end}`: Warm-up 68–75, Tempo 88–93, Float 75–82,
  Cool-down 65–72.
- В выводе нет ни одного ключа `value`.

## Почему это должно сработать

Опора на заметку коллеги (не инструкция, а наблюдение с их установки): там
тот же симптом (часы обрезают по своим зонам) был вылечен переименованием
`value` → `start` при том же `units: "%lthr"`. Их проверка: LTHR в Intervals
172, на часах 168, цель 75–82% дала 129–141 bpm, то есть ровно по Intervals.
Наш случай совпадает по симптому и по схеме тела запроса.

## Что не сделано и почему

- **Не проверено на реальных часах.** Нет доступа к Intervals API и Garmin
  из этой среды, а пушить событие без разрешения нельзя. Проверка: запушить
  новое событие (`push.sh`), прочитать его через `GET /events/{id}`
  (`start` должен сохраниться, а не превратиться в `value`), синхронизировать
  часы и сравнить коридор с 68–75% × 172 и т.д.
- **`readback/event-184233-as-sent.json` не трогал.** Это запись того, что
  реально ушло в API, и она остаётся верной для старого события.
- **Top-level `description` и текстовая грамматика из заметки не нужны.**
  В нашем случае `workout_doc.steps` уже заполнен (по `watch-notes.md`), то
  есть парсер принимает тело. Проблема была только в ключе цели, поэтому
  менять формат описания не стал.
- **Абсолютные bpm не используются.** Заметка и наш опыт (`units: "bpm"`,
  214–249 bpm) подтверждают, что нужны проценты от LTHR из Intervals.
- Изменения не закоммичены.
