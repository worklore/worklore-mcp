# Почему не подключался Intervals.icu

1. **Кнопка Connect давала 401 у всех.** Это была обычная ссылка `<a href="/api/intervals/auth/init">`, то есть навигация браузера. Заголовок `Authorization: Bearer` добавляет только fetch-обёртка SPA, поэтому у навигации его не было, и сервер отвечал `{"error":"unauthorized"}`. Исправление: `auth/init` теперь возвращает JSON `{url}`, кнопка вызывает его через `api()` с токеном и затем переходит по полученному URL. Callback от Intervals остаётся без заголовка: пользователя определяет подписанный `state`.

2. **Authorize-ссылка давала 400 `invalid_request` (после релиза календаря 2026-10-02).** Это единственная причина, которую я не мог проверить: внешние сервисы трогать нельзя, а тело ответа не называет параметр. Самая вероятная причина — запрос scope. После релиза он стал `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`, то есть `READ` и `WRITE` перечислены для одного ресурса. Рабочее подключение Rivera получило `ACTIVITY:WRITE,WELLNESS:READ`. `WRITE` включает `READ`, поэтому теперь запрашивается `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`. Если 400 останется, сначала проверьте scope и redirect_uri: в `config.py` стоят dev-значения (`tricoach-dev`, `http://localhost`), а в проде redirect_uri должен точно совпадать с зарегистрированным у клиента Intervals.

3. **Подключение «протухало» через час.** Intervals.icu выдаёт токен без `refresh_token` и без `expires_in`: он не истекает. Код подставлял `DEFAULT_TOKEN_TTL = 3600`, а без refresh-токена фоновый обработчик помечал соединение `expired, reconnect` и стирал access token. Так и получилось у Rivera (17:41 → 18:37). Исправление: срок действия ставится только если провайдер его прислал (`expires_at=None` означает бессрочный токен). Обновление в фоне пропускает такие соединения, а если у refresh-ответа нет `expires_in`, срок тоже не выдумывается.

Проверка: изменения только прочитаны и применены, сервер я не запускал и против настоящего Intervals не тестировал.
