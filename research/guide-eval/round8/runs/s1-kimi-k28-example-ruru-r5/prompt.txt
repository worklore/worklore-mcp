# Точные пульсовые коридоры на Garmin из тренировок Intervals.icu через API — start/end, а не value/end

Мой ИИ-агент генерирует структурированные триатлонные тренировки и отправляет
их в Intervals.icu через `POST /events`; Intervals экспортирует их в FIT на мои
часы Garmin. Симптом: каждый пульсовый коридор на часах был незаметно неверным —
обрезан под собственные (устаревшие, автоопределённые) зоны LTHR часов вместо
диапазона, который мы запланировали. Я неделями ошибочно считал, что дело в
несовпадении LTHR на стороне часов.

Что мы пробовали, каждый раз прогоняя полный круг: отправка → чтение через API →
синхронизация Garmin → экран часов:

1. `{units: "bpm", value, end}` — API принял; часы показали 214–249 уд/мин
   (невозможно). Экспорт в FIT прочитал `bpm` как процент от чего-то.
2. `{start_bpm, end_bpm}` — часы показали константу 101, запасной вариант
   Garmin «нет валидной цели по пульсу». Схема молча отбросила поля.
3. Изучили выпадающий список целей в UI Intervals и заключили: «абсолютные bpm
   невозможны». Неверно — этот список выбирает подпись единиц, а не форму
   значения.

Прорыв: собрать тренировку в **UI** Intervals с переключателем «Instant HR»,
а потом прочитать её обратно через API. Нижняя граница коридора называется
`start`, а не `value`. Одно это имя ключа переключает режим экспорта в FIT:
`{value, end}` уходит как цель **Lap-HR / по зонам** (часы обрезают её под свои
локальные зоны), а `{start, end}` становится **коридором Instant-HR** — часы
показывают сырые bpm, которые посчитал Intervals. Проверено от начала до конца:
LTHR в Intervals 172, LTHR на часах 168, цель 75–82% отобразилась на часах как
129–141 уд/мин — как в Intervals, без дрейфа. Исправление оказалось
переименованием одного слова после нескольких дней проб.

Бонусная ловушка из той же сессии: шаги не отображались в веб-UI Intervals,
потому что UI читает отдельное поле верхнего уровня `description` в текстовой
грамматике Intervals — где `m` означает *минуты* (`200m` = шаг на 200 минут!),
дистанция должна быть `mtr`/`km`, голое `Z2` трактуется как зона *мощности*
даже для плавания, а цифра в начале подписи съедается как длительность. Если
парсер споткнулся, Intervals стирает оба представления.

## Воспроизвести

Предварительные условия: аккаунт Intervals.icu с доступом к API (OAuth-токен
или API-ключ), настроенные в Intervals пороги атлета (как минимум LTHR) и часы
Garmin, которые синхронизируют тренировки из Intervals через Garmin Connect.

Агенту понадобятся от вас: id атлета в Intervals и учётные данные API; ваш
LTHR, как он сохранён в Intervals; разрешение создать (и потом удалить)
тестовое событие в календаре.

Шаги:

1. Создайте событие через `POST /api/v1/athlete/{id}/events` с
   `workout_doc.steps`, где каждая пульсовая цель шага имеет вид
   `{"units": "%lthr", "start": <низ>, "end": <верх>}` — никогда `value`.
   Проценты, а не абсолютные bpm: Intervals пересчитывает их при экспорте в
   FIT по собственному сохранённому порогу.
2. Задайте полю верхнего уровня `description` события текст в родной грамматике
   Intervals, чтобы шаги отображались в веб-UI, например
   `- Warm-up easy 10m 75-82% LTHR`. Правила: длительности `m`/`s`, дистанция
   `mtr`/`km`, пустые строки вокруг блоков повторов `Nx`, никаких цифр в начале
   подписей, никаких голых `Z<число>` вне велосипеда.
3. Прочитайте событие обратно через `GET /events/{id}`: непустой
   `workout_doc.steps` означает, что парсер принял описание; `steps: []`
   означает, что он споткнулся.
4. Синхронизируйте часы через Garmin Connect и откройте запланированную
   тренировку.

Проверка: часы показывают коридор в bpm, равный вашим процентам × LTHR,
сохранённый в Intervals — а не собственный LTHR часов (проще всего доказать,
когда они различаются). Веб-UI Intervals показывает полный график шагов, а не
только название и общую длительность.

Правила: работай только внутри текущей директории. Ничего не деплой, не публикуй, не отправляй и не сообщай ни в какой внешний сервис.
