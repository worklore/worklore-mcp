# Почему вторая публикация возвращает 500

## Причина

`publish()` сохраняет вместе с историей список `similar: [{slug, score}]`.
`score` считает `similarity()` — это `round(0.7 * tag_score + 0.3 * word_score, 4)`,
то есть **Python `float`**. Сериализатор DynamoDB в boto3 float не принимает:

```
TypeError: Float types are not supported. Use Decimal types instead.
```

(`logs/error.log`, `src/app.py:63` → `table.put_item(Item=item)`), и `handler()`
превращает это исключение в 500.

Почему первая публикация проходит: таблица пуста, `scan` ничего не возвращает,
`similar == []`, и в item нет ни одного float (`published_at` — `int`). Как только
в библиотеке появляется хотя бы одна история, у каждой следующей в `similar` есть
`score: float`, поэтому падает **каждая** публикация, начиная со второй (в логе — две
подряд). Существующий тест публиковал историю только в пустую таблицу, поэтому
этот путь ни разу не выполнялся.

## Исправление (`src/app.py`)

1. Добавлена функция `to_dynamo()`: рекурсивно проходит по item и заменяет каждый
   `float` на `Decimal(repr(value))` (через `repr`, чтобы `0.7` стало `Decimal('0.7')`,
   а не `0.6999999999…`). NaN/Infinity отвергаются как `ValueError` → 400.
   `publish()` пропускает через неё **весь** item перед `put_item`, а не только поле
   `score` — так любое числовое поле, добавленное позже, тоже не сломает запись.
2. `validate()` теперь требует, чтобы `tags` был списком строк. Раньше клиент мог
   прислать, например, `"tags": [1.5]` (float) или смешанные типы (`sorted()` падает
   с `TypeError`) и получить 500 вместо 400.

## Чтобы не повторилось (`tests/test_publish.py`)

- `test_second_publish_stores_scores` — три публикации подряд через `handler()`:
  все должны вернуть 201, у второй в `similar` хранится `score` типа `Decimal > 0`.
  На старом коде тест падает с `500 != 201`, т.е. воспроизводит баг из лога.
- `test_non_string_tags_rejected` — некорректные теги дают 400, а не 500.

`python3 -m unittest discover tests` — все 3 теста проходят.

Замечание вне рамок этой ошибки: `table.scan()` читает только первую страницу
(до 1 МБ) и не обрабатывает `LastEvaluatedKey`, так что при большой библиотеке
«похожие» будут считаться не по всем историям.
