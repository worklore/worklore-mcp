# Почему ломалась интеграция с Intervals.icu

Были три независимые причины — по одной на каждый симптом из `logs/`. Все исправлены
в `server.py` и `static/app.js`; наружу ничего не отправлялось и не деплоилось,
проверка шла против локального мока провайдера на `127.0.0.1`.

## 1. Кнопка Connect давала 401 у всех (тикет #214)

Кнопка в `static/app.js` была обычной ссылкой `<a href="/api/intervals/auth/init">`.
Токен сессии живёт в `localStorage` и подставляется **только** fetch-обёрткой SPA,
а браузерная навигация по ссылке заголовок `Authorization` не несёт — сервер законно
отвечал `401 {"error": "unauthorized"}`, и все видели белую страницу с этим текстом.

**Исправление:** `GET /api/intervals/auth/init` теперь возвращает `200 {"url": "<authorize url>"}`
вместо редиректа, а SPA запрашивает его через `api()` (с токеном) и делает
`window.location.assign(url)`. Запрос без токена по-прежнему получает 401.

## 2. Intervals.icu отвечал `400 invalid_request` на authorize-ссылку (тикет #219, раздел 2 лога)

URL собирался как `urllib.parse.urlencode(params, safe=":,")`: символы `:` и `,` не
кодировались. Из-за этого `redirect_uri` уходил частично закодированным —
`redirect_uri=http:%2F%2Flocalhost:8766%2F...` с «сырыми» двоеточиями (это видно
в `logs/connect-attempt.log`). OAuth 2.0 (RFC 6749, Appendix B) требует полного
form-encoding параметров; сервер провайдера не смог сличить такое значение с
зарегистрированным redirect URI и отклонял запрос с `invalid_request` ещё до экрана
согласия. Общее тело ошибки («не сказывает, какой параметр не нравится») маскировало
причину. Перестало работать вручную собранная ссылка после релиза календаря 2026-10-02:
именно тогда рядом со scope правили и этот вызов `urlencode`.

**Исправление:** `urlencode(params)` без «safe»-исключений (полное кодирование,
в т.ч. `:` и `,` внутри значений) плюс явный `response_type=code` (обязателен по
RFC 6749; у Intervals.icu формально опционален, но это стандартный параметр).
Сами scope-имена (`ACTIVITY:READ,...,CALENDAR:WRITE`) корректны по документации
Intervals.icu — их трогать не нужно.

## 3. Подключение Rivera «протухало» через час (тикет #219, раздел 3 лога)

Ответ токен-эндпоинта для Rivera не содержал ни `refresh_token`, ни `expires_in`
(таков реальный формат ответа Intervals.icu — пример в их документации тоже без этих
полей). Приложение вместо этого **само выдумало** срок жизни 3600 с
(`DEFAULT_TOKEN_TTL` в `server.py`) и по его истечении принудительно переводило
подключение в «expired, reconnect» — отсюда «подключитесь заново» на следующее утро.
Реконнект был невозможен из-за причин 1 и 2.

**Исправление:** если провайдер не сообщил `expires_in`, подключение считается
долгоживущим (`expires_at = None`), фоновый рефрешер его не трогает, и фактическая
протухшесть определяется лениво: когда Intervals API отвечает `401`, прокси
(`GET /api/intervals/wellness`) переводит статус в «expired, reconnect» и возвращает
409. Путь обновления токенов сохранён для ответов, где `refresh_token`/`expires_in`
есть (и устойчив к ответу рефреша без `expires_in`).

## Проверка (локально, без обращений к внешним сервисам)

Поднят мок Intervals.icu на `127.0.0.1:8899` (через `INTERVALS_BASE`), воспроизводящий
строгую проверку кодировки из п. 2 и оба формата ответа токена из п. 3:

- полный флоу для обоих пользователей: `auth/init` → authorize → callback → `connected`;
- authorize-запрос с незакодированным `:` отклоняется моком с 400, с исправленным
  URL — проходит;
- wellness через прокси → 200; после «отзыва» токена у провайдера → статус
  «expired, reconnect», wellness 409;
- токен с `expires_in=90` и `refresh_token` автоматически продлён фоновым циклом,
  новый токен принят провайдером;
- подключение без `expires_in`/`refresh_token` не «протухает» по таймеру;
- подделанный `state` → 400.
