# Почему интеграция Intervals.icu не работала

## Причины

**1. Кнопка Connect теряла авторизацию (ломала flow для всех).**
Кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`, то есть
полноценной навигацией браузера. SPA держит токен в localStorage и шлёт его
заголовком `Authorization` только через fetch — document-навигация этот
заголовок не отправляет. Поэтому `GET /api/intervals/auth/init` приходил без
заголовка, сервер отвечал 401, и атлет видел белую страницу
`{"error": "unauthorized"}` (тикет #214, раздел 1 лога). Это же объясняет,
почему «единственный рабочий» способ был вручную скопировать authorize-ссылку
через curl с заголовком.

Исправление: `auth/init` — теперь аутентифицированный **POST**, возвращающий
`{authorize_url}` JSON-ом; фронтенд делает `window.location.assign(authorize_url)`
(`server.py` `do_POST`/`auth_init`, `static/app.js`).

**2. Дублирующийся scope — authorize отклонялся ещё до экрана согласия.**
После выкатки calendar sync (2026-10-02) scope стал
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
Intervals.icu отклоняет перечисление одной области дважды (`:WRITE` уже
включает `:READ`) с ошибкой `invalid_request` / «Duplicate scope» — поэтому
даже ручное открытие ссылки стало давать HTTP 400 (тикет #219, раздел 2 лога).
Этот дефект просто перекрыл собой обходной путь из пункта 1.

Исправление: каждая область не более одного раза —
`ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` (`config.py`).

**3. Вечный токен принудительно «истекал» через час.**
У Intervals.icu в ответе токен-ендпоинта нет ни `refresh_token`, ни
`expires_in` — токен жив, пока атлет сам не отзовёт его в интерфейсе
Intervals. Код же при отсутствии `expires_in` ставил TTL по умолчанию
3600 с, а фоновый «refresher» через час помечал соединение
«expired, reconnect» и обнулял токен. Именно поэтому T. Rivera, чья связь
работала, через час получила требование переподключиться, хотя на стороне
Intervals приложение числилось активным (раздел 3 лога).

Исправление: вся refresh-машинерия удалена (`refresh_tokens`,
`REFRESH_INTERVAL`, `DEFAULT_TOKEN_TTL`); токен хранится как неистекающий.
Отзыв обрабатывается лениво: первый 401 от API очищает токен и ставит
статус «revoked, reconnect» (`mark_revoked` в `server.py`).

**4. Мелочи по ходу (по заметке коллеги).** Обмен кода шлёт только
`client_id`, `client_secret`, `code` (без `grant_type` и `redirect_uri`);
в state добавлен `purpose` (раньше была подписанная HMAC-строка с TTL —
функционально то же самое, что JWT из заметки); добавлен guard: при
переподключении callback с athlete id, отличным от уже привязанного,
отклоняется с 409.

## Что пригодилось из заметки коллеги

- **П. 4 (init должен быть POST → `{authorize_url}` → `window.location.assign`)** —
  прямое попадание в причину #1, применено как написано.
- **П. 2 (правило «одна область не более раза», `:WRITE` включает `:READ`)** —
  объяснило 400 «invalid_request» из раздела 2 лога (в теле ответа не сказано,
  какой параметр не нравится; в логе проверяли state и redirect_uri — дело
  было в scope).
- **П. 1 (нет refresh_token/expires_in, токен вечен; отзыв лениво по 401;
  «no refresh machinery at all»)** — причина #3, применено целиком, включая
  удаление фонового refresher'а.
- **П. 3 (токен-ендпоинт принимает только 3 поля; в ответе сразу `athlete`)** —
  применено: убраны `grant_type` и `redirect_uri` из обмена.
- **Follow-up про state и guard несовпадения аккаунта** — применено: state уже
  нёс личность (подпись + TTL 15 мин), добавлен `purpose`; guard добавлен.
- **Шаг «Verify»** — использован как чек-лист для end-to-end проверки.

Не пригодилось: оформление state именно как JWT (`sub`/`exp`) — существующая
подписанная строка с теми же свойствами проще и не тянет зависимостей;
«шифровать токен at rest» — для in-memory демо-хранилища (stdlib-only) не
применимо, это задача прода. «Узнать о смерти токена можно только по факту»
учтено пунктом 3 выше.

## Проверка

Внешние сервисы не трогал: поднял локальный стаб `intervals.icu`
(`INTERVALS_BASE` переопределён на 127.0.0.1, стаб удалён после тестов).
Прогнано: POST init без токена → 401, с токеном → `{authorize_url}` со scope
без дублей; полный цикл authorize → callback → 302 → status «connected» →
wellness 200 через прокси; подтверждено, что старый дублирующий scope стаб
(как и Intervals) отклоняет с «Duplicate scope»; подделанный state → 400;
guard: повторный connect с другим athlete id → 409, связь не трогается;
после 401 от API статус становится «revoked, reconnect»; в токен-запросе
ровно `client_id`, `client_secret`, `code`. GET `/api/intervals/auth/init`
удалён (404) — старый путь кнопки намеренно закрыт.
