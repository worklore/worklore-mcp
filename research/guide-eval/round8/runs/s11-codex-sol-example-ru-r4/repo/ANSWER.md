# Причина

Первая публикация прошла, потому что таблица была пустой: `related()` вернул пустой список `similar`. При второй публикации `similarity()` вычислил дробный `float` и поместил его в `similar[0].score`. `table.put_item()` передал этот элемент сериализатору DynamoDB, который отклоняет Python `float` (`TypeError: Float types are not supported`). Обработчик превратил исключение в HTTP 500. Это соответствует трассировке в `logs/error.log`.

# Исправление

- Расчёт сходства в `src/app.py` теперь ведётся в `Decimal` и округляется до четырёх знаков. Значение балла остаётся долей от 0 до 1, а в записываемом `Item` больше не появляется `float` из расчёта сходства.
- Проверка входной истории требует строковые `slug`, `title`, `body` и список строковых `tags`. Числа из JSON поэтому не могут попасть в записываемый элемент и вызвать ту же ошибку; некорректный запрос получает HTTP 400.
- Тест в `tests/test_publish.py` публикует две истории подряд через обработчик, проверяет HTTP 201 и сохранённый `Decimal` в `similar`. Отдельный тест проверяет отклонение числовых входных значений.

# Что пригодилось из заметки

Пригодились объяснение различия между первой записью в пустую таблицу и записью при уже существующей истории, указание на запрет `float` в DynamoDB, проверка вычисляемых значений перед `put_item` и тест с предварительно заполненной таблицей. Вариант с целыми процентами не использован: он изменил бы смысл и диапазон сохранённого `score`. Проверка на реальной таблице не проводилась, поскольку задача запрещает обращения к внешним сервисам; использован локальный `FakeTable`, проверяющий типы как сериализатор boto3.

Проверка: `python3 -m unittest discover tests -v` — 3 теста прошли. До исправления тест второй публикации воспроизводил HTTP 500 и ошибку `Float types are not supported`.
