# Пульсовые коридоры обрезаются под зоны часов

## Что изменил

В `gen.py`, функция `hr_target`: ключ нижней границы переименован с `value` на `start`.

```python
# было
return {"units": "%lthr", "value": lo, "end": hi}

# стало
# "start", not "value": with "value" Intervals exports a Lap-HR (zone) target
# that the watch clips to its own zones; "start" exports an Instant-HR corridor.
return {"units": "%lthr", "start": lo, "end": hi}
```

Проверка генератора: `python3 gen.py plans/tempo-run.json` теперь даёт во всех
пяти пульсовых целях `start`/`end` (68–75, 88–93, 75–82, 65–72), ни одного
`value` в выводе нет. Файл `readback/event-184233-as-sent.json` не менял: это
снимок того, что ушло в API раньше.

## Почему

Из `readback/watch-notes.md`: все коридоры на часах совпадали с зонами часов
(118–137, 137–151, 151–162), а не с 117–129, 151–160, 129–141 — то есть
Intervals экспортировал цель как зонную (Lap-HR), которую часы обрезают под
свои зоны. Пересчёт в bpm по LTHR из Intervals при этом не работал.

Заметка коллеги описывает ту же симптоматику и предлагает `start`/`end`
вместо `value`/`end` с `%lthr`: по его наблюдению, такой ключ переключает
экспорт на коридор Instant-HR, где часы показывают сырые bpm, посчитанные
Intervals. Это совпадает с нашими данными, поэтому я взял это изменение.

## Что не проверено

- **Поведение на часах не проверено.** Я не отправлял событие в Intervals и не
  синхронизировал часы: это внешнее действие, а вы его не просили. Поэтому
  правильность исправления пока основана на заметке коллеги и на совпадении
  симптомов, а не на наблюдении.
- **Документация API не подтвердила семантику.** Поиск по `workout_doc` и
  `%lthr` дал только форумные обсуждения: там описаны поля `start`/`end` для
  мощности (`_power`) и упоминается `%lthr` для пульса, но прямого подтверждения
  «`start` = Instant-HR, `value` = Lap-HR» я не нашёл.
- Заметка коллеги ссылается на наблюдения с часами и на `start_bpm`/`value` с
  абсолютными bpm. Это не проверялось здесь.

## Что из заметки коллеги не взял

- **Абсолютные bpm и `start_bpm`/`end_bpm`** — не нужны: в проекте цели заданы в
  процентах LTHR, и это остаётся.
- **Грамматика поля `description`** (`m` = минуты, `mtr`/`km`, `Z2` для плавания,
  пустые строки вокруг `Nx`, цифры в начале подписей) — полезно, если веб-UI
  Intervals не показывает шаги. В текущем `gen.py` поля `description` нет, и
  симптом про часы его не касается. Стоит добавить отдельной задачей, если
  понадобится.
- **Шаг «прочитать обратно через `GET /events/{id}` и проверить `steps`»** —
  хороший способ проверить, что парсер принял описание, но для текущего
  изменения не обязателен. Имеет смысл сделать при реальной отправке.

## Как проверить на часах

1. Отправить событие: `python3 gen.py plans/tempo-run.json > event.json` и
   `./push.sh event.json` (нужны `INTERVALS_API_KEY` и `ATHLETE_ID`).
2. Прочитать событие через API и убедиться, что в `workout_doc` у шагов есть
   `start`/`end`, а не `value`.
3. Синхронизировать часы через Garmin Connect и открыть тренировку. Ожидаемо:
   Warm-up 117–129, Tempo 151–160, Float 129–141, Cool-down 112–124 bpm
   (проценты × LTHR 172), а не границы зон часов (118–137, 151–162 и т.д.).
   Различие заметно, потому что LTHR на часах 168, а в Intervals 172.

Если часы по-прежнему показывают зонные границы, значит проблема не в ключе
`start`/`value`, и нужно смотреть экспорт в Intervals (тип цели) до генератора.
