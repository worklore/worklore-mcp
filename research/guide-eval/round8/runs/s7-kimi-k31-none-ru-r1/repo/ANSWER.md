# Причины сбоя интеграции Intervals.icu

1. **Кнопка Connect не передавала авторизацию tricoach.** Ссылка выполняла обычную навигацию браузера, поэтому Bearer-токен из `localStorage` не добавлялся к `GET /api/intervals/auth/init`. Сервер справедливо возвращал 401 ещё до начала OAuth.

2. **OAuth-запрос имел неверный формат.** Значение `scope` передавалось списком через запятую, хотя OAuth 2.0 требует разделять области пробелами. После добавления calendar-областей Intervals.icu отклонял такой запрос с `invalid_request`. Также не был явно указан обязательный `response_type=code`.

3. **Не запрашивался offline-доступ.** Без `access_type=offline` Intervals.icu выдал только часовой access-token, без refresh-token. После истечения срока приложению нечем было обновить доступ, поэтому подключение T. Rivera перешло в `expired, reconnect`.

4. **Обновление токена требовало необязательное поле `expires_in`.** Ответ Intervals.icu может его не содержать (это видно уже в исходном token-ответе в журнале). При обновлении это привело бы к ошибке и повторному требованию подключения, несмотря на наличие refresh-token.

# Исправления

- Кнопка теперь вызывает `/api/intervals/auth/init` через авторизованный `fetch` и переходит по возвращённой OAuth-ссылке.
- Authorize URL содержит `response_type=code`, `access_type=offline` и разделённый пробелами `scope`; параметры корректно кодируются.
- При обновлении токена сохраняется прежний refresh-token, если новый не выдан, а отсутствующий `expires_in` заменяется стандартным TTL в 3600 секунд.

Проверено локально с имитатором Intervals.icu: авторизованная инициация OAuth, callback, автоматическое обновление токена без `expires_in`, сохранение refresh-token и запрос wellness с обновлённым access-token. Обработчик кнопки проверен отдельно. Внешние сервисы не вызывались.
