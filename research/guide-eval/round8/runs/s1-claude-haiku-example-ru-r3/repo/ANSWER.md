# Ответ: почему пульсовые диапазоны обрезались по зонам часов

## Что изменил

`gen.py`, функция `hr_target`: нижняя граница пульсового коридора теперь пишется в ключ `start`, а не `value`.

```diff
-    return {"units": "%lthr", "value": lo, "end": hi}
+    return {"units": "%lthr", "start": lo, "end": hi}
```

Добавил в docstring одно предложение с объяснением, чтобы ключ не вернули обратно.

Проверка: `python3 gen.py plans/tempo-run.json` теперь даёт, например, `"hr": {"units": "%lthr", "start": 88, "end": 93}` для Tempo. Остальные шаги структуры не менялись.

## Почему

В `readback/watch-notes.md` видно, что все коридоры на часах совпадали с зонами самих часов (118–137, 137–151, 151–162). Это симптом того, что Intervals экспортирует цель как lap-HR, которую часы мапят на свои зоны. Коллега в заметке описывает похожий случай: при ключе `{value, end}` экспорт идёт в режиме lap-HR/zone-mapped, а при `{start, end}` — в режиме instant-HR с явным коридором в bpm, рассчитанным Intervals от его LTHR. Переименование ключа — единственное изменение, которое нужно для этого режима.

## Что не проверено

- **Ни одна часть не проверена на часах или в Intervals.** В окружении нет доступа к API и к Garmin, и по правилам задачи ничего никуда не отправлялось. Поэтому нельзя подтвердить, что Intervals принимает `start` с `units: "%lthr"` и что часы теперь показывают, например, 151–160 bpm.
- **Единственный источник для `start` — заметка коллеги.** Я поискал в открытых источниках: форум Intervals не подтверждает ни `start` для HR, ни значение `instant`. Официальной схемы для HR-единиц я не нашёл. Заметка коллеги в этой части остаётся непроверенной.
- `readback/event-184233-as-sent.json` всё ещё содержит старый вариант с `value`. Его я не трогал: это запись реального ответа API. После следующей отправки её нужно обновить.
- Тест на стороне Intervals: после отправки стоит прочитать событие через `GET /events/{id}` и убедиться, что `workout_doc.steps` не пустой. Это проверяет, что схема принята, но не режим экспорта.

## Что взял из заметки коллеги, а что пропустил

**Взял:**
- Идею, что ключ `start` (а не `value`) переключает режим экспорта. Это единственное изменение в коде.
- Подход «проверить на часах, а не по ответу API»: readback подтверждает только то, что API принял JSON, но не то, как часы его отобразят.
- Совпадение симптома: `start_bpm`/`end_bpm` давали постоянные 101 bpm (у нас в заметке это тоже есть).

**Пропустил:**
- Правила текстовой грамматики поля `description` (`m`/`mtr`, `Z<number>`, пустые строки вокруг `Nx`). В нашем `gen.py` поле `description` не заполняется, поэтому проблемы с отображением шагов в веб-интерфейсе Intervals у нас нет.
- Советы про сопоставление процентов и LTHR в самом Intervals. У нас этот подход уже используется, менять его не нужно.
- Шаги воспроизведения с созданием тестового события. Это внешнее действие, и без явного подтверждения я его не делал.
- Найденный в поиске баг прошивки Edge 840 (bpm читались как %HRmax). Это другое устройство; у нас Forerunner 965, и для него этот баг не подтверждён.

3. Если диапазон всё ещё совпадает с зонами часов, следующий шаг — проверить в Intervals, какой экспорт он отдаёт в FIT, и сравнить с заметкой коллеги.
