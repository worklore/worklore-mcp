# Кеширование после save_fact

## Причина
`build_system` складывал инструкции и контекст атлета (дата, факты) в один text-блок
с одним `cache_control`. Кеш работает по точному префиксу. `save_fact` дописывает
строку в факты, поэтому менялся единственный блок, и следующий вызов целиком
пересоздавал кеш (`cache_read_input_tokens: 0`, `cache_creation` около 1000 в `logs/usage.jsonl`).
Дата в начале блока делала то же самое раз в сутки.

## Что изменено (bot.py)
- `athlete_context` разделён на `athlete_profile` (имя, зоны, цель, язык) и
  `athlete_memory` (дата и факты).
- `build_system` отдаёт два блока, от стабильного к изменчивому:
  1. инструкции + профиль, `cache_control`;
  2. дата + факты, `cache_control`. Этот брейкпоинт нужен для раундов tool-цикла
     внутри одного сообщения.
- Дата и факты стоят после стабильного префикса, поэтому `save_fact` ломает только второй блок.
- Фильтрацию инструментов по ключевым словам не трогал (см. NOTES.md).

## Не проверено
- Реальных вызовов API не делал (запрещено правилами). Эффект проверьте по `logs/usage.jsonl`:
  после `save_fact` `cache_read_input_tokens` должен остаться около 900-1000.
- Минимум для кеша у Sonnet 4.5 составляет 1024 токена на префикс (инструменты + system).
  По логам оцениваю: инструменты + инструкции + профиль дают около 1000 токенов. Это
  на границе. Если префикс окажется меньше, первый брейкпоинт молча не сработает, и
  поведение вернётся к прежнему (кешируется только весь префикс целиком). Тогда нужно
  добавить в статичную часть содержимого или перенести профиль в неё целиком. Если
  `cache_creation` по-прежнему равен полному префиксу, проверьте именно это.
- Набор tools зависит от ключевых слов и стоит в префиксе перед system. Сообщение,
  которое добавляет `plan_week` или `predict_race`, инвалидирует кеш независимо от этой правки.
