# Причины сбоя Intervals.icu

1. Кнопка была обычной ссылкой на `/api/intervals/auth/init`. Токен входа в tricoach хранится в `localStorage` и добавляется только обёрткой `fetch` в `static/app.js`. При переходе браузера по ссылке заголовка `Authorization` нет, поэтому сервер отвечал 401. Теперь кнопка вызывает авторизованный API-запрос, получает URL согласия и переводит браузер на него.

2. Запрос согласия содержал `CALENDAR:READ` и `CALENDAR:WRITE`. Согласно сохранённым логам, после добавления календарных scope Intervals стал отвечать `invalid_request` ещё до экрана согласия. Это наиболее вероятная причина отказа; по одному ответу 400 нельзя доказать, какой именно параметр провайдер отверг. Календарные scope убраны; запрошены `ACTIVITY:READ`, `ACTIVITY:WRITE` и `WELLNESS:READ`. Реальное согласие с провайдером здесь не проверялось, поскольку внешние обращения запрещены.

3. В ответе токена Rivera не было ни `expires_in`, ни `refresh_token`. Сервер сам назначал срок 3600 секунд и затем принудительно помечал подключение истёкшим. Теперь срок записывается только при наличии `expires_in`; бессрочный по данным ответа токен фоновый процесс не инвалидирует. Для токенов с указанным сроком и без refresh token повторное подключение требуется лишь после фактического истечения.

Проверено локально: компиляция Python, синтаксис JavaScript, `git diff --check` и проверки сохранения токенов с указанным сроком и без него. Внешние сервисы не вызывались.
