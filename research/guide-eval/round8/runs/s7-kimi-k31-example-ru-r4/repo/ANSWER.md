# Исправление интеграции Intervals.icu

## Причины сбоя

1. **Кнопка Connect теряла авторизацию tricoach.** Она была обычной ссылкой на `GET /api/intervals/auth/init`. При полном переходе браузер не добавляет `Authorization: Bearer ...`, который SPA хранит в `localStorage` и подставляет только в `fetch`. Поэтому endpoint возвращал 401 всем пользователям. Это прямо видно в `logs/connect-attempt.log` и в обращении #214.

2. **Authorize URL содержал дублирующиеся области scope.** Были одновременно указаны `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`. У Intervals.icu `:WRITE` уже включает `:READ`, а повторение одной области приводит к ошибке `Duplicate scope` ещё до экрана согласия. Это объясняет, почему обход через вручную скопированную ссылку перестал работать после добавления calendar sync.

3. **Долговечный токен ошибочно считался истекающим через час.** Intervals.icu не выдаёт в этом ответе ни `refresh_token`, ни `expires_in`: access token действует, пока спортсмен не отзовёт доступ. Код подставлял собственный срок 3600 секунд, а фоновая задача затем очищал действующий токен и ставила `expired, reconnect`. Поэтому T. Rivera попросили подключиться заново примерно через час, хотя доступ не был отозван.

4. **Обмен authorization code содержал лишние параметры.** Для Intervals.icu нужны только `client_id`, `client_secret` и `code`; запрос также содержал `grant_type` и `redirect_uri`. Запрос приведён к требуемому формату.

## Что изменено

- `POST /api/intervals/auth/init` теперь требует обычную авторизацию tricoach и возвращает JSON `{authorize_url}`. Старый GET удалён.
- Кнопка в `static/app.js` вызывает этот POST через общий `fetch`-wrapper и затем выполняет `window.location.assign(authorize_url)`. Ошибка запуска OAuth показывается на карточке подключения.
- Scope в `config.py`: `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` — каждая область указана один раз, с записью там, где она нужна приложению.
- Обмен кода отправляет только три поддерживаемых поля. `athlete.id` и `athlete.name` берутся из ответа token endpoint.
- Удалены выдуманный `expires_at`, хранение `refresh_token` и фоновый refresher. Токен сохраняется как действующий до отзыва.
- При 401 от API Intervals.icu сохранённый access token очищается, статус становится `revoked, reconnect`; wellness возвращает 401, а status уже сообщает `connected: false`. Повторное подключение после этого работает.
- Подписанный HMAC `state` по-прежнему связывает неаутентифицированный callback с пользователем и имеет TTL 15 минут; добавлена проверка `purpose: intervals_oauth`, корректного timestamp и возраста state. JWT не понадобился: существующий stdlib-HMAC даёт те же требуемые здесь свойства подписи и проверки.
- При повторном подключении athlete ID сверяется с уже сохранённым. Другой аккаунт получает 409 и не перезаписывает подключение; для смены аккаунта нужно сначала явно отключить текущий.

## Какие части заметки коллеги пригодились

Применены все четыре описанные особенности интеграции:

- раздел про GET init и потерю `Authorization` — основа исправления кнопки на POST + JSON + `window.location.assign`;
- раздел про `Duplicate scope` — удалены повторы областей и лишние `:READ` при наличии `:WRITE`;
- раздел про отсутствие `refresh_token` и `expires_in` — удалён refresher, добавлена ленивая обработка отзыва по первому 401;
- раздел про token exchange — оставлены только `client_id`, `client_secret`, `code`, используется вложенный объект `athlete`.

Также применены рекомендации из пояснения к callback: назначение и TTL state, а также account-mismatch guard. Совет шифровать токен при хранении не реализован в этом dev-примере, потому что `CONNECTIONS` находится только в памяти и не записывается на диск; для постоянного prod-хранилища шифрование по-прежнему необходимо.

## Проверка

- Синтаксис `server.py`, `config.py` и `static/app.js` проверен.
- На локальном HTTP-имитаторе Intervals.icu пройден сценарий: клик Connect → авторизованный POST → authorize redirect → callback → обмен кода → connected status → успешный wellness.
- Имитатор проверил точный набор полей token request и отсутствие повторов scope.
- Отдельно проверены: 401 без tricoach-авторизации, отсутствие старого GET init, отказ по невалидному state, отсутствие искусственного срока жизни токена, переход в `revoked, reconnect` после 401 провайдера, успешное повторное подключение и отклонение другого athlete ID с 409.
- Внешние запросы не выполнялись, поэтому реальный аккаунт Intervals.icu в этой проверке не использовался.
