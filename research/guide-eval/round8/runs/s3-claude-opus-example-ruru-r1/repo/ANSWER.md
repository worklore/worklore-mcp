# Почему nightly-review ни разу ничего не сообщила

## Что показывают факты

- `launchctl-print.txt`: `runs = 6`, `last exit code = 1`, `state = waiting`.
  Задача **запускалась** каждую ночь (12→18 октября = 6 ночей). launchd тут ни при чём.
- `Library/Logs/nightly-review.err` — по две строки на каждый запуск:
  ```
  Not logged in · Please run /login
  /Users/vk/bin/nightly-review.zsh:19: read-only variable: status
  ```
- `nightly-review.out` пустой: stdout `claude` перенаправлялся в отдельный `.md`.

## Причины (два слоя)

1. **`claude -p` падал с «Not logged in».** launchd не выставляет `USER`
   (в `environment` из `launchctl print` только `PATH` и `XPC_SERVICE_NAME`).
   Без `USER` CLI не находит свой логин в keychain. Из терминала всё работает,
   потому что там `USER` есть.

2. **Сообщать было некому: строка 19 `status=$?` убивала скрипт.** В zsh
   `status` — встроенная read-only переменная (синоним `$?`), присваивание —
   фатальная ошибка, скрипт выходит с кодом 1. Эта строка стоит сразу после
   вызова `claude` и *до обоих* вызовов `notify.sh`. Поэтому не было ни
   уведомления об ошибке, ни — даже если бы `claude` отработал — уведомления
   об успехе. Тишина гарантировалась при любом исходе.

Дополнительно (не проявилось, но тоже давало бы тишину):

3. `notify.sh` вызывал `curl -sS ... > /dev/null` без `-f`: если Telegram
   отвечает ошибкой (HTTP 400/401, напр. неверный токен или битый текст),
   curl выходит с 0, а тело ответа выбрасывается. Ошибка доставки была бы
   невидима.
4. В уведомление шли первые 300 байт отчёта (`head -c 300`), а сводка «для
   телефона» по промпту стоит в конце; к тому же `head -c` может разрезать
   UTF-8-символ посередине, и Telegram отклонит текст (см. п. 3).

## Что исправлено

- `Library/LaunchAgents/com.vk.nightly-review.plist`: в `EnvironmentVariables`
  добавлены `USER`, `LOGNAME`, `HOME` (и `~/.local/bin` в `PATH` — частое место
  установки `claude`).
- `bin/nightly-review.zsh`:
  - `status=$?` → `rc=$?`;
  - промпт передаётся через stdin (`print -r -- "$PROMPT" | claude -p ...`),
    а не многострочным аргументом;
  - stderr `claude` сохраняется в `nightly-review-ДАТА.err`, и его хвост
    попадает в сообщение об ошибке (вы бы сразу увидели «Not logged in»);
  - `trap ... EXIT` — страховка: если скрипт умрёт где угодно до штатного
    уведомления (как с `status`), всё равно уйдёт «DIED unexpectedly (exit N)».
    Именно `trap`, а не функция `TRAPEXIT`: последняя наследуется подоболочками
    `$(...)` и при проверке слала ложные сообщения;
  - код 0 при пустом выводе считается неудачей;
  - в лог пишутся старт, `USER`/`HOME`, код выхода и длительность запуска
    (запуск в 0–5 с = агент упал до начала работы);
  - в сообщение об успехе идёт хвост отчёта (сводка), построчно;
  - если сам `notify.sh` упал — запись в лог и локальное уведомление macOS.
- `bin/notify.sh`: `curl --fail-with-body --max-time 30`, при ошибке ответ
  Telegram пишется в stderr и возвращается ненулевой код.

## Как я это проверил (здесь, без launchd и без сети)

`zsh -n`, `bash -n`, `plutil -lint` — ок. Прогон скрипта во временном HOME с
поддельными `claude` и `notify.sh`:

| сценарий | результат |
|---|---|
| `claude` пишет «Not logged in», exit 1 | 1 сообщение: `FAILED (exit 1, 0s): Not logged in…` |
| `claude` читает промпт из stdin, выдаёт отчёт | 1 сообщение: `done` + сводка |
| `claude` exit 0, пустой вывод | 1 сообщение: `FAILED: exit 0 but empty output` |
| в скрипт вставлен `status=$rc` (старый баг) | 1 сообщение: `DIED unexpectedly (exit 1)` |
| `notify.sh` сам падает | запись `notify.sh FAILED (rc=7)` в лог |

Настоящий `claude`, keychain и Telegram я не трогал.

## Что сделать вам на Mac

```sh
launchctl bootout gui/$UID/com.vk.nightly-review
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl kickstart -k gui/$UID/com.vk.nightly-review
launchctl print gui/$UID/com.vk.nightly-review | grep -E 'runs|last exit'
tail ~/Library/Logs/nightly-review.err
```
Убедитесь, что: код выхода 0, `~/Library/Logs/nightly-review-ДАТА.md` свежий и
непустой, длительность в логе правдоподобная (не секунды), сообщение пришло.
Затем один раз сломайте намеренно (например, временно `REPO=/nonexistent` или
`exit 3` после `cd`) и проверьте, что пришло сообщение об ошибке.
Если после этого всё ещё «Not logged in» — запустите `claude` один раз
интерактивно и выполните `/login`, либо задайте токен через
`claude setup-token` / `CLAUDE_CODE_OAUTH_TOKEN`.

## Какие части заметки коллеги пригодились

Пригодились:
- «Сначала докажите, запускалась ли задача» через `launchctl print`: `runs = 6`
  сразу сняли версию «launchd не запускает».
- «Прочитайте лог из StandardErrorPath прежде чем строить теории» — обе причины
  были в `.err` дословно.
- Баг `status=$?` в zsh — ровно тот же, на той же позиции (между агентом и
  уведомлением).
- «Задайте `USER` в `EnvironmentVariables`, иначе „Not logged in“» (из ссылки на
  статью Пердума) — это и есть первая причина.
- Передавать промпт через stdin — применил как профилактику.
- Поправка про код выхода: «0 ≠ сработало», проверять реальный результат и
  длительность — отсюда проверка на пустой вывод и логирование длительности.
- «Ставьте уведомление об ошибке ближе к началу пути отказа и проверьте его,
  намеренно вызвав ошибку» — отсюда `trap EXIT` и тест с вставленным `status=`.

Не пригодилось / не применимо:
- Ошибка «Input must be provided…» — в моём логе её нет; переход на stdin сделан
  только для надёжности.
- `< /dev/null` для промпта-аргумента — промпт теперь идёт через stdin, а
  launchd и так даёт `/dev/null` на stdin.
- Сторожевой таймер с exit 0 по тайм-ауту — в этом скрипте его нет.
- Время 16:50, `runs = 2` и прочие детали её случая.
