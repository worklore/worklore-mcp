# Почему не подключается Intervals.icu

## Причины

1. **Кнопка Connect даёт 401 всем** (тикет #214, лог §1). Кнопка была обычной
   ссылкой `<a href="/api/intervals/auth/init">`, а init-эндпоинт требовал
   `Authorization: Bearer`. Токен входа лежит в `localStorage` и добавляется
   только обёрткой `api()` над fetch. При переходе по ссылке браузер этот
   заголовок не отправляет, поэтому в логе `401 (no Authorization header)`.
   **Исправление:** `POST /api/intervals/auth/init` идёт через `api()` и
   возвращает `{"authorize_url": ...}`, после чего SPA делает
   `window.location.assign(authorize_url)` (`server.py`, `static/app.js`).
   Старый `GET` теперь отвечает 404.

2. **Authorize-ссылка, вставленная вручную, даёт 400 `invalid_request`** (лог §2,
   началось после релиза calendar sync 2026-10-02). В `SCOPES` для одной области
   запрашивались и READ, и WRITE: `ACTIVITY:READ,ACTIVITY:WRITE` и
   `CALENDAR:READ,CALENDAR:WRITE`. В Intervals `:WRITE` уже включает `:READ`,
   а повтор области отклоняется. Подтверждение косвенное: тело ответа не
   называет параметр. Но у Rivera грант `ACTIVITY:WRITE,WELLNESS:READ` прошёл, и в
   нём каждая область встречается один раз. Поломка совпала с добавлением
   calendar-scope, а state и redirect_uri, по логу, на ответ не влияют.
   **Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`
   (`config.py`).

3. **Рабочее подключение «протухло» через час** (тикет #219, лог §3). Intervals
   не возвращает ни `expires_in`, ни `refresh_token`: токен живёт, пока атлет
   не отзовёт доступ. Код подставлял `DEFAULT_TOKEN_TTL = 3600`, и фоновый
   `refresh_tokens()` через час стирал токен, хотя тот был ещё валиден.
   **Исправление:** убраны фиктивный срок жизни и refresher. Токен хранится
   без срока. Отзыв обрабатывается лениво: при 401 от API Intervals
   соединение помечается `revoked, reconnect`, токен удаляется, а в UI снова
   появляется кнопка Connect.

Дополнительно добавлена защита от подключения другого аккаунта: если при
повторном подключении `athlete.id` отличается от сохранённого, callback
отвечает 409. Чтобы сменить аккаунт, сначала нужно нажать Disconnect.

## Проверка

Проверял локально, с фейковым сервером Intervals через `INTERVALS_BASE`:
- POST init отдаёт authorize URL с новым scope;
- callback обменивает код и сохраняет подключение, status = connected;
- wellness отвечает 200;
- после того как фейк начинает отвечать 401, wellness отдаёт 409 «not
  connected», а status = `revoked, reconnect`.

С настоящим Intervals.icu поток не проверялся: запросы во внешние сервисы
запрещены. После деплоя стоит пройти его с реальным аккаунтом. Rivera нужно
подключиться один раз заново: их токен уже стёрт старым refresher-ом.

## Что пригодилось из заметки коллеги

- **п.1 (нет refresh_token/expires_in, ленивая обработка 401)** — да, это
  причина 3.
- **п.2 (`Duplicate scope`)** — да, это причина 2. Строку scope я взял не из
  заметки, а только нужные приложению области. `SETTINGS:WRITE` не добавлял:
  приложение в настройки не пишет.
- **п.4 (init как аутентифицированный POST + `window.location.assign`)** — да,
  это причина 1, исправлена ровно так.
- **Защита от несовпадения аккаунтов при reconnect** — взял.
- **п.3 (обмен кода только с `client_id`/`client_secret`/`code`)** — не
  менял. По логу Rivera обмен с `grant_type` и `redirect_uri` прошёл, лишние
  поля Intervals терпит, и к поломке они отношения не имеют. Из того же пункта
  пригодилось то, что `athlete.id` приходит прямо в ответе с токеном; код уже
  так и делал.
- **state как JWT с claim `purpose`** — не нужно. Текущий HMAC-подписанный
  state с user id и TTL 15 минут решает ту же задачу.
- **Шифрование токена при хранении** — разумно для prod (токен бессрочный), но
  здесь хранилище in-memory, и к симптомам это не относится. Не делал.
