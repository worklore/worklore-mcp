# Причина

`similarity()` вычисляет коэффициент похожести через деление и взвешенную сумму, поэтому возвращает `float`. При первой публикации таблица пуста, `related()` возвращает пустой список `similar`, и в `put_item` не попадает ни одного `float`. При второй публикации в `similar` уже есть запись вида `{"slug": ..., "score": <float>}`. DynamoDB через boto3 не сериализует Python `float`, из-за чего возникает `TypeError: Float types are not supported. Use Decimal types instead.` из `logs/error.log`; `handler()` перехватывает исключение и возвращает 500.

# Исправление

В `src/app.py` оценка преобразуется на границе записи в целое число процентов от 0 до 100: `round(similarity(story, other) * 100)`. Сам расчёт похожести не изменён, а сохраняемый `score` теперь имеет поддерживаемый DynamoDB тип `int`.

В `tests/test_publish.py` добавлен регрессионный тест `test_second_publish_stores_integer_similarity_scores`: он выполняет вторую публикацию при уже заполненной таблице, проверяет обе сохранённые записи, ожидаемую оценку и её тип `int`. Тест падает на прежней реализации с тем же `TypeError`.

Проверено:

- `python3 -m unittest discover tests` — 2 теста, успешно.
- Две последовательные публикации через `handler()` с `FakeTable` — обе возвращают 201; у второй записи сохранён целочисленный `score`.

# Что пригодилось из заметки коллеги

Использованы три идеи: объяснение, почему пустая таблица скрывает ошибку до второй записи; преобразование вычисленной оценки в целые проценты на границе записи; регрессионный тест, который сначала заполняет таблицу и затем выполняет вторую запись. Также пригодился совет проследить вычисляемые значения с делением и округлением до `put_item`. Проверка на реальной таблице AWS не выполнялась: локальный `FakeTable` воспроизводит проверку типов boto3, а обращения к внешним сервисам были исключены условием задачи.
