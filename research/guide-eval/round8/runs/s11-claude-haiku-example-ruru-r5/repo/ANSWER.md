# Почему вторая публикация возвращает 500

## Причина

`similarity()` в `src/app.py` возвращала `round(..., 4)` — значение типа Python `float`.
`related()` кладёт эти оценки в `similar: [{slug, score}]`, и `publish()` пишет этот
список в элемент DynamoDB. boto3 отклоняет `float` (`TypeError: Float types are not
supported. Use Decimal types instead.`), и `handler()` превращает исключение в 500.

Первая публикация проходит, потому что таблица пуста: `scan()` возвращает пустой
список, `related()` ничего не считает, и в элементе нет ни одного `float`. Вторая
публикация — первая, у которой есть существующие истории, и именно тогда
вычисляется оценка.

В `logs/error.log` это видно так: первая запись `similar=0 stored`, вторая падает.

Тест `test_publish_stores_story` сажал историю только в пустую таблицу, поэтому
путь с оценками никогда не выполнялся.

## Исправление

- `src/app.py`: `similarity()` возвращает `Decimal(str(round(..., 4)))`. Значение
  остаётся долей от 0 до 1 с четырьмя знаками, как и было в API. Целые проценты я
  не выбирал: это изменило бы смысл поля `score`.
- `tests/test_publish.py`: добавлены два теста на путь с заполненной таблицей:
  - `test_publish_with_existing_story_stores_scores` — публикация с одной уже
    существующей историей, проверка, что оценка записана и больше нуля;
  - `test_handler_second_publish_returns_201` — вторая публикация через `handler()`,
    то есть через тот же путь, что и `POST /stories`, с ожидаемым кодом 201.

До исправления оба теста падали (второй вернул `500 != 201`, первый упал в
`FakeTable` с тем же `TypeError`). После исправления все три теста проходят:

```
python3 -m unittest discover tests -v
test_handler_second_publish_returns_201 ... ok
test_publish_stores_story ... ok
test_publish_with_existing_story_stores_scores ... ok
```

## Как не допустить повтора

1. Источник исправлен: единственная вычисляемая дробная величина в элементе теперь
   `Decimal`.
2. Каждый тест записи, который может зависеть от состояния таблицы, сначала сажает
   одну историю (`seeded_table()`), а потом публикует вторую. Путь с заполненной
   таблицей теперь выполняется в тестах.
3. `tests/fake_dynamo.py` уже отклонял `float` так же, как boto3. Эта проверка
   была правильной; тесты просто не доходили до места, где появлялся `float`.
   Теперь доходят.

Проверка на повтор: если кто-то снова вставит `float` в элемент (например,
`round(x, 4)` без `Decimal`), `FakeTable.put_item` упадёт в тесте сразу, а не в
продакшене на второй публикации.

## Что взято из заметки коллеги

Пригодилось:
- Идея, что путь с пустой таблицей выполняется один раз, а с заполненной —
  постоянно. Отсюда тесты, которые сначала сажают запись, и тест через `handler()`.
- Поиск мест, где вычисляемые значения попадают в словари элементов. В `src/app.py`
  такие места — деления и `round()` внутри `similarity()`. `published_at` — это
  `int(time.time())`, он безопасен.

Не взято:
- «Оценки в целых процентах» — меняет контракт поля `score`. `Decimal` решает ту же
  проблему без смены смысла.
- Интеграционный тест с реальной таблицей DynamoDB и повторная публикация в неё —
  в этом окружении нет доступа к AWS, и публиковать/деплоить по правилам заметки
  нельзя. Проверка выполнена на `FakeTable`, который повторяет проверки boto3.

## Что не менял

`logs/error.log` оставлен как есть — это свидетельство продакшен-сбоя. Ничего не
деплоил и никуда не отправлял.
