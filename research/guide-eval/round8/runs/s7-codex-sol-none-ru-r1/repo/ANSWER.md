# Причины неисправности Intervals.icu

1. Кнопка `Connect Intervals.icu` была обычной ссылкой на `/api/intervals/auth/init`. Переход браузера по ссылке не использует `fetch`-обёртку приложения и не добавляет `Authorization: Bearer ...`. Сервер поэтому отвечал `401`, что прямо видно в `logs/connect-attempt.log`. Теперь кнопка сначала запрашивает URL авторизации через `api()` с токеном приложения, затем открывает полученный URL.

2. В запрос OAuth добавили `CALENDAR:READ` и `CALENDAR:WRITE`. После этого Intervals.icu стал отвечать `400 invalid_request` до экрана согласия; до изменения работал набор `ACTIVITY:WRITE,WELLNESS:READ`. Календарные разрешения в таком виде для этого OAuth-запроса не подходят. Возвращён ранее работавший набор: `ACTIVITY:WRITE,WELLNESS:READ`. Запланированные тренировки записываются как активности.

3. Ответ с токеном у Rivera не содержал ни `expires_in`, ни `refresh_token`, но код назначал ему срок жизни 3600 секунд. Фоновый процесс затем объявлял действующее подключение истёкшим примерно через час. Теперь срок жизни устанавливается только по явному `expires_in` от провайдера. Если провайдер вернёт `401` при запросе wellness, подключение помечается как требующее повторного согласия. Для токенов с явным сроком жизни обновление по `refresh_token` сохранено.

Проверка: `python3 -m unittest -v test_intervals.py` — локальные тесты подключения, callback, срока жизни, обновления и отзыва доступа; `node --check static/app.js`; `git diff --check`. К Intervals.icu и другим внешним сервисам запросы не отправлялись.
