# Intervals.icu: почему не подключается и что исправлено

## Причины

1. **Кнопка Connect всегда отдаёт 401.** Это `<a href="/api/intervals/auth/init">`,
   то есть полная навигация страницы. Браузер не отправляет заголовок
   `Authorization`, который SPA держит в `localStorage` и шлёт только через fetch.
   Бэкенд честно отвечает 401 (`logs/connect-attempt.log`, раздел 1).
   Ручная вставка authorize-ссылки обходила это, но ломалась отдельно (пункт 3).

2. **Authorize-шаг падает с 400 после релиза календаря (2026-10-02).**
   `SCOPES` содержит `ACTIVITY:READ,ACTIVITY:WRITE` и
   `CALENDAR:READ,CALENDAR:WRITE`: каждая область названа дважды, и `:WRITE`
   уже включает `:READ`. Intervals отклоняет такой запрос до экрана согласия
   (`logs/connect-attempt.log`, раздел 2). Тело ответа
   (`{"error":"invalid_request"}`) не называет параметр, поэтому по логам
   точную причину нельзя считать доказанной. Совпадение по времени с релизом
   календаря и заметка коллеги про `Duplicate scope` говорят в пользу этой
   причины.

3. **«Expired, reconnect» через час у T. Rivera — наша ошибка, а не отзыв.**
   Intervals не присылает ни `refresh_token`, ни `expires_in`. Бэкенд
   подставлял `DEFAULT_TOKEN_TTL = 3600` и через час ставил статус
   «expired». Токен при этом ещё был действителен: в ответе лежит
   `scope` и `athlete`, но не срок жизни. Фоновый «refresher» при отсутствии
   refresh-токена просто стирал рабочий токен. Инструкция в тикете
   «вставить ссылку» тоже перестала работать из-за пункта 2.

## Что исправлено

- `server.py`: `POST /api/intervals/auth/init` (аутентифицированный XHR)
  возвращает `{"authorize_url": ...}`. GET-вариант удалён, поэтому его больше
  нельзя открыть как ссылку.
- `static/app.js`: кнопка Connect — `<button>`, по клику делается `api(...)` с
  POST и `window.location.assign(authorize_url)`. Ошибки показываются в карточке.
- `config.py`: `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`. Каждая
  область один раз. `CALENDAR:READ` и `ACTIVITY:READ` убраны: приложение
  календарь не читает. Если на стороне Intervals `:WRITE` не покрывает `:READ`,
  приложение всё равно работает, потому что читается только wellness.
- `server.py`: срок жизни токена не выдумывается. Без `expires_in`
  `expires_at` не задаётся. Фоновый refresher и refresh-логика удалены.
  Токен протухает только по факту: при 401 от Intervals в `wellness`
  соединение переходит в «expired, reconnect» и access token очищается.
  Тогда же статус `disconnected` / `expired` возвращается в `/status`.
- `config.py`: удалён `REFRESH_INTERVAL` вместе с refresher-ом.

## Проверка

Настоящий intervals.icu из песочницы недоступен, поэтому прогонял на локальном
моке, построенном по данным из логов (мок в репозиторий не добавлен):

- `POST /auth/init` без токена → 401; с токеном → `authorize_url` с новым scope.
- Старый набор scope (с повторами) мок отклоняет с 400.
- Authorize → callback → обмен кода → `status`: connected, athlete `i98765`.
- `wellness` → 200 с данными.
- Отзыв на стороне Intervals → `wellness` 401 → 409, `status`
  «expired, reconnect».
- `python3 -m py_compile` и `node --check` проходят.

Не проверено: реальный поток с аккаунтом intervals.icu. Страница форума,
которую удалось открыть, не описывает OAuth-детали (scope, поля токена), так что
правила scope взяты из логов и заметки коллеги.

## Из заметки коллеги

Пригодилось:
- Пункт 1: токен бессрочный, без refresh; «протух» определяем лениво по 401.
- Пункт 2: каждая область один раз, `:WRITE` вместо пары `:READ` + `:WRITE`.
- Пункт 3: `athlete.id` из ответа на обмен кода (уже использовался).
- Пункт 4: init — аутентифицированный POST с JSON `authorize_url`, фронтенд
  делает `window.location.assign`.

Не взято:
- Удаление `grant_type` и `redirect_uri` из обмена кода. Обмен Риверы через
  ту же функцию дал токен, поэтому менять его без доказательств не стал.
- JWT вместо HMAC-`state`. Текущий `state` подписан HMAC, имеет TTL 15 минут
  и проверяется до обмена кода, поэтому замена не нужна.
- Проверка «идентичности аккаунта при переподключении». Атлет может
  законно сменить аккаунт Intervals; это решение продукта.

## Что осталось

- **Токены хранятся в памяти открытым текстом.** Заметка коллеги советует
  шифровать при хранении. Это задача для прод-хранилища (Postgres), здесь не
  сделано.
- **`state` не привязан к сессии браузера.** Злоумышленник с собственным кодом
  Intervals может заставить жертву открыть callback и привязать чужой аккаунт
  Intervals к её tricoach-аккаунту. Стоит добавить nonce в cookie или
  сессию, это отдельная правка.
- **Существующие соединения потеряны.** Хранилище в памяти, после перезапуска
  все атлеты (включая Риверу) переподключаются один раз.
- Коммит не делал, изменения лежат в рабочем дереве.
