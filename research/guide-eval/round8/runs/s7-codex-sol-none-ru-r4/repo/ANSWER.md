# Причины сбоев Intervals.icu

1. Кнопка Connect была обычной ссылкой на `/api/intervals/auth/init`. Переход браузера по ссылке не использует `fetch`-обёртку приложения и не передаёт `Authorization: Bearer`. Сервер поэтому отвечал 401 каждому атлету. Теперь кнопка запрашивает URL авторизации через авторизованный `fetch`, затем переводит браузер на полученный URL.

2. В запрос авторизации добавили `CALENDAR:READ` и `CALENDAR:WRITE`. После этого Intervals стал отвечать `400 invalid_request` до экрана согласия. По журналу точный отвергнутый параметр не назван, но изменение scope совпадает с началом ошибки; прежнее успешное подключение выдало `ACTIVITY:WRITE,WELLNESS:READ`. Запрос возвращён к этому набору: чтение wellness и запись запланированных тренировок как activities.

3. Успешный ответ с токеном Rivera не содержал ни `expires_in`, ни `refresh_token`. Код сам назначал такому токену срок 3600 секунд, после чего помечал соединение как истёкшее. Теперь отсутствие `expires_in` означает, что известного срока нет: фоновое обновление его не трогает. Токены с явным сроком обновляются при наличии refresh token; без него переподключение требуется только после фактического истечения. Если Intervals возвращает 401 при запросе wellness, соединение помечается для переподключения.

Проверено локально: тесты запуска OAuth с bearer-заголовком, callback и статуса через два часа; отдельно проверены токен с явным сроком, refresh и нажатие кнопки в SPA. Реальный запрос к Intervals не выполнялся в соответствии с ограничением на внешние сервисы.
