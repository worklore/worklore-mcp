# Что изменено

**Причина.** В `bot.py` `build_system` отдавал один блок (инструкции + контекст атлета) с одним маркером `cache_control`. `save_fact` меняет список фактов, хеш префикса меняется, и весь промпт (~1000 токенов) пересоздаётся. Это видно в `logs/usage.jsonl`: после `save_fact` `cache_read_input_tokens: 0` и `cache_creation_input_tokens` около 1100.

**Исправление.** `build_system` теперь возвращает два текстовых блока, и у каждого свой `cache_control: ephemeral`:
1. `INSTRUCTIONS` — статический текст. Я проверил, что в нём нет дат, имён и счётчиков.
2. `athlete_context(...)` — дата, профиль, зоны, цель, факты, язык.

Запись в память теперь инвалидирует только второй блок. Первый остаётся в кеше.

Проверку на реальном API я не запускал: ключа нет, и внешние сервисы трогать нельзя. После деплоя смотрите `usage.jsonl`. После `save_fact` `cache_read` должен покрывать статический блок (~780 токенов), а `cache_creation` должен быть около размера хвоста (~240 токенов).

# Что пригодилось из заметки

- **Два сегмента `cache_control`.** Это основа исправления. Статическую часть и хвост я разделил по её схеме.
- **Статический блок без подставленных значений.** Проверил, что `INSTRUCTIONS` стабилен.
- **Не отбирать факты под сообщение.** Так и оставил: в хвост по-прежнему попадают все факты. Лимит в 20 фактов из `NOTES.md` на кеш не влияет.
- **Инструменты стоят выше system в префиксе.** Фильтрацию по ключевым словам и порядок схем не трогал. Набор инструментов постоянен внутри цикла одного сообщения.
- **Читать `usage`.** Логирование уже есть, менять не пришлось.

Пропущено: часть про MCP и Telegram-контекст, потому что к этому коду она не относится. Цифры из заметки (~780 и ~240 токенов) взяты из неё, у нас они примерные.
