# Почему вторая публикация падала с 500

## Причина

`similarity()` в `src/app.py` возвращала Python-float: `round(0.7 * tag_score + 0.3 * word_score, 4)`.
Эти значения попадают в поле `similar` (`[{slug, score}]`) и записываются через `put_item`.
boto3 не сериализует float → `TypeError: Float types are not supported. Use Decimal types instead.`

Первая публикация проходит, потому что таблица пуста: `related()` получает пустой список
и возвращает `[]` — ни одного значения `score`, ни одного float. Ошибка проявляется только
со второй публикации, когда в `similar` появляется хотя бы один score. Баг существовал всегда,
но «пустая таблица» — это единственный случай, который маскировал его. Подтверждение —
`logs/error.log`: первая запись `similar=0 stored`, далее TypeError в `put_item`.

## Исправление

- `src/app.py` — `similarity()` теперь возвращает `Decimal(str(round(..., 4)))`.
  Конвертация на границе (в значении, которое уходит в DynamoDB); `str(...)` нужен,
  чтобы не пронести двоичные артефакты float (`Decimal(0.35)` дал бы `0.3499…97779`).
  Выбран `Decimal`, а не целые проценты — чтобы сохранить текущую точность 4 знака.
- `tests/test_publish.py` — добавлен регрессионный тест `test_publish_into_populated_table`:
  сначала публикуется одна история, затем вторая через `handler`. Теперь путь
  «непустая таблица» (score → запись) выполняется в тесте. До исправления этот тест
  падает с тем же TypeError, что и в проде; после — оба теста зелёные
  (`python3 -m unittest discover tests`). Проверено вручную: три публикации подряд → 201,
  score хранится как `Decimal('0.4333')`.

Весь код, пишущий в DynamoDB, прошерстил на другие источники float (grep по `round(` и `/`) —
других вычисляемых значений в записываемых атрибутах нет (`published_at` — уже `int`).

## Что пригодилось из заметки коллеги

- **Диагноз по симптому** «работает один раз, второй раз 500» и тексту ошибки — совпал точно,
  это сразу навело на `similarity()`.
- **Объяснение, почему первый write проходит**: пустая таблица → пустой `similar` → нет float.
  Это ключ к пониманию, почему тест «одна публикация» ничего не ловил.
- **Шаг «trace every value that feeds a DynamoDB write» + grep по `round(` и `/`** — использован
  как чек-лист, подтвердил, что float-источник один.
- **Идея «конвертировать на границе, в int или Decimal»** — использована; выбран Decimal
  вместо целых процентов, чтобы не терять точность.
- **Главный урок: «the populated path is the real path»** — взят на вооружение: тест на запись
  теперь сидирует таблицу одной записью, и только вторая публикация проверяется.
- **Проверка «publish twice against a real table»** — использована по сути (две-три публикации
  подряд через `handler`), но без реальной AWS-таблицы: `tests/fake_dynamo.py` валидирует
  элементы точно так же, как `boto3.types.TypeSerializer`, поэтому воспроизводит отказ один в один.

Не пригодилось / пропущено: миграция scores на целые проценты (у коллеги — их осознанный
выбор продукта; здесь Decimal точнее и минимально инвазивен) и привязка к AWS Lambda
(сервис здесь не лямбда-специфичен — трейс лога совпал просто по структуре).
