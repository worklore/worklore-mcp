# Разбор поломки интеграции Intervals.icu

Дата: 2026-11-07. Симптомы: кнопка Connect не работает ни у кого (401),
единственное прошедшее подключение через час потребовало переподключения.

## Причины

### 1. Кнопка Connect отдавала 401 всем (сломано для всех, лог §1, тикет #214)

Кнопка в SPA была ссылкой `<a href="/api/intervals/auth/init">`
(`static/app.js`), то есть полной навигацией страницы. Токен сессии
приложения хранится в localStorage и отправляется только обёрткой fetch —
полная навигация заголовок `Authorization` не отправляет. Серверный init
требует авторизацию и потому возвращал 401 каждому.

**Исправление:** init — аутентифицированный `POST`, возвращающий
`{authorize_url}` JSON-ом; SPA вызывает его через fetch-обёртку и делает
`window.location.assign(authorize_url)` (`server.py` `auth_init`, `static/app.js`).

### 2. Authorize URL стал отклоняться 400 после релиза календаря 2026-10-02 (лог §2, тикет #219)

С добавлением календаря в scope (`config.py`) строка стала
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
В Intervals.icu `:WRITE` подразумевает `:READ`; повторное именование одной
области в обоих видах — ошибка `Duplicate scope`, и authorize-шаг отклоняется
с `400 {"error":"invalid_request"}` ещё до экрана согласия. Поэтому перестал
работать даже обходной путь «вставить ссылку руками», сработавший для Rivera
в сентябре.

**Исправление:** каждая область названа один раз:
`ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` (WRITE там, куда пишем —
активности и календарь; READ — только wellness).

### 3. Подключение «истекало» через час (лог §3, тикет #219)

Intervals не присылает ни `refresh_token`, ни `expires_in` (видно в ответе
токена Rivera). Код сам выставлял TTL 3600 с по умолчанию
(`DEFAULT_TOKEN_TTL`) и фоновый поток `refresh_tokens` через час помечал
соединение «expired, reconnect», а так как refresh-токена нет — обновить было
нечем. Токен Intervals бессрочен: он живёт, пока атлет не отзовёт приложение.

**Исправление:** если провайдер не сообщил `expires_in`, соединение хранится
без срока годности; поток-рефрешер удалён вместе с `REFRESH_INTERVAL`.
Отзыв теперь обрабатывается лениво: первый 401 от API очищает сохранённый
токен, статус становится «not connected», UI показывает приглашение
подключиться заново (`server.py` `wellness`, плюс можно расширить на все
вызовы API-клиента `intervals_get`).

### 4. Обмен кода на токен слал лишние поля

`exchange_code` отправлял `grant_type` и `redirect_uri`. У Intervals
`POST /api/oauth/token` принимает только `client_id`, `client_secret`, `code`;
лишние поля рискуют дать отказ на этапе обмена (у нас он зафиксирован не был,
только зафиксирован у коллеги-автора заметки).

**Исправление:** отправляются только три поля. `athlete: {id, name}` из
ответа по-прежнему используется, отдельный запрос «кто я» не нужен.

### 5. Дополнительно: защита от подмены аккаунта при повторном подключении

Раньше callback безусловно перезаписывал соединение. Теперь, если
пользователь уже подключён к одному аккаунту Intervals, а callback пришёл от
другого атлета, он отклоняется с 409, существующее соединение сохраняется.

## Что в заметке коллеги пригодилось

- **П.4 про init как POST** — точное совпадение с нашей причиной №1:
  применено как основной фикс (init → POST + `{authorize_url}` +
  `window.location.assign`).
- **П.2 про «Duplicate scope»** — объяснило причину №2; правило «каждая
  область один раз, WRITE подразумевает READ» применено к `SCOPES`.
- **П.1 про отсутствие refresh_token / бессрочные токены** — объяснило
  причину №3; применено: убрана механика обновления/истечения, добавлена
  ленивая деградация по первому 401.
- **П.3 про обмен кода («стандарт-лайт»)** — применено: убраны `grant_type`
  и `redirect_uri`; заодно подтвердило, что `athlete` в ответе токена — всё,
  что нужно для identity.
- **Замечание про callback без заголовка авторизации и роль state** — в коде
  уже было реализовано (подписанный HMAC state с TTL 15 минут), перенимать
  JWT с `purpose`-claim не понадобилось; наш state уже несёт id
  пользователя и TTL.
- **Защита от несовпадения аккаунтов при повторном подключении** — добавлена
  (п.5 выше).

Часть заметки про шифрование токена при хранении и регистрацию OAuth-клиента
не использована: хранилище в dev-проекте in-memory, регистрация клиента
вне зоны этого репозитория. Шаг «воспроизвести» из заметки стал основой
проверки ниже.

## Проверка

Сквозной тест с локальным моком Intervals.icu (реальный внешний сервис не
задействовался; `INTERVALS_BASE` перенаправлен на `127.0.0.1`). Мок
воспроизводил задокументированное поведение: токен-эндпоинт принимает только
три поля и не возвращает `refresh_token`/`expires_in`, wellness отдаёт 401 для
отозванного токена. 17 проверок прошли:

- старый GET init ушёл (404), POST без токена 401, POST с токеном отдаёт
  authorize URL со scope без повторов областей;
- полный цикл init → callback → status/wellness (302, connected, данные);
- callback от чужого атлета → 409, старое соединение цело;
- подделанный state → 400;
- отозванный токен: wellness → 409, статус disconnected, повторное
  подключение сразу работает;
- соединение не «истекает» искусственно (нет фонового пометчика expiry).
