# Почему атлеты не могли подключить Intervals.icu

Дата разбора: 2026-11-08. В логах (`logs/connect-attempt.log`, `logs/support-tickets.md`)
и коде нашлось четыре причины. Первые две полностью блокировали кнопку Connect у всех,
третья «отключала» через час того, единственного, кто прошёл, четвёртая — защитная правка
по поведению провайдера. Все исправления проверены локальным end-to-end тестом
(обмен кода и API Intervals подменены заглушками, внешних вызовов не было).

## Причина 1. Init-эндпоинт был GET-ссылкой — кнопка не работала ни у кого

Кнопка «Connect Intervals.icu» в SPA была обычной ссылкой
(`<a href="/api/intervals/auth/init">` в `static/app.js`), а эндпоинт требовал
авторизацию по заголовку `Authorization: Bearer`. Полная навигация страницы в
браузере **не отправляет** этот заголовок (SPA держит токен в localStorage и
прикрепляет его только к fetch/XHR), поэтому каждый клик заканчивался 401 и
страницей `{"error": "unauthorized"}`. Это тикет #214 и запись №1 в
`connect-attempt.log` («GET /api/intervals/auth/init 401 (no Authorization
header)»).

Исправление: init — аутентифицированный `POST /api/intervals/auth/init`,
возвращающий `{"authorize_url"}` как JSON; фронтенд вызывает
`window.location.assign(authorize_url)` (`static/app.js`, `server.py` →
`Handler.auth_init` теперь в `do_POST`).

## Причина 2. Дублирующийся scope — authorize отклонялся до consent-экрана

В `config.py` scope был `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,
CALENDAR:READ,CALENDAR:WRITE`. В Intervals.icu `:WRITE` подразумевает `:READ`,
и упоминание одной области дважды отклоняется на шаге authorize с 400
(в наших захватах — телом `{"error":"invalid_request"}`, не говорящим, какой
параметр не нравится). Появилось это после выкатки календарного синка
2026-10-02 — поэтому «прошедший» в сентябре тоже больше не мог пройти по
вручную вставленной ссылке (запись №2 в логе, тикет #219).

Исправление: каждая область ровно один раз —
`ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` (WRITE там, куда пишем,
READ — только для wellness).

## Причина 3. Токену выдумали срок жизни 1 час — «подключитесь заново»

У Intervals.icu в ответе токена нет ни `refresh_token`, ни `expires_in` —
токен живёт, пока атлет не отзовёт приложение в своём UI. Код же при
отсутствии `expires_in` ставил TTL 3600 секунд по умолчанию
(`DEFAULT_TOKEN_TTL`), а фоновый «обновлятель» через час помечал соединение
«expired, reconnect» (запись №3 в логе: Rivera подключился 17:41, в 18:37 —
«token expiry passed and no refresh token on file»). Отсюда и утренний тикет
#219 «Status: expired, reconnect» без всякого отзыва со стороны атлета.

Исправление: срок жизни и вся механика refresh удалены. Токен хранится как
бессрочный; отзыв обрабатывается лениво — первый 401 от API очищает
сохранённое соединение, и интерфейс деградирует до «подключиться заново»
(вместо вечной пересылки ошибки).

## Причина 4 (защитная). Обмен кода слал лишние поля

`exchange_code` отправлял `grant_type=authorization_code` и `redirect_uri`.
Intervals принимает на `POST /api/oauth/token` ровно `client_id`,
`client_secret`, `code`. Лишние поля убраны (обмен у Rivera когда-то проходил,
но поведение зафиксировано как «стандарт-лайт» — не дожидаемся, пока начнёт
мешать). Заодно из ответа используются `athlete.id` / `athlete.name`, отдельный
запрос «кто я» не нужен.

## Что в итоге менялось

- `static/app.js` — кнопка Connect теперь POST + `window.location.assign`.
- `server.py` — init в `do_POST` и отдаёт JSON; `exchange_code` шлёт три поля;
  удалены TTL токена, `refresh_tokens()` и запуск потока; при 401 от API
  соединение очищается, wellness отвечает 409.
- `config.py` — scope без дублей; убран `REFRESH_INTERVAL`.

## Какие части заметки коллеги пригодились

Все четыре наблюдения из заметки подтвердились логами и были применены:

1. «Токен никогда не истекает и никогда не обновляется; обрабатывайте отзыв
   лениво при первом 401» — легло в причину 3 и в обработчик wellness.
2. «Duplicate scope: `:WRITE` подразумевает `:READ`» — причина 2, состав scope.
3. «Обмен кода — стандарт-лайт: только client_id, client_secret, code;
   в ответе сразу athlete» — причина 4.
4. «Init-эндпоинт должен быть аутентифицированный POST, возвращающий
   {authorize_url}; навигация страницы теряет Authorization» — причина 1.

Не понадобилось: формат state как JWT с claim `purpose` (у нас уже была
эквивалентная подписанная строка `user_id:timestamp:sig` с HMAC и TTL 15
минут — оставили), правило «отклонять reconnect при несовпадении id атлета»
(у нас одно соединение на пользователя, перезапись допустима), `SETTINGS:WRITE`
из примерного scope (приложению не нужен).

## Проверка

Локальный прогон (см. итог в истории команд): 16 проверок — POST init без
токена 401 / с токеном 200 и URL без дублей scope; протухший и подделанный
state → 400; полный flow до 302; status connected; wellness 200 → после
«отзыва» 401 → 409 и disconnected; обмен шлёт ровно три поля. Все прошли.
Живой прогон против intervals.icu в этой среде не выполнялся (правила
запрещают внешние вызовы) — стоит пройти поток реальным аккаунтом на стейдже,
включая сценарий «отозвать приложение в UI Intervals → wellness → предложение
переподключиться».
