# Реализация аналитики событий воронки регистрации

Все события аналитики из `docs/EVENTS.md` были реализованы на экранах регистрации (`RegistrationScreen`) и списка предложений (`OfferScreen`) через класс `Analytics.capture`.

## 1. Что было сделано

### Экран регистрации (`lib/screens/registration_screen.dart`)
1. **`registration_email_started`**:
   - Отправляется при первом вводе символа в поле ввода Email (`onChanged` у `TextField`).
   - Используется флаг `_emailInputFired`, предотвращающий повторные отправки при каждом нажатии клавиши.
   - PII (сам email) не передаётся.
2. **`registration_phone_started`**:
   - Отправляется при первом вводе символа в поле ввода телефона (`onChanged` у `TextField`).
   - Используется флаг `_phoneInputFired`, предотвращающий отправку на каждое нажатие клавиши.
   - PII (номер телефона) не передаётся.
3. **`loan_amount_changed`**:
   - Передаётся свойство `amount` (тип `int`, округленное значение `v.round()`).
   - Отправка перенесена в коллбек слайдера `onChangeEnd`, чтобы событие отправлялось один раз при отпускании ползунка, а не на каждый шаг движения (`onChanged` остался только для обновления UI).
4. **`terms_accepted`**:
   - Отправляется в `onChanged` у `CheckboxListTile`, когда пользователь устанавливает флажок (`newValue && !_terms`).
5. **`registration_continue_tapped`**:
   - Отправляется в коллбеке кнопки `FilledButton.onPressed` перед переходом на экран предложений.
   - Передаются свойства:
     - `amount` (тип `int`) — выбранная сумма займа (`_amount.round()`).
     - `terms` (тип `bool`) — состояние принятия условий (`_terms`).

### Экран списка предложений (`lib/screens/offer_screen.dart`)
6. **`offers_scrolled`**:
   - Обернут `ListView.builder` в `NotificationListener<ScrollEndNotification>`.
   - Событие отправляется по завершении прокрутки с передачей свойства:
     - `offset` (тип `double`) — текущее смещение списка (`notification.metrics.pixels`).
   - Использование `ScrollEndNotification` вместо слушателя каждого изменения скролла защищает от лавинообразной отправки событий при непрерывной прокрутке.

---

## 2. Какие части из заметки коллеги пригодились

Из заметки коллеги о проблеме перерасхода квоты событий в PostHog пригодились следующие рекомендации:

1. **Флаги однократного срабатывания для текстовых полей (пункт 2 заметки):**
   - Добавлены флаги `_emailInputFired` и `_phoneInputFired` в состояние экрана `_RegistrationScreenState`.
   - Проверка `if (!_<field>InputFired)` внутри `onChanged` гарантирует, что события `registration_email_started` и `registration_phone_started` отправляются ровно один раз за визит на экран при первом вводе, а не на каждый keystroke.

2. **Использование `onChangeEnd` для слайдера (пункт 5 заметки):**
   - Перенос отправки события `loan_amount_changed` из `onChanged` в `onChangeEnd` слайдера `Slider`. Это позволило отправлять выбранную сумму займа один раз при завершении перемещения ползунка, сохранив обновление UI в `onChanged` без спама событиями.

3. **Слушатель завершения скролла `ScrollEndNotification` (пункт 6 заметки):**
   - Для события `offers_scrolled` был использован `NotificationListener<ScrollEndNotification>` вместо слушания каждого шага скролла (`ScrollUpdateNotification` или `ScrollController.addListener`), что обеспечивает отправку `offset` только в момент остановки прокрутки пользователем.

4. **Сохранение точных названий событий и типов свойств (пункт 7 заметки):**
   - Все имена событий (`snake_case`) и свойства (`amount: int`, `terms: bool`, `offset: double`) в точности соответствуют спецификации `docs/EVENTS.md`.

*(Остальные части заметки, такие как отслеживание потери фокуса через `FocusNode` для передачи валидности/финального значения или отладка через `PostHogConfig.debug`, не потребовались, так как по спецификации события ввода не требуют финальных значений).*
