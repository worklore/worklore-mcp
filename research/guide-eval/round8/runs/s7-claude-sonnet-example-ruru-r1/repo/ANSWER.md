# Почему не подключался Intervals.icu — причины и исправления

## Причины (три независимые поломки)

1. **Кнопка Connect не работала ни у кого.** Кнопка была ссылкой `<a href="/api/intervals/auth/init">`
   на GET-эндпоинт. Полная навигация браузера не отправляет заголовок `Authorization`
   (токен лежит в localStorage и добавляется только fetch-обёрткой), поэтому сервер отвечал 401
   `{"error":"unauthorized"}` (logs/connect-attempt.log №1, тикет #214).
2. **Authorize URL отклонялся (400 `invalid_request`) даже при ручной вставке ссылки.**
   В `SCOPES` были `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`: `:WRITE`
   уже включает `:READ`, а повтор области Intervals не принимает (это «Duplicate scope»).
   Сломалось 2026-10-02, когда добавили календарь (тикет #219). Тело ответа не называет параметр,
   поэтому в логах причина не видна. Это вывод по заметке коллеги и по совпадению дат; на живом
   Intervals я не проверял.
3. **Подключение «протухало» через час.** Intervals не отдаёт ни `refresh_token`, ни `expires_in`:
   токен живёт до отзыва. Код подставлял `DEFAULT_TOKEN_TTL=3600`, а фоновый `refresh_tokens`
   через час помечал соединение «expired, reconnect» и стирал рабочий токен (лог Rivera:
   17:41 подключение, 18:37 «expired»; в Intervals приложение осталось в списке, то есть токен не отзывали).

Дополнительно: обмен кода на токен слал лишние `grant_type` и `redirect_uri`. Intervals нужны
только `client_id`, `client_secret`, `code`. Это по заметке коллеги; в логах нет случая, который
показал бы, что лишние поля ломают обмен, но я привёл запрос к описанному виду.

## Что изменено

- `server.py`: `auth/init` теперь аутентифицированный **POST**, возвращает JSON `{authorize_url}`.
- `static/app.js`: кнопка делает `api(..., {method:"POST"})` и `window.location.assign(authorize_url)`.
- `config.py`: `SCOPES = ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` (без дублей; прочитать календарь
  по-прежнему можно, `:WRITE` включает `:READ`).
- Обмен кода: только `client_id`, `client_secret`, `code`.
- Убраны искусственный TTL, `expires_at` и фоновый refresher. Токен бессрочный. При 401 от Intervals
  (`/wellness`) токен очищается, статус становится «revoked, reconnect», пользователь видит приглашение
  подключиться заново.
- `state` теперь содержит claim `purpose=intervals_oauth` (проверяется в callback).
- При повторном подключении callback отклоняет (409) другой athlete id, если на файле уже есть иной.

## Какие части заметки пригодились

- Пригодились: п.1 (нет refresh_token/expires_in, ленивая обработка отзыва по 401), п.2 (Duplicate scope),
  п.3 (упрощённый обмен кода, athlete в ответе), п.4 (init как POST + JSON, state несёт идентичность,
  purpose, защита от несовпадения аккаунтов).
- Не применено: подписанный JWT для `state` (оставлен имеющийся HMAC-state с TTL 15 минут и purpose,
  работает так же и без зависимостей); шифрование токена при хранении (здесь in-memory хранилище,
  в проде шифровать нужно); регистрация OAuth-клиента на форуме Intervals (внешнее действие, не делалось);
  проверка на реальном аккаунте Intervals и отзыв приложения (нет доступа к внешним сервисам).

## Проверка

Локально проверено только то, что `POST /api/intervals/auth/init` с Bearer-токеном возвращает JSON с
authorize URL без дублей scope, а GET на этот путь больше не обслуживается. Сквозной поток с реальным
Intervals.icu не проверялся.
