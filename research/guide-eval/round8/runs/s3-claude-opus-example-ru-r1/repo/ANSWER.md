# Почему nightly-review молчал

## Что показали факты

- `launchctl-print.txt`: `runs = 6`, `last exit code = 1`. Агент загружен 12.10,
  снимок сделан 18.10 в 09:10. Это шесть ночей в 02:30 (13–18.10), так что
  **launchd срабатывал каждую ночь**. Задача запускалась, но каждый раз падала.
- `Library/Logs/nightly-review.err` — шесть одинаковых пар строк:
  ```
  Not logged in · Please run /login
  /Users/vk/bin/nightly-review.zsh:19: read-only variable: status
  ```

## Причины (их две, одна поверх другой)

1. **`claude` под launchd не видит логин: "Not logged in".** В окружении
   задачи (`environment` в launchctl print) есть только `PATH` и
   `XPC_SERVICE_NAME`, а `USER` нет. CLI ищет свою учётную запись в связке
   ключей по имени пользователя и без `USER` её не находит. Поэтому ревью
   падает сразу с кодом 1, и `$OUT` получается пустым.
2. **`status=$?` убивал скрипт до отправки уведомления.** В zsh `status` —
   встроенная read-only переменная (синоним `$?`). Присвоить ей значение
   нельзя: это фатальная ошибка, скрипт тут же завершается с кодом 1. Строка 19
   стояла между вызовом `claude` и `notify.sh`. В итоге сначала падало ревью, а
   потом погибал и код, который должен был сообщить об ошибке. Отсюда полная
   тишина: ни сводки, ни сообщения о сбое. Сам `notify.sh` ни разу не
   вызывался (при ручном запуске он работает).

## Что исправлено

`Library/LaunchAgents/com.vk.nightly-review.plist`
- В `EnvironmentVariables` добавлены `USER=vk` и `HOME=/Users/vk` (лечит
  "Not logged in"), а также `LANG=en_US.UTF-8`, чтобы zsh обрезал текст по
  символам, а не по байтам: для Telegram нужен валидный UTF-8.

`bin/nightly-review.zsh`
- `status=$?` заменён на `rc=$?` (с комментарием, почему так).
- Промпт передаётся через stdin (`print -r -- "$PROMPT" | claude -p ...`).
  Многострочного аргумента больше нет, и claude не может зависнуть, ожидая
  stdin.
- Добавлен страховочный `trap ... EXIT`: при любом незапланированном выходе
  (ошибка zsh и т.п.) всё равно уходит сообщение «FAILED unexpectedly».
  Я проверил, что в zsh этот trap срабатывает даже на `read-only variable`.
- Код возврата 0 больше не считается успехом сам по себе: пустой вывод тоже
  отправляется как FAILED.
- В лог пишутся время запуска, `USER`/`HOME`, код возврата, длительность и
  размер вывода. Длительность попадает и в сообщение: ревью, которое заняло
  пару секунд, почти наверняка ничего не сделало.
- stderr claude сохраняется в отдельный файл за день, и его последние строки
  попадают в сообщение о сбое. Например, «Not logged in» вы увидите прямо в
  Telegram.
- Попутный баг: промпт просит сводку **в конце**, а скрипт отправлял
  `head -c 300`, то есть начало. Теперь отправляются последние строки,
  обрезанные по символам.
- Если упал сам `notify.sh`, это пишется в лог, а скрипт завершается с
  ненулевым кодом.

`bin/notify.sh`
- `curl --fail-with-body --max-time 30`. Раньше ошибка Telegram API
  (неверный токен, плохой текст, HTTP 4xx) молча считалась успехом, потому
  что `-sS` без `-f` возвращает 0. Теперь это ненулевой выход, а ответ
  Telegram пишется в stderr.

## Как проверено (локально, без отправки куда-либо)

`plutil -lint`, `zsh -n`, `bash -n` проходят. Затем скрипт прогнан во временном
HOME с подставными `claude` и `notify.sh` (пишет в файл):
успех → «done» со сводкой из конца файла, exit 0; «Not logged in» → FAILED с
текстом ошибки, exit 1; пустой вывод → FAILED, exit 1; нет репозитория →
FAILED; намеренно вставленный `status=1` → «FAILED unexpectedly» через trap.
Временные файлы удалены.

## Что сделать на настоящей машине (я этого не делал)

```sh
launchctl bootout gui/$UID/com.vk.nightly-review
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl kickstart -k gui/$UID/com.vk.nightly-review
launchctl print gui/$UID/com.vk.nightly-review | grep -E 'runs|last exit'
```
После этого проверьте: `last exit code = 0`, есть свежий непустой
`~/Library/Logs/nightly-review-<дата>.md`, в `.err` записана правдоподобная
длительность (не пара секунд), сообщение пришло в Telegram. Потом один раз
сломайте что-нибудь нарочно (например, временно переименуйте репозиторий) и
убедитесь, что пришло сообщение FAILED.

Если «Not logged in» останется и с `USER` (например, связка ключей
заблокирована в 02:30), запасной путь такой: `claude setup-token` и
`CLAUDE_CODE_OAUTH_TOKEN` в окружении задачи. Хранить токен лучше не в
plist открытым текстом. Та же оговорка про заблокированную связку ключей
касается `security find-generic-password` в `notify.sh`.

## Какие части заметки коллеги пригодились

- **Пригодилось:** «сначала докажи, что задача запускалась» (`launchctl print`,
  `runs`/`last exit code`) и «прочитай StandardErrorPath, прежде чем строить
  теории». Именно так и нашлись обе причины.
- **Пригодилось, совпало один в один:** `status=$?` в zsh как read-only
  переменная, стоящая между сбоем и уведомлением; замена на `rc=$?`.
- **Пригодилось:** ловушка из поправки к заметке (Mihai Perdum): без `USER` в
  `EnvironmentVariables` CLI не находит логин в keychain и пишет
  «Not logged in». Это ровно первая строка нашего лога.
- **Пригодилось как профилактика:** передавать промпт через stdin / не
  оставлять claude ждать stdin; «код 0 ≠ работа сделана», проверять реальный
  результат и длительность; ставить уведомление о сбое как можно ближе к
  началу пути ошибки и проверять его намеренной поломкой.
- **Не пригодилось:** ошибка «Input must be provided either through stdin or as
  a prompt argument» — в нашем логе её нет, промпт как аргумент доходил.
  Переход на stdin сделан не ради неё, а для надёжности. Время задачи (16:50) и
  прочие детали случая коллеги к нам не относятся.
