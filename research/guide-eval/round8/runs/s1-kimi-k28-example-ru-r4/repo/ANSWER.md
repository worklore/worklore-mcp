# Ответ: почему коридоры пульса обрезались и что исправлено

## Причина

Генератор отправлял HR-таргет как `{"units": "%lthr", "value": <low>, "end": <high>}`.
Пара ключей `value`+`end` — это режим Lap-HR/zone-mapped: Intervals при FIT-экспорте
прикладывает «зоновую» цель, и часы подменяют коридор границами собственных
авто-детектированных зон (LTHR 168). Поэтому на часах всегда появлялись полосы
118–137 / 151–162 / 137–151 — ровно зоны Z2/Z4/Z3 часов, а не запланированные
коридоры (таблица в `readback/watch-notes.md` совпадает с зонами часов построчно).
Сам API данные принимал без ошибок — `workout_doc.steps` в readback заполнен, —
проблема была не в схеме, а в режиме экспорта.

## Что изменил

`gen.py`, функция `hr_target` (gen.py:10): нижняя граница коридора теперь
`start` вместо `value`:

```python
return {"units": "%lthr", "start": lo, "end": hi}
```

Ключ `start` переключает FIT-экспорт в режим Instant-HR: коридор остаётся сырым
диапазоном bpm, который Intervals считает от своего LTHR (172) при экспорте.
Часы покажут 117–129 / 151–160 / 129–141 / 112–124 — запланированные коридоры,
независимо от собственных зон и LTHR часов. Одно слово в одном месте, плюс
комментарий у функции, чтобы ключ не «починили» обратно. Единицы оставил
`%lthr` (проценты, не абсолютные bpm) — конвертацию Intervals делает сам.

## Проверка

`python3 gen.py plans/tempo-run.json` → diff с `readback/event-184233-as-sent.json`:
отличаются только четыре ключа `value` → `start`, остальное байт-в-байт совпадает.
Реальный пуш и синхронизацию часов не выполнял — по условию ничего наружу не
отправляем; проверка по генерации и сопоставлению с readback-таблицей.

## Что пригодилось из заметки коллеги

- **Главная зацепка — `start` вместо `value`.** Точное попадание: одно слово
  меняет режим FIT-экспорта (zone-mapped → Instant-HR). Это и был фикс.
- **Диагностический метод «UI → readback».** Полезен как объяснение, почему
  `workout_doc.steps` заполнен, а на часах всё равно мусор: API принимает
  payload, а режим экспорта определяется формой таргета. Здесь, в отличие от
  случая коллеги, опыт через UI не потребовался — симптом (зоновые полосы)
  уже однозначно указывал на zone-mapped режим.
- **Описание уже провалившихся попыток** (`units: "bpm"` → невозможные
  214–249; `start_bpm`/`end_bpm` → константа 101) совпало с нашими ранними
  пробами из watch-notes — подтвердило, что это те же грабли и дальше по
  этим путям идти не надо.
- **Ловушка с выпадающим списком единиц в UI** («absolute bpm impossible») —
  не пригодилась: мы и так держим проценты LTHR, менять единицы не требовалось.
- **Бонус-трап про top-level `description` в текстовой грамматике** (`m` = минуты,
  дистанция `mtr`/`km`, голое `Z2` = мощность, цифры в начале метки съедаются)
  применять не стал: наш симптом — коридоры на часах, а не невидимые шаги в
  веб-UI, и без возможности кругового теста хрупкая грамматика рискует обнулить
  оба представления. Если позже понадобится рендер шагов в веб-UI — это
  отдельная задача с осторожной грамматикой описания.
