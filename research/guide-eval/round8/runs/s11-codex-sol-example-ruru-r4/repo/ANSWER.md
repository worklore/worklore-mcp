# Почему вторая публикация возвращала 500

Первая история сохранялась с пустым `similar`: в таблице ещё не было историй для сравнения. При второй публикации `related()` вызывала `similarity()`, а та вычисляла оценку через `/` и возвращала Python `float`. В `similar[].score` этот `float` попадал в `table.put_item(Item=item)`. Сериализатор boto3 не поддерживает `float` в элементах DynamoDB, что подтверждает `TypeError` в `logs/error.log`; обработчик превращал исключение в HTTP 500.

# Исправление

Оценка сходства теперь вычисляется целиком в `Decimal`, включая дроби и веса, и остаётся в прежней шкале от 0 до 1 с округлением до четырёх знаков. Поэтому в сохраняемом `similar[].score` не появляется `float`. Добавлен регрессионный тест: он публикует две истории через `handler`, проверяет оба ответа 201, наличие второй записи и тип её оценки. `FakeTable` отклоняет `float` так же, как сериализатор boto3.

Проверка: `python3 -m unittest discover tests -v` — 2 теста прошли. Внешние сервисы не использовались.

# Что пригодилось из заметки коллеги

Пригодились объяснение зависимости ошибки от уже существующих данных, поиск вычисляемого значения в записываемом элементе и проверка записи после заполнения таблицы. Совет заменить оценку целым процентом не применялся: это изменило бы формат и точность поля `score`, поэтому выбран `Decimal`. Проверка публикацией в реальную таблицу не проводилась из-за запрета на внешние сервисы; вместо неё использован локальный `FakeTable`.
