# Intervals.icu: почему не подключались атлеты и что исправлено

## Причины

### 1. Кнопка Connect: 401 у всех (тикет #214, лог §1)
Кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`. При переходе по ссылке
браузер загружает страницу целиком и не отправляет заголовок `Authorization: Bearer …`:
токен лежит в `localStorage` и подставляется только fetch-обёрткой SPA. Поэтому
`require_user()` отвечал 401 `{"error": "unauthorized"}` (в логе видно: `401 (no Authorization header)`).

**Исправление:** `/api/intervals/auth/init` теперь `POST` (`server.py`, `do_POST` → `auth_init`).
Он возвращает JSON `{authorize_url}`, а не 302. В `static/app.js` кнопка вызывает его через `api()`,
затем делает `window.location.assign(authorize_url)`. Старый `GET` убран, теперь отдаёт 404.

### 2. Вставленная вручную ссылка: 400 `invalid_request` (лог §2)
С 2026-10-02 запрашиваемый scope такой:
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`, то есть области
ACTIVITY и CALENDAR указаны дважды. У Intervals `:WRITE` уже включает `:READ`, а повтор одной
области отклоняется («Duplicate scope»; здесь тело ответа общее, `invalid_request`).

**Исправление** (`config.py`): `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`. Каждая
область указана один раз. Права те же: чтение wellness, плюс чтение и запись активностей и календаря.

> Оговорка: по логам эту причину нельзя подтвердить на 100%. Тело 400 не называет параметр,
> а в git нет истории, по которой видно, был ли повтор `ACTIVITY:READ,ACTIVITY:WRITE` ещё в
> сентябре, когда подключение Rivera прошло. Но scope менялся только в этом месте, и сломалось
> всё именно после добавления календаря. `client_id`, `redirect_uri` и `state` не менялись, и
> без них ошибка та же (лог §2). Проверить окончательно можно только на настоящем Intervals:
> открыть новую authorize-ссылку и увидеть экран согласия.

### 3. Rivera «expired, reconnect» через час (тикет #219, лог §3)
Ответ Intervals на обмен кода не содержит ни `expires_in`, ни `refresh_token`: токен бессрочный,
действует до отзыва приложения атлетом. Код в таком случае сам подставлял
`DEFAULT_TOKEN_TTL = 3600`. Через час фоновый `refresh_tokens()` не находил refresh-токен, стирал
`access_token` и ставил статус `expired, reconnect`. Intervals здесь ни при чём: «срок» придумали
мы сами.

**Исправление** (`server.py`): если `expires_in` нет, `expires_at = None`, и рефрешер такие
соединения пропускает. Отзыв доступа обнаруживается по факту: если Intervals ответил 401 на
`/wellness`, токен стирается, статус ставится `revoked, reconnect`, и UI предлагает подключиться
заново.

### Сопутствующие мелочи
- Callback обрабатывает `?error=…` от Intervals (например, атлет нажал «Отказать»): вместо
  «bad state or code» он перенаправляет на `/?intervals_error=…`, и SPA показывает ошибку.
- Защита от смены аккаунта при переподключении. Если у пользователя уже записан другой
  `athlete.id`, callback отклоняется (`account_mismatch`). Чтобы сменить аккаунт, нужно сначала
  нажать Disconnect.
- Если в ответе на обмен нет `athlete.id`, соединение не сохраняется: этот id нужен в каждом
  пути API.

### Что сделать после выкладки (вручную, я не делал)
- У Rivera и у всех, кто попал в `expired, reconnect`, `access_token` уже стёрт. Им нужно один
  раз переподключиться, теперь кнопка работает.
- Токены бессрочные, поэтому в prod-таблице их стоит хранить зашифрованными (в этом
  dev-сервере хранение в памяти, его я не трогал).

## Проверка
Локальный мок Intervals (`INTERVALS_BASE=http://127.0.0.1:8799`), весь поток через curl:
`GET init` → 404; `POST init` → `authorize_url` с новым scope; callback → 302 `/?connected=1`,
статус «connected», в логе `no expiry, valid until revoked`; `/wellness` → данные; после «отзыва»
(мок отдаёт 401) → 409 `revoked, reconnect`, статус `revoked, reconnect`; `callback?error=access_denied`
→ `/?intervals_error=access_denied`. Против настоящего intervals.icu я не проверял: нет
настоящего client_id/secret, и внешние сервисы трогать нельзя.

## Что пригодилось из заметки коллеги
- **п.4 (init должен быть POST, а не ссылка):** ровно наша причина №1, решение взято оттуда.
- **п.2 («Duplicate scope», `:WRITE` включает `:READ`):** объясняет причину №2, правило
  применено к нашему scope. Их набор scope я не копировал: `SETTINGS:WRITE` нам не нужен.
- **п.1 (нет `refresh_token`/`expires_in`, токен до отзыва, отзыв ловить по 401, шифровать):**
  объясняет причину №3, ленивую обработку 401 я взял. Шифрование оставил как рекомендацию для prod.
- **п.3, частично:** пригодилось, что в ответе приходит `athlete: {id, name}`. Совет слать только
  `client_id/client_secret/code` без `grant_type`/`redirect_uri` **не применял**: у Rivera обмен с
  этими полями прошёл успешно (лог §3), значит они не мешают, и менять работающее незачем.
- **`state` как подписанный JWT с `purpose`:** не понадобилось. У нас уже есть HMAC-подписанный
  `state` с TTL 15 минут, по сути он делает то же самое. Защиту от смены аккаунта при
  переподключении взял.
- Раздел «Reproduce this» и ссылку на форум для регистрации клиента пропустил: клиент уже
  зарегистрирован, а внешние действия по условиям задачи запрещены.
