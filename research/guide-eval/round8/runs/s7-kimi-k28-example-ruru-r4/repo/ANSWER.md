# Почему ломалось подключение Intervals.icu — причины и исправления

Интеграция ломалась в трёх независимых местах; каждое закрывало своё
проявление из `logs/connect-attempt.log` и `logs/support-tickets.md`.

## Причина 1 — кнопка Connect открывала init-эндпоинт обычной ссылкой

**Симптом:** 401 `{"error": "unauthorized"}` у всех, кто нажимал кнопку
(тикет #214, лог №1). SPA хранит токен входа в `localStorage` и добавляет
заголовок `Authorization` только обёртка `fetch`. Кнопка была
`<a href="/api/intervals/auth/init">` — полная навигация страницы **не**
отправляет этот заголовок, поэтому `require_user` отвечал 401 каждому.

**Исправление:** `POST /api/intervals/auth/init` (аутентифицированный)
возвращает `{authorize_url}` JSON, фронтенд уводит браузет через
`window.location.assign(authorize_url)`. Старый GET маршрут убран.
(`server.py` — `do_POST`/`auth_init`, `static/app.js` — обработчик кнопки.)

## Причина 2 — «Duplicate scope»: 400 `invalid_request` на шаге authorize

**Симптом:** после релиза calendar sync (2026-10-02) даже вручную
собранная authorize-ссылка стала отдавать 400 до экрана согласия
(тикет #219, лог №2). `SCOPES` содержал `ACTIVITY:READ,ACTIVITY:WRITE` и
`CALENDAR:READ,CALENDAR:WRITE`. В Intervals.icu `:WRITE` подразумевает
`:READ`, и повторное название одной области отклоняется — поэтому раньше
(когда календаря в scope не было) ссылка работала, а после релиза перестала.

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"` —
каждая область не больше одного раза; покрывает чтение wellness и запись
активностей/календаря (`config.py`).

## Причина 3 — соединение «истекало» через час (T. Rivera)

**Симптом:** Rivera подключился 2026-09-19, wellness пришёл вечером, а через
час карточка перешла в «expired, reconnect» (тикет #219, лог №3). В ответе
токена Intervals.icu **нет** ни `refresh_token`, ни `expires_in` — access
token живёт, пока атлет не отзовёт его в UI. Сервер ставил TTL по умолчанию
3600 с и фоновый поток помечал соединение истёкшим; refresh-грант не нужен
провайдеру в принципе.

**Исправление:** у соединения убран `expires_at`, фоновый refresher
удалён. Отзыв токена обрабатывается лениво: при первом 401 от API токен
очищается (`mark_expired`), статус — «expired, reconnect», UI снова
показывает кнопку подключения (`server.py`).

**Заодно:** обмен кода приведён к поведению провайдера — в
`POST /api/oauth/token` уходят только `client_id`, `client_secret`, `code`
(`grant_type` и `redirect_uri` убраны; с ними раньше тоже работало, но
провайдер их не требует).

## Что пригодилось из заметки коллеги

- **Пункт 4 (init — POST, возвращает `{authorize_url}`)** — точное совпадение
  с причиной 1, стал основным исправлением. Заодно подтвердил, что идентификация
  пользователя в callback через `state` — правильное решение (у нас уже так).
- **Пункт 2 (Duplicate scope)** — диагноз причины 2 и правило «каждая область
  один раз».
- **Пункт 1 (нет refresh_token, токен бессрочен, ленивая обработка отзыва по
  401)** — диагноз и лечение причины 3.
- **Пункт 3 (обмен кода тремя полями, `athlete` в ответе)** — убраны лишние
  поля из обмена; `athlete{id,name}` из ответа и раньше использовался.

## Что из заметки не пригодилось

- **JWT-`state` с claim `purpose`** — существующий HMAC-подписанный `state`
  с `user_id` и TTL 15 минут уже работал и не был причиной сбоя.
- **Защита от несовпадения аккаунта при повторном подключении** — для
  восстановления интеграции не требовалась.
- **`SETTINGS:WRITE` из примера scope** — этому приложению не нужен.
- **Шифрование токена при хранении** — для in-memory dev-стора вне объёма
  задачи (в prod стоит сделать отдельно).

## Проверка

Интеграционный прогон полного потока против локального stub'а вместо
intervals.icu (внешние сервисы не вызывались), 17 проверок, все зелёные:

- `POST /api/intervals/auth/init` с токеном → 200 и `authorize_url`;
  scope без повторов областей; без токена → 401; старый GET → 404.
- callback с валидным `state` → обмен кода ровно тремя полями → 302 на
  `/?connected=1`; подделанный `state` → 400.
- status/wellness работают, в wellness уходит `Authorization: Bearer …`.
- Отзыв токена на стороне провайдера → wellness отдаёт 401 с «reconnect»,
  status переходит в «expired, reconnect», повторное подключение проходит
  end-to-end.

Заодно: `python3 -m py_compile server.py config.py`, `node --check static/app.js`.
