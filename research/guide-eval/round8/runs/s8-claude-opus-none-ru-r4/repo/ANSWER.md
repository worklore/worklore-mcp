# Кеширование системного промпта после save_fact

## В чём была проблема

Видно по `logs/usage.jsonl`: сразу после каждого `save_fact` идёт `cache_read_input_tokens: 0`
и `cache_creation_input_tokens` ~1000+. Причин две.

1. **Весь системный промпт был одним блоком с одним `cache_control`** (`build_system`):
   статические `INSTRUCTIONS` + профиль + дата + список фактов. Кеш промптов работает по
   точному совпадению префикса, поэтому новый факт в конце блока менял весь закешированный
   префикс, и ~1000 токенов инструкций каждый раз записывались в кеш заново.
2. **Системный промпт собирался заново в каждом раунде tool-loop** (`build_request(a, ...)`).
   `run_tool("save_fact")` меняет `a.facts`, и уже следующий раунд *того же* сообщения
   (round 2) получал новый system и промахивался мимо кеша. Именно это видно в логе:
   `tool: save_fact` → следующая строка `round 2` с `cache_creation`.

## Что изменено (bot.py)

- `athlete_context` разделена на две функции:
  - `athlete_profile(a)`: имя, вид спорта, зоны, цель, язык. Это поля, которые ни один
    инструмент не меняет;
  - `athlete_memory(a, today)`: дата и долговременные факты, то есть всё, что меняется.
- `build_system` теперь возвращает **два блока, у каждого свой `cache_control`**:
  1. `INSTRUCTIONS` + профиль. Этот блок не меняется ни при `save_fact`, ни при смене дня,
     поэтому продолжает читаться из кеша;
  2. дата + факты. Он маленький (десятки токенов), и после `save_fact` перезаписывается
     только он.
  Дата раньше тоже лежала внутри единственного блока и раз в сутки сбрасывала кеш целиком.
  Теперь она во втором блоке.
- `reply()` собирает `system` **один раз на сообщение** и передаёт его во все раунды
  (`build_request(system, messages, tools)`). Модель и так видит сохранённый факт в
  `tool_use`/`tool_result` текущего диалога, а в system он попадёт со следующего сообщения.
- README: обновлён абзац про кеширование.

Фильтрацию инструментов по ключевым словам не трогал (см. NOTES.md).

## Проверка

Сеть не использовал, API не вызывал. Прогнал локально `reply()` с фейковым LLM и
временной копией `athletes.json`, реальные данные и лог не менялись. Сообщение с
`save_fact`, затем следующее сообщение:
- раунды 1 и 2 одного сообщения получают побайтно одинаковый `system`;
- первый блок (инструкции + профиль) до и после `save_fact` совпадает побайтно;
- меняется только второй блок, и новый факт в нём есть.

## На что обратить внимание после выката

- **Минимальная длина кешируемого префикса.** У Sonnet 4.5 это 1024 токена, и считается
  весь префикс до маркера: определения tools + первый блок system. По логам весь прежний
  промпт был ~1024–1100 токенов, так что префикс до первого маркера по моей оценке
  (локально, без токенайзера) получается около 950–1000 токенов, то есть на границе или
  чуть ниже. Если он окажется короче 1024, первый маркер API молча проигнорирует.
  **Регрессии при этом не будет:** второй маркер стоит в конце system, и кеш работает
  ровно как раньше (плюс остаётся исправление пункта 2). Проверить можно через
  `messages.count_tokens` или по логу: в первом раунде после `save_fact` должно быть
  `cache_read_input_tokens` ≈ размер статической части и маленький `cache_creation`.
  Если там 0, статическую часть нужно сделать длиннее 1024 токенов, например перенести
  туда стабильный текст или всегда отправлять полный набор tools. Это решение по продукту,
  без измерения я его принимать не стал.
- **Tools стоят в префиксе раньше system.** Сообщение с другим набором инструментов
  (`plan_week`/`predict_race`) — это другой префикс и отдельная запись в кеш (в логе
  строки с 1305/1334). Это не связано с памятью и осталось как было.
