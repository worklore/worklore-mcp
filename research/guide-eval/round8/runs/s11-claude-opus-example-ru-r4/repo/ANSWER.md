# Почему вторая публикация возвращает 500

## Причина

`publish()` (`src/app.py`) перед записью делает `scan` таблицы и для каждой уже
существующей истории считает `similarity()`. Эта функция возвращает
`round(0.7 * tag_score + 0.3 * word_score, 4)`, то есть **`float`**. Результат
попадает в `item["similar"][i]["score"]`, а boto3 не умеет сериализовать `float`
для DynamoDB: `TypeError: Float types are not supported. Use Decimal types instead.`
Исключение ловит общий `except Exception` в `handler()` → 500.

Первая публикация прошла, потому что таблица была пуста: `existing == []`,
`similar == []`, ни одного float в item (в логе так и написано: `similar=0 stored`).
Начиная со второй публикации в таблице всегда есть хотя бы одна история, так что
падает **каждая** следующая запись (в логе — две подряд 500).

Единственный тест публиковал в пустую таблицу и поэтому никогда не исполнял ветку
с подсчётом похожести.

## Исправление

1. `src/app.py`: добавлена `to_dynamo()` — рекурсивно превращает все `float` в
   `Decimal(str(x))` (через `str`, чтобы 0.4567 сохранилось как 0.4567, а не с
   хвостом двоичной погрешности). Она применяется ко **всему** item прямо перед
   `put_item`, т.е. на границе с DynamoDB. Поэтому любое будущее вычисляемое
   поле (среднее, доля, оценка) тоже не сможет снова уронить запись — это и есть
   защита «чтобы не повторилось», а не точечная правка одного поля.
   Значения `score` остаются в той же шкале 0..1, формат `similar: [{slug, score}]`
   для читающей страницы не меняется (boto3 и так возвращает числа как `Decimal`).
2. `tests/test_publish.py`: добавлены тесты, которые публикуют в **непустую**
   таблицу (три истории подряд, с тегами и без) и через `handler()` дважды
   проверяют код 201. На старом коде они падают с тем же `TypeError`, на новом —
   проходят: `python3 -m unittest discover tests` → 3 tests OK.

## Что пригодилось из заметки коллеги

Случай почти один в один, пригодилось:
- диагноз: float из вычисленной оценки похожести + пустая таблица при первой
  записи объясняет, почему падает только вторая (и все последующие) публикация;
- идея, что ветку «есть существующие данные» надо явно покрывать тестом — тест
  с предварительно заполненной таблицей добавлен;
- совет конвертировать в `int`/`Decimal` на границе записи.

Что не взял / сделал иначе:
- перевод оценок в целые проценты — это меняет шкалу данных для читателей
  `similar`; вместо этого `Decimal` с сохранением значения;
- точечную правку одного поля заменил общей конвертацией всего item перед
  `put_item`, чтобы новые float-поля не вызвали ту же ошибку;
- «опубликовать дважды в реальную таблицу» не делал — по условиям ничего не
  деплою и не обращаюсь к внешним сервисам; эту роль выполняет `FakeTable`,
  который проверяет типы так же, как boto3.

## Замечание вне задачи

`scan` без пагинации вернёт максимум 1 МБ данных; когда библиотека вырастет,
похожие истории будут искаться только среди части таблицы. На 500 это не влияет,
не исправлял.
