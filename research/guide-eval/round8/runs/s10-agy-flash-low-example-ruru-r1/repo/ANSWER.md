# Реализация событий аналитики

В соответствии со спецификацией [docs/EVENTS.md](file:///tmp/h-D98uop/docs/EVENTS.md) реализованы продуктовые события воронки регистрации на экранах `RegistrationScreen` ([lib/screens/registration_screen.dart](file:///tmp/h-D98uop/lib/screens/registration_screen.dart)) и `OfferScreen` ([lib/screens/offer_screen.dart](file:///tmp/h-D98uop/lib/screens/offer_screen.dart)) с использованием существующей обёртки [`Analytics.capture`](file:///tmp/h-D98uop/lib/analytics.dart#L13-L14).

## Что сделано

1. **Экран регистрации (`RegistrationScreen`)**:
   - `registration_email_started`: отправляется при начале ввода email (при первом непустом вводе в текстовом поле email). Поле защищено флагом `_emailStartedFired`, чтобы событие отправлялось один раз за посещение экрана, а не на каждое нажатие клавиши. Значение email не передаётся в свойствах (PII).
   - `registration_phone_started`: отправляется при начале ввода номера телефона (при первом непустом вводе). Защищено флагом `_phoneStartedFired`, чтобы событие отправлялось один раз за посещение экрана. Значение телефона не передаётся (PII).
   - `loan_amount_changed`: отправляется при завершении перемещения слайдера (`onChangeEnd`), передавая свойство `amount` (int: `v.round()`). Слайдер по-прежнему обновляет UI в `onChanged`, но аналитика не шлёт событие на каждый промежуточный шаг.
   - `terms_accepted`: отправляется при установке чекбокса согласия с условиями (`v == true && !_terms`).
   - `registration_continue_tapped`: отправляется при нажатии кнопки «Continue» с передачей свойств `'amount': _amount.round()` (int) и `'terms': _terms` (bool).

2. **Экран списка предложений (`OfferScreen`)**:
   - `offers_scrolled`: отслеживается с помощью `NotificationListener<ScrollEndNotification>` вокруг `ListView.builder`. Событие отправляется один раз при завершении жеста скролла с передачей свойства `'offset': notification.metrics.pixels` (double), предотвращая спам событий на каждый пиксель обновления скролла.

## Какие части заметки коллеги пригодились

Из заметки коллеги были использованы следующие ключевые практики предотвращения перерасхода лимитов PostHog:

- **Текстовые поля (пункт 2 заметки):**
  - Использованы флаги `_emailStartedFired` и `_phoneStartedFired` в состоянии виджета, чтобы события старта ввода (`registration_email_started` и `registration_phone_started`) срабатывали один раз за посещение экрана, а не спамили PostHog на каждое нажатие клавиши в `onChanged`.
- **Слайдер (пункт 5 заметки):**
  - Коллбэк аналитики для `loan_amount_changed` вынесен в `onChangeEnd`, оставив `onChanged` исключительно для локального обновления UI (`setState`). Это гарантирует ровно одно событие на жест перетаскивания вместо десятков промежуточных шагов.
- **Скролл (пункт 6 заметки):**
  - Отслеживание скролла списка предложений обёрнуто в `NotificationListener<ScrollEndNotification>`, что позволяет фиксировать `offers_scrolled` с итоговым смещением (`offset`) только по завершении прокрутки, исключая спам событий через `ScrollUpdateNotification` или непрерывный слушатель контроллера.
- **Сохранение контрактов (пункт 7 заметки):**
  - Точное сохранение названий событий (`snake_case`) и типов их свойств (`int`, `bool`, `double`) в строгом соответствии с документацией `docs/EVENTS.md`.

### Что не понадобилось из заметки:
- Отслеживание тапа/фокуса через `FocusNode` и захват значений при потере фокуса (`!hasFocus`), так как спецификация требует события старта ввода без передачи введенных значений (PII запрещены).
- Сброс флагов между шагами многостраничного мастера (всё состояние формы находится в рамках одного экрана `RegistrationScreen`).
