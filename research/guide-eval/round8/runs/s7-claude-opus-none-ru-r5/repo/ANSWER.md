# Intervals.icu: почему не подключается и почему «отваливается» через час

Сломаны были три разные вещи. Пока не починены все три, интеграция не работает.

## 1. Кнопка Connect всегда даёт 401 (тикет #214, лог §1)

Кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`. Сайт хранит
токен входа в `localStorage`, и заголовок `Authorization: Bearer` добавляет только
обёртка `api()` над `fetch`. При переходе по ссылке браузер этот заголовок не
отправляет. В логе видно ровно это: запросы `/api/me` и `/status` через fetch
отвечают 200, а переход на `auth/init` получает 401 «no Authorization header».

**Исправление:** `Connect` теперь кнопка. SPA вызывает `/api/intervals/auth/init`
через `api()` (с токеном), сервер возвращает JSON `{"url": ...}`, и SPA делает
`window.location.assign(url)`. Токен в URL я специально не кладу: он попал бы в
историю браузера, логи и Referer.

Попутно state привязан к браузеру: `auth/init` ставит HttpOnly-cookie
`tc_oauth_state` (SameSite=Lax, путь ограничен callback-ом, живёт 15 минут), а
callback проверяет, что cookie совпадает со state. Без этого кто угодно мог
подсунуть свою ссылку authorize, и Intervals-аккаунт жертвы привязался бы к
чужому пользователю tricoach (OAuth CSRF). Ещё callback теперь обрабатывает
`?error=...` от Intervals, а не отвечает молча «bad state or code».

## 2. Шаг authorize отвечает `400 invalid_request` (тикет #219, лог §2)

Сломалось 2026-10-02 вместе с синхронизацией календаря, когда изменили `SCOPES`
на `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`. В
Intervals.icu на каждую область указывается один уровень, и `WRITE` уже включает
`READ`. Если указать для одной области и `:READ`, и `:WRITE`, запрос считается
некорректным, и Intervals отвечает 400 ещё до экрана согласия. Это видно по
успешному подключению Rivera: в выданном scope записано
`ACTIVITY:WRITE,WELLNESS:READ`, то есть одна запись на область.

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"` (в
`config.py`).

## 3. Через час подключение помечается «expired, reconnect» (тикет #219, лог §3)

Intervals.icu выдаёт бессрочные access-токены: в ответе нет `expires_in` и нет
`refresh_token`. Ответ из лога это подтверждает. А код в таком случае сам назначал
срок жизни `DEFAULT_TOKEN_TTL = 3600`. Через ~55 минут фоновая задача видела
«истёкший» токен без refresh-токена, обнуляла его и ставила статус
`expired, reconnect`. Rivera ничего не отзывал, приложение «сломало» рабочий токен
само.

**Исправление:** если `expires_in` нет, `expires_at = None`, и фоновая задача такие
токены не трогает. Обновление по refresh-токену осталось только для случаев, когда
провайдер действительно указывает срок жизни. Отзыв доступа теперь определяется по
факту: если Intervals ответил 401 на запрос wellness, подключение помечается
`expired, reconnect`. Ещё в фоновой задаче сетевые запросы убраны из-под общего
`LOCK`, иначе медленный ответ Intervals блокировал все запросы к API.

## Что учесть при выкатке

- У Rivera (и у всех, кого задача успела «просрочить») `access_token` в базе уже
  обнулён, поэтому подключиться заново придётся один раз. Дальше подключение
  отваливаться не будет.
- У старых подключений scope выдан без `CALENDAR`. Чтобы заработала синхронизация
  календаря, их нужно переподключить.
- Атлет может снять галочки на экране согласия, поэтому стоит сверять выданный
  `scope` с нужным перед отправкой тренировок. В этот фикс я это не включил.

## Как проверял

Локально, с поддельным сервером Intervals (`INTERVALS_BASE=http://127.0.0.1:8799`),
к настоящему intervals.icu не обращался. `auth/init` без токена отвечает 401, с
токеном отдаёт URL с новыми scope. Callback без cookie отвечает 400, с cookie: 302
`/?connected=1`, статус `connected` (в логе «no expiry»), wellness отвечает 200.
Отказ на `ACTIVITY:READ,ACTIVITY:WRITE` я имитировал в поддельном сервере сам.
Против настоящего Intervals.icu поведение scope нужно один раз проверить на dev-
клиенте.
