# Cache fix

`build_system()` now sends two text blocks, each with `cache_control: {"type": "ephemeral"}`. The first contains only fixed coaching instructions; the second contains the date, athlete profile, zones, goal, long-term facts and language. A `save_fact` write changes the second block, so the fixed prefix can still be read from cache on the next API call. I also added fixed, task-relevant coaching guidance to keep the first breakpoint comfortably above Claude Sonnet 4.5's 1,024-token minimum cacheable prefix; the old *entire* cached prompt was only about 1,046 tokens in `logs/usage.jsonl`.

The colleague's two-breakpoint approach, stable prefix, and usage-field verification apply here. Keeping all facts and the existing keyword-based tool selection also applies: the facts are not selected per message, and the selected tool list remains the same through a tool loop. I did not redo the earlier tool-filtering work or add per-message fact ranking. The log already records `cache_creation_input_tokens` and `cache_read_input_tokens` for every response.

`python3 -m unittest -v` passes. The test simulates a `save_fact` round, checks that the first cached block is byte-stable, and checks that only the athlete block changes and persists on the next request. No live cache hit was measured: this checkout has neither the Anthropic SDK nor `COACH_ANTHROPIC_KEY`. Once run with the API, inspect `logs/usage.jsonl` after a fact write: `cache_read_input_tokens` should remain nonzero for the fixed prefix, while `cache_creation_input_tokens` should represent the changed athlete tail. Tool-group changes or a cache TTL expiry can still produce a full-prefix write.
