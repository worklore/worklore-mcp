# Фикс: обрезанные пульсовые коридоры на часах

## Симптом

Каждая пульсовая цель на часах отображалась как одна из собственных зон часов
(по их авто-LTHR 168), а не как запланированный коридор в процентах от LTHR 172
из Intervals: 68–75% должно было дать 117–129 уд/мин, часы показывали
118–137 (границы их Z2). См. `readback/watch-notes.md`.

## Причина

`gen.py` отправлял пульсовую цель шага как `{"units": "%lthr", "value": lo,
"end": hi}`. Сочетание ключей `value` + `end` заставляет Intervals.icu
экспортировать цель в FIT как **Lap-HR / цель «по зонам»** — в этом режиме часы
подгоняют коридор под свои локальные зоны и не показывают сырые bpm. API тело
принимает без ошибок, поэтому проблема не видна до экрана часов.

## Что изменил

`gen.py`, функция `hr_target()`: нижняя граница коридора теперь
кодируется ключом `start` вместо `value`:

```python
return {"units": "%lthr", "start": lo, "end": hi}
```

С ключом `start` Intervals экспортирует ту же пару чисел в FIT как
**Instant-HR коридор** — часы получают готовые bpm, пересчитанные Intervals
по его сохранённому LTHR (172), и показывают их без обрезки. Это подтверждено
на другом аккаунте: LTHR Intervals 172, LTHR часов 168, цель 75–82% отобразилась
на часах как 129–141 — ровно как в Intervals.

Проценты (`%lthr`), а не абсолютные bpm, оставлены как были: Intervals сам
пересчитывает их при экспорте по своему порогу.

Проверка: `python3 gen.py plans/tempo-run.json` выдаёт все четыре пульсовые
цели с `start`/`end`; других мест, где генерируется ключ `value`, в генераторе
нет.

`readback/event-184233-as-sent.json` не менял — это запись того, что реально
было отправлено для события 184233 (и доказательство старого поведения).

## Что взял из заметки коллеги

- **Главный ключ к решению**: имя ключа нижней границы (`start`, а не `value`)
  переключает режим экспорта в FIT. Именно это и был фикс — переименование
  одного слова.
- **Контекст уже опробованных тупиков** (`units: "bpm"` с абсолютными значениями
  → часы показали 214–249; `start_bpm`/`end_bpm` → константа 101): подтвердило,
  что оставаться надо на `%lthr`, менять только форму ключей.
- Подтверждение, что API примет тело без ошибок даже с «неправильной» схемой —
  поэтому проверять надо вывод на часах, а не только readback.

## Что пропустил

- **Бонусную ловушку про текстовую грамматику `description`** (`m` = минуты,
  `mtr`/`km` для дистанции, голые `Z2`, цифры в начале подписей). Она влияет
  только на отображение шагов в веб-UI Intervals; наш симптом — на часах,
  а шаги на часах и в API читаются нормально (`workout_doc.steps` непустой,
  часы показывают все коридоры). Поле `description` генератор вообще не
  формирует, так что здесь нечего чинить. Если позже захотим отображение шагов
  в веб-UI — вернёмся к этому разделу заметки.
- **Способ «собрать тренировку в UI и прочитать обратно»**: в нашем случае
  ответ уже был в заметке (ключ `start`), воспроизводить весь круг
  UI → API → часы не потребовалось.
