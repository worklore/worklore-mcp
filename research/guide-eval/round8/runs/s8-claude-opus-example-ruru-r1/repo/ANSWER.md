# Почему `save_fact` сбрасывал кеш и что изменено

## Что показывал `logs/usage.jsonl`

Промах был в **round 2 того же сообщения**, а не только в следующем сообщении:
`round 1, tool: save_fact` → `round 2: cache_read 0, cache_creation ~1060`. Причин две:

1. `reply()` пересобирал системный промпт на каждой итерации цикла инструментов, а
   `run_tool("save_fact")` в это время дописывал факт в `a.facts`. Поэтому уже следующий
   раунд отправлял другой промпт.
2. В `build_system()` был один блок (`INSTRUCTIONS` + контекст атлета) с одним маркером
   `cache_control`. Кеш работает по хешу префикса, и любой новый факт (а также смена даты)
   сбрасывал весь промпт вместе с инструкциями, которые никогда не меняются.

## Изменения (`bot.py`)

- **`build_system()`: два блока, на каждом `cache_control: ephemeral`.** Блок 1 — только
  `INSTRUCTIONS`: байт в байт одинаковые для всех атлетов и всех дней. Блок 2 —
  `athlete_context()` (дата, профиль, зоны, цель, факты, язык). После записи факта заново
  кешируется только хвост (~70–100 токенов), а общий префикс tools + инструкции
  читается из кеша. Этот префикс общий у всех атлетов, поэтому сообщение другого
  пользователя тоже попадает в кеш.
- **Системный промпт собирается один раз на сообщение** (`system = build_system(...)` до цикла;
  `build_request()` теперь принимает готовый `system`). Раунды цикла после `save_fact`
  отправляют тот же промпт и получают полный cache read. Модель всё равно знает о новом
  факте из пары `tool_use`/`tool_result` в истории. В системный промпт факт попадает со
  следующим сообщением, как и описано в README.
- **Статический блок дотянут выше минимального кешируемого префикса.** Неочевидный момент:
  у `claude-sonnet-4-5` минимальный кешируемый префикс — 1024 токена. Он считается вместе
  с инструментами (и служебным промптом tool use), которые стоят в запросе перед `system`.
  По логу весь промпт был ~1046 токенов при хвосте ~80–90, значит tools + инструкции давали
  примерно 950–960 токенов. Если бы я просто разрезал блок, первый маркер оказался бы ниже
  порога, API молча проигнорировал бы его, и `save_fact` по-прежнему перекешировал бы весь
  промпт. Поэтому в `INSTRUCTIONS` добавлен раздел «Zone guide»: назначение каждой зоны,
  соответствие RPE и правило разминки/заминки, примерно +180 токенов. Он согласован с
  существующими правилами (зоны по профилю, Z1/Z2 — лёгкие, RPE как альтернатива). Это
  небольшое изменение промпта, то есть поведения бота: проверьте формулировки. Если
  инструкции когда-нибудь сократят, снова проверьте, что блок 1 остаётся выше 1024 токенов.
- В README обновлено описание кеширования.

Что не трогал: фильтрацию инструментов по ключевым словам (см. NOTES.md, она полезна) и
порядок и формулировки схем инструментов. Внутри одного сообщения список инструментов
не меняется, поэтому раунды цикла по-прежнему попадают в кеш.

## Проверка

Реальных вызовов API я не делал: нет ключа, и по правилам задачи во внешние сервисы
ничего не отправляется. Проверял офлайн: подставил фейковый клиент, который моделирует
префиксный кеш (маркеры, порог 1024, приблизительный подсчёт токенов), и прогнал его
на копии `data/athletes.json`. Результат:
`hi` → creation ~1340; `hi` → read 1340; `save_fact` round 1 → read; **round 2 → read
(раньше был полный промах)**; следующее сообщение → read ~1270 (статика) + creation ~80
(хвост); другой атлет → read ~1270 + creation ~66.

Как проверить на проде по `logs/usage.jsonl`: после `save_fact` раунд 2 должен показывать
`cache_creation_input_tokens: 0`, а следующее сообщение — `cache_read` около 1100+ и
`cache_creation` примерно размером с хвост. Если после записи факта `cache_creation`
снова ~1000+, значит блок 1 ниже порога 1024 или в нём оказалось подставленное значение.
Точный размер можно узнать через `messages.count_tokens` с одними tools + `INSTRUCTIONS`.

## Что пригодилось из заметки коллеги

- **Пригодилось:** главная идея — два маркера `cache_control` (статические инструкции
  отдельно от изменчивого хвоста). Правило «никаких дат, имён и счётчиков в статическом
  блоке». Наблюдение, что инструменты стоят в префиксе перед `system` и их нужно держать
  стабильными. Отказ от отбора top-N фактов под сообщение (я его не вводил). Методика
  проверки через `cache_creation`/`cache_read`, включая подсказку «если запись даёт
  `cache_creation` размером с полный промпт, ищите проблему в статическом блоке».
- **Не пригодилось / пропустил:** фильтрация инструментов по группам здесь уже есть с
  марта, менять её не нужно. Цифры «~780 + ~240 токенов» относятся к чужому боту.
  Кстати, в заметке статика ~780 токенов, что ниже порога 1024 для Sonnet 4.5. В нашем
  случае именно это и сломало бы фикс, поэтому пришлось дополнить инструкции.
- **Чего в заметке не было, но понадобилось:** промах внутри цикла инструментов
  (промпт пересобирался между раундами после `save_fact`) и порог минимального
  кешируемого префикса.
