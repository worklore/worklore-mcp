# Почему ломалась интеграция Intervals.icu и что изменено

## Причины сбоев

### 1. Кнопка Connect не работала ни у кого (тикет #214): init был обычной GET-ссылкой

`static/app.js` рисовал Connect как `<a href="/api/intervals/auth/init">`. Это
полноценная навигация документа, а браузер **не** посылает в ней заголовок
`Authorization: Bearer …` из localStorage — заголовки уходят только на
XHR/fetch. Серверный `auth_init` требует авторизацию, поэтому каждый атлет
получал 401 «unauthorized». POST-маршрута при этом не существовало, то есть
SPA физически не мог инициировать флоу с заголовком. Подтверждение:
`connect-attempt.log` №1 (`GET /api/intervals/auth/init 401 (no Authorization
header)`), воспроизведено локально.

### 2. Authorize-URL отвергался Intervals (тикет #219): продублированные области в scope

`config.SCOPES` был `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
У Intervals `:WRITE` подразумевает `:READ`, и область, названная дважды,
отклоняется (ошибка «Duplicate scope»; в нашем логе она выглядит как
`{"error":"invalid_request"}` — в `connect-attempt.log` №2 state и
redirect_uri исключены экспериментом, остаётся только scope). Сломалось
2026-10-02, когда к scope добавили календарные права и заодно получили вторую
дублирующую пару (CALENDAR:READ + CALENDAR:WRITE). До этого авторизоваться
можно было, если обойти баг №1 вставкой ссылки вручную — именно так
подключили Риверу.

### 3. Единственное успешное подключение «истекло» через час (Ривера): сервер придумал себе истечение

В ответе токена Intervals **нет** ни `refresh_token`, ни `expires_in` — токен
живёт, пока атлет не отзовёт приложение в настройках Intervals. Код же при
отсутствии `expires_in` выставлял TTL 3600 с по умолчанию, а фоновый
`refresh_tokens()` через час помечал соединение «expired, reconnect» из-за
отсутствия refresh-токена. У Риверы подключение сделали вручную в обход
бага №1, и через ~час его «уровло» именно это — на стороне Intervals ничего
не отзывали. Воспроизведено ускоренно (TTL 3 с вместо 3600): тот же переход
статуса `connected → expired, reconnect` без единого запроса к API.

### 4. (Сопутствующее) Обмен кода слал лишние поля

`exchange_code` отправлял `grant_type=authorization_code` и `redirect_uri`.
У Intervals `POST /api/oauth/token` принимает только `client_id`,
`client_secret`, `code`. Убрано, чтобы соответствовать контракту провайдера.

## Что изменено

- `config.py` — scope без дублей: `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`
  (набор прав из README сохранён: пишем тренировки и календарь, читаем wellness;
  WRITE покрывает READ той же области).
- `server.py`:
  - `init` — аутентифицированный **POST**, возвращает `{authorize_url}` JSON;
    GET-маршрут удалён (полная навигация всё равно теряет заголовок).
  - `exchange_code` шлёт ровно `client_id`, `client_secret`, `code`.
  - Удалены `DEFAULT_TOKEN_TTL`, фоновый refresher и поля `refresh_token` /
    `expires_at` — токен хранится как долгоживущий, до отзыва.
  - Ленивый детект отзыва: первый 401 от API помечает соединение
    `revoked, reconnect`, стирает токен; `/api/intervals/wellness` отвечает
    401 с подсказкой переподключиться.
- `static/app.js` — Connect теперь кнопка: клик делает POST `/init` через
  fetch-обёртку (заголовок на месте) и уводит браузер через
  `window.location.assign(authorize_url)`.

## Проверка

Порт 8766 занят посторонним процессом, поэтому код репозитория поднимался на
8769 с `INTERVALS_BASE` на локальный мок Intervals (8768), повторяющий
документированные особенности: ответ токена без `refresh_token`/`expires_in`,
строгий набор полей обмена, 401 после отзыва. Прогон (все пункты прошли):
воспроизведение всех трёх багов на старом коде; затем на новом: init без
токена → 401, init POST → `authorize_url` с недублированным scope; поддельный
state → 400; полный флоу callback → 302 `/?connected=1` → status connected →
wellness 200; обмен кода содержит только три поля; спустя время соединение не
«истекает»; после отзыва wellness → 401 «reconnect», status → `revoked,
reconnect`; повторное подключение работает; два атлета подключены независимо.

## Что пригодилось из заметки коллеги

- **П. 4 (init обязан быть POST)** — точное совпадение с причиной №1: ссылка
  теряет Authorization-заголовок. Применено.
- **П. 2 («Duplicate scope», `:WRITE` подразумевает `:READ`)** — совпадение с
  причиной №2. Применено.
- **П. 1 (нет `refresh_token`/`expires_in`, ленивая обработка отзыва по
  первому 401)** — совпадение с причиной №3. Применено.
- **П. 3 (обмен кода: только `client_id`/`client_secret`/`code`; в ответе сразу
  `athlete`)** — совпадение с причиной №4; `athlete.id` уже использовался.
- **Блок «Verify»** — взял как чек-лист прогона (полный флоу, 401 после
  отзыва, scope без дублей).

## Что не пригодилось / сознательно не делал

- **JWT-state с `purpose`-клеймом** — существующий state уже несёт user id,
  HMAC-подпись и TTL 15 минут; функционально эквивалентен, замена не нужна
  для исправления.
- **Account-mismatch guard** (отклонять reconnect с другим athlete id) — не
  причина текущих сбоев; меняет поведение, о котором не просили.
- **Шифрование токена at rest** — верная рекомендация для прода (токен теперь
  фактически бессрочный), но вне рамок этого stdlib-only dev-стенда.
- Регистрация OAuth-клиента через форум — клиент уже есть.
