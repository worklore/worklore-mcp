# Intervals.icu connection failures

1. **Connect always returned 401.** The SPA rendered a normal link to `/api/intervals/auth/init`. Following a link is a document navigation, so it did not use the SPA's `fetch` wrapper or send its `Authorization: Bearer` header. The endpoint required that header. The captured request in `logs/connect-attempt.log` confirms it was absent. Connect now calls an authenticated POST through the wrapper, receives an authorize URL, and navigates to it.

2. **The authorize URL was rejected.** `SCOPES` requested `ACTIVITY:READ` and `ACTIVITY:WRITE` together, and likewise both levels for `CALENDAR`. Intervals.icu permits one entry per area; `WRITE` includes read access. The duplicate areas caused the captured `400 invalid_request` before consent. The request now uses `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`, retaining the app's requested write access to activities and planned workouts. [Intervals.icu OAuth scopes](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)

3. **A successful connection was falsely expired.** The provider response in the log had an access token but no `refresh_token` or `expires_in`. The server assigned a one hour default lifetime, then the refresh thread marked the connection expired because no refresh token existed. Intervals.icu does not use refresh tokens for this OAuth flow. The server now keeps the access token until disconnect or a provider 401, then asks the athlete to reconnect. It also exchanges authorization codes using the form fields in the provider's documentation. [Intervals.icu OAuth support](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)

Local verification: `python3 -m unittest -v` covers authenticated initiation, the scope and redirect URL, callback storage without an invented expiry, the code exchange fields, and reconnect status after a provider 401. The real provider flow was not exercised; the client credentials in this repository are placeholders.
