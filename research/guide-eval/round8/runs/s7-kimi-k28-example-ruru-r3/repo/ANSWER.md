# Почему не работало подключение Intervals.icu — разбор и исправления

## Причины (по убыванию влияния, подтверждены логами)

**1. Кнопка Connect была обычной ссылкой на GET-эндпоинт → 401 у всех.**
В `static/app.js` кнопка была `<a href="/api/intervals/auth/init">`. Полная
навигация страницы не отправляет заголовок `Authorization`, который SPA держит
в localStorage и прикрепляет только к fetch/XHR. Поэтому `auth_init` видел
запрос без токена и отвечал 401 — это тикет #214 и строки 5–13
`logs/connect-attempt.log`. «Победителей» не было никаких: единственное
удачное подключение Rivera произошло, когда менеджер вручную вставил
authorize-ссылку в браузер атлета, минуя кнопку.

**2. «Duplicate scope» в authorize URL → 400 `invalid_request` до экрана согласия.**
После того как 2026-10-02 в интеграцию добавили календарь, `SCOPES` стал
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
В Intervals.icu `:WRITE` уже подразумевает `:READ`, и повторное упоминание
области он отклоняет с `Duplicate scope` (в логах виден обобщённый 400
`invalid_request`, без указания параметра — `connect-attempt.log` §2).
Поэтому ручной обход через вставку ссылки тоже перестал работать — шаг
авторизации теперь падал у всех.

**3. Самодельный «срок жизни» токена: «подключитесь заново» через час.**
У Intervals.icu в ответе токен-эндпоинта **нет ни `refresh_token`, ни
`expires_in`** — токен бессрочный и живёт, пока атлет его не отзовёт. Бэкенд
же сам назначал TTL 3600 с (`DEFAULT_TOKEN_TTL`), не находил refresh_token и
фоновый «refresher» через ~час помечал соединение `expired, reconnect` —
ровно то, что видно у Rivera: подключение 17:41 → пометка об отзыве 18:37
(`connect-attempt.log` §3, тикет #219). Атлет ничего не отзывал; сессия была
жива и исправно отдавала wellness в 17:44.

**4. Обмен кода слал лишние поля (исправлено по специфике провайдера,
прямых доказательств в логах нет).**
`exchange_code` отправлял `grant_type` и `redirect_uri`, которых
`/api/oauth/token` у Intervals.icu не ждёт — только `client_id`,
`client_secret`, `code`. Единственный успешный обмен в сентябре прошёл с
этими полями, так что, вероятно, провайдер их терпит; но код приведён к
документированному поведению провайдера, чтобы не зависеть от его снисходительности.

## Что изменено

- `server.py`
  - `/api/intervals/auth/init` стал аутентифицированным **POST**, возвращающим
    `{authorize_url}` JSON; GET-маршрут убран. Фронтенд сам делает
    `window.location.assign(authorize_url)`.
  - `exchange_code` отправляет только `client_id`, `client_secret`, `code`.
  - Удалены фейковый TTL, поля `refresh_token`/`expires_at` и фоновый
    рефрешер-поток. Соединение хранит `{athlete_id, athlete_name,
    access_token, scope, status}`.
  - Ленивая обработка отзыва: 401 от API Intervals очищает соединение, статус
    возвращается в «не подключено», UI снова показывает кнопку Connect.
  - Защита от смены аккаунта: callback с id атлета, отличным от сохранённого,
    отклоняется с 409, старое соединение сохраняется.
  - Подписанный `state` (HMAC + TTL 15 мин) оставлен как есть — он уже несёт
    id пользователя и защищает callback, приходящий без нашего заголовка
    авторизации.
- `config.py` — `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`
  (каждая область один раз; `:WRITE` подразумевает `:READ`).
- `static/app.js` — кнопка Connect: POST `/api/intervals/auth/init` →
  `window.location.assign(authorize_url)`.

## Что взято из заметки коллеги

Пригодились почти все четыре пункта:

1. **«Токен не истекает, refresh_token нет — обрабатывайте отзыв лениво по
   первому 401»** — ключевой пункт, стал причиной №3 и схемой хранения
   соединения. (Шифрование токена при хранении из этого же пункта в dev-харнесс
   не добавлено — он stdlib-only; это задача prod-хранилища, см. ниже.)
2. **«Duplicate scope»: `:WRITE` подразумевает `:READ`, область не больше
   одного раза** — причина №2, отсюда новая строка scope.
3. **«Обмен кода — стандарт-лайт: только client_id, client_secret, code;
   athlete уже в ответе»** — причина №4; `athlete.id` из ответа и раньше
   использовался, запрос «кто я» не понадобился.
4. **«init-эндпоинт должен быть POST, возвращающий authorize_url; callback без
   заголовка авторизации опознаётся через state; защита от несовпадения
   аккаунтов»** — причина №1 и форма исправления целиком, включая guard
   несовпадения athlete id.

Не пригодились: переход на JWT-формат `state` (существующий HMAC-state уже
покрывает id пользователя, TTL и подпись — менять формат незачем) и упоминание
регистрации клиента через форум (клиент уже был).

## Проверка

Внешние сервисы не трогал: поднял временный локальный стаб Intervals.icu
(удалён после тестов) и прогнал через него весь поток. Подтверждено:
init → callback → статус «connected» → wellness с сохранённым токеном;
409 при привязке чужого athlete id с сохранением старой связки; 401 от API
→ соединение очищается, статус «disconnected», повторное подключение
срабатывает; 400 на битый state, 502 на отказ token-эндпоинта, 401 на init
без заголовка, 404 на старый GET init.

## Остаток для prod (вне этого репозитория)

- Миграция таблицы соединений: убрать `refresh_token` и `expires_at`.
- Шифрование access_token при хранении — теперь он бессрочный секрет.
