# Why the nightly job was silent

The job did run. The captured `launchctl print` shows `runs = 6` and `last exit code = 1`; the error log has six matching pairs of errors. The first error, `Not logged in · Please run /login`, came from `claude` under launchd. The plist supplied `PATH` but omitted `USER`, which the headless CLI needs to locate its login. The script then tried `status=$?`. In zsh, `status` is read-only, so that assignment terminated the script before its failure notification. These two faults explain the absent summaries and failure notes.

I added `USER=vk` to the plist and exported it in the wrapper, replaced `status` with `rc`, and kept the failure notification immediately after the agent call. The wrapper now closes stdin when passing the prompt as an argument, logs the agent's duration and exit code, and treats empty output as a failure. This prevents a successful exit with no review from being reported as a completed review.

From the colleague's note, the launchd run count and exit code check, the zsh `status` bug, and the missing `USER` setting applied directly. Closing stdin, recording duration, and checking the real output were useful preventive checks. The prompt delivery bug did **not** appear in this snapshot: the log reports an authentication failure, not a missing prompt, and the command already supplied a quoted prompt argument. I retained that argument and closed stdin as suggested for that form. The colleague's exact two-run observation and `claude` prompt-via-stdin fix therefore do not describe this job.

The local snapshot cannot prove that the installed user agent now authenticates or delivers Telegram messages. After copying these edits to the real home directory and reloading the agent, verify a run with `launchctl kickstart -k gui/$UID/com.vk.nightly-review`, inspect the new log lines and fresh nonempty review file, and confirm both success and a deliberately forced failure reach Telegram. No live launchd or external-service action was performed here.
