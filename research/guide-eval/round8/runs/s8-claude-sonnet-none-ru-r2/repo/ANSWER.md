# Кеширование после save_fact

## Причина
`build_system` склеивал инструкции (~2.5k символов, статичные) и контекст атлета
(дата, зоны, цель, список фактов) в один text-блок с одним `cache_control`.
Кеш — префиксный, поэтому любое изменение текста блока, в том числе новый факт
после `save_fact` (а также смена даты), меняло весь блок и сбрасывало кеш:
следующий вызов платил `cache_creation` ~1000 токенов вместо `cache_read`.

## Что изменено (bot.py)
- `athlete_context` разделён на `athlete_profile` (имя, спорт, зоны, цель, язык —
  меняется редко) и `athlete_memory` (дата + факты — меняется часто).
- `build_system` теперь возвращает три блока в порядке от стабильного к
  изменчивому: `INSTRUCTIONS` [cache_control] → профиль [cache_control] →
  дата и факты (без cache_control).
  `save_fact` меняет только последний блок, префикс инструкций и профиля остаётся
  байт-в-байт тем же. Проверено: при добавлении факта блоки 1–2 равны, блок 3 отличается.
- Фильтрацию инструментов по ключевым словам не трогал (по NOTES.md это выигрыш).

## Оговорки
- Минимум для кеширования у Sonnet 4.5 — 1024 токена в префиксе. По логам весь
  запрос (инструменты + системный промпт) ≈ 1050 токенов, а инструкции + core-tools
  без контекста — по моей оценке (~3 символа/токен) ≈ 950, т.е. на грани порога.
  Второй breakpoint (после профиля) лежит выше порога и кешируется в любом случае;
  кеш префикса, переживающий save_fact, гарантирован, только если инструкции + tools
  + профиль ≥ 1024 токенов (с группами plan/race — заведомо да). Я не мог проверить
  это без вызова API, поэтому после выкладки сверьте `logs/usage.jsonl`: после
  `save_fact` `cache_read_input_tokens` должен быть > 0.
- Набор tools тоже входит в префикс (идёт перед system), так что сообщение, у
  которого набор tools другой, по-прежнему даёт отдельную запись кеша — это
  отдельная от save_fact проблема, не менял.
