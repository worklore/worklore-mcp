# Кеширование системного промпта после save_fact

## Проблема

В `build_system` был один текстовый блок (инструкции + контекст атлета) с одним
`cache_control`. Кеш работает по хешу префикса. `save_fact` дописывал факт в конец блока,
хеш менялся, и вместе с фактами из кеша вылетали неизменные инструкции. В
`logs/usage.jsonl` это видно: сразу после каждого `save_fact` идёт `cache_read_input_tokens: 0`
и `cache_creation_input_tokens` ≈ 1040–1100, то есть весь промпт по цене записи (1.25×).

Вторая причина того же промаха: `build_request` пересобирал system на каждом раунде
tool-loop. Если в раунде 1 был `save_fact`, раунд 2 того же ответа уже шёл с новым
промптом и промахивался (в логе все эти промахи приходятся на `round: 2`).

## Что изменено (`bot.py`)

1. **Два сегмента с `cache_control: ephemeral`** (`build_system`):
   - сегмент 1: `INSTRUCTIONS` + профиль атлета (имя, спорт, зоны, цель, язык), через
     новую функцию `athlete_profile`. Он не меняется ни от `save_fact`, ни от смены даты;
   - сегмент 2: дата + долговременные факты, через `athlete_memory`. Это единственная
     часть, которую трогает запись в память.
   Теперь после `save_fact` должен читаться из кеша префикс tools + сегмент 1, а заново
   записываться только хвост (~50–150 токенов в зависимости от числа фактов).
   `athlete_context` заменён этими двумя функциями.
2. **System собирается один раз на сообщение** (`reply`), а `build_request` принимает
   готовый `system`. Раунд 2 после `save_fact` теперь попадает в кеш полностью. Модель
   и так видит новый факт в собственном `tool_use`, а в system он появится со следующего
   сообщения. Именно так README и описывает поведение («the next message sees the fact»).
3. **`python3 bot.py --check-cache <user_id>`** через `count_tokens` считает длину префикса
   до первого маркера (core tools + сегмент 1) и сравнивает её с `MIN_CACHEABLE_TOKENS = 1024`.
   README обновлён.

## Важная оговорка: минимальная длина кешируемого префикса

Если префикс до маркера короче минимума модели (у `claude-sonnet-4-5` это 1024 токена),
API молча игнорирует маркер. Ошибки не будет, но всё будет как раньше. По логу весь
промпт Марты с core tools весит 1046 токенов, промпт Йонаса 1024. Значит, tools + одни
инструкции дают примерно 930–950 токенов, **ниже порога**. Поэтому я не стал делать
сегмент 1 «только инструкции, общий для всех пользователей», как в заметке. Профиль
перенесён в сегмент 1, чтобы добрать длину: он меняется ещё реже фактов. Цена этого в
том, что сегмент 1 персональный, а не общий. Для маленького клуба с TTL 5 минут
межпользовательские попадания всё равно редкость.

По моей оценке (≈ 50–60 токенов профиля) сегмент 1 выходит около 1000 токенов, **на грани
порога**. Реальный API я не вызывал: нет ключа, и внешние сервисы по условию трогать
нельзя. Проверить нужно так:
- `python3 bot.py --check-cache 42` должен напечатать `OK`;
- либо на живом трафике: в первом раунде после сообщения с `save_fact` (с новым
  кодом это следующее сообщение) `cache_read_input_tokens` должен быть ≈ размеру
  сегмента 1, а `cache_creation_input_tokens` должен быть порядка размера хвоста.
  Если там снова ~1050 записи и 0 чтения, сегмент 1 короче 1024. Тогда нужно либо
  дописать в `INSTRUCTIONS` реальные правила, либо перенести в сегмент 1 ещё что-то
  стабильное. Если сменить модель, проверить порог заново: у некоторых моделей он 2048
  или 4096.

## Что проверено

Офлайн-прогон `reply()` с фейковым LLM на копии `data/athletes.json`: внутри одного ответа
system в раундах 1 и 2 побайтно одинаковый, после `save_fact` сегмент 1 следующего
сообщения побайтно совпадает с прежним, а сегмент 2 изменился. Реальные `usage` с API
не проверялись (см. выше).

## Что пригодилось из заметки коллеги

- **Пригодилось:** главная идея с двумя маркерами `cache_control` вместо одного,
  стабильный префикс и волатильный хвост, и требование держать первый сегмент побайтно
  стабильным (без дат и счётчиков; дата у меня в хвосте). Пригодился и способ проверки
  через `cache_creation_input_tokens` / `cache_read_input_tokens`: сначала читать `usage`,
  потом искать «плавающее» значение.
- **Пригодилось как подтверждение, без изменений:** держать tools байт-стабильными и не
  выкидывать фильтрацию по ключевым словам. В NOTES.md прямо сказано её оставить, и
  внутри одного сообщения набор tools и так постоянен. Совет не делать top-N отбора
  фактов: у нас загружаются все факты, это я и оставил.
- **Не подошло как есть:** «сегмент 1 = только инструкции, ~780 токенов». В заметке
  ничего не сказано про минимальную длину кешируемого префикса. Здесь tools маленькие
  (2 core-схемы, а не ~55), и инструкций с tools не хватает до 1024 токенов Sonnet 4.5.
  Поэтому профиль атлета перенесён в первый сегмент (см. оговорку выше).
- **Не нашлось в заметке, добавлено своё:** заморозка system на время одного ответа.
  Отдельный источник промахов здесь был в том, что `save_fact` менял промпт посреди
  tool-loop.
- **Пропущено:** рассказ про фильтрацию ~55 MCP-инструментов (у нас она уже есть) и
  Telegram-специфика.
