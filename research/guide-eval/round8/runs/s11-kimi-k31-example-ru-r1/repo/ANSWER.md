# Причина

В `logs/error.log` вторая публикация падает в `table.put_item(Item=item)` с ошибкой `TypeError: Float types are not supported. Use Decimal types instead.`

`similarity()` в `src/app.py` вычислял оценку через деление и `round(..., 4)`, поэтому возвращал `float`. Функция `related()` помещала это значение в `similar[].score` сохраняемого объекта, а DynamoDB через boto3 не принимает Python `float`.

Первая публикация работала лишь при пустой таблице: существующих историй не было, `related()` возвращал пустой список, и ни один `float` не попадал в `put_item`. При второй публикации появлялась похожая история и вычисленная оценка, сериализация в DynamoDB завершалась ошибкой, а общий обработчик исключений в `handler()` возвращал 500.

# Исправление

- `similarity()` теперь возвращает целочисленный процент сходства от 0 до 100: `round(100 * (...))`. В сохраняемый объект попадает `int`, поддерживаемый DynamoDB; промежуточные вычисления могут оставаться вещественными.
- Формат `score` задокументирован в `README.md`.
- В `tests/test_publish.py` добавлен регрессионный тест `test_second_publish_stores_integer_similarity_scores`: он выполняет две публикации через `handler()` в таблицу с проверкой типов как у boto3, проверяет два ответа 201 и целочисленную оценку второй записи. До исправления этот тест воспроизвёл ответ 500 и исходный `TypeError`.

Проверка: `python3 -m unittest discover tests` — 2 теста, все прошли.

# Что пригодилось из заметки коллеги

Пригодились три части: объяснение, почему ошибка проявляется только при наличии данных; вариант преобразования оценки в целочисленные проценты; рекомендация тестировать запись на уже заполненной таблице. Именно заполненный путь теперь покрыт регрессионным тестом. Вариант с `Decimal` не понадобился, а публикация в реальную таблицу не выполнялась: локальный `FakeTable` воспроизводит проверку типов boto3.
