# Кеш промпта: запись в память не должна вытеснять инструкции

## Что изменено

`bot.py`, `build_system()`. Раньше системный промпт был одним блоком с маркером
`cache_control` в конце, и `save_fact` менял блок фактов внутри него, поэтому
весь префикс (включая инструкции) уходил в `cache_creation`. Теперь два блока,
у каждого свой маркер:

1. `INSTRUCTIONS` — статические правила. Байт-в-байт одинаковы для всех
   атлетов и всех дней.
2. `athlete_context()` — хвост на пользователя: дата, имя, зоны, цель, факты,
   язык.

Маркер кеширует весь префикс до себя. Поэтому изменение во втором блоке
(`save_fact`, смена дня) перезаписывает только хвост, а первый блок остаётся
в кеше.

`README.md`: абзац про кеш обновлён под два блока.

Проверка без API (ключа и сети здесь нет): скриптом с подменёнными
`ATHLETES_FILE` и без записи в лог.
- статический блок одинаков для разных атлетов, разных дат и после `save_fact`;
- `save_fact` меняет только второй блок;
- оба блока имеют `cache_control: ephemeral`.

Реальные `usage` из API я не проверял. Это нужно сделать вручную (см. ниже).

## Что взято из заметки коллеги

- **Два маркера и правило «статический блок байт-в-байт, всё изменчивое — ниже».**
  Взято целиком, это и есть исправление.
- **Не отбирать факты под сообщение (top-N).** Не делал, и не предлагаю:
  это ломает хвост для каждого сообщения.
- **Проверка через `cache_read` / `cache_creation` после `save_fact`.** Взято как
  критерий успеха (см. ниже).
- **Про инструменты выше системного промпта.** Заметка верна, но в нашем коде
  это отдельная проблема, которую я не чинил (см. ниже).

Не применимо или не взято:
- Telegram-часть, цифры «~780 токенов» и «~240 токенов» (у нас другой промпт,
  я их не мерил), общие цифры про ~10% цены кеша — не проверял, в код не
  переносил.

## Что может сломать исправление (проверить до того, как считать его рабочим)

**1. Минимальная длина кешируемого префикса.** Маркер ниже минимума молча
игнорируется. По моим данным, для `claude-sonnet-4-5` минимум — 1024 токена
(сверьте с актуальной документацией). Префикс до первого маркера — это
`tools` + `INSTRUCTIONS`. По символам `INSTRUCTIONS` ≈ 2484 символа
(~600–700 токенов), core-инструменты ≈ 424 символа (~110–150 токенов).
Получается около 900–1000 токенов, то есть, возможно, меньше минимума.

Косвенный признак из `logs/usage.jsonl`: полный префикс Марты (core-инструменты +
инструкции + её профиль) при первом вызове — `cache_creation` 1046. Вычесть
профиль (~100–130 токенов) — получаем ~920–950 на инструменты и инструкции.
Точного числа без токенизатора нет.

Если после деплоя `save_fact` по-прежнему даёт `cache_creation` ≈ 1000+,
значит первый блок не кешируется. Тогда варианты:
- добавить в статическую часть настоящее полезное содержимое, чтобы префикс
  перешёл минимум (это меняет поведение бота, решение за вами; набивать
  мусором не стоит);
- отдавать все инструменты всегда (тогда префикс стабилен и длиннее; но это
  отменяет фильтрацию инструментов, которую в NOTES просили оставить).

**2. Фильтрация инструментов ломает кеш.** `tools` стоят выше системного
промпта, поэтому смена набора групп меняет префикс целиком. В логе это видно
сразу: `06:43:47` — `cache_read` 1061; `06:44:31` (сообщение с «plan») —
`cache_creation` 1305 и `cache_read` 0. Исправление это не трогает, потому что
вы просили фильтрацию не менять. Если хочется, решение — отдавать фиксированный
набор инструментов (см. вариант выше).

## Как проверить на живом API

1. Два сообщения подряд в пределах 5 минут без группы инструментов. Второе
   должно показать `cache_read_input_tokens` ≈ весь префикс.
2. Вызвать `save_fact`, затем отправить сообщение. Ожидается:
   - `cache_read_input_tokens` ≈ статический блок (инструкции + инструменты);
   - `cache_creation_input_tokens` ≈ хвост на пользователя (~100–150 токенов).
3. Если `cache_creation` ≈ полный префикс — см. пункт 1 выше (первый блок
   не кешируется) или пункт 2 (инструменты поменялись).
