# Почему не подключался Intervals.icu

1. **Кнопка Connect → 401 (у всех).** Кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`.
   Переход по ссылке — навигация браузера, и fetch-обёртка с `Authorization: Bearer` не участвует,
   поэтому сервер отвечал `{"error":"unauthorized"}`. Исправлено: `auth/init` теперь отдаёт JSON `{url}`,
   SPA вызывает его через `api()` (с токеном) и затем сам переходит по `url`.

2. **Authorize-URL → 400 `invalid_request` (обходной путь с ручной ссылкой тоже сломан).**
   Единственное изменение с 2026-10-02 — в запрошенные scope добавили `CALENDAR:READ/WRITE`
   (до этого соединение Rivera прошло с `ACTIVITY:WRITE,WELLNESS:READ`). Ответ Intervals не называет
   параметр, поэтому это наиболее вероятная причина по логам, но проверить без обращения к Intervals
   я не мог. Scope по умолчанию возвращён к рабочему набору, переопределяется через `INTERVALS_SCOPES`.
   Чтобы вернуть календарь, нужно включить эти права в настройках OAuth-клиента на стороне Intervals.
   Заодно убрал нестандартное `safe=":,"` при кодировании URL (параметры теперь кодируются штатно).

3. **«Expired, reconnect» через час.** Intervals в ответе не отдаёт ни `expires_in`, ни `refresh_token`
   (токен долгоживущий). Код подставлял `DEFAULT_TOKEN_TTL = 3600` и по истечении помечал соединение
   как протухшее — хотя токен был рабочим. Теперь отсутствие `expires_in` = токен не истекает, рефрешер
   такие соединения пропускает; статус «reconnect» ставится только когда Intervals реально вернул 401
   на запрос с токеном. Также рефрешер больше не падает с `KeyError`, если в ответе refresh нет `expires_in`.

Не проверено вживую: внешние сервисы не вызывались. Для атлетов с уже сохранённым статусом «expired»
нужно один раз подключиться заново (хранилище в памяти, после перезапуска состояние и так сбрасывается).
