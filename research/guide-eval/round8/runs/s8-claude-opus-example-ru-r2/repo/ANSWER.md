# Почему save_fact сбрасывал кеш и что изменено

## Причина

`build_system()` собирал весь system prompt в один текстовый блок с одним
`cache_control` в конце: инструкции + профиль + дата + факты + язык. Кеш Anthropic
работает по хешу префикса, поэтому новый факт менял хеш всего блока, и следующий
вызов писал в кеш весь промпт заново (~1050 токенов по цене 1.25x). Это видно в
`logs/usage.jsonl`: round 2 после каждого `save_fact` даёт `cache_read_input_tokens: 0`
и `cache_creation_input_tokens` около 1040–1100. Сильнее всего это бьёт по вызову
внутри того же tool-loop, потому что `a.facts` уже изменён и промпт пересобирается.

## Что изменено (`bot.py`, `build_system` / `athlete_context`)

System теперь состоит из отдельных блоков:

1. `INSTRUCTIONS`: одинаковые для всех спортсменов и любого дня, с `cache_control`.
2. Шапка спортсмена: имя, вид спорта, зоны, цель, **язык**, дата, заголовок «Long-term facts:».
3. **Каждый факт в своём блоке**, в порядке добавления. `cache_control` стоит на последнем блоке.

`save_fact` дописывает блок в самый конец. Помимо явных маркеров, API проверяет
попадания на границах предыдущих блоков (до ~20 назад). Префикс до предыдущего
последнего факта уже лежит в кеше: это ровно позиция маркера в прошлом запросе.
Поэтому следующий вызов читает почти весь промпт из кеша, а пишет только новый
факт (~10–20 токенов). Строка `Language:`, которая раньше шла *после* фактов,
перенесена в шапку: всё, что стоит после фактов, сдвигалось бы при каждой записи.
Остальная логика (загрузка всех фактов, фильтр инструментов, tool-loop) не тронута.
В README обновлён абзац про кеширование.

## Проверка

Реального API-ключа нет, а внешние вызовы запрещены, поэтому проверял офлайн:
`reply()` с фейковым LLM, который моделирует префиксный кеш (маркеры, lookback по
границам блоков, минимум 1024 токена; токены считались грубо, как символы/4).
Результат: round 2 после `save_fact` даёт read ≈ 1150–1200, creation 4–8. Следующее
сообщение даёт read ≈ весь промпт. Полный промах был только в сообщении, где
ключевое слово подключило другую группу инструментов (так и ожидалось, см. ниже).
На реальном трафике стоит проверить по `logs/usage.jsonl`: после `save_fact`
`cache_creation_input_tokens` должен быть порядка длины одного факта, а не ~1000.

## Что пригодилось из заметки коллеги, а что нет

Пригодилось:
- Диагноз: кеш работает по хешу префикса, а запись в память меняет промпт и
  вытесняет всё, что идёт после изменённого байта.
- Отделить байт-стабильные инструкции (без дат и имён) от изменчивого хвоста и
  поставить маркер на инструкции. Он у меня есть: при более длинных инструкциях
  или на модели с меньшим порогом это даст общий префикс для всех спортсменов
  и защиту от смены даты или профиля.
- Не выбирать top-N фактов под сообщение: факты грузятся все и всегда.
- Инструменты стоят выше system в префиксе, поэтому фильтрацию оставил как есть
  (это совпадает с NOTES.md). Подключение группы `plan`/`race` по-прежнему даёт
  один полный промах. Это осознанная цена фильтра, не баг памяти.
- Шаг проверки через `usage`.

Не подошло как есть: схема «два маркера, хвост с фактами целиком во втором
сегменте». Здесь она бы ничего не дала. Инструкции занимают ~2500 символов
(≈600 токенов); вместе с инструментами и служебным промптом для tools префикс до
первого маркера около 900–950 токенов (по логам весь промпт ≈1046, хвост ≈100).
Это ниже минимальной кешируемой длины для `claude-sonnet-4-5` (1024 токена), а
маркер на более коротком префиксе API молча игнорирует. После `save_fact` снова
переписывался бы весь промпт. Поэтому основное исправление другое: факты как
append-only блоки в самом конце, плюс lookback по границам блоков. Оно не зависит
от того, дотягивают ли инструкции до порога. Цифры токенов в заметке (780/240)
относятся к другому боту, и их я не использовал. Пункт «упорядочить хвост от
редко меняющегося к часто» здесь важен не для читаемости, как сказано в заметке, а
по существу: факты должны идти последними.
