# Исправление подключения Intervals.icu

## Причины

1. Кнопка была ссылкой на `GET /api/intervals/auth/init`. Переход страницы не отправлял `Authorization` из SPA, поэтому сервер отвечал 401 каждому атлету. Теперь кнопка вызывает аутентифицированный `POST` через `fetch`, получает `authorize_url` и переводит браузер на него.
2. Запрошенные scope повторяли области `ACTIVITY` и `CALENDAR` с `READ` и `WRITE`. Это приводило к отказу на шаге авторизации. Оставлены `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`.
3. Ответ Intervals.icu в логе не содержал `refresh_token` и `expires_in`, но сервер назначал срок жизни 3600 секунд и фоновая задача удаляла рабочий токен. Убраны искусственный срок и обновление. При ответе 401 от API токен очищается, статус предлагает подключиться заново.
4. Обмен кода отправлял лишние поля `grant_type` и `redirect_uri`. Теперь отправляются только `client_id`, `client_secret` и `code`.

## Что пригодилось из заметки коллеги

Пригодились сведения о бессрочном токене без `refresh_token`, уникальных областях scope, составе запроса обмена кода и схеме `POST` init + переход браузера. Также применены проверка подписанного `state` в callback и защита от подключения другого Intervals-аккаунта к уже существующей связи. Для `state` оставлена существующая HMAC-подпись с лимитом 15 минут; дополнительно отклоняются метки времени из будущего и неизвестные пользователи. JWT не потребовался. Шифрование постоянного хранилища из заметки здесь неприменимо: этот пример хранит связи только в памяти; для продакшен-хранилища это остаётся отдельным требованием.

## Проверка

Локально пройдены проверки синтаксиса Python и JavaScript, состава полей обмена кода, сохранения связи без срока истечения, отклонения другого athlete id, а также HTTP-проверки авторизации init и перехода в статус `revoked, reconnect` после смоделированного 401. Живой OAuth-поток с Intervals.icu не запускался: в репозитории только заглушки клиентских реквизитов, внешние запросы запрещены условиями задачи.
