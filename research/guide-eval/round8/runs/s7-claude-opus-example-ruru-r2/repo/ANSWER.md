# Почему не подключался Intervals.icu и что исправлено

Нашлось три независимые причины. Две из них ломают кнопку Connect, третья
отключала тех, у кого подключение всё-таки прошло.

## 1. Кнопка Connect: 401 у всех (тикет #214)

`static/app.js` рисовал кнопку как обычную ссылку `<a href="/api/intervals/auth/init">`.
При переходе по ссылке браузер не отправляет заголовок `Authorization`: токен
tricoach лежит в `localStorage`, и добавляет его только fetch-обёртка `api()`.
Поэтому `GET /api/intervals/auth/init` отвечал
`401 (no Authorization header)` (`logs/connect-attempt.log`, §1), и атлет видел
белую страницу `{"error": "unauthorized"}`.

**Исправление:**
- `server.py`: init стал аутентифицированным `POST /api/intervals/auth/init`.
  Вместо 302 он возвращает JSON `{"authorize_url": ...}`. GET-маршрут удалён.
- `app.js`: ссылку заменила `<button>`. Она вызывает
  `api("/api/intervals/auth/init", {method: "POST"})`, затем
  `window.location.assign(authorize_url)`.
- Callback менять не пришлось: он и раньше определял пользователя по
  подписанному `state`, а не по заголовку.

## 2. Authorize-шаг: 400 `invalid_request` (вторая половина #219)

С 2026-10-02 (вместе с синхронизацией календаря) `config.SCOPES` равен
`ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`, то есть
области ACTIVITY и CALENDAR указаны по два раза. Intervals не принимает
повторную область: `:WRITE` уже включает `:READ`, а дубль даёт ошибку
«Duplicate scope». Поэтому даже ссылка, собранная вручную, получала 400 ещё до
экрана согласия (§2 лога). До календаря Rivera подключился, когда дублей,
судя по всему, не было: в ответе вернулся scope `ACTIVITY:WRITE,WELLNESS:READ`.

Оговорка: в логе только общий `{"error":"invalid_request"}`, текста
«Duplicate scope» там нет. Вывод сделан по правилу из заметки и по совпадению
дат: ошибка появилась после того, как к scope добавили области.

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`. Каждая
область указана один раз, `:WRITE` там, где приложение пишет (тренировки в
календарь), wellness только читается.

## 3. «Expired, reconnect» через час после подключения (тикет #219)

Токены Intervals.icu не истекают: в ответе нет ни `expires_in`, ни
`refresh_token` (это видно в §3 лога). Код же при отсутствии `expires_in`
подставлял `DEFAULT_TOKEN_TTL = 3600`. Через ~55 минут фоновый
`refresh_tokens()` видел «истекающий» токен без refresh_token и помечал
подключение `expired, reconnect`, стирая рабочий токен. Rivera ничего не
отзывал, отключили его мы сами.

**Исправление:**
- `store_connection` больше не придумывает срок жизни: без `expires_in` поле
  `expires_at = None`, `DEFAULT_TOKEN_TTL` удалён.
- `refresh_tokens()` пропускает токены без срока. Логику обновления я оставил
  на случай, если провайдер начнёт отдавать `expires_in`.
- Отзыв теперь обнаруживается лениво. Если `/wellness` получает 401 от
  Intervals, подключение помечается `revoked, reconnect`, токен стирается, SPA
  показывает кнопку Connect, а приложение не падает.

## Проверка

Проверял локально: поднимал заглушку Intervals через `INTERVALS_BASE`, во
внешние сервисы ничего не уходило. `POST init` → 200 с `authorize_url`, в scope
нет повторных областей. Callback → 302 `/?connected=1`, `expires_at=None`.
`status` = connected, `wellness` = 200. После того как заглушка начала отвечать
401, `wellness` возвращает 409, а `status` = `revoked, reconnect`. С настоящим
Intervals.icu поток не проверялся: нужны боевые `client_id`/`client_secret` и
реальный аккаунт.

## Что пригодилось из заметки коллеги

- **п.4 (init должен быть POST, а не ссылкой)**: это ровно причина №1.
- **п.2 (Duplicate scope)**: объясняет 400 на authorize-шаге (причина №2), по
  этому правилу собрана новая строка scope.
- **п.1 (нет refresh_token/expires_in, отзыв ловить по первому 401)**:
  объясняет «expired через час» (причина №3) и даёт ленивую обработку 401.
- **`state` как подпись с TTL 15 минут**: в коде это уже было (HMAC +
  timestamp, `max_age=900`). Подтвердило, что callback переделывать не надо.

Что не использовал:
- **п.3 (отправлять в обмен кода только `client_id`/`client_secret`/`code`)**:
  у нас обмен кода с `grant_type` и `redirect_uri` у Rivera прошёл успешно, так
  что это не причина поломки. Код я не трогал.
- **`state` как JWT с claim `purpose`**: текущий HMAC-формат уже работает,
  переписывать незачем.
- **Защита от несовпадения аккаунтов при переподключении, шифрование токена
  при хранении**: полезно, но к описанным симптомам не относится. Шифрование
  стоит сделать в проде (Postgres), раз токен бессрочный.
- **Регистрация клиента через форум, ручная проверка с реальным аккаунтом и
  отзывом**: в рамках задачи недоступно, и это внешние действия.
