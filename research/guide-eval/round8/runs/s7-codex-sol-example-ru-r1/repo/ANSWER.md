# Почему не подключался Intervals.icu

1. Кнопка была обычной ссылкой на `GET /api/intervals/auth/init`. При переходе браузер не добавлял токен приложения из `localStorage` в заголовок `Authorization`, поэтому сервер отвечал 401. Это видно в `logs/connect-attempt.log` и обращении #214.
2. После ручного обхода кнопки URL авторизации содержал `ACTIVITY:READ` вместе с `ACTIVITY:WRITE` и `CALENDAR:READ` вместе с `CALENDAR:WRITE`. Для Intervals.icu доступ `WRITE` уже включает `READ`; повтор области делает запрос некорректным. Лог показывает ответ 400 на этапе авторизации после добавления календаря.
3. Ответ на обмен кода в логе не содержал ни `expires_in`, ни `refresh_token`. Сервер сам назначал срок в 3600 секунд, затем удалял рабочий токен и требовал повторного подключения. Это объясняет обращение #219.

## Исправление

Кнопка теперь вызывает авторизованный `POST /api/intervals/auth/init` через `fetch`, получает `authorize_url` и перенаправляет браузер. Запрошены области `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`. Callback проверяет подписанное состояние с назначением `intervals_oauth` и сроком 15 минут, обменивает код с полями `client_id`, `client_secret`, `code`, сохраняет токен и идентификатор атлета. Токен не истекает по локальному таймеру. Если Intervals ответит 401 на запрос данных, сервер очищает токен и показывает необходимость переподключения. При повторном подключении другого аккаунта Intervals callback отклоняется, пока пользователь явно не отключит старый.

## Что пригодилось из заметки коллеги

Подошли все четыре описанные особенности: авторизованный POST для начала потока, отсутствие обновления и заранее известного срока жизни токена, уникальность областей доступа, а также набор полей для обмена кода. Идея передавать пользователя в подписанном `state` и проверять несовпадение аккаунта тоже применена. Использован существующий формат с HMAC, дополненный назначением и проверкой времени; JWT как формат здесь не требуется. Рекомендация шифровать токен при хранении относится к постоянному хранилищу: в этом репозитории соединения живут только в памяти процесса, а схему и код производственной базы здесь не предоставили.

## Проверка

Локальные тесты `python3 -m unittest -v test_intervals` проходят: начало потока и авторизация, области доступа, callback и несовпадение аккаунта, отсутствие искусственного истечения, отзыв доступа и проверка `state`. `node --check static/app.js` и `git diff --check` тоже проходят. Реальное согласие и запрос к Intervals.icu не проверялись: по условию задачи внешние запросы запрещены, а в `config.py` стоят тестовые значения клиента.
