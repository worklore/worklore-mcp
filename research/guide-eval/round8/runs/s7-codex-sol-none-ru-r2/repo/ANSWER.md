# Причины сбоя интеграции Intervals.icu

1. **Кнопка Connect обходила авторизованный API-клиент.** SPA хранит токен входа в `localStorage` и добавляет `Authorization: Bearer` только в вызовы `api()`. Обычная ссылка на `/api/intervals/auth/init` открывала документ без этого заголовка. Сервер возвращал 401, что видно в `logs/connect-attempt.log`. Кнопка теперь получает URL авторизации через `api()`, затем переводит браузер на него.

2. **Запрос разрешений перестал проходить у провайдера.** В логе URL с расширенным набором `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE` получает `400 invalid_request` ещё до экрана согласия. Ранее успешное подключение вернуло `ACTIVITY:WRITE,WELLNESS:READ`. Вернул этот подтверждённый логом набор. По одному ответу `invalid_request` нельзя определить, какое именно из добавленных разрешений провайдер отклонил. Доступ к реальному Intervals.icu по условию задачи не проверялся; если синхронизации календаря нужны дополнительные разрешения, их надо отдельно сверить с провайдером перед повторным добавлением.

3. **Сервер сам отключал токен без указанного срока действия.** У единственного успешного подключения ответ не содержал `expires_in` и `refresh_token`. Код назначал отсутствующему сроку значение 3600 секунд и фоновый процесс помечал связь как истёкшую. Теперь отсутствие `expires_in` означает, что локального срока нет; токен с явным сроком обновляется при наличии `refresh_token`, а без него помечается истёкшим после указанного срока.

Проверено локальными тестами: авторизация начального запроса, параметры URL, callback без токена входа, сохранение токена без срока, истечение токена с явным сроком и обновление через `refresh_token`. Проверка обращений к провайдеру не выполнялась.
