# Почему вторая публикация возвращала 500

`publish()` сначала читает существующие истории и добавляет в новую запись поле `similar`. Для первой истории список пуст. Для второй `similarity()` вычисляет оценку через деление и `round()`, возвращая `float`; эта оценка попадает в `similar[0].score`. В `logs/error.log` ошибка возникает именно при `table.put_item(Item=item)`: сериализатор boto3 для DynamoDB отклоняет `float` (`TypeError: Float types are not supported. Use Decimal types instead.`). Обработчик превращает исключение в HTTP 500.

# Исправление

Перед `put_item` весь элемент рекурсивно проходит через `dynamodb_safe()`: конечные `float` преобразуются в `Decimal(str(value))`, включая значения во вложенных списках и словарях. Неконечные значения отклоняются явно. Формат оценки и точность, заданная `similarity()`, сохранены; новые вычисляемые поля тоже не смогут передать `float` в сериализатор.

Добавлен тест двух последовательных запросов к `handler()` с одной таблицей. Он проверяет два ответа 201, наличие второй записи и её оценку типа `Decimal`. Отдельный тест проверяет преобразование вложенного числа и отклонение `NaN`. Команда `python3 -m unittest discover tests -v`: 3 теста прошли. Внешнюю таблицу не использовали.

# Что пригодилось из заметки коллеги

- Объяснение разницы между пустой и заполненной таблицей: только после первой записи выполняется путь с оценкой похожести.
- Указание проверить вычисляемые значения, попадающие в `put_item`, и преобразовать `float` в поддерживаемый DynamoDB тип на границе записи.
- Идея тестировать запись после уже существующей записи, а не только первую публикацию.

Предложение хранить целые проценты не применяли: оно изменило бы точность сохранённой оценки. Публикацию в реальную таблицу не выполняли из-за запрета на обращения к внешним сервисам.
