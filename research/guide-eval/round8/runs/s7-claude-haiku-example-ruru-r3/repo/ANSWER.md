# Intervals.icu: почему не подключались и что исправлено

Три независимые причины. Каждая видна в логах или в коде.

## 1. Кнопка Connect давала 401 (`logs/connect-attempt.log`, №1)

Кнопка была `<a href="/api/intervals/auth/init">`. Это обычная навигация
страницы: браузер не отправляет `Authorization: Bearer ...` (токен лежит в
localStorage и добавляется только в fetch-обёртке). Сервер на `/auth/init`
честно отвечал 401 всем пользователям.

**Исправлено:** `auth/init` стал `POST` и возвращает JSON
`{authorize_url}` (`server.py`, `auth_init`). SPA вызывает его через `api()`
и делает `window.location.assign(authorize_url)` (`static/app.js`). GET на
этот путь теперь даёт 404.

## 2. Intervals отвергает authorize-запрос: дубли в scope (`connect-attempt.log`, №2)

`SCOPES` были `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`.
Для `ACTIVITY` и `CALENDAR` указаны и READ, и WRITE. По заметке коллеги
`:WRITE` уже включает `:READ`, а такой список Intervals отвергает
(`Duplicate scope`). Календарь добавили 2 октября, и поломка совпадает по
времени с тикетами.

В логе тело ответа `{"error":"invalid_request"}` не называет параметр, поэтому
причину я вывел по составу запроса, а не по тексту ошибки. Это наиболее
вероятная причина, но проверить её на живом Intervals здесь было нельзя.

**Исправлено:** `config.py`, `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"`.
Каждая область один раз. Права не расширены: READ-дубли были единственным
отличием. Приложение ничего не читает из календаря и активностей, поэтому
`CALENDAR:READ` и `ACTIVITY:READ` не нужны.

## 3. Подключение «истекает» через час (`connect-attempt.log`, №3)

Intervals не отдаёт ни `expires_in`, ни `refresh_token`. Сервер подставлял
`DEFAULT_TOKEN_TTL = 3600` и через фоновый `refresh_tokens()` помечал
подключение как `expired, reconnect`, когда срок «проходил». В логе:
подключились в 17:41:04, отключили в 18:37:12. Refresh-ветка была мёртвой:
без refresh_token она только ставила статус.

**Исправлено:**
- Срока нет: токен живёт до отзыва приложения в Intervals. `store_connection`
  больше не считает срок; фоновый поток refresh удалён; `DEFAULT_TOKEN_TTL` и
  `REFRESH_INTERVAL` убраны.
- Смерть токена определяем лениво: если Intervals отвечает 401 на
  `/wellness`, `mark_revoked()` очищает токен и ставит `expired, reconnect`.
  Клиент получает 409 со статусом (`server.py`, `wellness`), SPA показывает
  кнопку «подключиться заново».

## Что проверено

Локально, без живого аккаунта Intervals. Я поднял заглушку Intervals, которая
отвергает дубли scope, не отдаёт `expires_in`/`refresh_token` и умеет
отзывать токен. Прогнал полный поток через сервер (порт 8767 на копии кода):

- `GET /auth/init` → 404; `POST` без токена → 401; `POST` с токеном → `authorize_url`.
- Authorize с новым scope → 302 с кодом; со старым (дубли) → 400 `Duplicate scope`.
- Callback → `/?connected=1`; `status` → `connected`, без срока.
- `/wellness` → 200 с данными.
- После отзыва в заглушке: `/wellness` → 409 `expired, reconnect`, `status` → `expired, reconnect`.
- `node --check static/app.js` и `py_compile` проходят.

Не проверено: реальный `intervals.icu` (нужны настоящие `client_id`/`client_secret`
и зарегистрированный `redirect_uri`). Утверждения про отказ на дубли и
поведение токенов взяты из заметки коллеги и из логов, а не из live-запроса.
Стоит пройти поток с реальным аккаунтом перед выкаткой.

## Что взял из заметки коллеги, что пропустил

Взято:
- POST для init, возвращающий authorize URL как JSON (пункт 4 заметки).
- Правило «каждая область один раз, `:WRITE` вместо пары READ+WRITE» (пункт 2).
- Ленивая обработка отзыва по 401 вместо refresh (пункт 1).

Пропущено, и почему:
- Обмен кода: убирать `grant_type`/`redirect_uri` не нужно. В логе №3 обмен
  с текущими полями прошёл успешно (токен и `athlete` пришли).
- `state` как JWT с `purpose`: текущий HMAC-подписанный `state` с TTL 15 минут
  уже делает то же самое. Переписывать незачем.
- Проверка «другой athlete id при переподключении»: это продуктовое решение
  (можно ли сменить аккаунт Intervals), а не исправление бага. Не добавлял.
- Шифрование токена при хранении: в репозитории сейчас in-memory dict, без
  БД и ключей. Шифровать в памяти без ключа бессмысленно. Когда появится
  Postgres, токен стоит хранить зашифрованным (так и советует заметка).

## Что сделать дальше

- Перезапустить сервер. Подключения in-memory, поэтому после рестарта все
  атлеты подключаются заново. Новый вариант не сломается через час.
- Атлетам, которые уже подключались (Rivera), нажать «Connect Intervals.icu»
  в обычном режиме. Ручная вставка ссылки из тикета #219 больше не нужна.
- Проверить поток на реальном аккаунте Intervals (см. выше).

Изменения не закоммичены.
