# Почему вторая публикация возвращала 500

`logs/error.log` показывает `TypeError: Float types are not supported. Use Decimal types instead.` при `table.put_item(Item=item)`. Первая публикация проходила, потому что таблица была пустой: `related()` возвращала пустой список. При второй публикации она находила первую историю, а `similarity()` записывала в `similar[0].score` результат деления и взвешивания типа `float`. Сериализатор DynamoDB не принимает `float`, поэтому обработчик возвращал 500.

# Исправление

В `src/app.py` расчёт сходства теперь целиком выполняется через `Decimal`, включая отношения множеств, веса и округление. `score` сохраняет прежний смысл и точность: число от 0 до 1 с округлением до четырёх знаков, но в совместимом с DynamoDB типе. Тест `test_second_publish_stores_dynamodb_compatible_similarity` отправляет две истории через обработчик, проверяет оба ответа 201, две записи и тип и значение сохранённой оценки.

Проверка: `python3 -m unittest discover tests -v` — 2 теста прошли. До исправления новый тест воспроизводил ответ 500 и тот же `TypeError`. Реальную таблицу не использовали: по условию задачи ничего не отправляли во внешние сервисы.

# Что пригодилось из заметки коллеги

- Причина с `float` в записи DynamoDB и различие между пустой и заполненной таблицей точно совпали с логом и кодом.
- Совет проследить вычисляемые значения до `put_item` указал на `similar[].score`; тест с уже существующей записью поймал ошибку, которую исходный тест первой публикации пропускал.
- Идея использовать `Decimal` подошла. Преобразование в целые проценты не понадобилось: оно изменило бы шкалу и потеряло бы часть точности оценки. Проверка публикацией в реальную таблицу тоже не применялась из-за запрета на внешние сервисы.
