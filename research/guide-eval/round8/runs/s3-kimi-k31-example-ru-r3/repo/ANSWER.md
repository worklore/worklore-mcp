# Почему задача молчала

Планировщик исправен: `launchctl-print.txt` показывает `runs = 6` и `last exit code = 1`. То есть задача шесть раз запускалась и падала, а не была неактивна.

Были две последовательные ошибки:

1. **Headless CLI не мог авторизоваться.** В `Library/LaunchAgents/com.vk.nightly-review.plist` в `EnvironmentVariables` был только `PATH`, но не было `USER`. В `Library/Logs/nightly-review.err` после каждого запуска записано `Not logged in · Please run /login`. Поэтому `claude` завершался с ошибкой и не создавал обзор.
2. **Затем ломался сам путь уведомления об ошибке.** В `bin/nightly-review.zsh` сразу после вызова `claude` выполнялось `status=$?`. В zsh `status` — readonly-переменная, поэтому присваивание аварийно завершало скрипт до ветки с `notify.sh`. Это подтверждается шестью строками `read-only variable: status` в том же журнале. В результате не отправлялись ни успешные сообщения (CLI падал), ни сообщения об ошибке (скрипт умирал до вызова notifier).

# Исправления

- В plist добавлено `EnvironmentVariables.USER = vk`, чтобы CLI мог найти авторизацию в keychain.
- В `bin/nightly-review.zsh` переменная `status` заменена на обычную `rc`; код ошибки сохраняется, передается в уведомление и возвращается из скрипта.
- Вызову `claude -p "$PROMPT" ...` добавлен `< /dev/null`. Это профилактика еще одного launchd-сбоя из заметки: при prompt-аргументе CLI не должен ждать данных на stdin. В исходных журналах такого зависания не было, поэтому это не относится к двум подтвержденным причинам прошлых падений.

# Что пригодилось из заметки коллеги

- Проверка `launchctl print`: именно счетчик запусков и код выхода показали, что проблема не в расписании.
- Чтение `StandardErrorPath` до построения гипотез: журнал дал обе точные ошибки.
- Замена `status=$?` на `rc=$?`.
- Добавление `USER` в окружение plist.
- Закрытие stdin через `< /dev/null` при передаче prompt аргументом.
- Проверка реального результата, а не только кода выхода, и принудительный запуск ошибочной ветки.

Вариант с передачей prompt через stdin не использован, поскольку применен предложенный в той же заметке альтернативный вариант: prompt остается аргументом, а stdin закрыт. Логирование длительности и дополнительный перенос notifier не понадобились для устранения найденных причин.

# Проверка

- `zsh -n`, `bash -n` и `plutil -lint` прошли; значение `USER` также извлечено из plist и проверено.
- Исправленный скрипт запущен с локальными заглушками `claude` и `notify.sh`, без обращения к внешним сервисам.
- Успешный сценарий: создан свежий markdown-файл с результатом и вызвано сообщение `nightly review done: mock review`.
- Ошибочный сценарий: заглушка вернула 23, скрипт тоже вернул 23 и вызвал сообщение `nightly review FAILED (exit 23), see ...`.
- В обоих сценариях заглушка CLI увидела `USER=vk` и EOF на stdin.

Реальный launchd-агент и Telegram не задействовались: изменены только файлы снимка в текущей директории.
