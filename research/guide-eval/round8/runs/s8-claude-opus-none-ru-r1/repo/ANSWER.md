# Почему после save_fact кеш промахивался и что изменено

## Причина

Системный промпт был **одним блоком** с `cache_control`: `INSTRUCTIONS` + профиль
атлета + список фактов. Кеш промпта префиксный (порядок: tools → system → messages),
поэтому изменение любого байта внутри блока даёт новый ключ кеша для всего блока.

`save_fact` дописывает факт в `a.facts`, а `reply()` пересобирает system **на каждом
раунде** tool-loop. Поэтому уже следующий вызов (round 2 того же сообщения) получал
другой текст → `cache_read_input_tokens: 0`, `cache_creation_input_tokens` ~1050
(по цене 1.25× от обычного input). В `logs/usage.jsonl` так выглядит каждая строка
после `save_fact`. Длина фактов и их количество роли не играют — промах вызывает сам
факт изменения, поэтому попытки из NOTES.md ничего не дали.

## Что изменено (`bot.py`)

1. **System разбит на три блока** (`build_system`):
   - `INSTRUCTIONS`: статичен, одинаков для всех атлетов, есть breakpoint `cache_control`;
   - `athlete_context(a)`: имя, вид спорта, зоны, цель, язык и факты, уже
     «вшитые» в промпт (`facts[:facts_in_prompt]`), есть breakpoint;
   - `volatile_context(a, today)`: **без** `cache_control`. Здесь факты, сохранённые
     в текущей «тёплой» сессии (`facts[facts_in_prompt:]`), и дата. Текст
     продолжает список «Long-term facts:», так что модель видит один общий список.
     Дату я тоже унёс сюда, чтобы смена суток не сбрасывала кешированный профиль.
2. **Факты переносятся в кешируемый блок лениво** (`fold_facts`). В записи атлета
   появились поля `facts_in_prompt` и `last_call`. Новые факты переходят в кешируемый
   блок только когда с последнего вызова прошло ≥ 5 минут (`CACHE_TTL`), то есть
   когда кеш всё равно уже истёк. Пока сессия тёплая, всё, что стоит до последнего
   breakpoint, остаётся побайтно одинаковым, и `save_fact` его не трогает.
   `last_call` обновляется после каждого API-вызова.

Почему не ограничился одним разбиением «инструкции | профиль+факты». У Sonnet 4.5
минимальная длина кешируемого префикса 1024 токена. По логу весь промпт с тремя
фактами занимает ~1046 токенов, значит tools + инструкции дают около 950. Breakpoint
сразу после `INSTRUCTIONS` оказался бы ниже минимума и молча не сработал бы. Ленивый
перенос не зависит от этого порога. Breakpoint на инструкциях оставлен как бонус: если
инструкции вырастут выше порога, их общий кеш будут использовать все атлеты.

Ожидаемый эффект: вызовы после `save_fact` (round 2 и следующее сообщение в течение
5 минут) читают из кеша тот же префикс, что и до записи. Новые факты добавляют лишь
~15 некешированных токенов каждый. Полная запись кеша происходит только на «холодном»
вызове, где она была бы и так.

## Проверка

Реального API-ключа нет, и наружу я ничего не отправлял. Проверял на фейковом LLM,
который моделирует префиксный кеш по breakpoint'ам. Сценарий: log_session →
вопрос → save_fact → вопрос → save_fact → вопрос. Все вызовы после `save_fact`
дали полный cache read и нулевой cache creation. Единственная запись — на сообщении
со словом «race»: оно подключает `predict_race`, а это другой набор tools. Ещё
проверил, что после 6 минут простоя факты переносятся в кешируемый блок.
После деплоя в `usage.jsonl` строки после `save_fact` должны показывать
`cache_read_input_tokens` ≈ как у предыдущего вызова.

## Что не трогал / на что обратить внимание

- Фильтрацию tools по ключевым словам не трогал (как просит NOTES.md). Но tools
  стоят в префиксе раньше system, поэтому сообщение с plan/race-ключевыми словами
  по-прежнему пишет свою отдельную запись кеша. Это отдельный, давний компромисс.
- `reply()` теперь сохраняет запись атлета после каждого вызова (ради `last_call`).
  Для нового пользователя запись создаётся с первого сообщения, а не с первого `save_fact`.
  Старые записи без новых полей загружаются нормально (у полей есть дефолты).
- Порог 5 минут считается по пользователю, а не по конкретному префиксу. Если запись
  кеша вытеснят раньше TTL, будет один промах, как и раньше.
