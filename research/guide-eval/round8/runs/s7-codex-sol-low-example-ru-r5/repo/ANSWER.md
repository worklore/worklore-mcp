# Intervals.icu: причины и исправления

1. Кнопка `Connect` была ссылкой на защищённый `GET /api/intervals/auth/init`. При переходе браузер не добавлял токен приложения из `localStorage` в заголовок `Authorization`, поэтому сервер возвращал 401. Теперь кнопка вызывает авторизованный `POST` через `fetch`, получает `authorize_url` и переводит браузер на него.
2. Запрашивались одновременно `ACTIVITY:READ` и `ACTIVITY:WRITE`, а также `CALENDAR:READ` и `CALENDAR:WRITE`. Intervals отклонял такой запрос до экрана согласия как дублирование областей доступа; в логах виден 400 `invalid_request`. Оставлены `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`.
3. Ответ Intervals для успешного подключения не содержал `expires_in` и `refresh_token`. Приложение назначало выдуманный срок 3600 секунд и фоново сбрасывало рабочий токен, из-за чего Rivera попросили подключиться снова. Этот таймер и обновление удалены. При реальном 401 от API токен очищается и статус становится `reconnect`.

Из заметки коллеги пригодились: запуск через авторизованный `POST`, правило об уникальности областей `scope`, обмен кода с полями `client_id`, `client_secret`, `code`, отсутствие обновления токена и обработка отзыва по 401. Уже существующий подписанный `state` связывает callback с пользователем; проверка дополнена ограничением времени в обе стороны и проверкой существования пользователя. Также добавлена проверка совпадения athlete ID при повторном подключении. JWT из заметки не вводился: имеющаяся HMAC подпись решает задачу в этом приложении. Шифрование токена в хранилище здесь не реализовано: текущий прототип хранит все подключения только в памяти; для постоянного хранилища это остаётся обязательной мерой.

Проверено локально без запросов к Intervals: синтаксис Python, отказ неавторизованному запросу, `POST` и его URL/scope/state, callback с подставленным ответом токена без срока действия, статус подключения и переход в `reconnect` при подставленном API 401. Реальное согласие в Intervals не проверялось: в репозитории только заглушки OAuth клиента.
