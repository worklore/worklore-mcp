# Кеширование промпта и `save_fact`

## В чём была проблема

`build_system` собирал один блок `INSTRUCTIONS + athlete_context` с одним
маркером `cache_control`. Кеш работает как хеш префикса, а в `athlete_context`
входит список фактов. Внутри цикла инструментов `run_tool` дописывает факт в
`a.facts`, и второй раунд пересобирает системный промпт из того же `a`. Значит,
промпт меняется уже на втором раунде того сообщения, в котором вызван
`save_fact`. В `logs/usage.jsonl` так происходит со всеми шестью вызовами
`save_fact`: в первом раунде `cache_read` около 1046, во втором
`cache_read: 0` и `cache_creation` около 1061. Каждый раз весь промпт кешируется
заново.

## Почему «просто поставить два маркера» здесь не сработает

Очевидное исправление — два кешируемых блока: инструкции отдельно, контекст
атлета отдельно. Здесь оно тихо не сработает. Sonnet 4.5 (`MODEL`) кеширует
префикс только от **1024 токенов**, причём в префикс до первого маркера входят
и инструменты, а не только системные блоки. По логу весь промпт атлета 77
(2 факта, базовые инструменты) занимает ровно 1024 токена. Значит, инструменты
вместе с `INSTRUCTIONS` — это около 930–960 токенов, и даже с профилем остаётся
меньше 1024. Маркер ниже минимума API игнорирует без ошибки, и поведение
осталось бы прежним. Офлайн-симуляция это подтверждает
(`python3 tests/sim_cache.py --naive`): после каждого `save_fact` снова
`cache_creation` около 1050.

## Что изменено (`bot.py`)

Системный промпт теперь состоит из двух блоков, от самого стабильного к самому
изменчивому:

1. **Кешируемый блок** (`cache_control: ephemeral`): `INSTRUCTIONS` + профиль
   (имя, спорт, зоны, цель, язык) + *снимок* фактов. Вместе с инструментами это
   больше 1024 токенов, так что блок реально кешируется.
2. **Некешируемый хвост** без маркера: сегодняшняя дата и факты, сохранённые
   после снимка. Это несколько десятков токенов по обычной цене входа — намного
   дешевле, чем пересоздавать 1000+ токенов по цене ×1,25.

Новые факты переносятся в кешируемый блок (`snapshot_size`) только тогда, когда
он всё равно будет создан заново:
- последний вызов API для этого атлета был больше 4,5 минут назад, то есть
  5-минутный TTL уже истёк;
- или в хвосте накопилось больше `MAX_PENDING_FACTS = 8` фактов;
- или процесс перезапустился (состояние хранится в памяти, `_prompt_state`).
  В худшем случае это стоит одного создания кеша, как и раньше.

Дата переехала из начала контекста в хвост: раньше в полночь она меняла
кешируемый префикс, теперь не меняет.

Модель по-прежнему видит все факты уже на следующем запросе; недавно
сохранённые идут под заголовком «More long-term facts (recent)». Фильтрацию
инструментов я не трогал (NOTES.md просит её оставить). Формат `athletes.json`
не изменился. В README обновлён абзац про кеширование.

## Проверка

Ключа API нет, а обращаться к внешним сервисам запрещено, поэтому проверить на
живом API я не мог. Вместо этого `tests/sim_cache.py` прогоняет `reply()`
через фейковый кеш с теми же правилами (хеш префикса, точки разрыва, минимум
1024 токена, оценка токенов откалибрована по логу):

| раскладка | cache_creation за 11 вызовов (2 из них save_fact) |
|---|---|
| наивные два маркера | 3163 (полный промпт заново после каждого save_fact) |
| новая | 1036 (только первый вызов) |

После деплоя стоит проверить настоящий `logs/usage.jsonl`: вызов после
`save_fact` должен показывать `cache_creation_input_tokens: 0` и `cache_read`
примерно на размер всего кешируемого блока. Числа токенов в симуляции —
оценки. Аргумент про порог 1024 опирается на реальные числа из лога.

## Что пригодилось из заметки коллеги, а что нет

Пригодилось:
- Главный диагноз: кеш — это хеш префикса, а запись в память переписывает
  промпт и вытесняет всё после изменённого байта.
- Порядок блоков от стабильного к изменчивому и требование, чтобы кешируемая
  часть совпадала байт в байт. Поэтому дата ушла из кешируемого блока.
- Инструменты выше системного промпта должны быть стабильными, а
  фильтрацию по ключевым словам не надо убирать. Внутри цикла одного сообщения
  список инструментов постоянен, и именно там кеш окупается больше всего.
- Не отбирать top-N фактов под сообщение: факты грузятся все и всегда.
- Проверять результат по `cache_creation_input_tokens` /
  `cache_read_input_tokens` в `usage`. Их раздел «Проверка» прямо ложится на
  проверку выше.

Не пригодилось или использовано по-другому:
- Главный рецепт — два маркера `cache_control` (инструкции | хвост
  пользователя) — здесь в лоб не работает. Наш статический префикс меньше
  минимума 1024 токена для Sonnet 4.5. В заметке про минимум ничего не сказано;
  их ~780 токенов инструкций, видимо, добирались до порога за счёт ~55
  инструментов. Вместо второго маркера я сделал хвост некешируемым, а новые
  факты переношу в кешируемый блок отложенно.
- «Статический блок, общий для всех пользователей байт в байт»: здесь
  кешируемый блок у каждого атлета свой (в нём профиль и снимок фактов).
  Закешировать только общую часть не даёт тот же минимум, а в чате один на
  один такое разделение почти ничего не даёт.
- Части про ~55 MCP-инструментов и экономию 75% от фильтрации: этот бот уже
  фильтрует инструменты (с марта).
