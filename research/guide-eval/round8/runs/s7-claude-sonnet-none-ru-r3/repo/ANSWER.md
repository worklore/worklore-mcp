# Почему не подключался Intervals.icu

1. **Кнопка Connect давала 401 (тикет #214).** Кнопка была ссылкой `<a href="/api/intervals/auth/init">` — это навигация браузера, а токен входа передаётся только заголовком `Authorization: Bearer` через fetch-обёртку SPA. Заголовка в навигации нет → `{"error":"unauthorized"}` у всех. Исправлено: кнопка делает `api("/api/intervals/auth/init")` (с токеном), эндпоинт возвращает JSON `{url}`, и SPA переходит по нему.

2. **Токен «истекал» через час (тикет #219).** Intervals.icu в ответе на обмен кода не присылает ни `refresh_token`, ни `expires_in` (см. лог 2026-09-19): токен долгоживущий. Код же подставлял выдуманный `DEFAULT_TOKEN_TTL = 3600`, а фоновый рефрешер без refresh-токена помечал подключение «expired, reconnect». Исправлено: без `expires_in` срок не задаётся (`expires_at=None`), рефрешер такие подключения пропускает; обновление токена срабатывает, только если провайдер сам выдал срок и refresh-токен.

3. **Ручная ссылка авторизации давала 400 `invalid_request` (после 2026-10-02).** Единственное, что изменилось, — запрошенные scope: добавили календарь, и список стал `ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE`. Сейчас он избыточный (в Intervals `:WRITE` включает `:READ`; у Rivera при рабочем подключении был выдан только `ACTIVITY:WRITE,WELLNESS:READ`). Я сократил до `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`. Также параметры теперь кодируются стандартным `urlencode` (раньше `:` и `,` оставлялись как есть). **Это не проверено**: сообщение 400 не говорит, какой параметр плох, а обращаться к внешним сервисам мне нельзя. Если 400 останется — проверить имена scope в настройках OAuth-приложения на Intervals.icu и `redirect_uri`/`client_id` (в config сейчас placeholder'ы; реальные значения — в окружении деплоя).

Пункты 1 и 2 — ошибки в коде, видны из логов и подтверждены чтением; пункт 3 — наиболее вероятная причина, требует проверки на реальном Intervals.icu.
