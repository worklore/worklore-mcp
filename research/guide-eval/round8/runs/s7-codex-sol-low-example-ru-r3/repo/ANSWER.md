# Причины и исправление Intervals.icu

1. Кнопка была обычной ссылкой на `GET /api/intervals/auth/init`. При переходе браузер не добавляет токен приложения из `localStorage` в заголовок `Authorization`, поэтому сервер возвращал 401. Кнопка теперь вызывает авторизованный `POST` через существующий `fetch`-wrapper, получает `authorize_url` и переводит браузер на него.
2. Запрашивались `ACTIVITY:READ` вместе с `ACTIVITY:WRITE` и `CALENDAR:READ` вместе с `CALENDAR:WRITE`. Intervals отвергал запрос до экрана согласия. Оставлены `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE` — по одному scope на область.
3. Ответ Intervals в логах не содержит `expires_in` и `refresh_token`. Сервер придумывал срок 3600 секунд и сам отключал работающий токен. Удалены искусственный срок, обновление токена и фоновый поток. При настоящем 401 от API токен очищается и статус меняется на `reconnect`.

Дополнительно обмен кода теперь отправляет только `client_id`, `client_secret` и `code`; проверяется наличие токена и ID атлета в ответе. При повторном подключении другого аккаунта Intervals для того же пользователя колбэк возвращает 409. Существующий подписанный `state` с 15-минутным сроком сохранён; добавлены проверка будущей даты и принадлежности ID известному пользователю.

Из заметки коллеги пригодились объяснения про POST-init, уникальные области scope, отсутствие обновления токена, упрощённый обмен кода и обработку 401. Рекомендацию заменить `state` именно на JWT не применяли: в проекте уже есть подписанный и ограниченный по времени `state`, который выполняет нужную роль. Шифрование токена при хранении относится к постоянному хранилищу; в этом репозитории соединения существуют только в памяти процесса.

Локально проверены маршруты HTTP, параметры ссылки авторизации, поля обмена кода, сохранение токена без срока и переход в `reconnect` при смоделированном 401. Реальный OAuth с Intervals не запускался: для него нужны действующие учётные данные и внешний сервис.
