# Почему nightly-review молчал

## Что было на самом деле

Задача **запускалась**. В `launchctl-print.txt` видно `runs = 6` и `last exit code = 1`.
Агент загружен 2026-10-12, снимок сделан 2026-10-18 утром, то есть все шесть ночей
по расписанию в 02:30 отработали. launchd ни при чём: скрипт каждый раз падал и не мог об этом сообщить.
В `Library/Logs/nightly-review.err` одна и та же пара строк повторяется 6 раз:

```
Not logged in · Please run /login
/Users/vk/bin/nightly-review.zsh:19: read-only variable: status
```

## Причина 1: `claude` не залогинен в окружении launchd

В окружении launchd есть только `PATH` (это видно в `launchctl print` и в plist), а переменной `USER` нет.
Без `USER` CLI не находит свою учётную запись в связке ключей и падает с
`Not logged in`. В терминале всё работает, потому что там `USER` задан.

**Исправление:** в `EnvironmentVariables` в plist добавлен `USER = vk`.

## Причина 2 (из-за неё и была тишина): `status=$?` в zsh

В zsh `status` — специальный параметр только для чтения (синоним `$?`).
Присваивание `status=$?` даёт ошибку `read-only variable: status`, и неинтерактивный zsh
тут же завершается с кодом 1. Отсюда и `last exit code = 1`. Строка 19 стоит
**между** вызовом `claude` и вызовом `notify.sh`, поэтому код уведомления о сбое не выполнялся
ни разу. Проверено локально: `zsh -c 'false; status=$?; echo reached'` печатает ошибку,
`reached` не выводит и завершается с кодом 1.

**Исправление:** вместо `status` используется `rc=$?`.

## Что ещё изменено, чтобы тишина была невозможна

- `bin/nightly-review.zsh`:
  - промпт передаётся через stdin (`print -r -- "$PROMPT" | claude -p ...`), так что
    CLI не будет ждать открытый stdin и не будет проблем с многострочным аргументом;
  - в лог пишутся время начала, код выхода, длительность и размер отчёта;
  - в уведомление о сбое попадают первые 300 байт stderr от `claude`, и причина видна прямо в Telegram;
  - код выхода 0 при пустом отчёте тоже считается сбоем и приходит уведомление;
  - если упал сам `notify.sh`, об этом остаётся запись в `nightly-review.err`.
- `bin/notify.sh`: у `curl` добавлен `--fail-with-body`. Раньше ответ Telegram с HTTP-ошибкой
  (неверный токен или chat_id) считался успехом, потому что `-sS` без `-f` не меняет код выхода.

Проверка с заглушками `claude` и `notify.sh` во временном HOME (без сети):
сбой, успех и «exit 0, но пустой отчёт» дают по одному уведомлению с правильным текстом.

## Что сделать на машине (я ничего не запускал и не перезагружал)

```sh
launchctl bootout gui/$UID/com.vk.nightly-review
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.vk.nightly-review.plist
launchctl kickstart -k gui/$UID/com.vk.nightly-review
launchctl print gui/$UID/com.vk.nightly-review | grep -E 'runs|last exit'
tail ~/Library/Logs/nightly-review.err
```

Ожидаемый результат: `last exit code = 0`, свежий непустой `nightly-review-YYYY-MM-DD.md`,
правдоподобная длительность в логе (секунды, а не 0–2 с) и сообщение в Telegram.
После этого стоит один раз сломать что-нибудь нарочно (например, временно поменять `REPO`)
и убедиться, что приходит уведомление о сбое.
Если `Not logged in` останется, проверьте, что в терминале под тем же пользователем
работает `claude -p "hi"`. Если не работает, нужно заново выполнить `/login`.
Если не придёт само уведомление, `nightly-review.err` теперь покажет ошибку `notify.sh`
(например, `security find-generic-password` без доступа к связке ключей).

## Какие части заметки коллеги пригодились

Пригодились:
- **Сначала доказать, что задача запускалась** через `launchctl print` (runs и last exit code).
  Это сразу сняло версию «launchd не срабатывает».
- **Читать лог StandardErrorPath до того, как строить теории.** Обе причины были в нём.
- **`status` в zsh только для чтения, использовать `rc=$?`.** Это ровно моя причина 2,
  и уведомление о сбое тоже стояло после места падения.
- **Задать `USER` в `EnvironmentVariables`, иначе `Not logged in`** (из поправки от 2026-09-30).
  Это моя причина 1.
- **Код выхода показывает, что задача запустилась, а не что она сработала.** Поэтому пустой отчёт
  при exit 0 тоже считается сбоем, а длительность пишется в лог.
- **Логировать длительность и проверить уведомление, сломав скрипт нарочно.** Длительность
  добавлена в лог, проверка сбоя описана в шагах выше.
- **Передавать промпт через stdin.** Применено как защитная мера, хотя здесь причиной это не было.

Не подошло или не применимо:
- Ошибка `Input must be provided either through stdin or as a prompt argument`. В моих логах
  её нет: промпт доходил, падение было из-за входа в аккаунт.
- Совет про `< /dev/null`. Он нужен, только если промпт передаётся аргументом. Здесь промпт
  теперь идёт через stdin, а launchd и так по умолчанию подключает stdin к `/dev/null`.
