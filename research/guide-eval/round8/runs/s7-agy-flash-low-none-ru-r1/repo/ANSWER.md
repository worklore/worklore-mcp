# Причины сбоев интеграции с Intervals.icu

В ходе анализа логов (`logs/connect-attempt.log`), обращений атлетов (`logs/support-tickets.md`) и исходного кода приложения (`server.py`, `config.py`, `static/app.js`) были выявлены следующие причины проблем:

---

### 1. Кнопка «Connect Intervals.icu» выдавала ошибку 401 Unauthorized

* **Причина:**  
  В `static/app.js` кнопка была реализована как обычная ссылка `<a href="/api/intervals/auth/init">`. При клике по ней браузер выполнял стандартный GET-переход на эндпоинт инициализации авторизации. В отличие от AJAX-запросов через функцию `api()`, при переходе по ссылке браузер не отправляет заголовок `Authorization: Bearer <token>`, хранящийся в `localStorage`. В результате `server.py` возвращал `401 Unauthorized` (`no Authorization header`), а пользователь видел белую страницу с ошибкой.
* **Исправление:**  
  - В `static/app.js` кнопка подключения теперь вызывает `POST /api/intervals/auth/init` через обёртку `api()`, которая корректно передаёт токен атлета в заголовке `Authorization`. Получив сформированный URL авторизации, скрипт перенаправляет пользователя на страницу Intervals.icu.
  - В `server.py` добавлена поддержка метода `POST` для `/api/intervals/auth/init`, возвращающего JSON с URL авторизации `{"url": auth_url}`.

---

### 2. Ошибка 400 `invalid_request` при попытке открыть страницу авторизации Intervals.icu

* **Причина:**  
  В `config.py` параметр `SCOPES` был настроен как:
  ```python
  SCOPES = "ACTIVITY:READ,ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:READ,CALENDAR:WRITE"
  ```
  OAuth-сервер Intervals.icu не допускает дублирования одной функциональной области (area) с разными уровнями доступа (например, одновременное указание `ACTIVITY:READ` и `ACTIVITY:WRITE` или `CALENDAR:READ` и `CALENDAR:WRITE`). Поскольку уровень `:WRITE` автоматически включает права на чтение (`:READ`), одновременный запрос обоих вариантов расценивается как некорректный запрос (`invalid_request`). После добавления прав на календарь авторизация перестала открываться у всех атлетов.
* **Исправление:**  
  В `config.py` строка `SCOPES` приведена к правильному формату без дублирования функциональных областей:
  ```python
  SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"
  ```

---

### 3. Сброс подключения через час со статусом «expired, reconnect»

* **Причина:**  
  Intervals.icu выдаёт долгоживущие OAuth access token'ы, не возвращая в ответе `refresh_token` и `expires_in` (токен действует бессрочно до тех пор, пока пользователь не отзовёт доступ в интерфейсе Intervals).  
  В `server.py` при отсутствии `expires_in` токену ошибочно назначался искусственный срок жизни по умолчанию `DEFAULT_TOKEN_TTL = 3600` секунд (1 час). Фоновый поток `refresh_tokens()` проверял срок действия и, не обнаружив `refresh_token`, принудительно переводил статус подключения в `"expired, reconnect"`, сбрасывая рабочий токен.
* **Исправление:**  
  - В `store_connection()` токен теперь сохраняется без искусственного таймера истечения, если провайдер не указал время жизни.
  - Фоновый процесс обновления токенов `refresh_tokens()` больше не аннулирует бессрочные токены.
  - Добавлена реактивная обработка: если Intervals.icu при вызове API возвращает HTTP `401 Unauthorized` (токен был отозван атлетом), подключение переводится в статус `"expired, reconnect"`.
