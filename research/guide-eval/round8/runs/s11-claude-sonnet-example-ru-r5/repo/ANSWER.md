# Почему вторая публикация возвращает 500

**Причина.** `similarity()` в `src/app.py` возвращала `round(..., 4)` — это Python `float`.
`publish()` кладёт список `similar: [{slug, score}]` в item, и `put_item` в boto3 падает с
`TypeError: Float types are not supported. Use Decimal types instead.` (см. `logs/error.log`).
При первой публикации таблица пуста, `related()` возвращает `[]`, floats нет — всё проходит.
Начиная со второй в `similar` попадает score-float, и запись падает. Единственный тест
проверял только путь с пустой таблицей, поэтому баг не ловился.

**Исправление.**
1. `similarity()` теперь возвращает целые проценты (0–100).
2. Добавлен `dynamo_safe()` — на границе записи рекурсивно превращает любые float в `Decimal`,
   так что новый вычисляемый float не уронит запись снова.
3. Добавлен тест `test_second_publish_with_similar_story`: сначала кладёт запись, потом
   публикует вторую (путь с непустой таблицей). `FakeTable` валидирует типы как boto3.

Проверка: `python3 -m unittest discover tests`.

**Что пригодилось из заметки коллеги:** диагноз (float → DynamoDB, первая запись «чистая»
из-за пустой таблицы), целочисленные проценты, конвертация на границе записи и тест с
предварительно засеянной таблицей. Шаги про grep по `round(`/`/` я выполнил вручную
(в коде один такой случай). Реальную таблицу и «публикацию дважды» не использовал —
деплой и внешние сервисы запрещены; вместо этого `FakeTable`.
