# Причины и исправления

1. Кнопка Connect была обычной ссылкой. Переход браузера по ссылке не добавляет `Authorization: Bearer`, который приложение добавляет только через `fetch`. Поэтому `/api/intervals/auth/init` возвращал 401 каждому атлету. Теперь кнопка получает URL авторизации через API с токеном, затем переводит браузер на Intervals.icu.

2. После добавления синхронизации календаря в OAuth-запрос включили `CALENDAR:READ` и `CALENDAR:WRITE`. Лог показывает, что запрос с этими scope Intervals.icu отвергал с `invalid_request` до экрана согласия. Эти scope удалены; сохранены `ACTIVITY:READ`, `ACTIVITY:WRITE` и `WELLNESS:READ`. Запись запланированных тренировок относится к activity-доступу.

3. В успешном ответе на обмен кода не было ни `expires_in`, ни `refresh_token`. Сервер сам назначал срок действия в 3600 секунд, затем объявлял соединение истёкшим, хотя провайдер такого срока не указывал. Теперь отсутствие `expires_in` означает, что локальный таймер истечения не создаётся. Если провайдер явно задаёт срок, существующий механизм обновления или переподключения продолжает работать.

Проверка: локальный HTTP-запрос к `/api/intervals/auth/init` вернул URL с ожидаемыми scope; сохранение ответов с `expires_in` и без него дало соответствующие сроки. Внешних запросов и развёртывания не выполнялось.
