# Кеширование: запись в память не должна вытеснять инструкции

## Причина

В `build_system` весь системный промпт шёл одним блоком с одним `cache_control`.
Кеш работает по хешу префикса: блок `INSTRUCTIONS` (статичный) и блок с данными
атлета (дата, профиль, зоны, цель, `facts`) попадали в один кешируемый фрагмент.
Каждый `save_fact` меняет `facts`, меняет хеш, и вместе с ним промахивается всё,
включая инструкции, которые не меняются никогда. Это видно в `logs/usage.jsonl`:
после каждого `save_fact` `cache_creation_input_tokens` равен примерно полному
промпту (≈1000–1100), а `cache_read_input_tokens` равен 0.

## Что изменил

1. `bot.py`, `build_system`: системный промпт теперь два текстовых блока, у каждого
   свой `cache_control: ephemeral`.
   - Блок 1: `INSTRUCTIONS`. Константа, байт в байт одинаковая для всех атлетов и дней.
   - Блок 2: `athlete_context(...)`. Всё переменное: дата, профиль, зоны, цель, факты, язык.

   Запись в память меняет только блок 2. Префикс до первого маркера остаётся прежним,
   поэтому инструкции остаются в кеше.
2. `README.md`: абзац о кешировании обновлён, чтобы описывать два маркера.

Больше ничего не менял. Выбор инструментов, порядок схем и содержимое инструкций
не трогал.

## Что проверено

Без сети и без ключа API (внешние сервисы не вызывались):

- `build_system` возвращает два блока, у обоих `cache_control: ephemeral`.
- `INSTRUCTIONS`-блок байт в байт совпадает до и после `save_fact`, для другой даты
  и для другого атлета.
- Блок с данными атлета после `save_fact` меняется.
- `reply()` с подменённым LLM отправляет `system` с двумя блоками с маркерами. Файлы
  `data/athletes.json` и `logs/usage.jsonl` не трогались: проверка писала во временные
  пути.

Реальные числа кеша не проверены: нужен запуск с ключом. Ожидаемая картина после
деплоя:

- Первый запрос после `save_fact`: `cache_creation` ≈ размер блока 2 (сотни токенов),
  а не ≈1000+ как раньше.
- `cache_read` на том же запросе ≈ размер блока `INSTRUCTIONS` плюс инструменты.

## Риск, который надо проверить: минимум для кеширования

У Sonnet минимальный кешируемый префикс 1024 токена. Префикс до первого маркера —
это инструменты плюс `INSTRUCTIONS`. Это оценка по символам, а не замер токенизатора:
`INSTRUCTIONS` ≈ 2484 символа, схемы core-инструментов ≈ 424 символа, итого
примерно 750–950 токенов. Логи показывают, что весь префикс с данными атлета
около 1024–1100 токенов, так что статическая часть, скорее всего, ниже минимума.

Если это так, маркер на блоке 1 молча не создаёт запись в кеше. Тогда после
`save_fact` промах будет полный, как и раньше, и правка ничего не даст.

Как проверить после деплоя:

- Если после `save_fact` `cache_read_input_tokens` равен 0, а `cache_creation` ≈
  полному промпту, статический префикс короче 1024 токенов.
- Варианты исправления: сделать статичную часть длиннее настоящим содержимым (например,
  развёрнутые правила и примеры) или перенести в статичный префикс то, что сейчас
  попадает в блок 2 и не меняется. Выбор за вами, я ничего не добавлял для набора объёма.

## Что осталось за рамками

- Выбор инструментов по ключевым словам меняет список `tools`, а `tools` стоят в
  префиксе выше системного промпта. Сообщение с «plan» после сообщения без него даёт
  полный промах, инструкции тоже. Внутри одного сообщения список постоянен, так что
  цикл инструментов не страдает. Между сообщениями это остаётся источником промахов.
  Это отдельная задача, я её не трогал.
- Блок 2 остаётся одним маркером. Можно разбить его на три сегмента (профиль / факты /
  дата), чтобы запись в память не перекешировала профиль. Выигрыш на фоне блока 2 мал,
  поэтому не делал.

## Что взял из заметки коллеги

Пригодилось:

- Разделение на два маркера: статичные инструкции отдельно от пер-атлетного хвоста.
- Правило «статичный блок байт в байт стабилен»: в нём нет даты и имени.
- Порядок блоков: статичный первым.
- Проверка по `usage`: `cache_creation` и `cache_read` показывают, что произошло.

Не взял:

- Фильтрацию инструментов как решение этой задачи: она уже есть в коде, и её поведение
  отдельная тема.
- Конкретные цифры коллеги (780 / 240 токенов): у нас свои, и их надо мерить.
- Отбор фактов по релевантности: в проекте его нет, и он не нужен.
