# Почему не подключался Intervals.icu

1. **Кнопка Connect (у всех) → 401.** Кнопка была обычной ссылкой `<a href="/api/intervals/auth/init">`.
   Навигация браузера не отправляет заголовок `Authorization: Bearer` (токен лежит в `localStorage` и
   добавляется только fetch-обёрткой), поэтому `require_user()` отвечал 401 (см. logs, п.1).
   Исправление: `auth/init` теперь отдаёт JSON `{url}`, а кнопка делает `api()`-запрос (с заголовком)
   и затем переходит на этот URL.

2. **Ручная ссылка → 400 `invalid_request` на стороне Intervals.** Единственное, что изменилось с момента
   рабочего подключения (19.09, scope `ACTIVITY:WRITE,WELLNESS:READ`), — 02.10 в запрос добавили
   `CALENDAR:READ,CALENDAR:WRITE` (и избыточный `ACTIVITY:READ`). Я вернул проверенный набор scope
   (`config.SCOPES`, переопределяется `INTERVALS_SCOPES`). Это вывод по логам, без проверки на реальном
   Intervals (внешние вызовы запрещены): тело ошибки не указывает параметр. Для синка календаря нужно
   включить CALENDAR-scope в регистрации OAuth-клиента, потом задать `INTERVALS_SCOPES`.

3. **«Expired, reconnect» через час.** Intervals в ответе не вернул ни `refresh_token`, ни `expires_in`
   (токен долгоживущий). Код подставлял выдуманный TTL 3600 с (`DEFAULT_TOKEN_TTL`) и по истечении без
   refresh-токена помечал подключение истёкшим, хотя токен был валиден (Rivera не отзывал доступ).
   Исправление: без `expires_in` токен считается бессрочным (`expires_at=None`), рефрешер его пропускает;
   рефреш-ответ без `expires_in` тоже больше не падает с KeyError.
