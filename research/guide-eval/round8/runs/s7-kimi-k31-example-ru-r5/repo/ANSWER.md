# Причины сбоя

1. **Кнопка Connect не отправляла авторизацию tricoach.** Это была обычная ссылка на `GET /api/intervals/auth/init`. При полноценном переходе браузер не добавляет `Authorization: Bearer ...`, который SPA хранит в `localStorage` и выставляет только через `fetch`. Поэтому endpoint возвращал 401 всем пользователям (`logs/connect-attempt.log`, 2026-10-14).
2. **Authorize URL содержал дублирующиеся области scope.** Одновременно передавались `ACTIVITY:READ,ACTIVITY:WRITE` и `CALENDAR:READ,CALENDAR:WRITE`. У Intervals.icu `:WRITE` уже включает чтение, а повтор области приводит к ошибке ещё до экрана согласия. Это объясняет поломку ручных ссылок после добавления календарной синхронизации.
3. **Бессрочный токен искусственно истекал через час.** Intervals.icu не возвращает ни `refresh_token`, ни `expires_in`: access token действует, пока спортсмен не отзовёт доступ. Код подставлял TTL 3600 секунд, а фоновая задача затем удаляла токен и ставила статус `expired, reconnect`. Именно это произошло с T. Rivera; реального истечения или отзыва не было.
4. **Обмен кода содержал лишние поля.** Отправлялись `grant_type` и `redirect_uri`, хотя endpoint Intervals.icu принимает только `client_id`, `client_secret` и `code`. Это несоответствие также устранено.

# Исправления

- `POST /api/intervals/auth/init` теперь требует авторизацию и возвращает `{authorize_url}`. Кнопка в SPA вызывает его через `fetch`, после чего выполняет `window.location.assign(authorize_url)`. Старый GET-маршрут удалён.
- Scope сокращён до `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`: каждая область указана один раз, без лишнего `SETTINGS:WRITE`.
- Обмен кода отправляет ровно три требуемых поля.
- Искусственный TTL и фоновый refresher удалены. Токен остаётся подключённым без ограничения по времени.
- При первом ответе 401 от API токен очищается, статус меняется на `disconnected, reconnect`, а интерфейс предлагает подключиться заново. Остальные ошибки API не разрывают подключение.
- Существующая подписанная `state` с TTL 15 минут сохранена; добавлена защита от смены Intervals-аккаунта при переподключении.

# Какие части заметки коллеги пригодились

Пригодились все четыре описанные особенности: отсутствие refresh token и срока действия, правило «одна область scope один раз», точный формат token exchange и перенос init на авторизованный POST с JSON-ответом. Также применены рекомендации о lazy-обработке отзыва по 401 и account-mismatch guard.

Переводить `state` именно на JWT не потребовалось: существующий HMAC-подписанный state уже связывает callback с пользователем и ограничен 15 минутами. Шифрование at rest в этом изменении не добавлялось, поскольку текущий backend хранит подключения только в памяти; при переносе того же потока в постоянное хранилище токен нужно шифровать.

# Проверка

Полный поток проверен через реальные HTTP-запросы к локальному приложению и локальному имитатору Intervals.icu: успешное подключение, callback без `Authorization`, отсутствие автоматического истечения, wellness с Bearer token, отзыв доступа с 401, повторное подключение и отклонение чужого athlete id. Также проверены 401 на init без авторизации, отсутствие старого GET-маршрута и точный набор полей token exchange. Внешние сервисы не вызывались.
