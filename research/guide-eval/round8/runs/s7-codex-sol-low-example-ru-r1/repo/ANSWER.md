# Intervals.icu: причины и исправление

1. Кнопка открывала `GET /api/intervals/auth/init` как переход страницы. Такой запрос не содержит `Authorization` из SPA, поэтому сервер отвечал 401. Теперь кнопка отправляет авторизованный `POST` через `api()`, получает `authorize_url` и переводит браузер на него.
2. В `SCOPES` одновременно запрашивались `ACTIVITY:READ` и `ACTIVITY:WRITE`, а также `CALENDAR:READ` и `CALENDAR:WRITE`. Intervals отклонял URL до экрана согласия. Оставлены `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`.
3. В ответе токена из лога нет `expires_in` и `refresh_token`. Сервер придумывал срок 3600 секунд и фоновый процесс удалял действующий токен примерно через час. Искусственный срок и обновление удалены. При ответе Intervals 401 на запрос данных токен очищается, статус становится `reconnect`.

Из заметки коллеги пригодились: POST для запуска OAuth при авторизации через заголовок, уникальные области доступа, состав запроса обмена кода (`client_id`, `client_secret`, `code`), отсутствие обновления токена, подписанный `state` для callback без заголовка авторизации и проверка совпадения athlete id при повторном подключении. `state` здесь подписан HMAC существующим секретом приложения; JWT как формат не требуется. Токены в этом демонстрационном приложении хранятся только в памяти, поэтому рекомендация о шифровании постоянного хранилища к этому коду не применима. Запрос к реальному Intervals и проверка отзыва через его интерфейс не проводились, поскольку внешние обращения запрещены.

Локально проверены: авторизованный POST и его scopes/state, параметры обмена кода, отсутствие искусственного срока и переход в `reconnect` после смоделированного ответа 401.
