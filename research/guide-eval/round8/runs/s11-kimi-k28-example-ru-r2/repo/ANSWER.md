# Почему вторая публикация падала с 500

## Причина

`src/app.py`, функция `similarity()` (строка 30 до правки) возвращала
`round(0.7 * tag_score + 0.3 * word_score, 4)` — всегда Python-`float`.
Эти значения попадали в поле `similar` (top-3 похожих историй) и уезжали в
`table.put_item(Item=...)`.

DynamoDB через boto3 не принимает `float`: `TypeSerializer` бросает
`TypeError: Float types are not supported. Use Decimal types instead.` —
ровно та ошибка и тот стектрейс (`put_item` → `inject_attribute_value_input` →
`_get_dynamodb_type`), что в `logs/error.log`.

Первая публикация выживала лишь потому, что таблица была пуста: `related()`
находил ноль кандидатов и возвращал пустой список — нечему было упасть, и
`float` в item просто не было. Начиная со второй публикации в таблице уже есть
записи, в `similar` появляются оценки-поплавки, и `put_item` падает. Баг не
«появляется» на второй записи — он всегда был в коде; он существует ровно с
того момента, как в данных появился первый кандидат на сравнение. Проверено
воспроизведением: publish #1 → ok, publish #2 → TypeError, до правки.

Заодно выяснилось, что существующий тест покрывал только пустую таблицу — он
никогда не исполнял код сравнения, поэтому баг прошёл в прод.

## Исправление

`src/app.py`, `similarity()` теперь возвращает `Decimal` вместо `float`:

```python
return Decimal(str(round(0.7 * tag_score + 0.3 * word_score, 4)))
```

- `Decimal` — родной тип для boto3/DynamoDB, формат хранимых значений
  (доля 0–1, 4 знака) не меняется.
- Через `str()`, а не `Decimal(float)`: иначе в десятичное значение
  протекла бы двоичная погрешность float (`Decimal(0.7)` →
  `0.700000000000000011102230246251565404236316680908203125`), а так в
  таблице остаётся чистое `Decimal('0.7')` и т.п.

В `tests/test_publish.py` добавлен регрессионный тест
`test_publish_with_existing_record_stores_similar_scores`: сначала сидирует
таблицу одной записью, затем публикует вторую и проверяет, что item лёг, а все
оценки в `similar` — `Decimal`, а не `float`. Путь с непустой таблицей теперь
исполняется в тестах.

Проверка: `python3 -m unittest discover -s tests -v` — 2/2 ok; сквозной прогон
через `handler` — три публикации подряд, все 201, оценки сохраняются как
чистые `Decimal('0.0375')` и т.п.

## Что пригодилось из заметки коллеги

- **Диагноз «float в DynamoDB» и стектрейс** — совпал один в один, сразу
  навёл на `similarity()` / `put_item`.
- **Объяснение, почему первый write проходит** (пустая таблица → нет кандидатов
  → нет float) — ключ к пониманию; подтвердил воспроизведением.
- **Идея сидировать таблицу перед тестом записи** — взята как есть; теперь
  путь «непустая таблица» покрыт регрессионным тестом.
- **Рекомендация конвертировать на границе с DynamoDB в Decimal** — применена.

Не пригодилось / отличается:

- **Переход на целые проценты** (int вместо Decimal) — не понадобился: `Decimal`
  нативно поддерживается boto3 и сохраняет текущий формат значений (доля 0–1),
  поэтому не менял контракт данных. Их мотив («int/Decimal, DynamoDB доволен»)
  сохранён — просто через Decimal.
- **Проверка `grep round( и /`, ведущих в item-dict'ы** — баг был найден по
  стектрейсу и чтению `publish()`/`similarity()`; grep не потребовался.
- **Публикация дважды против реальной таблицы** — по правилам задачи ничего во
  внешние сервисы не отправлял; эквивалентная проверка сделана через
  `FakeTable`, который валидирует типы так же, как `TypeSerializer` boto3.
