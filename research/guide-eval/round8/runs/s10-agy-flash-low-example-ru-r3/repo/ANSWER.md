# Реализация событий аналитики

## Что сделано

В соответствии со спецификацией [docs/EVENTS.md](file:///tmp/h-vd8qic/docs/EVENTS.md) реализована отправка всех продуктовых событий воронки регистрации через обёртку `Analytics.capture`:

1. **Экран регистрации ([`RegistrationScreen`](file:///tmp/h-vd8qic/lib/screens/registration_screen.dart))**:
   - `registration_email_started`: срабатывает один раз при вводе первого символа в поле ввода email (без передачи PII).
   - `registration_phone_started`: срабатывает один раз при вводе первого символа в поле ввода телефона (без передачи PII).
   - `loan_amount_changed`: срабатывает при завершении перемещения ползунка (`onChangeEnd`) с параметром `amount` (`int`, округлённое значение).
   - `terms_accepted`: срабатывает при установке флага согласия с условиями (чекбокс).
   - `registration_continue_tapped`: срабатывает при нажатии на кнопку «Continue» с параметрами `amount` (`int`) и `terms` (`bool`).

2. **Экран предложений ([`OfferScreen`](file:///tmp/h-vd8qic/lib/screens/offer_screen.dart))**:
   - `offers_scrolled`: срабатывает при завершении скролла списка предложений через `NotificationListener<ScrollEndNotification>` с параметром `offset` (`double`, текущая позиция скролла `pixels`).

## Какие части заметки коллеги пригодились

Из заметки коллеги пригодились следующие ключевые подходы для предотвращения исчерпания лимита событий (event quota):

1. **Флаги однократного срабатывания для текстовых полей**:
   - Использованы булевы флаги (`_emailStarted` и `_phoneStarted`) в состоянии экрана регистрации. События `registration_email_started` и `registration_phone_started` отправляются только один раз при первом вводе, а не на каждое нажатие клавиши (`onChanged`).
2. **Использование `onChangeEnd` вместо `onChanged` для слайдера**:
   - Событие `loan_amount_changed` вынесено в коллбэк `onChangeEnd`, благодаря чему событие отправляется один раз в момент, когда пользователь отпускает слайдер, а не десятки раз во время непрерывного перетаскивания.
3. **Отслеживание скролла через `ScrollEndNotification`**:
   - Список предложений обёрнут в `NotificationListener<ScrollEndNotification>`, что позволяет фиксировать событие `offers_scrolled` с финальным `offset` только при окончании скролла, а не генерировать спам событий на каждый тик движения скролла.
4. **Сохранение точных названий событий и структуры свойств**:
   - Все имена событий (`snake_case`) и типы свойств строго соответствуют спецификации, чтобы сохранить совместимость с дашбордами и воронками.

Не потребовались рекомендации по focus/blur (`FocusNode`), так как спецификация не требует отправки событий по потере фокуса или валидации финальных значений текстовых полей (согласно требованиям, PII email/phone передавать запрещено).
