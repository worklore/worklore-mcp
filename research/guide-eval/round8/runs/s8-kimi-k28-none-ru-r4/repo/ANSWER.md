# Что изменил

## Проблема

`build_system()` в `bot.py` собирал системный промпт в один текстовый блок: статические
инструкции (`INSTRUCTIONS`, ~1000 токенов) + изменяемый контекст атлета (зоны, цель,
факты) — и ставил `cache_control` на весь блок целиком. Кеш Anthropic работает по
префиксу: при любом изменении текста внутри блока инвалидируется весь блок. Поэтому
каждый `save_fact` менял список фактов, и следующий вызов в цикле (и последующие
сообщения) заново платили за создание кеша на все ~1000+ токенов вместо чтения из кеша
— это видно в `logs/usage.jsonl`: после каждого `save_fact` `cache_read_input_tokens: 0`
и `cache_creation_input_tokens` снова ~1060–1100.

## Фикс

`bot.py`, функция `build_system()`: системный промпт разбит на два блока с отдельными
точками кеширования, статический блок первым:

1. `INSTRUCTIONS` — с `cache_control: {"type": "ephemeral"}`; текст никогда не меняется.
2. `athlete_context(...)` — с `cache_control: {"type": "ephemeral"}`; меняется при
   `save_fact` (и при смене даты).

Кеш ищется по префиксу: когда факт добавляется, меняется только блок 2, блок 1
продолжает читаться из кеша. Маркер на блоке 2 нужен, чтобы неизменный контекст тоже
кешировался между раундами тул-лупа и сообщениями в пределах 5-минутного окна.

Эффект: после `save_fact` следующий вызов платит за создание кеша только на маленький
блок контекста (десятки токенов) вместо всего системного промпта (~1000+).

## Проверка

Прогнал `reply()` с фейковым LLM, который на первом раунде вызывает `save_fact`:
- системный промпт — 2 блока, у обоих есть `cache_control`;
- текст блока с инструкциями побайтово идентичен в обоих раундах;
- меняется только блок контекста (в него попадает новый факт).

Записи в `logs/usage.jsonl` и `data/athletes.json` тестом не трогались.

## Что сознательно не трогал

Смена набора инструментов (`plan_week`, `predict_race` по ключевым словам) всё ещё
инвалидирует кеш целиком — это другой механизм, и по NOTES.md фильтрация тулов была
осознанным выигрышем, её оставил как есть.
