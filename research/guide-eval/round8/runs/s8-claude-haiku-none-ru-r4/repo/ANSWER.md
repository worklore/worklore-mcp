# Кеширование и save_fact

## Причина

`build_system()` в `bot.py` собирал системный промпт из одного текстового блока:
инструкции + контекст атлета (профиль, зоны, цель, `facts`). Маркер `cache_control`
стоял на этом блоке целиком. Поэтому любой `save_fact` менял `facts`, менял весь блок,
и кеш-префикс переставал совпадать. Следующий вызов писал весь промпт заново
(`cache_creation_input_tokens` ~1000), а `cache_read_input_tokens` был 0. Это видно
в `logs/usage.jsonl` и описано в `NOTES.md`.

## Что изменено

- `bot.py`, `build_system()`: системный промпт теперь два блока.
  1. `INSTRUCTIONS` (статичный текст) с `cache_control: ephemeral`.
  2. `athlete_context(...)` (профиль, дата, факты) без маркера, идёт после первого.
  Запись в память меняет только второй блок, поэтому первый остаётся в кеше.
- `README.md`: абзац про кеширование приведён в соответствие с новой схемой.

Порядок кеша в API: tools → system → messages. Маркер на первом системном блоке
кеширует tools + инструкции.

## Проверка

Офлайн, с фейковым LLM (SDK не установлен, сеть не использовалась, `data/athletes.json`
и `logs/usage.jsonl` не трогались; `save_athlete` и `USAGE_LOG` подменены в тесте):

- Сценарий: сообщение → `save_fact` → ответ. Два вызова API.
- Первый блок системного промпта побайтно одинаков в обоих вызовах.
- Второй блок изменился и содержит новый факт.
- Список tools одинаков в обоих вызовах.

Реального вызова API не делалось, поэтому экономия пока не измерена. Её стоит
проверить по `logs/usage.jsonl` после выкладки: на вызове сразу после `save_fact`
должен быть `cache_read_input_tokens` около 1000 и малый `cache_creation_input_tokens`
(только блок с контекстом атлета, а не весь промпт).

## Ограничения и что не сделано

- Минимальный размер кешируемого префикса у модели зависит от версии. В логах
  префикс tools + инструкции около 1090 токенов, что выше минимума 1024, который
  действует для Sonnet. Если модель сменится на модель с большим минимумом, статичный
  блок может не закешироваться совсем. Проверяется тем же способом: в логах должен
  появиться `cache_read_input_tokens` на первом блоке.
- `select_tools()` меняет список tools по ключевым словам. Сообщение со словом
  «race» или «plan» меняет префикс tools, и кеш инструкций инвалидируется. Это тоже
  вызывает всплески `cache_creation`, но не из-за `save_fact`. Я это не трогал, потому
  что `NOTES.md` называет фильтрацию tools выигрышем. Возможное решение: всегда
  передавать полный список tools (дороже по токенам, но стабильный префикс), либо
  сравнить две стоимости по логам.
- Блок с контекстом атлета не кешируется. Он короткий (сотни токенов) и платится
  по обычной цене на каждом вызове. Если фактов станет много, стоит поставить второй
  маркер на этот блок.
