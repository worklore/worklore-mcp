# Intervals.icu: почему не подключается и что исправлено

Три независимые причины, все подтверждены в коде и логах.

## 1. Кнопка Connect возвращает 401 (logs/connect-attempt.log, #214)

`Connect` был обычной ссылкой `<a href="/api/intervals/auth/init">`. Переход по ссылке — полная навигация страницы, и браузер не отправляет заголовок `Authorization`, который SPA держит в `localStorage` и шлёт только через fetch-обёртку. Сервер отвечал `401 {"error": "unauthorized"}` каждому атлету.

**Исправление:** init стал `POST /api/intervals/auth/init` (`server.py`). Он возвращает JSON `{authorize_url}`, а `static/app.js` вызывает `fetch` с заголовком и затем `window.location.assign(authorize_url)`. GET на этот путь теперь 404.

## 2. Authorize отвечает 400 — дублирующиеся области в scope (logs/connect-attempt.log, шаг 2)

В `config.py` было `ACTIVITY:READ,ACTIVITY:WRITE,...,CALENDAR:READ,CALENDAR:WRITE`. Одна и та же область указана дважды; `WRITE` уже включает `READ`. Из-за этого Intervals отклоняет authorize-запрос. Этот 400 появился после выпуска calendar sync 2026-10-02, что совпадает с тикетом #219.

**Исправление:** `SCOPES = "ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE"` — каждая область один раз. Это тот же набор, что был у T. Rivera в успешном подключении 2026-09-19, плюс `CALENDAR:WRITE` для записи тренировок.

**Что не проверено:** в логе Intervals возвращает общий `{"error":"invalid_request"}`, а не текст «Duplicate scope». Причина выведена из совпадения по времени и по содержимому scope, а не из явного сообщения. Подтвердить можно только реальным authorize-запросом с боевым `client_id` (сейчас в `config.py` плейсхолдеры).

## 3. Токен «истекает» через час и не продлевается (logs/connect-attempt.log, T. Rivera)

Intervals не присылает ни `expires_in`, ни `refresh_token`. Код подставлял `DEFAULT_TOKEN_TTL = 3600`, и фоновый обновлятор через час помечал подключение как `expired, reconnect`, хотя токен был ещё действителен.

**Исправление (`server.py`):**
- `expires_at` ставится только если провайдер прислал `expires_in`; иначе `None`. Фоновый обновлятор пропускает такие подключения.
- Отзыв токена обрабатывается лениво: если `/wellness` возвращает 401 от Intervals, подключение помечается `expired, reconnect`, токен очищается, а SPA показывает «подключиться заново». Раньше 401 просто пробрасывался.

## Проверка

Сервер запущен на свободном порту (8867) с `INTERVALS_BASE` на локальный mock, который повторяет форму ответа из логов (без `expires_in`, без `refresh_token`). Результаты:

- `GET /auth/init` → 404; `POST` без заголовка → 401; `POST` с заголовком → `{authorize_url}`.
- В authorize URL scope `ACTIVITY:WRITE,WELLNESS:READ,CALENDAR:WRITE`, дублей нет.
- Callback с кодом → подключено, `expires_at` не выставлен.
- `/wellness` → 200 с данными.
- После отзыва на стороне mock → 409, статус `expired, reconnect`.

Реальный Intervals.icu из этой среды недоступен, поэтому проверка на боевом аккаунте остаётся за вами.

**Важно:** на порту 8766 уже работал другой процесс Python (PID 88629), и mock на 8799 тоже был чужой. Первый прогон теста попал в него, а не в мой код; я его не трогал. Если вы сами держите dev-сервер на 8766, перезапустите его, иначе он будет отдавать старый код.

## Что взято из заметки коллеги

**Использовано:**
- Аутентифицированный POST для init, который возвращает `authorize_url` JSON. Это и есть основная причина пункта 1.
- Правило «каждая область один раз, WRITE вместо READ+WRITE» (пункт 2).
- Отсутствие `refresh_token` и `expires_in` и ленивая обработка отзыва по 401 (пункт 3).

**Не понадобилось:**
- JWT для `state`. Текущий `state` уже подписан HMAC и имеет TTL 15 минут, `verify_state` проверяет оба. Смена формата не решала ни одну из проблем.
- Убирать `grant_type` и `redirect_uri` из обмена кода. Обмен работал в логе 2026-09-19 с этими полями, поэтому менять его без необходимости не стал.
- Берём `athlete.id` из ответа токена — так уже сделано.
- Ссылка на тред регистрации OAuth-клиента — к коду не относится.

**Не сделано, но стоит рассмотреть:** защита от несовпадения аккаунтов при повторном подключении (сравнивать пришедший `athlete.id` с сохранённым). Сейчас новое подключение просто перезаписывает старое. Это отдельная доработка, в текущие проблемы она не входила.

## Что изменено

- `config.py` — `SCOPES` без дублей.
- `server.py` — init как POST с JSON; `expires_at` только при наличии `expires_in`; `mark_revoked` при 401 от Intervals.
- `static/app.js` — кнопка Connect вызывает POST и переходит по `authorize_url`.
