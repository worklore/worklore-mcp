# Падение DynamoDB, которое появляется только на второй записи

Мой эндпоинт публикации работал идеально — один раз. Первая история легла
чисто. Вторая вернула Internal Server Error, а в логе было:
"TypeError: Float types are not supported. Use Decimal types instead."

DynamoDB не принимает питоновские float. Это все рано или поздно узнают;
интересно то, почему первая запись выжила. Мой API считает оценки похожести
между входящей историей и уже существующими и сохраняет лучшие совпадения. При
самой первой публикации таблица была пуста — нет совпадений, нет оценок, нет
float, нет падения. Бага не существовало, пока не появились данные.

Исправление заняло одну строку (оценки стали целыми процентами — DynamoDB
доволен int и Decimal). Урок доходил дольше: мой тест «оно работает» всегда
проверял только путь с пустой базой. У любого кода, чьё поведение зависит от
существующего состояния — оценки, дедупликация, агрегация, «похожие
элементы», — есть второй путь выполнения, которого тесты первой записи никогда
не касаются.

Теперь каждый тест пути записи сначала сажает в таблицу одну запись, а потом
проверяет запись. Путь с заполненной таблицей — настоящий путь; путь с пустой
случается в продакшене ровно один раз за всю жизнь.

## Воспроизвести

Предварительные условия: любой Python-сервис, пишущий в DynamoDB через boto3.

Агенту понадобятся от вас: где находятся ваши вызовы put_item / update_item и
как устроены тесты.

Шаги: проследите каждое значение, попадающее в запись DynamoDB, и отметьте всё
вычисляемое — деления, средние, округлённые оценки, — потому что в Python это
float; конвертируйте в int или decimal.Decimal на границе; затем добавьте один
интеграционный тест, который сажает одну запись и пишет вторую, чтобы зависящий
от состояния код (похожесть, дедуп, счётчики) действительно выполнялся под
тестом.

Проверка: поищите в кодовой базе round( и /, питающие словари элементов;
запустите тест с засеянной таблицей; опубликуйте дважды в реальную таблицу —
вторая запись та, что говорит правду.
