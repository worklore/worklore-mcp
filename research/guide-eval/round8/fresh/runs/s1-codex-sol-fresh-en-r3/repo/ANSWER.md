# HR range export fix

Changed `gen.py` so each planned HR corridor is emitted as `hr: {"units": "%lthr", "start": lower, "end": upper}`. The previous `value`/`end` pair did not encode the lower bound as a range. The October 2026 watch readback showed zone-sized targets even though the API returned that payload unchanged; API acceptance alone did not prove the Garmin export preserved the corridor.

The event now also includes an Intervals workout `description` matching the structured steps, including repeats, percentage-of-LTHR ranges, and `hr=1s` for instant HR targets. This gives Intervals' workout parser and device export an explicit text representation. Its [workout schema](https://forum.intervals.icu/t/downloading-planned-workouts-from-the-api/93737) defines `start` and `end` for ranges; its [Garmin guidance](https://forum.intervals.icu/t/power-and-hr-targets-for-garmin-workouts/2926) specifies `hr=1s` for watches. An [API-created workout investigation](https://forum.intervals.icu/t/events-created-via-api-with-workout-doc-the-web-download-produces-an-empty-fit-while-the-api-download-does-not-which-representation-feeds-device-sync/132326) found that `workout_doc` could read back intact while the web/device export lost the steps, and that including `description` resolved that export path.

Verified locally with `plans/tempo-run.json`: every structured HR target has `start`/`end` and the description contains all four planned corridors plus the 3x repeat. No event was posted or synced, so the final bpm display on the watch remains unverified. With Intervals LTHR 172, the planned corridors correspond approximately to warm-up 117–129, tempo 151–160, float 129–141, and cool-down 112–124 bpm.
