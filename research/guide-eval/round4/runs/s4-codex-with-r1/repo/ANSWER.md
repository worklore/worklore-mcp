# What is not in 3NF?

This audits the **final schema after all migrations**, not just the initial `CREATE TABLE` statements. A primary key on `id` does not make a table 3NF when another column determines a third column. Database-enforced consistency reduces the risk of a copy, but does not remove the functional dependency that makes it redundant.

## Clear remaining dependencies

| Table and columns | Dependency and consequence | Evidence / sensible change |
| --- | --- | --- |
| `model_calls`: `usage`, `tokens_in`, `tokens_out`, `cost_usd` | For a call with a usage breakdown, `tokens_in = input + cache_read + cache_write`, `tokens_out = output`, and `cost_usd` is also present in `usage`. These are separately writable copies. They can disagree, including in the spend view, which sums the scalar columns. | [Migration](supabase/migrations/20261015010000_ask_code_model_calls.sql) lines 28–31, 45–52; [writer](supabase/functions/_shared/server/usage.ts) lines 64–68 and [ask-code writer](supabase/functions/_shared/server/ask_code.ts) lines 87–90. Keep one representation and derive the other, or enforce a single database writer if the breakdown is optional. Preserve `NULL` for unknown cost rather than treating it as zero. |
| `code_questions`: `usage`, `cost_usd` | The completed run stores cost both as `usage.cost_usd` and as `cost_usd`; the error path separately computes `cost_usd` from `model_calls`. ## Intentional redundancy, still outside strict 3NF

- **Child `project_id` copies.** For example, `document_chunks.document_id → documents.project_id`, yet `document_chunks.project_id` is stored too. The same dependency exists in `identities` through `person_id`, `items` through `person_id` (and `account_id` when present), `touches` through `person_id`/`item_id`, `idea_items` through either parent, and `project_memory`/`documents` through a non-null `theme_id`. The [normal-forms migration](supabase/migrations/20261010040000_normal_forms.sql) lines 23–71 explicitly retains these for RLS and indexes and adds composite foreign keys. Thus these are formal redundancies, **but the listed composite FKs prevent conflicting project IDs**. `items.platform` likewise copies `accounts.platform` for account-backed items and is checked by the composite FK; accountless discovery items have their own platform.
- **Cached aggregates.** `ideas.asked_by` is determined by linked `idea_items` and their `items.person_id`; `people.first_touch_at` and `last_touch_at` are determined by `touches`. The [normal-forms migration](supabase/migrations/20261010040000_normal_forms.sql) lines 77–95 and 201–221 installs recount/span triggers. These are deliberate derived caches, not independently owned facts. The `idea_items` trigger handles insert/delete, and the `items` trigger handles `person_id` changes, but an **UPDATE of `idea_items.idea_id` or `item_id` is not covered**; that can leave `asked_by` stale. Privileged direct updates to either cache can also bypass its intended meaning.
- **Content hashes.** `documents.content_sha256` is a hash of the incoming document's kind, title, publication date, label, language, and original Markdown; `document_chunks.content_sha256` hashes a chunk's title and text. They are application-written reuse keys, with no database expression or trigger checking them. See [hash definition and knowledge writer](supabase/functions/_shared/server/knowledge.ts) lines 27–38 and 65–107. The original Markdown is not stored verbatim in `documents`, so the document hash cannot simply be regenerated from its row. `voice_samples.text_sha256` is similar, but its normalization uses the server's JavaScript whitespace rule and the [migration](supabase/migrations/20261010040000_normal_forms.sql) lines 15–18 explicitly documents why it was kept. Keep these as identified application-maintained caches, or move hash creation and validation to one authoritative writer where possible.

## What the earlier migration already fixed

Do **not** count these as current findings: `idea_items.person_id` was dropped (the original partial-key/2NF problem); `document_chunks.kind`, `source_url`, `source_ref`, and `label` were dropped in favor of the parent document; `documents.is_public`, `drafts.tokens_in/out`, `items.triage_*`, and `projects.url_key` are generated; `plans.allowed_models` became `plan_models`. See [normal-forms migration](supabase/migrations/20261010040000_normal_forms.sql) lines 73–198 and 276–341, plus the later [safe token expression](supabase/migrations/20261011120000_tokens_generated_safe.sql).

Arrays and JSON are **not automatically** 1NF or 3NF violations in Postgres. The old `plans.allowed_models` was relational data queried as membership and has been normalized. Current arrays such as project languages/topics and draft checks need separate child tables only if the app needs independently identifiable, constrained, or joined elements. Similarly, `code_questions.repo` and `commit_sha` describe the repository and revision used *for that answer*; treating `repo` as a historical snapshot avoids falsely calling it a copy of the project's current repository.

This is a **static audit** of migrations and writers. No live database was provided, so I cannot claim a count of inconsistent rows. Before changing these columns, run read-only mismatch counts on the deployed schema and decide which representation is authoritative; then test the migration and all writers together.
