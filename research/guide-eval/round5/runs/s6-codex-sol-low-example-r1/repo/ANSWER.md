# MCP client checkup

Checked the local Streamable HTTP server at `http://127.0.0.1:54756/mcp` without authorization. Requests were sequential and read-only. Only `get_note` and `search_notes` were called; `add_note` was not called. The server source and repository were also inspected. The tested server reported MCP protocol `2025-06-18` and server version `0.3.1`.

| Check | Result | Evidence and client impact | Relevant story for failures |
|---|---|---|---|
| C1 · Anonymous discovery | PASS | `server/discover` returned HTTP 200 with JSON-RPC `-32601`; `initialize` and `tools/list` returned HTTP 200. The list contains 3 tools, including 2 marked read-only. | — |
| C2 · Tool refusal | FAIL | `get_note({"id":"n-999"})` returned HTTP 200 with JSON-RPC error `-32602`, `note not found: n-999`. Missing `id` also returned `-32602`, `missing required argument: id`. | C3 · Recovery after error | PASS | In the same `Mcp-Session-Id` session, `get_note({"id":"n-1"})` after both errors returned HTTP 200 with `isError: false` and the note. | — |
| C4 · Published output schemas | PASS | Both read-only tools that declare an `outputSchema` returned HTTP 200, `isError: false`, and `structuredContent` on valid calls. `get_note` included the required `id`, `title`, `body`, and integer `words`; `search_notes` returned an object, satisfying its published schema (`{"type":"object"}`). This is a narrow pass because that search schema specifies no fields. The write tool's schema was not exercised. | — |

**Overall: has the problem.** C2, C5, C6, and C10 failed. No token was needed for the read-only tool checks. A registry entry would unlock registry-version comparison; a local JSON Schema validator would allow an independent C10 validation run.

## Additional client-facing finding

`initialize` advertises `resources`, but anonymous `resources/list` and `resources/templates/list` each return HTTP 401 with `{"error":"unauthorized"}`. The sole listed resource in source is a guide, while read-only tools are public. Clients that enumerate advertised resources without a token will encounter an authorization failure. This is the resource-access part of the colleague's anonymous discovery example, though C1's tool-list and `server/discover` checks pass here. [Tool-list access story](https://worklore.dev/s/2026-09-27-my-mcp-server-hid-its-own-tool-list-behind-a-login).

## How the colleague's note applied

The Streamable HTTP procedure, session reuse, read-only call rule, and checks C1–C10 applied. Its registry verification path did not apply because this server has no registry entry. Its token fallback was unnecessary for public tools; authenticated resource behavior was not tested. Its worklore recording step did not apply and nothing was submitted externally. The note's claim that a schema should reject corrupted values revealed the permissive `search_notes` schema, while its advice about a changing resource list did not apply to this fixed guide list.
