# Check your MCP server in a few minutes: the failures real clients hit

Several of my worklore stories are about an MCP server failing in ways I did not see: the tool list hidden behind a login, a refusal that made the client throw, a Decimal that broke a tool for days, a listing that described a server which no longer existed. Each one cost me a day or more to find. Each one can also be found in a few minutes by asking the server the right questions, without changing anything.

So this story does not fix anything. It is the questions, in one place: ten read-only checks your agent runs against your server, and a report that says, for each failure, which story fixes it. You read the report and decide what to fix, one story at a time.

I checked it two ways before writing it down. First against a small server I broke on purpose, with seven of these failures planted in it: tool list closed without a token, refusals sent as JSON-RPC errors, a Decimal in a result, a dotted tool name, version negotiation that echoes "banana", no logging, no surface lock. My agent found all seven in 39 seconds, linked the right story for each, and marked the one thing the server did right (the session survived an error) as a pass.

Then against worklore's own live server, with no token. That run was more useful than flattering. What can be checked anonymously passed: the tool list answers, the names are clean, the version matches the registry, "banana" gets an honest answer. But four of the nine checks need a signed-in session, and the agent said so instead of guessing. It also noticed something I had not: the server advertises resources at `initialize` and then answers `resources/list` with a 401. I fixed it the same day: `resources/list` and `resources/read` now answer without a token with public stories only, and a signed-in caller also gets their own private ones. Two days later I went further: a list that grows with every new story can't be part of a version promise, so `resources/list` now holds three fixed documents (a guide, the story format, the access rules) and the stories sit behind a resource template, `worklore://story/{slug}`. See C6.

That second run changed the rules below. "No failures" with half the checks skipped is not "you're fine", so a checkup that could not run the tool calls is reported as incomplete, and nothing is recorded.

## Check if this applies to you

Applies if: you run, or are about to list, an MCP server that clients reach over HTTP(S) (Streamable HTTP), and you can send it requests. Does not apply if you only use other people's MCP servers, or your server is stdio-only on your own machine (several checks still make sense there, but the commands below do not).

The check is the whole checkup in "Reproduce this" below. It is read-only by design: it sends `initialize`, `ping`, `tools/list` and calls only to tools that are marked read-only, and it changes nothing on the server or in your repository.

- **Has the problem:** at least one check comes back FAIL.
- **Doesn't have it:** every check is PASS, or a deliberate decision you can name (for example "tools/list needs a token on purpose, because …"). NOT CHECKED rows (for example logging, when nobody gave the agent the source or the logs) don't count either way.
- **Incomplete — record nothing:** if C2–C5 could not be run (the tools need a token you did not give), no FAIL does not mean "doesn't have it". Say so in the report and do not record a result.

## Reproduce this

This contract does not fix anything. It produces a report: one row per check, PASS / FAIL / DECIDED / NOT CHECKED, the evidence, and the worklore story that fixes each failure. The fixing is a separate decision, one story at a time.

Prerequisites: the server's MCP URL; `curl` or Python 3 (standard library only). Optional, each unlocks a check: a bearer token the server accepts, read access to the server's source, its name in the official MCP Registry.

Your agent will need from you: the URL; whether it may use a token (and where it is — read it from an environment variable, never print it); which tools are safe to call if the server does not mark them `readOnlyHint: true`; one argument value that should make a read-only tool refuse (an id that does not exist); where the source is, if you want the logging check.

Ground rules — the agent must follow all of them:
- READ-ONLY. Send only `initialize`, `notifications/initialized`, `ping`, `server/discover`, `tools/list`, `resources/list`, `prompts/list`, and `tools/call` on tools whose `annotations.readOnlyHint` is `true` (or that the human named as safe). Never call a tool that writes, deletes, publishes, pays or sends — not even with "fake" arguments. Do not edit any file.
- A handful of requests, one at a time. No load, no fuzzing.
- Never print a token. Put it in a header from an environment variable.
- Report what you saw, with the exact status codes and short excerpts. If a check cannot be run, write NOT CHECKED and why; never guess a PASS.

Talking to the server: POST JSON-RPC to the URL with `Content-Type: application/json` and `Accept: application/json, text/event-stream`. Some servers answer as `text/event-stream`; then the JSON is on the `data:` line. If the response carries an `Mcp-Session-Id` header, send it back on every later request — that is "the same session". Start every session with `initialize` (`{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"checkup","version":"1"}}`), then `notifications/initialized`.

Steps — the checks:

1. **C1 · The tool list answers without a token.** With NO `Authorization` header: `initialize`, then `tools/list`. PASS: both answer 200 with a result, and the tools are there (count them). FAIL: 401/403 — no directory, scanner or stranger can see what the server offers, and nobody outside your repository can test it. DECIDED if the human says it is closed on purpose and can say why. Fix: [My MCP server hid its own tool list behind a login](https://worklore.dev/s/2026-09-27-my-mcp-server-hid-its-own-tool-list-behind-a-login). If it is closed and you have a token, continue the remaining checks with the token; if you have none, every check below that needs `tools/list` or `tools/call` is NOT CHECKED. Also send `server/discover` with no token. PASS: 200 with a result or a `-32601` error. FAIL: 401 — Claude Code 2.1.299+ probes with it before `initialize` and marks the whole server needs-auth on a 401, so anonymous users get no tools even though `initialize` and `tools/list` are open.

2. **C2 · A tool refusal comes back as a result, not a protocol error.** Call a read-only tool with an id that does not exist, and separately with a required argument missing. PASS: HTTP 200 with a `result` that has `isError: true` and a readable message. FAIL: a JSON-RPC `error` (typically `-32602`) — a client SDK throws on that, so the model never reads "not found" and cannot correct itself; the 2025-11-25 spec revision moved input validation into tool results ([SEP-1303](https://modelcontextprotocol.io/community/seps/1303-input-validation-errors-as-tool-execution-errors)). An UNKNOWN tool name may stay a JSON-RPC error. Fix: [My live MCP test asserted the bug: a real client threw where my test passed](https://worklore.dev/s/2026-10-02-my-live-mcp-test-asserted-the-bug-a-real-client-threw-where-).

3. **C3 · The session survives an error.** In the same session as C2 (same `Mcp-Session-Id`, if the server issued one), right after the refusal, make a normal call to a read-only tool with valid arguments. PASS: a normal result. FAIL: an error, a hang, or the session is gone. Fix: the same story as C2.

4. **C4 · The published outputSchema is honoured.** Keep the schemas from the `tools/list` response — not from the source code. For every read-only tool that declares an `outputSchema`, make one call with valid arguments. PASS: no `isError`, `structuredContent` is present, and it validates against that schema (types, `required` fields, nested objects and arrays). FAIL: `isError` on a valid call, a missing `structuredContent`, or a mismatch — clients that validate results will reject them. An error result proves nothing about the schema, so it is a FAIL here, not a pass. Fix: [My tests passed because they agreed with me](https://worklore.dev/s/2026-09-28-my-tests-passed-because-they-agreed-with-me).

5. **C5 · Results survive serialisation.** Look at every response from C2–C4. PASS: every body parses as JSON, and the `content` text and `structuredContent` agree. FAIL: an error text like "Object of type Decimal is not JSON serializable" (or any "not serializable" / encoder error), numbers coming back as strings where the schema says number, or a body that does not parse — your database's types are leaking into the response. Fix: the same story as C4.

6. **C6 · The version moves when the surface moves.** First, check whether the server publishes a fingerprint: read its official MCP Registry entry (`GET https://registry.modelcontextprotocol.io/v0.1/servers/<name>/versions/<version>`) and look under `_meta` → `io.modelcontextprotocol.registry/publisher-provided` for a block with `"form": "mcp-surface/1"`. That is a shared format ([the spec](https://github.com/SidneyBissoli/mcp-br-commons/blob/main/packages/mcp-surface/SPEC.md)); if it is there, run its independent checker, [`verify.mjs`](https://github.com/SidneyBissoli/mcp-br-commons/blob/main/packages/mcp-surface/exemplos/verify.mjs) (`node verify.mjs <name> <version>`, Node only, no dependencies), and use its verdict. If there is no such block, compute the fingerprint yourself by the same spec (the `initialize` result without `serverInfo.version`, plus `tools/list`, `resources/list`, `resources/templates/list` and `prompts/list`, normalised and hashed as its §2–§3 say) and report it with `serverInfo.version`; compare the Registry's latest version with `serverInfo.version`. If you have the source, look for a committed surface lock (a file holding the version and this hash, checked by a test). Also look at what the lists contain: a list that changes by itself (stories, records, daily files) cannot be in a version promise, because its hash changes every day while nothing breaks; such items belong behind a resource template or a tool. PASS: `verify.mjs` passes, or the Registry version equals the live version and a lock exists. FAIL: `verify.mjs` reports a mismatch, or the Registry lists a different version than the live server reports — the listing describes a server that no longer exists. WARN (count as FAIL for "has the problem"): no lock, so nothing stops the next drift; or the fingerprint covers a list that changes by itself. NOT CHECKED: no registry entry and no source. Fix: [My MCP listing said read-only. My server could write.](https://worklore.dev/s/2026-09-30-my-mcp-listing-said-read-only-my-server-could-write), and for republishing the entry, [Getting into the MCP Registry](https://worklore.dev/s/2026-09-23-getting-into-the-mcp-registry-server-json-a-read-org-token-a).

7. **C7 · Calls are logged.** From outside this cannot be seen, so: if you have the source, find the single place every JSON-RPC call passes through and check that it writes one structured line per call (method, tool name, ok/error, latency, who). If you have log access, look for the calls you just made. PASS: one line per call, errors included. FAIL: no per-call log, or only an HTTP access log (every line is `POST /mcp 200`, which tells you nothing). NOT CHECKED: no source and no logs. Fix: [Your MCP server is one URL — getting per-tool, per-user analytics anyway](https://worklore.dev/s/2026-09-23-your-mcp-server-is-one-url-getting-per-tool-per-user-analyti).

8. **C8 · Tool count and names.** From `tools/list`: report the count, and check every name against `^[a-zA-Z0-9_-]{1,64}$`. PASS: all match. FAIL: any name with a dot, space or other character, or longer than 64 — OpenAI's function-name rule rejects it, and Anthropic's has the same shape, so whole clients cannot call that tool, whatever a directory scorecard says about dotted names. Names are hard to change once a registry has scanned you. Fix: [An MCP server for the price of one more endpoint](https://worklore.dev/s/2026-09-25-an-mcp-server-for-the-price-of-one-more-endpoint) (step 1), and [Submitting an MCP server to the directories](https://worklore.dev/s/2026-09-23-submitting-an-mcp-server-to-the-directories-one-cli-one-gith) on the scorecard trap.

9. **C9 · Version negotiation is honest.** Send `initialize` with `"protocolVersion": "banana"`. PASS: the server answers with a version it really implements (not "banana"), or a clear error. FAIL: it echoes "banana" — it would claim any future revision too. Fix: [An MCP server for the price of one more endpoint](https://worklore.dev/s/2026-09-25-an-mcp-server-for-the-price-of-one-more-endpoint) (Verify section).

10. **C10 · The outputSchema can reject a wrong answer.** Use the `tools/list` response from C1 and call nothing. For every tool that declares an `outputSchema`, build a corrupted result with the same structure: include the `required` properties (all properties if none are required), follow `$ref` into `$defs`, take the first branch of any `anyOf`/`oneOf`/`allOf`, and set every string to `"mcp-drill-corruption"`, every integer to `-999999999`, every number to `-1.5e308`, every boolean to `false`. Validate it against the schema with a real JSON Schema validator (Python `jsonschema`, JS `ajv`), or run [mcp-drill](https://github.com/TimurRakhmatullin86/mcp-drill) (`mcp-drill scan --url <server>`). PASS: every schema rejects the corrupted result because of a value constraint (`enum`, `const`, `pattern`, a bound) or a required field. FAIL: any schema accepts it — the contract cannot tell a wrong answer from a right one, so a client that validates learns nothing. A lone `type` error at a `$ref` means the builder did not follow the reference: count that tool as FAIL. NOT CHECKED: no tool declares an `outputSchema` (it is optional); say so in the report. Fix: [My MCP server's output schemas accepted wrong answers](https://worklore.dev/s/2026-10-15-my-mcp-server-s-output-schemas-accepted-wrong-answers-7-of-8).

11. **Write the report** as a table: check, result (PASS / FAIL / DECIDED / NOT CHECKED), evidence (status code, a short excerpt), and for each FAIL the story link above. Then one line: "has the problem" if any row is FAIL; "incomplete" if no row is FAIL but C2–C5 were NOT CHECKED; otherwise "doesn't have it". List what you could not check and what would unlock it (a token, the source, the registry name).

Verify: the report has all ten checks, each with evidence or a reason it was not checked; no tool that writes was called; no file changed (`git status` is clean if you are in the server's repository); the token never appears in the output. Then, if you use worklore, record the result for this story — `has_problem` or `no_problem` — only if the check applied to you and was not incomplete (see "Check if this applies to you").

Ground rules: work only inside the current directory. Do not deploy, publish, submit or report anything to any external service.
