## Detailed Findings: What Real MCP Clients Trip Over in `server.py`

### 1. Tool refusals and validation failures return JSON-RPC `-32602` instead of `isError: true` (C2 — `server.py:94-98, 113-121, 161-164`)
- **What happens:** In `get_note`, a missing `id` or an unknown note ID (`n-999`) raises `ValueError`, which `handle()` converts into a JSON-RPC protocol error (`code: -32602`). Similarly, passing a non-integer `limit` to `search_notes` raises `ValueError` and returns `-32602`.
- **Why clients trip over it:** Client SDKs treat JSON-RPC `error` objects as transport/protocol exceptions and throw, aborting the tool turn instead of showing the error message (`"note not found: n-999"`) to the model so it can recover. Under MCP (and [SEP-1303](https://modelcontextprotocol.io/community/seps/1303-input-validation-errors-as-tool-execution-errors)), domain refusals and tool input validation failures must return a normal JSON-RPC `result` using `tool_result(str(e), is_error=True)` (which is already defined at `server.py:94` with `is_error=False`, but never called with `is_error=True`).

### 2. `search_notes` publishes a vacuous `outputSchema` and mismatches `content` vs `structuredContent` (C10 & C5 — `server.py:34, 112`)
- **Vacuous `outputSchema` (`server.py:34`):** `search_notes` declares `"outputSchema": {"type": "object"}`, which accepts `{}` or any arbitrary corrupted object. It should require `["hits", "total"]`, constrain `total` (`{"type": "integer", "minimum": 0}`), and define the `hits` array item schema (`required: ["id", "title", "snippet"]`, `id` matching `"^n-[0-9]+$"`, `title` with `minLength: 1`, `snippet` as `string`).
- **`content[0].text` vs `structuredContent` mismatch (`server.py:112`):** `search_notes` returns `tool_result(json.dumps(hits), {"hits": hits, "total": len(hits)})`. `content[0].text` is a JSON array (`[...]`) missing `total`, whereas `structuredContent` is an object (`{"hits": [...], "total": ...}`). Clients or test harnesses that compare parsed text content with `structuredContent` will see a type mismatch (`list` vs `dict`).

### 3. `initialize` advertises `resources`, but `resources/list` returns HTTP `401` without a token (C1 / C6 — `server.py:138, 148-155`)
- **What happens:** `initialize` unconditionally advertises `"resources": {"subscribe": False, "listChanged": False}`, even to anonymous sessions (`who == "anon"`). When the client follows up with `resources/list` or `resources/templates/list`, lines 148–150 return HTTP `401` `{"error": "unauthorized"}`.
- **Why clients trip over it:** Clients that automatically enumerate advertised capabilities upon connection hit an unexpected `401` right after `initialize`, causing them to treat the whole server as unauthorized or fail connection setup—even though `search_notes` and `get_note` are meant to be open without a token. Furthermore, `notes://guide` is a public usage guide (`"# notes-mcp\nsearch_notes, get_note, add_note."`), so `resources/list`, `resources/templates/list`, and reading public resources should work without a token.
- **`resources/read` ignores `params.uri` (`server.py:155`):** `resources/read` never inspects `params.get("uri")` and always returns `notes://guide`, even when a client requests a nonexistent URI.

### 4. No committed surface lock (`mcp-surface/1`) (C6)
- There is no surface lock file or test in the repository tying `serverInfo.version` (`0.3.1`) to the server's surface hash (`sha256:4d069975b7acb158f2f12ceb8c69abeb4fd1569723f844bcab6988682a982d03`), so tools, schemas, or capabilities can drift without bumping `0.3.1`.

### 5. Additional Protocol & Implementation Pitfalls in `server.py`
- **Other JSON-RPC notifications receive `-32601` responses (`server.py:142-143, 168`):** Only `notifications/initialized` returns HTTP `202` with no body. Any other JSON-RPC notification (such as `notifications/cancelled` or `notifications/roots/list_changed`, where `"id"` is omitted) falls through to line 168 and returns HTTP `200` with `{"jsonrpc": "2.0", "id": null, "error": {"code": -32601, ...}}`, violating JSON-RPC 2.0 (servers must not reply to notifications).
- **JSON-RPC batch requests bypass logging, session ID creation, and status handling (`server.py:205-211`):** When `req` is a `list`, `do_POST` returns early at line 211 before calling `log()`, never generates an `Mcp-Session-Id` if `initialize` is batched, embeds non-JSON-RPC `401` bodies (`{"error": "unauthorized"}`) directly inside the `200` batch response list, and returns `200 []` instead of `202` for notification-only batches.
- **Logger marks `isError: true` tool results as `ok: true` (`server.py:215`):** `ok = status < 400 and not (isinstance(body, dict) and "error" in body)` does not check `body.get("result", {}).get("isError")`, so once C2 is fixed to return `isError: true`, failed tool calls will be logged as `"ok": true`.
- **Missing input validation in `search_notes` and unhandled `KeyError` in `add_note` (`server.py:103-104, 125-126`):**
  - `search_notes` does not check that required `"query"` was provided (`args.get("query", "")` silently matches all notes) and does not enforce `limit` bounds `1..50`.
  - `add_note` accesses `args["title"]` and `args["body"]` directly; missing arguments raise an uncaught `KeyError` that aborts the HTTP response instead of returning a clean tool error.
- **Bare HTTP `401` on `add_note` without `WWW-Authenticate` or JSON-RPC body (`server.py:123-124, 165-166`):** Returning raw HTTP `401 {"error": "sign in required"}` with no `WWW-Authenticate` header on a single tool call when the session is already established anonymously causes Streamable HTTP clients to either fail the transport call or attempt OAuth metadata discovery (`/.well-known/oauth-protected-resource` → `404`), rather than letting the model explain to the user that signing in is required for `add_note`.
